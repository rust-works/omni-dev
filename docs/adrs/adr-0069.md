# ADR-0069: A Drive-Specific Named-Account Store and Read-Only OAuth2 Client, Mirroring Gmail's Design

## Status

✅ Accepted (2026-08-15)

Applies [ADR-0063](adr-0063.md) (Gmail OAuth2 credential storage) and
[ADR-0066](adr-0066.md) (Gmail named-account store) to a second Google API,
without amending either; inherits [ADR-0067](adr-0067.md) (automatic
Chrome-profile resolution for Gmail login) by field, not by re-deciding it.

## Context

`omni-dev` has no Google Drive integration today — only Gmail
(`src/gmail/**`, `src/cli/gmail.rs`, `src/mcp/gmail_tools.rs`), which since
issue #1500 / [ADR-0066](adr-0066.md) supports genuine multi-account access:
named accounts configured in `~/.omni-dev/settings.json`, selected per
invocation (CLI `--account`) or per MCP tool call (an optional `account`
parameter), with no stateful "switch active account" step and no cross-call
side effects. Issue #1520 asks for the identical property for Google Drive —
multiple named Drive accounts, addressable per-call from both the CLI and
MCP surfaces — but **read-only only**: no upload/create/rename/move/
trash/share/permission-mutation capability anywhere in the surface, simpler
than Gmail's opt-in `gmail.modify` scope.

Nearly every structural question this raises was already answered by
[ADR-0063](adr-0063.md) and [ADR-0066](adr-0066.md) for Gmail: an OAuth2
authorization-code-plus-PKCE loopback flow, a refresh-token-on-disk /
access-token-in-memory split, a named-account store sibling to
`profiles`/`mcp`, an `--account` flag scoped to a subcommand tree rather
than the root CLI. Re-litigating each of those for Drive would be pure
churn. What earns this its own ADR is not new deliberation but recording
*which* parts of that design Drive inherits unchanged and *where* it
diverges — a new OAuth scope, a new settings block, and, unlike Gmail, no
pre-existing single-account state to preserve — so #1520's remaining child
issues (#1522's settings schema, #1523's OAuth/client/account code) implement
a decided design rather than a set of underspecified defaults.

Two narrower alternatives were considered and rejected before settling on a
sibling `drive` block:

1. **Folding Drive into `gmail.accounts.<name>`** — rejected: a Drive
   account and a Gmail account are different credential axes even when the
   underlying human is the same person. A user may want Drive connected
   without touching Gmail at all, or vice versa, or connect Drive under a
   different named identity than any configured Gmail account.
2. **Nesting Drive under `gmail.accounts.<name>.drive`** — rejected: it
   would force a Drive-only user to invent an unused Gmail account entry,
   and would couple Drive's account list to Gmail's for no reason the two
   services actually share.

Both are rejected for the same load-bearing reason [ADR-0066](adr-0066.md)
rejected reusing `--profile` for Gmail: multi-tenancy axes that are
conceptually independent need to compose independently, not be forced
through one another's storage.

## Decision

### 1. Storage: `DriveSettings`/`DriveAccountSettings`, a field-for-field mirror of Gmail's

We will add `drive: { default_account, accounts: { <name>: {...} } }` to
`~/.omni-dev/settings.json`, read through new `DriveSettings`/
`DriveAccountSettings` structs on `Settings` (`src/utils/settings.rs`),
sibling to the existing `gmail: GmailSettings` field — not nested under it.
`DriveAccountSettings` copies `GmailAccountSettings` field for field:
`client_id`, `client_secret`, `refresh_token`, `scope`, `email_address`, and
— because the browser-targeting UX these two fields provide is orthogonal
to which Google API is being authorized — `chrome_profile_from_email`/
`browser_command` ([ADR-0067](adr-0067.md)) as well. The write side reuses
`ensure_object_at`/`object_at_mut` verbatim, the same generalized
path-segment walkers `upsert_gmail_account`/`remove_gmail_account`/
`set_gmail_default_account` already ride (`src/utils/settings.rs`); new
`upsert_drive_account`/`remove_drive_account`/`set_drive_default_account`
are ~15-line copies passing `["drive", "accounts", name]` instead of
`["gmail", "accounts", name]` — no new file-handling code.

### 2. A single read-only scope, no `DriveScope` enum

We will request exactly one OAuth2 scope,
`https://www.googleapis.com/auth/drive.readonly`, and no other — this
feature is read-only by design (#1520's explicit scope). Gmail's
`GmailScope` enum (`src/gmail/auth.rs`) exists because Gmail offers a real
choice between `readonly` and opt-in `modify`; Drive offers no such choice,
so there is no `DriveScope` enum, just a scope constant.
`DriveAccountSettings.scope` still stores the granted scope string for
status-reporting parity with Gmail, but login only ever requests the one
value.

### 3. No legacy-migration path; `ResolvedAccount::{Named(String), Unconfigured}`

We will not build a `drive account import-legacy` command. Gmail's
account-resolution enum has a `Legacy` variant (`src/gmail/account.rs`)
specifically because Gmail had a real pre-#1500 single-account credential
convention — bare `GMAIL_CLIENT_ID`/`GMAIL_CLIENT_SECRET`/
`GMAIL_REFRESH_TOKEN`, or the base `env` map — that had to keep resolving
identically after named accounts landed: a genuine migration target. Drive
is brand new: there is no prior Drive behavior to preserve, so there is
nothing to migrate away from and no variant name that should claim
otherwise. `crate::drive::account`'s equivalent enum is
`ResolvedAccount::{Named(String), Unconfigured}`.

The literal-env bypass — a `DRIVE_CLIENT_ID`+`DRIVE_CLIENT_SECRET`+
`DRIVE_REFRESH_TOKEN` triple set directly in the process environment — is
kept only as a scripting/CI convenience, mirroring Gmail's equivalent bypass
rule, not a migration path, since there is nothing to migrate. It resolves
to `Unconfigured`, the same variant an empty `drive.accounts` map resolves
to: both cases mean "no named account selected," and both fall through to
the same subsequent env-cascade credential load (process env, then base
settings `env`) that already has to exist regardless of the bypass.
`Unconfigured` deliberately carries that dual meaning rather than gaining a
`Legacy`-shaped sibling variant that would imply pre-migration state Drive
never had. Unlike Gmail's `Legacy`, which always has a real fallback to
fall through to (an installed base's actual pre-#1500 credentials, however
sparse), `Unconfigured` with no literal-env bypass present has nothing to
load — the credential-load step must fail loudly with a
"run `drive auth login`" remedy rather than attempt a network call with
absent credentials.

### 4. Deliberate code duplication, not extraction

We will write `src/drive/auth.rs`, `src/drive/client.rs`,
`src/drive/error.rs`, and `src/drive/account.rs` as structurally parallel,
independent modules from their Gmail counterparts — not a shared
`google_oauth`/`named_account` module. This follows the repo's own stated
convention, `BrowserLaunch`'s doc comment (`src/gmail/auth.rs`):

> Deliberately duplicated from (not shared with)
> `crate::snowflake::client::config::BrowserLaunch` — a small, stable shape
> with no existing "generic browser launch" module to promote into; extract
> only on a third consumer.

Drive is Gmail's *second* such consumer, for both the OAuth-flow shape and
the account-resolution precedence logic — one short of that threshold. We
will not extract a shared module now. The trigger to revisit is a third
Google API integration (Calendar, Sheets, …) actually appearing, not this
one.

### 5. `--account` flag scoping

We will scope `--account` (`--account NAME` / `OMNI_DEV_DRIVE_ACCOUNT`) to
`DriveCommand`'s subtree only — `#[arg(long, global = true, value_name =
"NAME")]` on `DriveCommand` (`src/cli/drive.rs`), not a root-level global on
`Cli` — for the identical reason [ADR-0066](adr-0066.md) scoped Gmail's
`--account` the same way: clap rejects two args on the same command sharing
a long flag string, and a CLI-wide global is inherited by every subcommand,
including Snowflake's pre-existing, unrelated `snowflake
query/cancel/disconnect --account` (a Snowflake account identifier). A
root-level `--account` would colonize a word another subsystem already
owns. This repo's own structural test (added for issue #1420, which renamed
the worktrees service's `register --repo` to `--repo-name` after hitting
the identical collision) walks the whole command tree asserting no
subcommand re-uses a global arg id — a regression here fails that test, not
just a manual review.

### 6. API host

We will use base host `https://www.googleapis.com` with `/drive/v3/...`
path prefixes for Drive's REST calls — unlike Gmail's dedicated
`https://gmail.googleapis.com` host (`DEFAULT_BASE_URL`,
`src/gmail/client.rs`). The two OAuth2 endpoints are shared Google
infrastructure and need no Drive-specific equivalents:
`https://accounts.google.com/o/oauth2/v2/auth` (authorization) and
`https://oauth2.googleapis.com/token` (token exchange), both already used
by `src/gmail/auth.rs` and reused identically for Drive. Recording the base
host here means #1520's child issue implementing `src/drive/client.rs`
(#1523) does not have to re-derive it.

## Consequences

- **Applies [ADR-0063](adr-0063.md) and [ADR-0066](adr-0066.md) to a second
  Google API; introduces no new multi-tenancy concept.**
  `--account`/`OMNI_DEV_DRIVE_ACCOUNT` means exactly what it means for
  Gmail — "which Drive account, everything else about the environment held
  constant" — orthogonal to `--profile` for the same reason Gmail's is.
- **No new storage or permission model.** The `drive` block rides the same
  `write_settings` hardening (0700 directory, 0600 file) and
  unknown-field-preserving round-trip every other settings write already
  uses. `client_secret`/`refresh_token` are `Secret`-wrapped the moment
  they're read, inheriting [ADR-0043](adr-0043.md)'s redaction guarantee
  identically to Gmail's credentials.
- **No migration guarantee needed, because there is nothing to migrate.**
  Unlike [ADR-0066](adr-0066.md)'s zero-migration guarantee — which exists
  to protect an installed base with real legacy credentials — Drive ships
  with an empty `drive.accounts` map for every installation;
  `Unconfigured` is simply the starting state, not a compatibility shim.
- **Narrower blast radius than Gmail's.** There is no `modify` scope, no
  write/mutate capability anywhere in this surface to guard against — a
  leaked Drive refresh token grants read access only, unlike Gmail's opt-in
  label-mutation scope.
- **One integration away from a real extraction decision.** Duplicating
  Gmail's OAuth/client/account-resolution shape a second time is this ADR's
  explicit, deliberate choice, not an oversight — but it is also the last
  time that choice is free. A third Google API integration should trigger
  revisiting a shared module, not another round of duplication.
- **Explicitly out of scope**, deferred with reasons rather than silently
  dropped: write/mutate operations (upload, create, rename, move, trash,
  sharing/permissions) — this is a read-only feature by design;
  cross-account fan-out in a single call — each account already resolves to
  an independent `DriveClient`, so this remains addable later without a
  storage-shape change; a local sync/archive engine (`drive sync`) — Drive's
  own API is directly browsable/searchable in a way a mailbox isn't, so
  Gmail's motivating use case is weaker here; Google Docs/Sheets/Slides →
  Markdown export (`drive render`) — Google's currently-supported export MIME
  types should be confirmed against current API docs before committing to
  this; Shared Drives as first-class objects (e.g. `drive shared-drives
  list`) — `supportsAllDrives`/`includeItemsFromAllDrives` are threaded
  through `search`/`read` from the start, but dedicated management tooling
  is a separate feature; OS keyring storage for refresh tokens — same
  deferral as [ADR-0063](adr-0063.md)'s own out-of-scope note.
- **Sync obligation.** `docs/drive.md` (written in #1526) must document the
  `--account`/`OMNI_DEV_DRIVE_ACCOUNT` flag, the `drive account` commands,
  and the `drive` settings.json block shape, mirroring `docs/gmail.md`'s
  Authentication section — keep the two in sync when either's resolution
  precedence or storage shape changes. `.omni-dev/scopes.yaml` and
  `.omni-dev/commit-guidelines.md`'s `## Scopes` list (STYLE-0007) are kept
  in sync by this same change, registering the `drive` commit scope ahead
  of the first `drive:`-scoped commit.
