# ADR-0060: The Main Working Tree Is a Valid Batch-Rebase Target

## Status

✅ Accepted (2026-07-28)

Supersedes [ADR-0055](adr-0055.md) **in part**: on *whether* the repository's
main working tree is a valid rebase target. Everything else ADR-0055 §3 decided
— selection is explicit (`<PATH>...` or `--all`, never a bare invocation), and
the main tree is identified by the structural `is_main` fact rather than a
branch-name heuristic — is unchanged and still governs.

## Context

[ADR-0055](adr-0055.md) §3 made "the main working tree is never rebased" a
**structural** rule: `Inspected::classify` (`src/git/worktree_rebase.rs`)
hard-skipped any path where `is_main` was true, ahead of every other
classification check, and `Selection::All`'s enumeration
(`linked_worktree_paths`) never listed the main root as a candidate in the
first place — so even `--all` could not reach it. The rule was inherited from
[ADR-0049](adr-0049.md)'s `close` op, which refuses to delete the main working
tree on the same structural fact.

That inheritance does not hold up under scrutiny. `close`'s refusal is
load-bearing because `close` is **destructive** — it deletes a worktree, and
deleting the repository's main checkout would be a different order of mistake
than deleting a linked one. Rebase is not destructive to the repository's set
of worktrees: it rewrites a branch's history, which is exactly as reversible
(`git reflog`, `--abort`/`--continue`) for the main tree as for any linked one.
There was no correctness or safety reason for the exclusion — only an
unexamined assumption that the feature was about linked worktrees specifically.

In practice, a repository's main working tree drifts from `origin/<default>`
exactly like a linked worktree does, and "rebase everything in this repo" is a
reasonable reading of `worktrees rebase --all` that the old rule silently
narrowed. Issue #1438 asks for the exclusion to be lifted.

## Decision

### 1. `classify` no longer hard-skips `is_main`

The structural `is_main` check is removed from `Inspected::classify`
(`src/git/worktree_rebase.rs`). The main working tree now falls through to
exactly the same classification every other worktree gets: still refused if
dirty (absent `--autostash`), detached, mid-operation (rebase/merge/
cherry-pick in progress), or if the onto ref can't be resolved — never refused
**for being main**. The `is_main` fact itself is no longer read by the rebase
engine at all (the `Inspection` struct dropped the field); it remains
meaningful elsewhere, e.g. the unrelated `close` deletion guard.

### 2. `--all` now includes the main working tree

`Selection::All`'s path enumeration (renamed `all_worktree_paths`, was
`linked_worktree_paths`) now pushes the repository's main root onto the
candidate list alongside every linked worktree it already found. `omni-dev
worktrees rebase --all` and the VS Code batch action driven by `Selection::All`
now mean "every worktree of this repository," main included — closing the gap
between what `--all` said and what it did.

### 3. Explicit-path selection was already possible; it's simply unblocked

`Selection::Paths` already let a caller name the main tree's path directly —
it was just discarded by the `classify` skip. That path now works: `omni-dev
worktrees rebase <path-to-main-tree>` rebases it like any other named target.

### 4. `SkipReason::MainWorkingTree` is removed, not deprecated

The variant is deleted outright from `SkipReason`, along with every match arm
that rendered it (the CLI's `skip_reason_text`, the VS Code extension's
`skipReasonText`). This is a clean removal rather than an additive-only
change: unlike this project's other wire types with a documented
cross-version-skew contract (`worktrees tree`/`sessions subscribe`, both
`#[serde(default)]`/`skip_serializing_if`-guarded for a client and daemon that
may be on different versions), `SkipReason` is a synchronous plan/execute
response value, never persisted or subscribed to — there is nothing for a
lagging client to have cached. The one asymmetry (an old, not-yet-restarted
daemon could in principle still emit the retired `"main-working-tree"` slug to
a freshly upgraded extension) degrades gracefully: the extension's
`skipReasonText` falls through to its existing `default` case rather than
crashing, and resolves itself on the daemon's next restart.

### 5. The VS Code extension offers and executes it, not just displays it

Offering "Rebase on main" on the main tree's row without also changing what
happens when it's clicked would just replace an absent menu item with an inert
one: `rebaseCommand.ts`'s `rebaseOnMain` previously partitioned a selection by
role and unconditionally dropped every main-tree target before sending
anything to the daemon. That client-side pre-filter is removed — a selected
main-tree row is now included in the paths sent to the daemon like any other
target, and gets a real per-worktree classification back (up-to-date,
would-rebase, dirty, etc.) instead of a hardcoded client-side skip. The
context-menu `when` clause is loosened from a linked-only role gate to the same
unconditional `/worktree/` gate "Open Worktree" already uses.

## Consequences

- A user can now rebase — and, on conflict, leave mid-rebase — their
  repository's main branch via this command, whether through `--all`, an
  explicit path, or the VS Code row action. That is git-recoverable
  (`--continue`/`--abort`) exactly as for any other target, and it is exactly
  what "rebase everything" and "rebase this worktree" now mean when the
  targeted worktree happens to be main.
- No change to **how** the main tree is identified: `is_main`/
  `!repo.is_worktree()` remains a purely structural fact, unrelated to branch
  naming, and is untouched everywhere else it's used — most notably `close`'s
  deletion guard (ADR-0049), which keeps refusing to delete the main working
  tree. That guard is unaffected by this ADR; rebase and delete are
  independent operations with independent hazards, and only rebase's exclusion
  was ever unjustified.
- No new trust boundary. The daemon's `rebase` op already ran the same engine
  the CLI does, over paths the client supplies (never `Selection::All` itself
  — the daemon always receives concrete paths); this ADR changes what those
  paths may now include and how the engine classifies them, not who can reach
  the op or what it authenticates as.
- Documentation and prior-ADR restatements of the old rule needed updating in
  lockstep: [ADR-0055](adr-0055.md) §3 and its Consequences section, and
  [ADR-0059](adr-0059.md)'s two restatements of "the classifier skips the main
  working tree" / "refuses the main working tree" — both now point here.

This extends [ADR-0055](adr-0055.md) and [ADR-0059](adr-0059.md); applies
[ADR-0003](adr-0003.md) and [ADR-0027](adr-0027.md); leaves
[ADR-0049](adr-0049.md)'s `close` deletion guard untouched. See
[docs/worktrees-service.md](../worktrees-service.md) for the operator guide.
