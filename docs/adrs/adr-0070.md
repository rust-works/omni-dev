# ADR-0070: Security-Gated Rename/Move for the Drive Integration

## Status

✅ Accepted (2026-08-18)

**Reverses [ADR-0069](adr-0069.md) §2** ("a single read-only scope, no
`DriveScope` enum") — Drive is no longer read-only by design. Everything
else ADR-0069 decided (the named-account store, the OAuth2 flow, the
deliberate-duplication-from-Gmail stance, the API host) still governs
unchanged. Applies [ADR-0063](adr-0063.md) (OAuth2 credential storage) and
[ADR-0066](adr-0066.md) (named accounts) exactly as ADR-0069 already did —
neither is touched by this ADR.

## Context

[ADR-0069](adr-0069.md) shipped Drive as deliberately read-only: one scope
(`drive.readonly`), no `DriveScope` enum, no write/mutate capability
anywhere in the surface. Its own Consequences section listed "rename, move"
among what was explicitly out of scope, not overlooked.

Issue #1557 asks for `rename` and `move`. Renaming is simple: it only ever
touches a file's `name` field, never `parents`, so it can never change who
can see the file. Move is a different kind of feature. Drive resolves a
file's *effective* visibility from two sources merged together: permissions
granted directly on the file, and permissions inherited from its parent
folder chain. Moving a file changes that chain — so a move that looks like
routine reorganization ("put this in the Archive folder") can silently
expose a file to a wider audience, or cut off people who relied on
folder-level access, with nothing in Drive's own UI calling that out.

This ADR records the decisions that make `move` safe to ship: the
visibility-diff algorithm, the opt-in gate model, and the operational
posture (bulk behavior, logging, no interactive confirmation) — the same
rigor [ADR-0059](adr-0059.md)–[ADR-0061](adr-0061.md) gave the daemon's
first credentialed-write and remote-publishing capabilities, applied here
to this project's first Drive write capability.

## Decision

### 1. An additive `drive.metadata` scope, not a `ReadOnly`/`Modify` split

Unlike Gmail's `GmailScope` (`ReadOnly` xor `Modify` — `gmail.modify` alone
already grants read access), Drive's narrowest write scope,
`drive.metadata` (`files.update` on `name`/`parents` only, **no
file-content access**), does not subsume `drive.readonly`. So
`DriveScope::Metadata` requests both scopes together
(`src/drive/auth.rs::build_authorization_url`), never replacing
`drive.readonly` — `search`/`read` still need it. `drive auth login
--write` is the opt-in (`src/cli/drive/auth.rs`); the default login still
requests `drive.readonly` alone. `DriveCredentials.scope` is promoted from
a plain `String` to the new `DriveScope` enum (mirroring `GmailScope`'s
shape exactly — `as_str`/`from_granted`/`allows_write`); the *stored*
`DriveAccountSettings.scope` in `settings.json` stays a plain `String`, for
the same reason Gmail's does — it is a status-reporting cache of whatever
Google actually granted, not the value driving a live decision.

### 2. No client-side scope pre-flight gate

Gmail's `gmail.modify`-gated mutations (`label add`/`remove`) do not
pre-check scope client-side either — they call the API unconditionally and
let a 403 surface. `drive rename`/`drive move` mirror that: the
`files.update` PATCH is always attempted, and `insufficientPermissions` is
made actionable at the point it's caught
(`src/drive/files_api.rs::append_write_scope_hint`), appending "run `drive
auth login --write`" rather than duplicating a scope check that would
inevitably drift from Google's actual grant.

### 3. The visibility-diff algorithm (the security-critical core)

`permissions.list(fileId)` returns a file's full *effective* permission set
(direct + inherited, merged) — but the `permissionDetails[].inherited` flag
that would split "direct" from "inherited" is only populated for Shared
Drive items, not My Drive files, which is where most of this project's
users' files live. `src/drive/visibility.rs` derives the split by
subtraction instead, from three snapshots `src/drive/file_move.rs::plan`
fetches:

```text
before          = principal_set(permissions.list(file_id))
current_parent  = principal_set(permissions.list(union of file's current parent(s)))  // ∅ if none
dest            = principal_set(permissions.list(dest_folder_id))

direct_on_file  = before − current_parent      // what's granted on the file, not inherited
after           = direct_on_file ∪ dest

added   = after − before     // visibility increase: new principals gain access
removed = before − after     // visibility decrease: principals lose access
```

A `Principal` is `(type, identity)` — email for `user`/`group`, domain
string for `domain`, a fixed sentinel for `anyone`. `role` is deliberately
excluded from the key: a privilege change for an already-visible principal
(`reader` → `writer`) doesn't gate a move in v1.

**Known, accepted limitation: shadowed grants.** If a principal has *both*
a direct grant on the file *and* inherited access via the current parent,
the subtraction can't distinguish them — `direct_on_file` won't include
that principal (it's masked by `current_parent` too), so if `dest` also
doesn't grant it, `after` won't either, and the diff reports a false
`removed` for a principal who actually keeps access via the shadowed direct
grant. This is the **safe failure direction**: `direct_on_file ⊆ before`
always holds and `dest` enters `after` unfiltered, so it can only produce a
false positive on `removed` (an unnecessary
`--allow-visibility-decrease` requirement) — **never** a false negative on
`added`. A real visibility increase is always caught. This is stated here,
in `visibility.rs`'s module doc, and in `docs/drive.md`, the same way
ADR-0069 documented its own boundaries — not left for someone to discover
as a bug. `visibility.rs` is intentionally pure (zero `DriveClient`/network
dependency), so this algorithm and the limitation above are covered by 23
unit tests with no wiremock at all, including a dedicated test asserting
the shadowed-grant scenario produces exactly the documented false-positive
and no false negative.

A `permissions.list` fetch failure for any of the three snapshots produces
a `Failed` outcome for that file, never a silent `unwrap_or_default()`
empty-set fallback — an empty-set fallback would quietly reintroduce a
fail-open bug (any principal in an unreadable snapshot would read as
"never had access," which can only ever manufacture false *removals*, but
could just as easily mask a real one). This is asserted by a named
regression test in `src/drive/file_move.rs`.

### 4. Three independent opt-in flags; moves are refused by default

`drive move` computes the diff above for every file and, absent an
opt-in, refuses any move that would change visibility at all — an
increase or a decrease, either one. Two independent flags,
`--allow-visibility-increase` and `--allow-visibility-decrease`, opt in to
each direction separately (a user comfortable exposing a file more widely
is not thereby assumed to be comfortable revoking someone else's access,
or vice versa). A third, `--allow-drive-boundary-crossing`, is independent
of the visibility diff entirely — a move between a My Drive and a Shared
Drive can matter (different retention/ownership/audit posture) even when
it changes nobody's *access*. `BlockReasons` (`src/drive/visibility.rs`)
is a struct of three bools, not a single-variant enum: a move can fail more
than one gate simultaneously, and the audit log says so precisely rather
than reporting only the first match.

### 5. Bulk moves skip only the unsafe files

`drive move` takes one or more file ids and one shared destination folder
per invocation. A file blocked by a safety gate, or one that fails for an
unrelated reason (a bad id, a transient API error), becomes that file's own
`Blocked`/`Failed` outcome — the rest of the batch proceeds regardless
(`src/drive/file_move.rs::plan_one`/`execute`). The only thing that fails
the *whole* call is a batch-level precondition: the destination not
resolving to an actual folder, checked once up front rather than
per-file, so a bad destination produces one clear error instead of N
confusing ones.

### 6. No interactive confirmation, ever

`drive rename`/`drive move` have no confirmation prompt, `--dry-run` or
not — `--dry-run` plus the `--allow-*` flags are the entire gate. Two
reasons, not just "bulk doesn't fit one prompt": Drive's existing read
surface has full CLI/MCP parity as a design goal, and an
interactive-by-default confirm would either hang or be silently
force-skipped when driven by a future MCP caller with no TTY. The opt-in
flags are already captured verbatim in the existing invocation log's
`command_line`, so this loses no auditability relative to a confirm
prompt.

### 7. Logging happens inside the engine, not the CLI layer

`src/request_log.rs` gains `RecordKind::DriveMutation`
(`kind: "drivemutation"`), covering both `rename` and `move` via `command`/
`context` rather than one kind per verb (mirroring how `RecordKind::Worktree`
already covers multiple `git worktree` verbs). Unlike
`record_worktree` — called from `src/cli/git/worktree.rs`, safe there only
because `git worktree` has no MCP surface at all — `record_drive_mutation`
is called from *inside* `src/drive/rename.rs::rename` and
`src/drive/file_move.rs::execute` themselves. "Every move/rename must be
logged" is a hard invariant, and Drive's write surface may grow an MCP
caller later (see §9); logging inside the engine makes the guarantee hold
for every current and future caller, not just today's CLI. It is also
additive to, not redundant with, the automatic per-request `kind: "http"`
records `DriveClient::send_once` already writes for every call it makes: a
`Blocked` outcome makes *no* `files.update` call at all, so without this
record the single most security-relevant event — "we refused this because
visibility would change, here's exactly why" — would never appear in the
log. A `Blocked` record carries the specific `added_principals`/
`removed_principals` that triggered it.

### 8. Folder moves don't recurse in v1

Moving a folder evaluates the folder's *own* visibility change, exactly
like any other file — but does not walk its contents, so a file three
levels deep inside a moved folder could have its own effective visibility
change with nothing evaluating it. This is an explicit, documented v1
boundary, not an oversight: the CLI emits a loud warning line whenever the
moved item is itself a folder (`src/cli/drive/move_file.rs`), naming the
gap rather than silently under-covering it.

### 9. CLI-first; MCP tools deferred

This delivery is CLI-only. Precedent: `gmail label add`/`remove` — the
closest existing *mutating* CLI commands in this project — have no MCP
equivalents either. `drive_file_rename`/`drive_file_move` MCP tools are a
follow-up once the CLI has proven out, not part of this ADR's scope.

### 10. Exit code convention

`drive move`/`drive rename` return exit 0 as long as the command
mechanically completed, regardless of individual `Blocked`/`Failed`
outcomes — status lives in the table/JSON output, matching `worktree
push`'s existing convention (`src/git/worktree_push.rs`). Scripts that need
to detect a blocked/failed outcome must inspect the output, not `$?`.

## Consequences

- **This is the Drive integration's first write capability**, and the
  largest escalation to its threat model since ADR-0069. It remains
  narrowly scoped by design: `drive.metadata` grants `files.update` on
  `name`/`parents` only, never file content, never sharing/permissions
  mutation, never trash/delete. A leaked `drive.metadata` refresh token can
  rename and reorganize files, not read or exfiltrate their content, and
  not change who can see anything beyond what the visibility gate itself
  already evaluates and, by default, refuses.
- **The gate is default-deny, not default-allow-with-a-warning.** A move
  that would change visibility is refused unless the specific direction is
  explicitly opted into, per invocation — there is no "always allow" mode
  and no global config to disable the gate.
- **A refusal is exactly as auditable as a success.** Every outcome —
  moved, blocked, already-in-folder, or failed — produces a request-log
  record with the same fidelity, so "why was this move refused" is always
  answerable from `omni-dev log --query kind:drivemutation` without
  reproducing the call.
- **The shadowed-grant limitation is accepted, not deferred as a bug.** It
  is documented in three places (`visibility.rs`'s module doc, this ADR,
  `docs/drive.md`) precisely because its failure direction is safe — it can
  only make the gate stricter than strictly necessary, never looser.
- **Folder moves are shallow in v1.** A user reorganizing a folder tree
  gets a loud warning, not a silent gap; recursive evaluation of a moved
  folder's contents is explicitly deferred, not designed around.
- **No interactive confirmation exists on this surface at all** — a
  deliberate divergence from this project's usual destructive-action
  posture ([ADR-0027](adr-0027.md)'s confirm-by-default convention),
  justified by MCP parity being a stated goal for Drive from ADR-0069
  onward. The `--allow-*` flags and `--dry-run` are the complete safety
  surface.
- **Sync obligation.** [docs/drive.md](../drive.md) documents the
  `--write` scope, `drive rename`, `drive move`, the three `--allow-*`
  flags, the shadowed-grant limitation, and the `kind: "drivemutation"`
  log record; [docs/log.md](../log.md) documents the log record itself.
  Keep both in sync when this ADR's decisions change. MCP tool ADRs, if
  any are needed when §9's follow-up lands, are a separate document.
