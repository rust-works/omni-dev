# ADR-0078: Sheet Formatting, Data Validation and Protected Ranges via `spreadsheets.batchUpdate`

## Status

✅ Accepted (2026-09-08)

**Extends [ADR-0075](adr-0075.md), reverses none.** ADR-0075 shipped the
additive-and-rename third of ADR-0075 §3's structural surface — `addSheet`,
rename, `insertDimension` — and deferred everything else: formatting, data
validation, protected ranges, `duplicateSheet`, and sheet reorder/hide. This
ADR is the deferred design pass issue #1643 asked for. It resolves the two
questions ADR-0075 §3 left open (where does each capability sit in the gate
vocabulary, and does the "one record per request" equivalence still hold)
and ships all of it.

## Context

Issue #1613 named seven `batchUpdate` capabilities; ADR-0075 shipped three.
Issue #1623 ([ADR-0077](adr-0077-sheets-deletion-via-batchupdate.md)) picked
up the genuinely destructive ones — `deleteSheet`, `deleteDimension`, and
`deleteRange` — as a separate design pass, shipped alongside this one:
deletion's hazard (one call destroys more than its arguments suggest) is a
different problem from this ADR's, and the two must not be conflated.

What's left is a mixed bag, and issue #1643 named the mix precisely:

- **Formatting** (`repeatCell`/`CellFormat`, `updateBorders`, `mergeCells`/
  `unmergeCells`, `autoResizeDimensions`, `updateDimensionProperties`),
  **data validation** (`setDataValidation`), `duplicateSheet`, and sheet
  reorder/hide are all additive-or-neutral — none destroy data outright.
  `mergeCells` is the one exception worth care: it keeps only the top-left
  cell's value, silently discarding the rest.
- **Protected ranges** (`addProtectedRange`/`updateProtectedRange`/
  `deleteProtectedRange`) are categorically different: a protected range is
  a *permission* inside the document (who may edit, not what the sheet
  contains). `deleteProtectedRange` removes a guard someone deliberately
  placed; `updateProtectedRange` can widen who may edit. Neither destroys
  data, but both are the kind of change ADR-0073's Consequences never
  contemplated when it said "blast radius smaller than `drive edit`'s".

## Decision

### 1. Formatting, validation, duplicate and reorder/hide all join `SheetsStructure`

None of them destroy data (§2 handles `mergeCells`'s one exception), and an
operator who granted `sheets-structure` for "add sheets, rename them, insert
rows" is not being asked to consent to anything categorically new by also
covering "format cells, validate input, copy or reorder a tab". This is the
call issue #1643 asked to be made explicit rather than assumed, and it is
made here: `DriveOperation::SheetsStructure`'s doc comment is updated to
name the newly-covered verbs, and — as ADR-0075 §1 already bound — sheet and
row **deletion** still may not join this variant when #1623 lands.

### 2. Protected ranges get their own operation: `SheetsProtection`

This is the one case where folding into `SheetsStructure` would be wrong in
kind, not just in scope. `updateProtectedRange`/`deleteProtectedRange` are
permission changes, and every `allow: ["sheets-structure"]` rule written
since ADR-0075 was written for a vocabulary that never included "may change
who can edit this workbook". A new `DriveOperation::SheetsProtection`
(default-deny like every write) is added, following ADR-0075 §1's own
precedent exactly — the identical argument, one operation further out.

`list-protections` (a read) is ungated, like `sheets info`: a user must be
able to see what protections exist — their numeric ids, ranges and current
editors — before `update-protection`/`unprotect-range` can address one at
all.

### 3. No `updateCells` anywhere; `format-cells` uses `repeatCell` exclusively

Issue #1613 asked whether `updateCells` belongs with the cell-write surface
or the structural one, since it can set values and formats in the same
request. The answer is: neither surface reaches it. `format-cells` builds a
`repeatCell` request whose `cell` payload
([`RepeatCellData`](../../src/drive/sheets/types.rs)) has no
`userEnteredValue` field at all — a type-level guarantee, in the same spirit
as ADR-0075 §4's "the destructive requests are not modelled, so they are
not constructible". A `sheets-structure` grant can restyle a cell; it can
never be used to write into one, regardless of what a caller asks for.

### 4. `mergeCells` reads before it merges, and says what it would discard

`merge-cells` is the one request in this ADR that destroys data: merging
keeps only the top-left cell's value. Its `--dry-run` (and its real run,
before mutating) issues a `values.get` on the target range and lists every
non-top-left, non-blank cell by A1 address and value — both in the CLI
output and the `drivemutation` record's new `discarded_cells` field. No
confirmation flag is added; ADR-0075 §3 and ADR-0070 §6 already establish
this integration has none anywhere, and a preview that names exactly what
would be lost is the substitute, following ADR-0075 §6's "a preview must
state the effect in terms the user can check" applied to data loss instead
of a dimension shift.

### 5. Curated flag surfaces, not full API coverage — for `CellFormat`, `DataValidationRule`, and `update-borders`

Each of these Sheets structures is large. Rather than a raw passthrough
(forbidden outright by ADR-0075 §2, and that prohibition is unchanged and
non-negotiable here), each verb exposes a bounded, named set of flags:

- **`format-cells`**: `--bold`/`--italic`/`--strikethrough`/`--underline`,
  `--font-size`, `--text-color`/`--background` (`#RRGGBB`),
  `--horizontal-align`/`--vertical-align`, `--number-format` +
  `--number-format-type`, `--wrap`. Font family, text rotation, hyperlink
  display type, padding and text direction are cut, not silently missing —
  a documented follow-up if requested.
- **`update-borders`**: `--top`/`--bottom`/`--left`/`--right`/`--all`,
  shared `--style`/`--color`. The two inner-grid-line fields
  (`innerHorizontal`/`innerVertical`) are cut for the same reason.
- **`set-data-validation`**: exactly one of `--one-of-list`,
  `--number-between`, `--checkbox`, `--custom-formula` (a `clap::ArgGroup`
  enforces "exactly one"), plus `--input-message`/`--show-warning`. Sheets'
  several dozen other condition types (per-type date/text conditions,
  `NUMBER_GREATER`, …) are cut.
- **`update-dimension-properties`**: pixel size only.
  `hiddenByUser` (per-row/column hiding) is cut — sheet-level hide/show
  already covers the common case.

Every cut is named in `docs/drive.md`, following this issue's general
stance: the useful subset ships now, the rest is a documented limitation
rather than a silent gap, and nothing about the typed-verb shape forecloses
adding a flag later.

### 6. A new, required A1 → `GridRange` conversion, kept to a bounded grammar

Every structural verb through ADR-0075 addressed either a whole sheet or a
whole dimension (`DimensionRange`); this ADR's range-targeted verbs
(`format-cells`, `update-borders`, `merge-cells`, `unmerge-cells`,
`set-data-validation`, `protect-range`) address a rectangular
[`GridRange`](../../src/drive/sheets/types.rs) — a numeric, zero-based,
half-open shape the wire format requires, not a preference. `a1.rs`
deliberately never parses A1 grammar (ADR-0073 §7's "the server is
authoritative"), because every existing caller passes an A1 string straight
through to an endpoint that resolves it server-side. That reasoning does not
survive here: the wire shape itself demands numbers, so parsing is required,
not optional — the same status ADR-0075 §8's `dimension_range` conversion
has.

`grid_range::parse_grid_range` is the one conversion site, and its grammar
is deliberately bounded: a cell, a bounded rectangle, a whole column or
column span, a whole row or row span, and a column open-ended downward from
a cell (`A5:A`). Forms outside that set are refused with a message naming
what is supported, rather than guessed at — the same "refuses to guess"
posture `geometry.rs`'s title-matching cascade takes for an ambiguous
window match.

### 7. `update-protection`/`unprotect-range` resolve their target by exact range match, and refuse rather than guess

Sheets exposes no user-typeable handle for an existing protected range
except its server-assigned numeric `protectedRangeId` — which is why
`list-protections` ships in this same ADR, as the only way to discover one.
`update-protection`/`unprotect-range` instead take the same `--sheet`/
`--range` pair every other verb does, and resolve it against the workbook's
*current* protected ranges (re-fetched fresh, like every other verb's
pre-mutation read) by exact `GridRange` equality. Zero matches or more than
one are both refused — never a guess at which was meant — the same
principle `geometry.rs`'s exact→suffix→substring title-matching cascade
documents for an ambiguous window.

Sheets also has no incremental editor add/remove: `updateProtectedRange`'s
`editors` field replaces the whole list. `update-protection
--add-editor`/`--remove-editor` compute the full resulting set from the
resolved protection's *current* editors (read in that same fetch) before
sending it — the protected-range analogue of `push`'s "the plan the user
confirms and the enforcement mechanism agree by construction"
([ADR-0061](adr-0061.md)), here because both the read and the write use one
fetch, not two.

### 8. One `drivemutation` record per CLI verb; new context fields, not overloaded old ones

ADR-0075 §7 predicted this day would reopen "one record per batch or per
request", and it has for exactly one verb: `update-borders` can set up to
four `Border` sides in a single `updateBordersRequest` — still one request,
so the record stays one-per-verb-per-request as before, but it is the first
verb whose *single* request carries more than one independently-toggleable
effect. Rather than trying to decompose that into several log entries, the
record gets a `fields_changed` string naming exactly which sub-effects
applied — the formatting analogue of `dimension_range`, extended to a
request wide enough that a single named field can't describe it.

Five more fields land the same way, each new rather than reusing an
existing field for a subtly different meaning (the standing convention: see
`decided_by_folder_id`/`decided_by_file_id`'s deliberate mutual
exclusivity): `discarded_cells` (`merge-cells`'s losses),
`validation_type` (the condition type applied, or `"cleared"`),
`protected_range_id`, `protection_editors_added`,
`protection_editors_removed`.

New `operation` strings: `sheets-format-cells`, `sheets-update-borders`,
`sheets-merge-cells`, `sheets-unmerge-cells`,
`sheets-auto-resize-dimension`, `sheets-update-dimension-properties`,
`sheets-duplicate-sheet`, `sheets-reorder-sheet`, `sheets-hide-sheet`,
`sheets-show-sheet`, `sheets-set-data-validation`,
`sheets-clear-data-validation`, `sheets-protect-range`,
`sheets-update-protection`, `sheets-unprotect-range`.

### 9. This ADR ships alongside issue #1623's deletion pass, not instead of it

Issue #1623 landed concurrently and is its own ADR-0077: it lifts ADR-0075
§4's `no_destructive_request_is_reachable` grep-guard entirely, replacing
an asserted *absence* with a proven *presence* property instead (every
delete verb routes through `sheets-delete`, never `sheets-structure`). None
of `format.rs`/`validation.rs`/`protection.rs` construct a `DeleteSheet`/
`DeleteDimension`/`DeleteRange` request — there is simply no code path that
would — but with the guard gone crate-wide, that is now a property of this
code's construction and review, not one a test pins directly.
`DeleteProtectedRange`/`deleteProtectedRange` were never in scope for that
guard either way: removing a protection is this ADR's own, intentionally-
shipped and separately-gated capability, not the *data*-deletion hazard
issue #1623 addresses.

### 10. Unchanged from ADR-0075

CLI-first with MCP deferred (§9), the exit-0 convention regardless of
outcome (§10), and every structural property §2/§4/§5 established
(typed verbs, no raw `--requests` passthrough — ever, the gate preceding
every Sheets call, a `--dry-run` sharing one classification with the real
run).

## Consequences

- **No new OAuth grant and no new trust boundary.** Same as ADR-0075's
  Consequences: every new request rides the same Drive scopes already
  covered.
- **The permission vocabulary grows to seven operations**, with
  `sheets-protection` the reason. Correct per ADR-0073 §3's standing rule:
  new *capability* earns new vocabulary; a variation on an existing one
  would not. Protected ranges are a permission change, which is new
  capability in the relevant sense.
- **`sheets-structure` now means more than it did.** An operator who granted
  it before this ADR shipped is not retroactively exposed to anything that
  destroys data — the binding constraint ADR-0075 §1 recorded on the
  variant holds — but they are exposed to formatting/validation/duplicate/
  reorder/hide, which this ADR argues is within what granting "restructure
  this workbook" already implied. `docs/drive.md`'s `sheets-structure`
  section is updated to name the full current set.
- **A `merge-cells` dry run costs one extra read** beyond the
  `spreadsheets.get` every structural verb already pays for (ADR-0075 §5).
  Deliberate: it is the price of a preview that tells the truth about data
  loss, the same trade `insert-rows`' dry run already makes for a dimension
  shift.
- **`update-protection`/`unprotect-range` cost a read too**, always: they
  cannot resolve their target without one, since Sheets' only stable handle
  is a numeric id these commands do not take as input.
- **A user who needs a `CellFormat`/`DataValidationRule` property, or an
  `update-borders` inner grid line, outside the curated set must use the
  Sheets UI.** Documented in `docs/drive.md` per property group, the same
  stance ADR-0075's Consequences take on sheet/row deletion.
- **Sync obligation.** `docs/drive.md` documents every new verb, the
  `sheets-protection` write-permission row, and the `sheets-structure` row's
  expanded scope; `docs/log.md` documents the new `drivemutation`
  operations and the six new context fields. Keep both in sync when this
  ADR's decisions change.
