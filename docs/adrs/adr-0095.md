# ADR-0095: Extract Google Workspace Functionality into the Standalone gwi Project

## Status

🟡 Proposed (2026-10-07, [#2203](https://github.com/rust-works/omni-dev/issues/2203)). The
design choices below were made in phase 1 of #2203; the ADR becomes Accepted when the
removal pull request merges. The matching decision on the gwi side is
[gwi ADR-0001](https://github.com/rust-works/gwi/blob/main/docs/adrs/adr-0001.md); the
inventory and revised phases are in [docs/plan/gwi-extraction.md](../plan/gwi-extraction.md).

## Context

omni-dev has grown a second product inside it: the `gmail` and `drive` command trees
(Drive includes Docs, Sheets and Slides), their library modules, 23 MCP tools and 27
ADRs. Together they are roughly 195k of the crate's 548k lines of Rust (about a third), in a
crate that is already near its published size cap. They share no behaviour with the git, Atlassian, Datadog or
daemon features, and they have a different audience, release cadence and security posture
(OAuth tokens, write gates, leases and a fail-closed audit log). #2200 moved coverage out
the same way; this is the larger case. The new home is
[rust-works/gwi](https://github.com/rust-works/gwi).

The extraction is not a clean cut, in both directions.

- **Outbound.** Gmail/Drive use omni-dev's `utils::secret`/`secret_env` (~124 call sites),
  `utils::settings` (~72), `request_log` (~60, including the `audit.jsonl` sink), the
  `daemon::paths` file helpers (17), `test_support` (~100) and a handful of smaller
  helpers. These modules are self-contained: the only edges back into Google code are
  `settings.rs` (the `GmailSettings`/`DriveSettings`/lease types and the write-gate rule
  types) and doc comments.
- **Inbound.** Only five files reach into Gmail/Drive: `settings.rs`, `request_log.rs`
  (the `DriveMutation` record kind and the audit outcome builders), `cli.rs`,
  `utils/browser_command.rs` and `utils/multipart.rs`. No daemon service, session feed or
  worktrees code hosts Gmail/Drive work.

Three ways to handle the shared infrastructure were considered. Depending on omni-dev as a
library would make gwi build `ratatui`, `alacritty_terminal`, `axum`, `git2` and `syn` for
a Gmail/Drive CLI, turn omni-dev's library surface into a public contract, and forbid
omni-dev ever depending on gwi. A shared `omni-dev-core` crate is the cleanest, but costs a
refactor of about 12k lines and ~300 re-exported call sites plus a second crate on
omni-dev's release train, all to serve two consumers. Forking copies only what gwi needs
and leaves each project free to evolve its own settings schema, log and release process.

## Decision

We will remove the Google Workspace functionality from omni-dev and make gwi a
standalone project that shares no crate with it.

1. **No shared crate.** gwi forks what it needs (secret handling, the env-injection seam,
   the settings loader, the request/audit log, the file-lock and `0600` helpers, test
   support) at a recorded omni-dev commit. omni-dev keeps its own copies and does not
   depend on gwi.
2. **Own configuration, state and log.** gwi reads `~/.gwi/settings.json`, keeps its
   ledgers under its own state directory and writes its own `log.jsonl` and `audit.jsonl`.
   A `gwi` import command copies the existing `gmail`, `drive` and `lease` settings blocks
   and the Drive lease ledger from omni-dev's locations. The import copies and never moves
   or modifies omni-dev's files.
3. **Own MCP server.** The 23 Gmail/Drive MCP tools move to a `gwi-mcp` binary in gwi.
   omni-dev's MCP server drops them.
4. **One-release compatibility stub.** The first omni-dev release after gwi's first real
   release keeps `omni-dev gmail` and `omni-dev drive` as hidden stubs that exit non-zero
   with a message naming gwi, its install instructions and the import command. The
   following minor release deletes them. The 23 MCP tools and the `omni_dev::{gmail,drive}`
   library modules go in the stub release, since a stub cannot sensibly keep serving them.
   The removal is a breaking change, so a minor version bump under the pre-1.0 policy.
5. **Tolerate and preserve what users already have.** omni-dev's `Settings` stops defining
   the `gmail`, `drive` and `lease` blocks, but existing files keep them: unknown blocks
   must still load and must survive any omni-dev write to the file. `RecordKind` keeps
   `DriveMutation` and `Audit` as read-only legacy kinds so `omni-dev log` still displays
   historical records. omni-dev stops writing `audit.jsonl` (Drive was its only writer),
   never deletes an existing one, and `docs/log.md` says so.
6. **Decouple by deleting, not by refactoring.** With no shared crate there is no
   inversion to land first. The only prerequisite is a pair of tests, added before the
   removal, pinning point 5.
7. **Gate the removal.** omni-dev removes the code only after gwi has a published release
   on which every `gmail` and `drive` subcommand and MCP tool works, the import is tested
   against a real omni-dev settings file and ledger, and the docs and ADRs have been
   carried over.

## Consequences

- omni-dev sheds about 195k lines, the Google-only dependencies (to be confirmed with
  `cargo machete`: `mail-parser`, `mail-builder`, `htmd`, `csv`, and `mime_guess` only if
  Atlassian stops using it) and most of its crate-size pressure. Its CLI, MCP surface and
  docs become about one product smaller.
- Users who use Gmail or Drive must install a second binary, run the import and, for MCP,
  add `gwi-mcp` as a second server. Environment variables read by the moved code move from
  the `OMNI_DEV_` prefix to `GWI_`; the unprefixed `GMAIL_*`/`DRIVE_*` credential names are
  unchanged. This is the cost of independence and is the reason for the stub release.
- Two copies of the secret-handling, settings and audit-log code now exist. A security
  fix to one is not automatically a fix to the other. The fork-point commit is recorded in
  the plan, and a fix in either project to a copied module must open a matching issue in
  the other.
- Audit history is not merged: records written before the move stay in omni-dev's
  `audit.jsonl`, and gwi's start a new file. Neither project may weaken the fail-closed
  guarantee to make the move easier.
- Moved ADRs stay in omni-dev as history, marked as relocated to gwi, so existing links
  keep working. ADR-0023 (ADF) and any other ADR that mentions Drive only in passing stay
  untouched.
- The `update-snapshots` skill must be run for the stub and removal changes, accepting only
  a diff that removes or hides the `gmail` and `drive` subtrees.
- Follow-ups: the crates.io placeholder for `gwi` is still unpublished (it needs a token),
  and the exact import behaviour is specified in the plan and finalised in phase 3.
