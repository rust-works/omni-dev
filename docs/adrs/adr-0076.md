# ADR-0076: Google Docs Text Mutation Behind a Revision Lease

## Status

✅ Accepted (2026-09-07)

**Extends [ADR-0071](adr-0071.md), [ADR-0073](adr-0073.md) and
[ADR-0061](adr-0061.md); reverses none.** ADR-0071 added content mutation
behind a folder-scoped permission gate and deferred Google-native documents
in §9. ADR-0073 answered that deferral for Sheets and built the shared
`GoogleApiClient` transport. ADR-0061 established the "no escape hatch
anywhere in the surface" posture for an operation whose dangerous form must
be structurally unreachable; this ADR applies it to a different API.

Numbered 0076 because 0074 ([file-id-keyed rules](adr-0074.md), issue #1612)
and 0075 ([structural sheet edits](adr-0075.md), issue #1613) were taken by
branches in flight. Both are cited below and neither had merged when this was
written, so those two links resolve only once their branches land; nothing in
this ADR's own decisions depends on either shipping.

Landed under this ADR so far (issue #1615, phase 1): `DocsClient` over the
shared transport, `documents.get`, the structural flattener, and the
read-only `drive docs info` / `drive docs read`. The mutating verbs are
specified here and land in the commits following this ADR's acceptance — the
same sequencing ADR-0071 and ADR-0073 used, where the ADR is written and
accepted before, not after, the mutating phase.

## Context

`drive edit` refuses every `application/vnd.google-apps.*` target
client-side, because a raw media `PATCH` has no meaningful content to
replace. ADR-0073 answered that for Sheets by adding a second Google host
and a cell-level surface. A Doc has no cells, no rectangular read and no A1
notation, so almost nothing of ADR-0073's Sheets-specific half transfers —
what transfers is its transport, its gate wiring and its refusal shapes.

The genuinely new hazard is the mutation model. `documents.batchUpdate` is
**index-addressed, order-dependent and atomic**: requests apply in sequence,
and an insertion shifts every subsequent index. Worse, the indices a caller
computes come from a `documents.get` that has already returned — so if
anyone edits the document in between, those indices still *resolve*, just
against different text. The failure is silent. Nothing 400s; the edit simply
lands somewhere else.

That moves the safety question. For Sheets it was "which cells does this
touch"; here it is **"against which version of the document is this
computed"**. Everything below follows from taking that question seriously.

## Decision

### 1. A third distinct client, and `drive edit` still refuses Docs

`DocsClient` wraps the shared `GoogleApiClient` and stays a distinct type
from `DriveClient` and `SheetsClient`, for ADR-0073 §1's reason: `FilesApi::new`
takes a `&DriveClient`, so a Docs-hosted client cannot be handed to it and
silently issue `/drive/v3/files` against `docs.googleapis.com`. It shares the
Drive client's OAuth session, since every mutating verb necessarily talks to
both APIs — Drive for the `files.get` and ancestor walk that feed the gate,
Docs for the text.

`content_edit.rs`'s `RefusedNativeDocument` is **unchanged**. Routing a Doc
from `drive edit` into the Docs engine was considered and rejected. That
refusal is a *nonsense* refusal, not a policy one: `drive edit` takes bytes
and a content type and does a media `PATCH`, and there is no meaning to
"replace this Doc's bytes with these bytes". Making it work would require
convert-on-import re-upload — precisely the round-trip ADR-0073's Context
already rejected, which destroys comments, suggestions, revision history,
tabs, named ranges and formatting for a one-word change. It would also have
to run under `Edit`, which §2 exists to forbid. `drive docs …` is the
parallel tree, exactly as `drive sheets …` was.

What that costs is discoverability, and that is paid with the *message*
rather than the behaviour: `drive edit`'s refusal names both `drive sheets`
and `drive docs`, so the user is one line away from the command that works.

### 2. A new `DriveOperation::DocsWrite`, folded into neither `Edit` nor `SheetsWrite`

ADR-0073 §3 rejected reusing `Edit` for cell writes; ADR-0075 §1 rejected
reusing `SheetsWrite` for structural edits. The identical argument applies a
third time, and now in **two directions at once**.

Against `Edit`: every `allow: ["edit"]` rule in existence was written when
`drive edit` refused Google-native documents outright — which, per §1, it
still does.

Against `SheetsWrite`: every `allow: ["sheets-write"]` rule was written when
Docs were structurally unreachable through this tool. That operation is also
*lexically* about cells; making it govern prose would be a lie told by the
config vocabulary itself.

Fail-closed both ways, unchanged from ADR-0073 §3. Forwards it defaults
`Deny`; backwards an older binary reading a config naming `docs-write` fails
`Settings::load()`, and `active_account_rules` degrades to an empty rule set,
which denies everything.

**This binds future work**, in the form ADR-0075 §1 established: a Docs
*deletion* verb must not later be folded into `docs-write` either. A grant
issued today for "may replace text" must not silently become consent to
remove content tomorrow. The rule is recorded on the enum variant, where
someone adding a delete verb will read it.

### 3. Every mutation carries a revision lease, and `targetRevisionId` is unrepresentable

**This is the load-bearing section.**

`writeControl` is a two-arm union. `requiredRevisionId` says *refuse if the
document has moved*; `targetRevisionId` says *apply my edit against that old
revision, rebasing over whatever landed since*. Every mutation this ADR
authorises sends the first, taken from the same `documents.get` that computed
it. No mutation may send the second.

**Why the second arm is worse than `--force`.** With a force-push you at
least know you overwrote something. A rebase-mode `replaceAllText` reports
plain success on a document containing a collaborator's paragraph that the
edit was never computed against and that nobody looked at. The dangerous
outcome is indistinguishable from the safe one.

So, following ADR-0061 §2's stance exactly — *not an engine option, not a
CLI flag, not a wire field* — `WriteControl` is a **struct with one field,
not an enum over the union**, and `BatchUpdateDocumentRequest.write_control`
is not `Option`. An unleased or rebasing `batchUpdate` does not compile.
There is likewise no `--revision-id` flag: a lease supplied from a previous
invocation is stale by construction, and a flag naming the revision you
*expect* is one `$(…)` away from being the force flag.

**Leased uniformly, including where it is not strictly necessary.**
`replaceAllText` is index-free and would be *correct* unleased. It is leased
anyway, for two reasons. First, it is unbounded — it changes every match at
the moment the call lands — so without a lease a collaborator's three new
occurrences are three edits the user never previewed, which is ADR-0061's
shape: a preview whose truth the operation does not enforce. Second, and
decisively: **uniformity is what makes the guarantee checkable.** A
`batch_update` taking `Option<&str>` has an unleased path; one taking `&str`
does not. One exception and neither the type nor the grep-guard means
anything.

The obvious objection — that a live-edited document churns revisions and the
lease will always fail — dissolves on timing. The `documents.get` and the
`batchUpdate` are consecutive calls in one invocation, and this integration
has no interactive confirmation (ADR-0070 §6, ADR-0071 §7, ADR-0073 §9). The
lease window is a network round-trip, not human think time.

**Google may withhold the lease.** `revisionId` is populated only for callers
with edit access, so a reader-only caller receives none. That is refused
distinctly (`RefusedNoRevisionId`) rather than falling back to an unleased
write. The `batchUpdate` would 403 anyway; refusing is cheaper, clearer, and
— the real reason — keeps "there is no unleased path" true without exception.

Pinned by two tests. `a_batch_update_body_always_carries_the_lease_and_exactly_one_request`
asserts the wire shape; `no_lease_escape_hatch_exists_in_the_docs_write_surface`
is a grep-guard modelled on ADR-0061's, failing the build if any production
line in the wire types, the façade or the engines names `targetRevisionId` or
a force. The type fence alone would not catch a hand-built `serde_json::json!`
body — and that is not hypothetical, since `sheets/api.rs` already builds
request bodies that way.

### 4. Typed verbs; no raw request passthrough, and the log question dissolves

ADR-0075 §2 and §4 are adopted wholesale rather than restated: the surface is
typed verbs, `DocsRequest` models only the requests those verbs need, and
`deleteContentRange` has **no Rust representation at all** — not a variant,
not a struct, not a string constant. `DocsApi::batch_update` takes an
already-built `DocsRequest`, so the only requests expressible are the ones
that enum models, and it carries `pub(in crate::drive)` so no module outside
the gated engines can reach it.

`batch_update` takes **one** `DocsRequest`, not a `Vec`. That makes "one
verb, one request, one batch, one `drivemutation` record" a signature rather
than a convention, and it dissolves #1613's question — which ADR-0075 §7
answered the same way — about whether to log per batch or per request: with a
one-request batch the two answers are the same record, and partial
application cannot arise.

It also removes this API's signature hazard entirely from v1. Ordering inside
a batch, where an insertion shifts every subsequent request's indices, is
where Docs integrations break. A one-request batch cannot exhibit it. The day
a verb genuinely needs several requests, that ADR owns both the ordering
question and the log shape.

### 5. `insertText` at `endOfSegmentLocation`, never a computed index

`InsertTextRequest` takes either an explicit `location { index }` or an
`endOfSegmentLocation`. `docs append` uses the latter, and the reason is
larger than convenience.

Docs indices are **UTF-16 code units**; Rust strings are UTF-8. Any index
this crate computed would be wrong for astral-plane characters in a way that
corrupts silently rather than failing — the emoji case, invisible in every
ASCII test. Letting the server locate the end means **no UTF-16 arithmetic
exists anywhere in this crate**. It also removes the single most common Docs
API bug: the body's last character is its segment terminator, and inserting
*at* the body's `endIndex` is rejected outright.

This is the entry cost `deleteContentRange` and arbitrary `--index`
insertion will have to pay. The moment a verb takes an index, this crate owns
the index model and all of the above returns — which is a reason to defer
them, not merely an observation about them.

The user-visible consequence is documented rather than papered over:
`endOfSegmentLocation` inserts before the segment's trailing newline and adds
no separator, so appending `hello` to a document ending `world` yields
`worldhello`.

### 6. A lost lease is its own outcome, not a generic failure

A stale `requiredRevisionId` is documented as HTTP **400**, and Docs v1
returns the `google.rpc` envelope that ADR-0073 §2 already taught
`error_reason` to read via `error.status`. It becomes
`WriteResult::StaleRevision`, carrying the lease presented and the server's
own message, so the report can say what happened and what to do:

> Refused: 'Q3 Plan' changed since it was read (revision lease abcd1234 no
> longer current) — nothing was written. Re-run to apply against the current
> version.

Nothing was written: a one-request `batchUpdate` is trivially atomic.

**An honest limitation.** The 400 is documented; the `status` string and
message wording are not. `is_stale_revision` therefore matches the status
code plus a message substring rather than trusting either alone, and the
failure direction is safe: a miss degrades to `Failed { detail }` carrying
the server's message verbatim, and there is no input for which it returns
true and a write happens. The observed values should be confirmed against
the live API and this section amended.

### 7. `--dry-run` parity by construction, reporting what each verb can know

The linear shape of ADR-0073 §9 is unchanged — one function, gate check, then
a `dry_run` early return — so a dry run and a real run share their gate
classification by construction rather than by convention. Docs adds one
strengthening: the preview values are computed from the snapshot *before* the
branch and are the same values on both paths, so the two cannot disagree
about what they saw.

Issue #1615 correctly observed that Sheets' "N rows × M columns" affordance
does not translate. What does:

- **`replace`** reports an occurrence count over the text just read.
- **`append`** reports the body's end index and the size being inserted, in
  characters and bytes — deliberately *not* UTF-16 code units, which would
  imply this crate reasons in them when §5 exists so that it need not.

**The count is display-only and never gates the mutation.** A count of zero
still sends the `batchUpdate`. Acting on a client-side estimate would let
`omni-dev` report "nothing to do" for a document that does have matches — the
count is over the body text this command read, while the server's match may
span a `textRun` boundary or a segment we did not fetch. The real run reports
the server's `occurrencesChanged`, so both numbers are separately visible in
the outcome and the log.

`--search` is a literal substring and must be non-empty, validated before any
network call. Case matching **defaults to sensitive, inverting the API's own
`matchCase: false`**: under Google's default `--search it` also rewrites `It`
and `IT`, in a verb with no undo and — per §4 — no `deleteContentRange` to
repair with. Following `ValueInputOption`'s precedent (ADR-0073), the choice
is made deliberately, both spellings are documented, and `--ignore-case` is
the opt-out.

### 8. Refusals before the gate, and one after it

Unchanged in shape from ADR-0073 §4 and §9, inverted for this target:

- **Not a Google Doc**, and **a shortcut** (never followed, its own message
  because "not a Google Doc" is confusing said about a shortcut *to* one) are
  refused before the gate and before any Docs call. They are nonsense, not
  policy.
- **No visible parents** keeps ADR-0073 §4's distinct outcome. Note
  [ADR-0074](adr-0074.md) narrows when this is reached, and file-id-keyed
  rules are the eventual fix for it.
- **No revision id** is refused after the gate, per §3.

The gate runs **before** `documents.get`, not after. The naive ordering — read
first, so the preview is nicer — would hand the document body to a caller the
gate is about to refuse. A blocked write makes zero Docs API calls.

### 9. `docs create` owns its verb, and its seed pays for its own lease

ADR-0073 §11 applies, and one of its arguments is *stronger* here.
`documents.create` accepts only a title and drops the new document in the
caller's My Drive root — it cannot set a parent folder. Since the folder is
the gate's entire input, `FilesApi::create` is not merely the tidier choice
(avoiding a phantom `["drive","create"]` record from composing `drive
create`'s engine); it is the only shape the gate can evaluate at all.

The optional `--text` seed resolves `DocsWrite` on the same folder and
refuses **only on an explicit deny** (`Decision::decided_by.is_some()`),
never on the bare default policy — otherwise `docs create --text` would
create an empty document and then report itself blocked on every folder
granting only `create`. The `Create` verdict authorises the pair, defensible
because the id being written is one this same invocation just created inside
an already-cleared folder.

The seed costs a second `documents.get`, purely to mint a lease for a
document created milliseconds earlier. That round-trip is paid deliberately
rather than adding a "we just made it, nobody can have touched it" unleased
path — which is exactly the escape hatch the next caller reaches for, and
whose existence would void both the type fence and the grep-guard of §3.

There is no `files.delete` anywhere in this integration, so a seed that fails
after a successful create cannot be rolled back; that outcome gets its own
result variant carrying the new file id, so a created-but-empty document is
never reported as a clean failure that leaves an orphan.

### 10. Logging reuses `RecordKind::DriveMutation`, and never records the text

No new record kind, following ADR-0070 §7, ADR-0071 §8, ADR-0073 §10 and
ADR-0075 §7. `operation` becomes `docs-replace` / `docs-append` /
`docs-create`. `DriveMutationOutcome` gains three omit-if-absent context
fields: `occurrences_changed`, `inserted_chars`, and
`required_revision_id` — the last so a `stale-revision` refusal is as
auditable as a success. The Sheets keys (`range`, `updated_*`) are not
reused; overloading them would make a `--service drive` query lie.

**The search text, the replacement text and the appended text are never
logged.** They are user prose, and often the most sensitive thing in the
invocation. This is the Docs analogue of ADR-0073's note that Sheets
responses contain user data, but sharper: an A1 range is metadata, whereas a
search string is content. Bodies remain behind the opt-in, default-off
`OMNI_DEV_LOG_BODIES`; only counts and the opaque revision id are recorded.

Logging happens inside the engine module, never the CLI layer, so a future
MCP caller cannot bypass it by construction.

### 11. Tabs: `replaceAllText` spans every tab, `insertText` hits one

`ReplaceAllTextRequest` with `tabsCriteria` omitted applies to **every** tab;
`insertText` with an empty `tabId` applies to the **first**. That asymmetry
is real and is documented rather than papered over.

As in §6, the honest caveat belongs in the record: this is the documented
behaviour of the two requests, but it is default behaviour rather than
anything the request bodies state explicitly, and it should be confirmed
against the live API before the mutating verbs merge. It is a *scope*
question, not a safety one — the lease of §3 holds whichever tabs are
touched — but it decides whether `replace`'s preview is exact or a lower
bound, so §7's "display-only, never gates the mutation" rule is what keeps
being wrong about it harmless.

Because phase 1 reads with `includeTabsContent=true` and models the tab tree,
`replace`'s occurrence count is taken across **every** tab, so the preview
matches the mutation's scope. Narrowing `replace` to one tab via
`tabsCriteria` was rejected for v1: it would silently narrow what the user
asked for, which is the worse direction to be wrong in.

### 12. CLI-first; MCP, deletion, styling and index insertion deferred

MCP tools follow the deferral of ADR-0070 §9, ADR-0071 §11, ADR-0073 §12 and
ADR-0075 §9. Also out of scope: `deleteContentRange`, arbitrary `--index`
insertion, text styling, paragraph styling, tables, lists, headers/footers
and named-range manipulation.

The cut is principled rather than arbitrary, and it is §5's line: every
deferred item requires this crate to own the index model, which §5 exists to
avoid. Deletion additionally requires §2's re-consent argument to be settled.

### 13. Exit code convention

Unchanged from ADR-0070 §10, ADR-0071 §12, ADR-0073 §13 and ADR-0075 §10:
exit 0 regardless of individual `Blocked` / `Refused*` / `StaleRevision` /
`Failed` outcomes. Scripts detecting a refusal must inspect the output, not
`$?`.

## Consequences

- **No new OAuth grant and no new trust boundary.** The Docs API accepts the
  Drive scopes, so `drive.readonly` covers reading and ADR-0071's
  `--write-file`/`--write-full` tiers cover writing. The narrower `documents`
  scope was considered and rejected for the reason `spreadsheets` was:
  narrower than `drive` on one axis but *broader* than `drive.file` on
  another, and the local gate bounds writes better than either.
- **An existing `write_permissions` config keeps meaning exactly what it
  meant.** The direct consequence of §2, and the reason a third operation
  was worth its cost.
- **Blast radius is larger than a Sheets cell write in one respect worth
  naming.** `sheets write` touches one declared A1 range; `replaceAllText` is
  unbounded, changing every match wherever it occurs. That is precisely why
  §3 leases it and §7 previews it — the mitigation is attached to the
  specific way this operation is broader.
- **A document being actively edited may need a re-run.** That is the feature
  working, not a defect, and there is no flag to avoid it.
- **The occurrence count is an estimate** and may disagree with the server's
  `occurrencesChanged`. It is display-only and never gates the mutation.
- **`omni-dev` cannot delete document content**, however wrong the
  invocation — the §4 analogue of ADR-0061's claim about force-push, enforced
  by a grep-guard rather than by prose.
- **A link-shared Doc cannot be written until it lives in a folder**,
  inheriting ADR-0073 §4's limitation and [ADR-0074](adr-0074.md)'s fix.
- **Read-path enforcement remains the scoped gap** ADR-0071 §11 recorded;
  `docs info`/`read` inherit it.
- **Slides is a separate issue** (#1630): an object-graph model to which none
  of §5's index reasoning applies, though §3's lease design should transfer
  if `presentations.batchUpdate` carries the same `writeControl`.
- **Sync obligation:** [docs/drive.md](../drive.md) for the `drive docs`
  tree, the `docs-write` row and the lease behaviour, and
  [docs/log.md](../log.md) for the three operations and three context keys.
