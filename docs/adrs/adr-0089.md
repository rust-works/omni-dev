# ADR-0089: `<NAME>_FILE` for Every Secret Environment Variable

## Status

✅ Accepted (2026-09-27, #2006)

## Context

omni-dev reads 16 secrets from the environment or from the `env` maps in
`~/.omni-dev/settings.json`: AI backend keys, the Jev, Atlassian, Datadog, Gmail,
Drive and Snowflake credentials, and the browser-bridge token. A secret held in a
variable shows up in `env` listings, in `/proc/<pid>/environ`, in shell history,
and in every child process. A secret held in settings.json sits in a plain JSON
file next to non-secret configuration. Docker and Kubernetes have a convention for
this: `<NAME>_FILE` names a file whose contents are the secret. Before this ADR
omni-dev had no such convention. Only two paths read a secret from a file:
`SNOWFLAKE_PRIVATE_KEY_PATH` (no permission check), and the bridge's
`--token-file` flag (`0600` required).

Each secret was read at its own call site, through `EnvSource::var`,
`Settings::get_env_var` or `std::env::var` directly. So adding `_FILE` handling at
each site would have given 16 slightly different implementations.

Five questions shaped the design:

- **Layering.** `SettingsEnv` merges the process environment over settings.json
  one key at a time. If `NAME` and `NAME_FILE` were resolved separately, a
  `NAME_FILE` in the environment and a `NAME` in settings.json would look like
  "both set". Either choice is then wrong: raising a conflict blocks the natural
  override, and picking one silently mixes layers.
- **Aliases.** `OPENAI_API_KEY`/`OPENAI_AUTH_TOKEN` and
  `TYPESAFE_API_KEY`/`OMNI_DEV_JEV_API_KEY` already have a precedence order.
- **A name collision.** `GMAIL_CLIENT_SECRET_FILE` already exists with a
  different meaning: it is the path to a Google `client_secret.json` for
  `gmail auth import`. One alternative was to rename it (for example to
  `GMAIL_CLIENT_SECRET_JSON`) with a deprecation period. During that period the
  old name would mean two things at once. A user who still exported it for
  `import` would have JSON silently read as their raw client secret, or would
  need a content-sniffing heuristic to tell the two apart.
- **Relative paths.** Docker resolves them against the current directory. The
  daemon runs under launchd with a current directory of `/`, and a value in
  settings.json has no meaningful current directory at all. So the same relative
  path would mean different things depending on who reads it.
- **Kubernetes projects secrets through symlinks** (`..data/`), so a check that
  refused symlinks would reject the standard layout.

## Decision

We will read every secret environment variable through one resolver,
`crate::utils::secret_env`, and every such variable will accept `<NAME>_FILE`.

1. **One registry, one resolver.** `SECRET_ENV_VARS` lists every secret.
   `secret_var(env, name)` and `secret_var_any(env, names)` return
   `Result<Option<Secret>, SecretEnvError>`. `secret_var_is_set` serves the
   presence-only `auth status` reports without reading the file.
   `read_secret_file` is the single reader for `_FILE` values. No call site
   handles `_FILE` itself. (The bridge's `--token-file` flag keeps its own
   reader: it is a command-line path, not a variable.)
2. **Pairs are resolved one layer at a time.** A new `EnvSource::var_pair(key,
   file_key)` returns both members of the pair from a single layer.
   `SettingsEnv` and the borrowed `Settings::env_source()` override it: the
   process environment's pair is used if it sets either member, otherwise the
   active profile's `env` pair, otherwise the base `env` pair. A conflict inside
   one layer is an error that names both variables. Between layers, the normal
   precedence applies, so `NAME_FILE` in the environment overrides `NAME` in
   settings.json.
3. **Aliases keep their order.** The resolver goes through the names in order
   and stops at the first one whose pair is set. A conflict can only occur
   within a single name's pair.
4. **File rules.**
   - The path must be absolute, and `~` is not expanded.
   - Symlinks are followed, and the checks apply to the target, which must be a
     regular file.
   - On Unix, the target must also pass an ownership check. A file owned by
     the effective uid must grant no group or other bits
     (`mode & 0o077 == 0`). A file owned by root is accepted when no group or
     other user can write it (`mode & 0o022 == 0`); group and other *read* is
     allowed there, because that is the shape Kubernetes (`0644`, or `0440`
     with `fsGroup`) and Docker Swarm (`0444`) give their secret mounts, and
     only root could have placed or swapped such a file. Any other owner is
     refused. The file is stat'ed before it is opened, and the opened handle
     is checked again.
   - Exactly one trailing `\n` or `\r\n` is trimmed. An empty result is an
     error, and so is non-UTF-8 content.
   - Empty variable values (`NAME=` and `NAME_FILE=`) count as unset, which is
     the existing way to neutralise an exported variable.
   - Windows gets no mode or owner check. That is a documented caveat.
5. **Errors never contain the secret.** `SecretEnvError` messages name the
   variable, the path, the octal mode or owner uid, and the fix
   (`chmod 600 <path>`, or `chmod go-w <path>` for a root-owned file), and
   nothing else.
6. **`GMAIL_CLIENT_SECRET` is exempt.** The existing `GMAIL_CLIENT_SECRET_FILE`
   keeps its meaning. Google documents an installed-app OAuth client secret as
   non-confidential, and `gmail auth import` already reads it from a file.
   Exemptions live in `EXEMPT_SECRET_ENV_VARS`, each with its reason. Two other
   names are exempt: `SNOWFLAKE_PRIVATE_KEY_PASSPHRASE`, until encrypted keys are
   supported, and `PROGRAMMATIC_ACCESS_TOKEN`, which is a wire value rather than
   a variable.
7. **`SNOWFLAKE_PRIVATE_KEY_PATH` stays as an alias.** It outranks
   `SNOWFLAKE_PRIVATE_KEY_FILE` and is read through `read_secret_file`, so it
   now gets the same checks. It is a separate variable, not part of the
   `SNOWFLAKE_PRIVATE_KEY` pair, so it keeps its old precedence across layers:
   a `SNOWFLAKE_PRIVATE_KEY_PATH` in settings.json still outranks a
   `SNOWFLAKE_PRIVATE_KEY_FILE` in the process environment. That is the one
   exception to point 2, and it is kept so that existing configurations don't
   change which key they sign with.
8. **Writers keep pairs consistent.** `Settings::upsert_env_vars_in`, which
   every `auth login` uses, removes a registered secret's `_FILE` companion from
   the map it writes to, so a login never creates a same-layer conflict.
   `Settings::remove_env_vars_in`, used by `auth logout`, removes both members,
   so a logged-out secret can't keep resolving through its file.
9. **`claude-cli` scrubbing covers `_FILE`.** When the tool escape hatch is on,
   `<NAME>_FILE` is scrubbed from the nested `claude`'s environment whenever
   `NAME` is a secret. This includes the `ANTHROPIC_*` names whose values are
   deliberately kept, because the nested process never reads our convention.
   Naming the `_FILE` variable in `OMNI_DEV_CLAUDE_CLI_KEEP_ENV` still keeps it.
   The scrub also now treats every registered secret, and
   `SNOWFLAKE_PRIVATE_KEY_PATH`, as a secret, which closes a gap where names
   like `DATADOG_APP_KEY` and `SNOWFLAKE_PRIVATE_KEY` escaped the suffix list.
10. **Grep guards enforce the registry.** Tests in `secret_env.rs` scan
   production sources and fail in three cases:
   - A secret-shaped `"UPPER_SNAKE"` literal is neither registered nor exempt.
   - A registered name is passed to a plain accessor (`var`, `var_any`,
     `get_env_var`, `non_empty_var`, `std::env::var`, …), either as a literal or
     through a `const` bound to it.
   - A registered name's `_FILE` companion already exists as a literal, which is
     the collision check.

   [STYLE-0030](../STYLE_GUIDE.md) records the rule for authors.
11. **Named-account secrets get `_file` fields** (added 2026-09-27, #2008).
   Named Drive and Gmail accounts are not environment variables. They are
   `drive.accounts.<name>` and `gmail.accounts.<name>` entries in
   settings.json ([ADR-0066](adr-0066.md), [ADR-0069](adr-0069.md)). Each
   entry's `client_secret` and `refresh_token` accept a `client_secret_file`
   and `refresh_token_file` companion. These are resolved by
   `resolve_secret_pair`, the pair logic factored out of `secret_var`, so the
   file rules in point 4 and the conflict rule apply per entry. Errors name the
   full settings key, for example `drive.accounts.work.refresh_token_file`.
   Two choices differ from the flat variables:
   - **Writers write through to the file.** Under point 8, a login that writes
     a flat variable removes its `_FILE` companion. For a named account that
     rule would do the wrong thing in the common case: re-logging every account
     after an OAuth client rotation would move each account's secrets back
     into settings.json. So when an entry names a `_file`,
     `Settings::upsert_{drive,gmail}_account` writes the new value into that
     file with `write_secret_file` and removes the plain field. A file that
     already holds the value is left alone, which keeps a shared file or a
     root-owned read-only mount working. Any other file is replaced
     atomically: a new `0600` file is created beside the symlink-resolved
     target and renamed over it. Every secret file is written before
     settings.json, so a failed write leaves settings.json unchanged. A named
     account's logout removes its entry but not the files, which may be shared.
   - **No fallback to the flat variables.** A named account missing
     `client_secret` does not borrow `DRIVE_CLIENT_SECRET` or
     `GMAIL_CLIENT_SECRET`. That fallback would mix credential layers
     silently. Accounts that share one OAuth client point their
     `client_secret_file` at the same file instead.

   A Gmail `client_secret_file` that holds JSON is refused. The flat
   `GMAIL_CLIENT_SECRET_FILE` names a `client_secret.json` (point 6), so the
   field is easy to point at one by mistake, and an OAuth client secret never
   starts with `{`. The field has only this one meaning, so this check is
   input validation, not the content sniffing that point 6 rejected.

## Consequences

- **Positive.**
  - Every secret can stay out of the environment and out of settings.json.
    Mounted secret files (Docker, Kubernetes, systemd `LoadCredential`, a
    password manager's file export) work without a wrapper script.
  - There is one implementation with one set of tests, and the guards stop a
    new secret from quietly bypassing it.
  - The `auth status` presence flags now count a `_FILE` as configured.
  - AI preflight now resolves the key rather than only checking that one is
    present, so a bad file fails early with the precise reason.
- **Negative.**
  - A root-owned secret that is group- or world-readable is accepted. On a
    shared host, a root-owned `0644` file named by a `_FILE` variable is
    readable by every local user; the check does not second-guess that,
    because only an administrator could have created it, and refusing it
    would reject every standard Kubernetes and Docker Swarm secret mount.
    Files you own stay owner-only.
  - `SNOWFLAKE_PRIVATE_KEY_PATH` used to accept a relative path and any mode.
    Both are now errors.
  - An empty `ATLASSIAN_API_TOKEN`, `DATADOG_*_KEY` or Gmail/Drive secret used
    to become an empty credential. It now reads as "not configured".
  - `GMAIL_CLIENT_SECRET` is a named exception to an otherwise uniform rule.
- **Neutral.**
  - Windows is unchecked. ACL inspection can follow if a Windows user needs it.
  - Relative paths can be allowed later without breaking anyone. Allowing them
    now and forbidding them later would break users.
  - The grep guards work on text. They strip `#[cfg(test)] mod` blocks by
    matching braces with a small lexer that skips strings, chars and comments,
    and a module that never closes panics the guard rather than hiding what
    follows it. Unusual formatting could still evade them, so they are a safety net and do not replace review.
