# ADR-0081: Permission-Gate Mapping for the Second Sheets Capability Tranche

## Status

✅ Accepted (2026-09-20)

**Extends [ADR-0075](adr-0075.md), [ADR-0077](adr-0077-sheets-deletion-via-batchupdate.md)
and [ADR-0078](adr-0078.md); reverses none.** Those three ADRs built the
`DriveOperation` vocabulary this one reuses without change: `SheetsWrite`
(ADR-0073 §3) for cell values, `SheetsStructure` (ADR-0075 §1, extended by
ADR-0078 §1) for non-destructive structural/cosmetic edits, `SheetsDelete`
(ADR-0077) for grid-data deletion, and `SheetsProtection` (ADR-0078 §2) for
permission changes inside a workbook. This ADR is a pure gate-mapping design
pass — issue #1800, blocking issues #1796/#1797/#1798 — and ships no code.
Every capability it covers is still unimplemented; the operation each one
resolves to is a decision made once, here, so the three implementing issues
do not each re-litigate it and none of them accidentally settle it three
different ways.

## Context

Issue #1663 is the tracker for the second Sheets capability tranche: seven
capabilities (#1793–#1799) with no request type anywhere in
`src/drive/sheets/` — #1663's "entirely unimplemented" set. #1791 and #1792
are excluded from that count: they add flags to verbs that are already
gated (`format-cells`, `update-borders`, `set-data-validation`), not new
capabilities needing a gate decision of their own, and neither is discussed
further in this ADR. Two of the seven need no new argument — their gate
follows directly from work `SheetsStructure`'s own doc comment already
covers:

- **Conditional formatting** (#1793) — `addConditionalFormatRule`/
  `updateConditionalFormatRule`/`deleteConditionalFormatRule` are
  presentational and destroy no data, exactly like `format-cells` and
  `clear-data-validation`, which already sit under `sheets-structure`.
- **Filter views and the basic filter** (#1794) — `setBasicFilter`/
  `addFilterView`/etc. hide rows; that is view state, not data.
- The **read halves** of every capability in the tranche
  (`list-conditional-formats`, `list-filter-views`, `list-named-ranges`,
  `list-charts`, `search-developer-metadata`) are ungated, following
  `list-protections`' precedent (ADR-0078 §2): a caller must be able to see
  what exists before an id- or index-addressed verb can act on one at all.
- The **additive halves** of named ranges (`addNamedRange`/`updateNamedRange`,
  #1796) and of charts/slicers (`addChart`/`updateChartSpec`/`addSlicer`/
  `updateSlicerSpec`, #1797) are equally uncontested: a label over a region,
  or a chart/slicer definition, is created or repointed without touching
  existing cell values.

Four questions remain, and each is the kind ADR-0078 §2's "wrong in kind, not
just in scope" test exists to settle rather than assume:

1. **`deleteNamedRange`** (#1796) removes a label, not cells — but every
   formula referencing that name becomes an error, so cell *values* change as
   a visible consequence, even though no cell's stored content is touched.
2. **`deleteEmbeddedObject`** (#1797, shared by charts and slicers) destroys
   an artifact that cannot be reconstructed from cell data — a stronger claim
   than "removes something placed deliberately," which is nonetheless exactly
   the description that already covers `unmerge-cells`/`clear-data-validation`
   under `sheets-structure`.
3. **Developer metadata** (#1795) is the channel other add-ons key their own
   state on: deleting it has an effect outside this tool's own data, unlike
   every other `sheets-structure` capability, which is self-contained.
4. **Pivot tables** (#1798) have no `addPivotTable` request at all — they are
   created by `updateCells` carrying a `pivotTable` in `CellData`, writing
   through the grid with a server-computed rendered extent. That is
   `SheetsWrite`'s territory by construction, not `SheetsStructure`'s, which
   ADR-0078 §3 deliberately made unable to reach `updateCells` at the type
   level.

## Decision

### 1. Uncontested reuse of `sheets-structure`, recorded for completeness

Conditional formatting (#1793), filter views/the basic filter (#1794),
named-range add/update (#1796's non-delete half), and chart/slicer add/update
(#1797's non-delete half) all join `SheetsStructure` — none destroy grid data
and none change who may edit. Every `list-*` verb across the tranche
(`list-conditional-formats`, `list-filter-views`, `list-named-ranges`,
`list-charts`) stays ungated, matching `list-protections`. `search-developer-
metadata` (§3 below) is ungated for the same reason.

### 2. `delete-named-range` joins `sheets-structure`, with a mandatory referencing-formula preview

Deleting a named range does not touch a single cell's stored value or
formula text — it removes a label, and every formula that referenced it
starts evaluating to `#NAME?` in place. That is a real, visible effect, but
it is the same *shape* of harm ADR-0078 §4 already accepted under
`sheets-structure`: `mergeCells` actually discards cell **values** — a
strictly larger harm than an unchanged formula evaluating differently — and
stayed under `sheets-structure` because its `--dry-run` (and real run, before
mutating) reads the target range first and reports exactly what would be
lost. `delete-named-range` gets the same treatment, scaled to its smaller
harm: before deleting, it scans the workbook's formulas for the name being
removed and reports the count and A1 locations of every referencing formula,
in both `--dry-run` output and the real run's `drivemutation` record. The
harm is also more recoverable than `mergeCells`'s: re-adding a named range
with the same name over the same range restores every dependent formula to
working order, since the name — not the formula text — is what changed.

This preview costs more than the light, tab-list-only `spreadsheets.get`
every other structural dry run in this tranche reuses (`api.rs`'s
`SPREADSHEET_FIELDS`, whose own doc comment warns that an unmasked
`spreadsheets.get` "embeds every cell of every sheet in the response, so on
a large workbook the difference between sending this and not is an
out-of-memory failure rather than a slower request"). A referencing formula
can live on any sheet, so the scan needs a workbook-wide formula read —
`values.batchGet` with `valueRenderOption=FORMULA` across every sheet,
chunked through `api.rs`'s existing `MAX_RANGES_PER_BATCH`, never the
unmasked call that mask exists to avoid. That is the same *shape* of read
[ADR-0077](adr-0077-sheets-deletion-via-batchupdate.md) §5 declined to pay
for when it settled `delete-rows`/`delete-columns`/`delete-range` on a fixed
caveat instead of a formula-impact preview, for two named reasons: cost, and
the data-exposure question issue #1623 raised. Both are judged differently
here, and the difference — not an inconsistency — is why this ADR reaches
the opposite conclusion for named-range deletion specifically. Cost: a name
search is a single exact-match text scan per formula with a complete,
correct answer in one bounded pass; ADR-0077 §5's read would have had to
reason about which cells a *shifted* range now covers after a dimension
delete, an open-ended impact analysis, not a lookup. Data exposure: the
preview reports only the *count* and *A1 location* of each referencing
formula — never a cell's value or its formula text — so it stays inside the
"no cell content ever appears" line ADR-0077 §5 itself draws for every
destructive preview in this integration; it does not reopen the
read-every-sheet exposure question that ADR raised for a *content* preview,
because this one is never that.

Folding the delete into `SheetsDelete` was the other candidate, but
`SheetsDelete`'s own doc comment scopes it to "a sheet, a row/column range,
or an arbitrary cell range" — grid data. A named range is not grid data; the
cells underneath it are completely untouched by its removal.

### 3. `delete-chart`/`delete-slicer` join `sheets-structure`, with a mandatory object-spec preview

`deleteEmbeddedObject` is a stronger case for `sheets-delete` than named-range
deletion — the issue's own framing is right that a chart or slicer cannot be
reconstructed from cell data the way a value can. But `SheetsDelete`'s
binding scope, fixed by ADR-0077, is specifically **grid data**: a sheet, a
row/column range, or a cell range. A chart or slicer is a visual artifact
layered over the grid, never a grid value itself, so routing its deletion
through `SheetsDelete` would be the same category error ADR-0078 §2 ruled out
in the other direction for protected ranges — widening an operation beyond
what its own binding definition covers. The closer precedent already inside
`sheets-structure` is `unmerge-cells`/`clear-data-validation`: both remove
something a user deliberately placed, and both were judged additive-in-kind
because what they remove is a *property of the grid* (a merge, a validation
rule), not the grid's data. A chart/slicer is the same kind of thing one
level further out — a property of the *sheet*, not of any cell.

The unrecoverability is real, so it gets the same mitigation as §2:
`delete-chart`/`delete-slicer` read back and report the object's current
spec — type, title or id, anchor position — before deleting, in both
`--dry-run` and the real run's `drivemutation` record. This is the
`discarded_cells` treatment (ADR-0078 §8) applied to an object instead of a
value: the operator sees exactly what is about to become unrecoverable
before it happens, which is the standard this codebase already holds
non-restorable-but-additive removals to, not a stricter gate.

### 4. Developer metadata joins `sheets-structure`, restricted to `DOCUMENT` visibility, with a mandatory preview on delete

`createDeveloperMetadata`/`updateDeveloperMetadata`/`deleteDeveloperMetadata`
attach or remove key/value annotations on the spreadsheet, a sheet, a row or
a column. None of that is grid data and none of it is a permission change,
so developer metadata fails both of the categorical tests that pull a
capability out of `sheets-structure` (§2's "destroys data" and ADR-0078 §2's
"changes who may edit"). The concern issue #1795 raises — that deleting
metadata can break an unrelated add-on that keyed its own state on it — is
real, but it is a *functional/compatibility* risk to a third party's
integration, not a data-destruction risk to this spreadsheet or a
permission-widening risk inside it. It does not change which operation this
belongs to; it changes what the surface is allowed to touch and how loudly it
must say so before doing it, and both land with #1795's first version rather
than after:

- The surface reads and writes `DOCUMENT`-visibility metadata only, never
  `PROJECT`-visibility metadata — which belongs to whatever OAuth client
  created it and is categorically not this tool's to touch. This is the
  cheapest and most direct mitigation for the cross-add-on concern: it
  removes the case where deleting metadata reaches into a different
  integration's project-scoped state at all, rather than merely warning
  about it after the fact.
- `delete-developer-metadata` reads back and reports the key, value, and
  location of the metadata being removed before deleting — the same preview
  pattern as §2 and §3, since a third party's dependency on a given key is
  exactly the kind of effect a caller cannot be expected to know without
  being shown it.

`search-developer-metadata` reaches a different endpoint
(`spreadsheets.developerMetadata.search`, not `batchUpdate`) and is a read;
it stays ungated like every other `list-*`/`search-*` verb in this tranche.

### 5. Pivot-table creation requires **both** `sheets-write` and `sheets-structure`; deletion requires `sheets-write` alone

Pivot tables are the one capability in this tranche that is not additively
one existing operation's territory. Creation is an `updateCells` request
carrying a `pivotTable` in `CellData` at an anchor cell, and the server
renders the pivot's result outward from that anchor — overwriting whatever
values are already there, with an extent the request itself never states.
That is `SheetsWrite`'s territory by construction: ADR-0078 §3 went out of
its way to make `sheets-structure`'s formatting request type
(`RepeatCellData`) carry no `userEnteredValue` field at all, a type-level
guarantee that a `sheets-structure` grant can never be used to write into a
cell. Routing pivot-table creation through `SheetsStructure` alone would
break that guarantee for the first time since it was made. But a pivot table
is also a named, persistent, structural feature of a sheet in exactly the
sense `sheets-structure` grants are understood to cover — closer to
`duplicateSheet` or a conditional-format rule than to a plain value write.

Rather than invent a ninth operation for a capability that is, in substance,
the union of two capabilities the vocabulary already has, `add-pivot-table`
requires **both** `SheetsWrite` and `SheetsStructure` to resolve `Allow`
against the same target. This is not new consent manufactured for the
occasion: an operator who has already granted both operations has, by
definition, already consented to arbitrary cell overwrites (via
`sheets-write`) and arbitrary structural changes (via `sheets-structure`).
Pivot-table creation asks for nothing beyond exactly that union, so no
existing single-operation grant is retroactively widened, and no operator who
holds both is asked to grant a third, redundant permission naming "pivot
tables" specifically.

`delete-pivot-table` — an `updateCells` clearing the anchor cell's
`pivotTable` field — only ever touches that one cell's value, with no
structural effect, so it needs `SheetsWrite` alone.

**This is the first capability requiring more than one `DriveOperation` to
independently resolve `Allow` — but not the first two-operation check in the
codebase.** `src/drive/sheets/create.rs` (ADR-0073 §11) already resolves two
operations for `sheets create --values`: `Create` against the target folder,
then, only when seed values are given, `SheetsWrite` — but *asymmetrically*,
since `SheetsWrite`'s bare default-deny does not block the seed, only an
explicit `deny: ["sheets-write"]` rule does (`Decision::decided_by.is_some()`
is what the engine checks). That composition exists so "no `sheets-write`
rule needed to seed a brand-new file" stays true for the common case while
still honoring a deliberate veto; it does not fit pivot-table creation, which
is not one operation with an opt-out but a genuine union of two capabilities
an operator must have separately and fully granted. `add-pivot-table` is
therefore the first capability in the codebase requiring **both** operations
to independently resolve `Allow` — a stricter, symmetric composition, not the
codebase's first multi-operation check.

`src/drive/sheets/target_gate.rs::resolve` takes a single `DriveOperation`
and is called once per verb everywhere else in the crate — `create.rs`
included, since it calls `folder_ancestry::resolve_decision` directly rather
than `target_gate::resolve` (there is no pre-existing target to resolve a
gate against until `files.create` returns one). `add-pivot-table` calls
`target_gate::resolve` twice against the same, already-existing target — once
for `SheetsWrite`, once for `SheetsStructure` — and must deny unless both
calls return `Allow`. Implementing #1798 needs to add that composition; it
does not need a new variant or a change to either operation's existing
semantics.

`--dry-run` cannot enumerate the region a pivot table will overwrite, because
the server computes it from the source data at creation time — the same
"cannot be computed from the request alone" problem ADR-0075 §6 hit for
dimension-shift previews, one size larger. The honest answer, and the one
`--dry-run` must give, is to name the anchor cell, the source data range, and
the pivot configuration, and to state plainly that the affected region is
server-computed and unknown until the request is sent — a documented
limitation, not a claim the tool cannot back up.

### 6. No new `DriveOperation` variant

Every capability in this tranche resolves to `SheetsWrite`, `SheetsStructure`,
or — for pivot-table creation only — both at once. `SheetsDelete`'s and
`SheetsProtection`'s binding clauses, and their doc comments, are unaffected
and untouched by this ADR.

## Consequences

- **No new OAuth grant and no new trust boundary.** Every request in this
  tranche rides the same Drive scopes already covered, unchanged since
  ADR-0073.
- **`sheets-structure` grows again in meaning.** An operator who granted it
  before this ADR shipped is not retroactively exposed to anything that
  destroys grid data or widens who may edit — the same guarantee ADR-0078's
  Consequences record — but is exposed to named-range/chart/slicer/developer-
  metadata management once #1795/#1796/#1797 land, which this ADR argues is
  within what granting "restructure this workbook" already implied.
- **First symmetric two-operation gate, extending an asymmetric precedent
  ADR-0073 §11 already set.** Pivot-table creation (§5) establishes that a
  hybrid capability can require more than one `DriveOperation` to
  *independently* resolve `Allow` at once, instead of earning a new
  operation for every combination that arises — the stricter sibling of
  `sheets create --values`'s existing Create-decides/SheetsWrite-vetoes
  composition. Future hybrid capabilities should pick whichever of the two
  shapes matches theirs — a primary operation with an explicit-deny veto, or
  a full union requiring both to `Allow` — before proposing a new variant.
- **Every non-restorable removal that stays under `sheets-structure` in this
  tranche picks up a mandatory pre-mutation preview** — named-range deletion
  (§2), embedded-object deletion (§3), developer-metadata deletion (§4).
  This extends ADR-0078 §4's `mergeCells` preview from "the one exception in
  that batch" to the standing mitigation this codebase uses whenever an
  operation stays additive-in-kind but one of its verbs has an
  unrecoverable, previewable side effect.
- **Developer metadata is scoped to `DOCUMENT` visibility from its first
  version** (§4) — `PROJECT`-visibility metadata is never reachable through
  this surface, by construction, not by convention.
- **Sync obligation, deferred to each implementing issue.** This ADR ships
  no code. `docs/drive.md`'s default-policy table and `sheets-structure`/
  `sheets-write` prose, and `src/drive/write_gate.rs`'s `SheetsStructure`/
  `SheetsWrite` doc comments, all need the new verb names added once
  #1795/#1796/#1797/#1798 actually land — the same deferral pattern
  ADR-0075 §1 used for the deletion binding clause ADR-0077 later fulfilled.
