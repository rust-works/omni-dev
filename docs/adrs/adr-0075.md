# ADR-0075: Structural Sheet Edits via `spreadsheets.batchUpdate`

## Status

✅ Accepted (2026-09-07)

**Extends [ADR-0073](adr-0073.md), reverses none.** ADR-0073 added the
Sheets v4 API and cell-level access — `values.get`/`update`/`append`/`clear`
behind a new `DriveOperation::SheetsWrite` gate. Its §12 deferred
**structural** edits via `spreadsheets.batchUpdate` "entirely", pending
their own safety analysis, and named the reason: "row and column deletion is
the sharp edge, where one call destroys far more than its arguments
suggest."

This ADR is that analysis. It ships the half of the surface that does not
have that property, and makes the other half unreachable rather than merely
unimplemented.

## Context

The existing write surface has a property that makes it comparatively safe:
every mutation names an explicit A1 range, and `--dry-run` reports the exact
dimensions before anything lands. `batchUpdate` breaks that in three ways,
all identified in issue #1613:

- **`deleteDimension` is unbounded by its own arguments.** Deleting rows
  5–10 also silently rewrites every formula referencing them across the
  whole workbook.
- **Requests are a batch.** Sheets applies them atomically, but the
  result and request-log model is built around one mutation per record.
- **`deleteSheet` destroys data with no per-cell footprint**, so ADR-0073's
  Consequences claim that "blast radius per call is smaller than `drive
  edit`'s" does not obviously carry over.

Structural editing is nonetheless the most-requested thing the Sheets
surface cannot do: adding a tab for a new reporting period, renaming one,
and making room for rows are ordinary operations that today require leaving
the CLI entirely.

## Decision

### 1. A new `DriveOperation::SheetsStructure`, not a reused `SheetsWrite`

ADR-0073 §3 rejected reusing `Edit` for cell writes because every existing
`allow: ["edit"]` rule was written when `drive edit` refused Google-native
documents outright. The identical argument applies one level up, and is
accepted for the identical reason: every `allow: ["sheets-write"]` rule that
exists today was written when structural edits were **impossible**. Reusing
`SheetsWrite` would retroactively convert those grants into "may restructure
every workbook in this folder" — no config change, no re-consent, no way for
the operator to have anticipated it.

Fail-closed in both directions, as §3's variant is. Forwards: it defaults
`Deny` like every other write. Backwards: an older binary reading a config
naming the new operation fails `Settings::load()`, and `active_account_rules`
degrades to an empty rule set, which denies everything.

**This binds future work, and that is the point.** Sheet and row deletion
must not later be folded into `sheets-structure` either. Doing so would make
a grant issued today silently become consent to destroy data tomorrow —
exactly the widening this variant exists to prevent. When deletion is
designed, it needs its own operation, or explicit re-consent. The rule is
recorded on the enum variant itself, where someone adding a delete verb will
read it.

### 2. Typed verbs, and no raw request passthrough — ever

The surface is four commands — `add-sheet`, `rename-sheet`, `insert-rows`,
`insert-columns` — each with typed arguments. The rejected alternative was a
single `sheets batch-update --requests requests.json` forwarding the
caller's `Request[]` array verbatim: full API coverage on day one for a
fraction of the code.

It is rejected because it defeats every safety property the rest of this ADR
establishes. The gate would resolve one verdict for "some requests"; the
request log would record "a batch happened"; `--dry-run` could report only a
count. That opacity *is* the hazard ADR-0073 §12 declined to inherit, not an
incidental cost of it.

The same reasoning forbids adding such a command later as an escape hatch
beside the typed verbs, which is the shape that usually survives review. A
bypass reachable from the surface is not weaker than no guard at all only if
nobody uses it. This is [ADR-0061](adr-0061.md)'s central conclusion applied
to a different operation: force-push has no escape hatch anywhere in the
worktrees surface — not an engine option, not a CLI flag, not a wire field —
so the daemon *cannot* overwrite a remote tip it has not seen, however wrong
the request is. Here the equivalent claim is that `omni-dev` cannot issue a
`deleteSheet`, however wrong the invocation is.

### 3. Additive and rename only; deletion is deferred, not gated

v1 covers `addSheet`, `updateSheetProperties` (title only) and
`insertDimension`. `deleteSheet`, `deleteDimension`, `deleteRange`,
formatting, data validation, protected ranges, `duplicateSheet` and sheet
reorder/hide are all out of scope.

The cut is not arbitrary, and this is the one ADR-0073 conclusion this work
has to re-earn. ADR-0073's Consequences claim that "blast radius per call is
smaller than `drive edit`'s" **survives intact for this subset**: adding a
sheet, renaming one and inserting rows destroy nothing and remove no data.
An insert shifts rows, which is a real effect on formulas, but it is
additive and reversible by the inverse operation. `deleteSheet` and
`deleteDimension` are precisely the two requests that would break that
claim — which is what makes them a separate design pass rather than two more
verbs, and gives the boundary a principled place to sit.

Deferred, specifically, rather than shipped behind a confirmation or a
`--force`. ADR-0070 §6 and ADR-0073 §9 already establish that this
integration has no interactive confirmation and no `--force`; adding one
here for deletion would introduce that pattern for the single most dangerous
operation in the tree, which is the worst possible place to introduce it.

### 4. The requests are not modelled, so they are not constructible

`BatchUpdateRequestItem` is an externally-tagged enum with three variants,
matching Sheets' own wire shape. The destructive requests have **no Rust
representation at all** — not a variant, not a struct, not a string
constant. `SheetsApi::batch_update` takes already-built
`BatchUpdateRequestItem`s rather than a JSON body, so the only requests
expressible are the ones that enum models.

That is a type-level guarantee, and it is pinned by a grep-guard test
(`no_destructive_request_is_reachable`) modelled directly on ADR-0061's
`no_force_escape_hatch_exists_in_the_ui_surface`: no production line in the
engine, the API façade or the wire types may name a delete request. A future
change cannot add one without failing the build. Prose in this repository
describes what we refuse to do; the test is what makes the refusal true.

The method carries `pub(in crate::drive)`, like the `values.*` mutating
methods (ADR-0073 §1), so no module outside `crate::drive` — where every
engine runs the gate first — can reach it.

### 5. The gate precedes every Sheets call; `--dry-run` follows one read

The engine follows ADR-0073 §9's linear shape exactly: pre-gate refusals,
then the gate, then a `dry_run` early return, then the mutation. A preview
and a real run share one gate classification by construction.

One ordering decision is specific to this surface. Describing a structural
effect honestly needs the target sheet's real current dimensions, which
means a `spreadsheets.get`. It is placed **after** the gate, so:

- a gate-blocked attempt still makes **zero** Sheets calls, preserving
  ADR-0073's "a refusal stays exactly as auditable as a success"; but
- a dry run *does* make one `spreadsheets.get`, unlike `sheets write`'s dry
  run, which touches Sheets not at all.

A read is not a mutation, so this is a deliberate difference rather than a
weakening, and it has its own test. It also pays for itself twice: the same
response resolves the sheet title to the numeric `sheetId` that
`batchUpdate` addresses, so no extra call is needed for that either.

### 6. `--dry-run` names the effect and the shift, not a range

This answers issue #1613's "what does `--dry-run` show for a request whose
effect isn't expressible as a range?"

```
Would insert 3 row(s) before row 5 of 'Q2' (sheetId 118293) in 'Budget'
  (500 rows -> 503; existing rows 5-500 shift down)
```

The second line is the substance. An insert's effect is unbounded in the
same *direction* a delete's is — everything below moves — so the preview
states the resulting dimension and names the shift explicitly, read from the
sheet's real size rather than assumed. Stating only "rows 5-7 would be
inserted" would be true and misleading in exactly the way ADR-0073 §12
warned about.

Two refusals exist so a dry run can never promise a change the real run then
fails: a named sheet that does not exist (listing the ones that do), and an
`add-sheet` title already in use. This is **not** the client-side validation
ADR-0073 §7 rejects. §7 is about A1 *grammar*, where a naive validator
rejects legal forms and the server is the only authority. Here the server's
own authoritative sheet list is already in hand for the dry run, so the
check costs nothing and is exactly as correct as the server's.

### 7. One `drivemutation` record per verb, which is also one per request

No new record kind, following ADR-0073 §10. `operation` becomes
`sheets-add-sheet` / `sheets-rename-sheet` / `sheets-insert-rows` /
`sheets-insert-columns`.

Issue #1613 asked whether to log one record per batch or one per request
within it. **The question dissolves under §2's decision**: every typed verb
sends a batch of exactly one request, so the two answers are the same
record. Partial application semantics likewise do not arise — a one-request
batch is trivially atomic.

Both questions genuinely reopen the day a verb emits several requests. That
is a further reason the raw-JSON surface is refused outright rather than
deferred: it would have forced both answers immediately, for a surface whose
effects the log could not describe anyway.

`DriveMutationOutcome` gains three omit-if-absent context fields: `sheet_id`
(the stable numeric id, which survives a later rename and so is the only
durable answer to "which tab was this"), `sheet_title`, and
`dimension_range` (e.g. `"ROWS 5:7"`) — the structural analogue of the
existing `range` key, for effects A1 cannot express. Logging happens inside
the engine module, never the CLI layer, so a future MCP caller cannot bypass
it by construction.

### 8. `--at` is 1-based and inclusive

The API's `DimensionRange` is zero-based and half-open; A1 notation and the
spreadsheet UI are 1-based. The CLI follows what the user can see —
`--at 5` inserts above the row the spreadsheet labels 5 — and the single
conversion lives in one pure function with its own tests, never inlined at a
call site. This is the obvious off-by-one in this feature, and the one place
it could hide.

### 9. CLI-first; MCP tools deferred

Unchanged from ADR-0070 §9, ADR-0071 §11 and ADR-0073 §12.

### 10. Exit code convention

Unchanged from ADR-0073 §13: exit 0 regardless of individual
`Blocked`/`Refused`/`Failed` outcomes. Scripts detecting a refusal must
inspect the output, not `$?`.

## Consequences

- **No new OAuth grant and no new trust boundary.** `batchUpdate` accepts
  the same Drive scopes ADR-0073 §1's Consequences already cover; it is a
  new method on a host the same bearer token is already presented to.
- **ADR-0073's "blast radius smaller than `drive edit`" claim survives**,
  because the two requests that would have broken it are not implemented.
  That is the load-bearing consequence of §3, and the reason the v1 cut is
  where it is rather than "everything behind a scary flag".
- **An existing `write_permissions` config keeps meaning exactly what it
  meant.** The direct consequence of §1, and the reason a second Sheets
  operation was worth its cost.
- **A user who needs to delete a sheet or a row must use the Sheets UI.**
  This is a real limitation, recorded as such rather than worked around. It
  is the correct amount of friction for an operation whose effect exceeds
  its arguments, and the same stance ADR-0061 takes on force-pushing the
  default branch.
- **The permission vocabulary grows to six operations.** Fragmentation is
  the standing risk, and the answer is the one ADR-0073 §3 gave: the gate's
  vocabulary growing alongside genuinely new *capability* is correct. A
  seventh operation for deletion would also be correct; a seventh for a
  variation on an existing capability would not.
- **A refusal stays exactly as auditable as a success** — a gate-refused
  structural edit produces a `drivemutation` record with zero Sheets calls
  made, matching ADR-0070, ADR-0071 and ADR-0073.
- **A dry run now issues one read**, where every other `--dry-run` in the
  integration issues none beyond the gate's own. Deliberate (§5), tested,
  and the price of a preview that tells the truth about a shift.
- **Sync obligation.** [docs/drive.md](../drive.md) documents the four
  verbs, the `sheets-structure` row in the write-permission table, and the
  no-deletion limitation; [docs/log.md](../log.md) documents the new
  `drivemutation` operations and context fields. Keep both in sync when this
  ADR's decisions change.
