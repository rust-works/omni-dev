# ADR-0085: Sheet View Properties via `updateSheetProperties`

## Status

✅ Accepted (2026-09-21)

**Extends [ADR-0078](adr-0078.md), reverses none.** ADR-0078 §1 already
generalizes the gate reasoning this ADR applies: a change to a property of
the sheet rather than to the sheet's data, destroying nothing, joins
`SheetsStructure` — the same category `reorder-sheet`/`hide-sheet` and
(ADR-0082 §1) banded ranges sit in. This ADR is the one-capability design
pass issue #1835 (split out of tracker #1830, and named there as the
"sheet properties" member of ADR-0083's additive/structural group) asked
for; it resolves the two questions the issue's own scope note left open and
ships the implementation alongside it.

## Context

`UpdateSheetPropertiesRequest` already exists in `src/drive/sheets/types.rs`
with three users — `rename-sheet`, `reorder-sheet` and `hide-sheet`/
`show-sheet` — but each sets a single named field, and between them they
reach only `title`, `index` and `hidden`. The rest of `SheetProperties` is
unsettable from the CLI at all: `gridProperties.frozenRowCount`/
`frozenColumnCount` (frozen header rows and columns), `tabColor`/
`tabColorStyle`, `rightToLeft`, and `gridProperties.hideGridlines`.

Two questions needed settling before implementation, both already answered
by precedent elsewhere in the crate rather than by anything new:

1. **Whether `hideGridlines` belongs in v1.** The issue raised it as a
   scope question because it lives under `gridProperties` alongside the
   freeze counts rather than at the top level with `tabColor`/`rightToLeft`.
   Structurally that is a distinction without a difference: it is a
   per-sheet display flag that changes no cell, exactly like `rightToLeft`.
2. **How a property gets back to its default.** Most of this set answers
   itself: an omitted flag leaves the property alone, and
   `--right-to-left false`/`--hide-gridlines false` restore the defaults
   directly, being plain booleans. Tab color is the exception — a color has
   no "off" value to pass, so without a deliberate clearing mechanism a tab
   painted once could never be unpainted.

## Decision

### 1. Joins `SheetsStructure` — no new operation

Freeze counts, tab color, right-to-left and gridline visibility are all
presentation: none touches a cell, and turning one off destroys nothing that
turning it back on would not restore. That is precisely the "property of the
sheet, not the sheet's data" test ADR-0078 §1 established and ADR-0081 §§1–4
and ADR-0082 §1 each reused. This capability adds no new fact to weigh, so
it joins `SheetsStructure` rather than earning a variant, and
`write_gate.rs`'s `DriveOperation::SheetsStructure` doc comment is extended
to name the new verb. `SheetsDelete`'s, `SheetsWrite`'s and
`SheetsProtection`'s binding clauses are untouched.

### 2. A new verb, `update-sheet-properties`, not a wider `rename-sheet`

We will add one new `StructureVerb`, matching the shape issue #1835
proposed. Folding four more optional flags into `rename-sheet` would turn a
verb whose name states its entire effect into a catch-all whose name states
one of five, against the family's standing one-verb-per-logical-subcommand
convention. The new verb takes `--freeze-rows`, `--freeze-columns`,
`--tab-color`, `--clear-tab-color`, `--right-to-left` and
`--hide-gridlines` as independently optional flags, following
`update-protection`'s precedent of sending only what the caller passed.

### 3. `hideGridlines` ships in v1; the deprecated group-control fields never do

`--hide-gridlines` ships alongside the rest rather than deferring to a
follow-up issue: it is the same class of per-sheet display flag as
`--right-to-left`, rides the same request and mask, and costs one more
optional flag. `gridProperties`' deprecated `rowGroupControlAfter`/
`columnGroupControlAfter` stay out of scope and are not modelled on the
request type at all — a documented cut, the stance ADR-0082 §3 took for
two-axis banding, not a gap awaiting an issue.

### 4. The field mask names exactly what was populated

This is the first `updateSheetProperties` verb that may set *several*
independently-optional fields in one request — each existing user sets
exactly one, so "which fields does the mask name" has never been a question
before. The mask is built from the flags actually passed, naming exactly the
properties the body populates, so an omitted `--freeze-rows` leaves an
existing frozen-row count alone rather than resetting it to zero. That is
`update-banding`'s "merge a changed value onto what exists; unset flags
never clear something already set" rule (ADR-0082 §2) applied to a property
mask instead of a properties struct. Tab color is the deliberate exception,
and §5 is why.

### 5. `--clear-tab-color` — the family's first deliberate clear-via-mask

We will add `--clear-tab-color`, mutually exclusive with `--tab-color`. It
names `tabColorStyle` in the field mask while leaving the property *unset*
in the request body — the Sheets API's documented way to clear a field: the
mask says "this field is in scope", the empty body says "and its new value
is nothing". This is the first time this crate's structural-edit family uses
that behavior on purpose; every prior verb's mask names exactly the field it
populates, so a mask entry with no matching body value would until now have
been a bug. The verb's module doc records the inversion so a later reader
does not take it for one.

### 6. Tri-state booleans for `--right-to-left` and `--hide-gridlines`

Both take an explicit value — `--right-to-left <BOOL>`, modelled as
`Option<bool>` — rather than being valueless presence flags. An omitted flag
must mean "leave this property alone", which a presence flag cannot express:
it distinguishes only `true` from absent, collapsing "set it false" into
"don't touch it". This is the convention `format-cells --bold` (ADR-0078 §5)
and `update-protection --warning-only` already use, and it is what makes
§4's mask construction well-defined.

### 7. Freeze counts validated client-side against the snapshot already in hand

`--freeze-rows`/`--freeze-columns` must be non-negative and, when the
sheet's current row/column count is known, strictly less than it: Sheets
requires at least one unfrozen row and column and rejects a request that
would freeze the whole grid. Both the dry run and the real run already issue
the `spreadsheets.get` that resolves the sheet by title, so the
authoritative dimensions are in hand for free. This is `insert-rows`' `--at`
bound check exactly (ADR-0075 §6) — validate what the server would reject
anyway, from the server's own data, so a `--dry-run` can never promise a
change the real run then fails. Nothing here is inferred, so it is not the
client-side grammar guessing ADR-0073 §7 forbids.

### 8. `tabColorStyle` only, RGB only, and never read back

`--tab-color` takes `#RRGGBB` and populates `tabColorStyle`; the plain
`tabColor` field, which the Sheets v4 discovery document marks deprecated
in favor of it, is not modelled. The `themeColor` arm of `ColorStyle` gets
no flag surface, the hex syntax being the statement of the cut. Both are
the `format-cells` cut (ADR-0078 §5) that `add-banding`/`update-banding`
(ADR-0082 §2) already repeated verbatim.

The *current* tab color is deliberately never read back onto the
response-side `SheetProperties` type, so a `--dry-run` states what the color
becomes and never what it is now. The reason is structural, not incidental:
`ColorStyle` holds `f32` channels and so cannot derive `Eq`, while this
crate's response types — `SheetProperties`, `Sheet`, `Spreadsheet` — all
derive it today. A color field there would strip `Eq` from the whole chain
for a value nothing else reads.

### 9. One `drivemutation` record per verb, reusing `fields_changed`

`operation` becomes `sheets-update-sheet-properties`. The record reuses the
existing `fields_changed` context key on `DriveMutationOutcome` — the key
ADR-0078 §8 introduced for `format-cells`/`update-borders`, for exactly the
case of one request carrying several independently-toggleable effects — and
adds no new field. This verb is the first case since formatting to have that
shape, and the key already describes it.

## Consequences

- **No new OAuth grant and no new trust boundary.** Same as every prior
  Sheets ADR: the new request rides the scopes already covered.
- **`sheets-structure` covers one more capability.** An operator who
  granted it before this ADR shipped is not retroactively exposed to
  anything that destroys data or widens who may edit — the binding
  constraint on that variant holds — but is exposed to per-sheet view
  properties, which is within what granting "restructure this workbook"
  already implied, the argument ADR-0078/ADR-0081/ADR-0082 each made for
  their own additions.
- **`rename-sheet` stays a verb whose name is its whole effect**, and
  `hideGridlines` needs no follow-up issue — it ships here rather than being
  deferred as a scope question, closing the issue's own open point.
- **A multi-field mask pattern now exists to copy.** §4 and §5 settle, in
  one place, how a verb populating several optional properties builds its
  mask and how it clears a field on purpose — decisions the next multi-field
  `updateSheetProperties`/`updateSpreadsheetProperties` verb inherits rather
  than re-litigates.
- **The deprecated `rowGroupControlAfter`/`columnGroupControlAfter` remain
  unreachable.** A documented cut (§3), not a gap: a user who needs either
  must use the Sheets UI, the same stance every prior curated-surface ADR
  takes.
- **Tab color has no readback.** Neither `sheets info` nor a `--dry-run`
  can state a sheet's current tab color — only what it would become, or that
  it would be cleared. A deliberate trade (§8) to keep `Eq` on the response
  types; revisiting it means dropping that derive chain-wide.
- **Sync obligation.** `docs/drive.md`'s structural-verbs section and its
  `sheets-structure` policy-table row, `src/drive/write_gate.rs`'s
  `SheetsStructure` doc comment, `docs/log.md`'s operation list and
  `CHANGELOG.md` all need `update-sheet-properties` added — recorded the
  same way ADR-0081's and ADR-0082's Consequences do, except that here the
  implementing work lands alongside the ADR rather than under a later
  issue, so the sync is due in the same change.
