# ADR-0065: `gmail sync --extract-attachments`

## Status

✅ Accepted (2026-08-04)

Extends [ADR-0064](adr-0064.md) (`gmail sync`'s archive format), which
explicitly named attachment extraction to separate files as a deferred,
additive layer rather than something it decided. Filed as its own ADR for
the same reason ADR-0064 was filed separately from ADR-0063: a new
on-disk contract element and a new dependency choice are a substantial
decision, not a natural extension of an existing ADR's scope.

## Context

`gmail sync`'s manifest already records `attachment_count`/
`attachment_filenames` per message (#1467), computed by a deliberately
cheap heuristic (`extract_attachment_filenames` in
`src/gmail/raw_message.rs`) that scans for `Content-Disposition:
attachment` header lines without ever parsing MIME boundaries. Attachment
*bytes* stay inline inside the `.eml` — nothing writes them out as
separate files. ADR-0064's Consequences section named this out of scope
by design: "attachment extraction to separate files ... [is an] additive
layer a future issue can build on top of it without changing anything
decided here." PR #1485's scale-verification review, diffing the archive
against a real-world reference implementation, confirmed this as the one
remaining parity gap: citing a specific attachment as evidence requires
re-parsing the `.eml` by hand.

Writing attachment bytes to disk is a materially bigger lift than the
existing metadata heuristic: it needs real multipart boundary parsing and
Content-Transfer-Encoding decoding (base64, quoted-printable), neither of
which anything in the crate does today — the heuristic scanner's own
module doc is explicit that it is "not a MIME parser."

## Decision

Add an opt-in `--extract-attachments` flag to `omni-dev gmail sync`. When
set, each fetched message's `Content-Disposition: attachment` MIME parts
are additionally written to disk, alongside the unchanged `.eml`. Four
sub-decisions:

1. **Use the `mail-parser` crate (0.11, MIT/Apache-2.0) for real MIME
   parsing**, isolated to this one feature in the new
   `src/gmail/attachments.rs` module, rather than hand-rolling multipart
   boundary parsing and Content-Transfer-Encoding decoding. Correctness
   here (base64/quoted-printable decoding, RFC 2231 continuation
   parameters, nested multipart) has enough edge-case surface that a
   mature, purpose-built parser is a better trade than in-house code with
   no comparable test corpus behind it. The existing heuristic scanner in
   `src/gmail/raw_message.rs` is untouched — it is cheap specifically
   *because* it avoids a real MIME parse, and that trade-off still holds
   for computing manifest metadata on every sync, flag or not.

2. **Layout: `messages/<year>/<month>/<day>/<id>/attachments/<filename>`**
   — a sibling directory of `<id>.eml` within the existing date-sharded
   bucket ADR-0064 established, not a new archive-root `<id>/` scheme
   (the archive isn't id-sharded, and ADR-0064's own measurements are why:
   an id-prefix scheme distributes badly against real Gmail ids). `<id>.eml`
   (a file) and `<id>/` (a directory) are distinct filesystem entries, so
   they never collide.

3. **Filename handling: sanitise, then de-duplicate within one message.**
   Every filename goes through `crate::utils::path::attachment_filename`
   (already used by the Jira/Confluence attachment downloaders) for
   traversal-safety and an empty-name fallback. A second attachment in the
   same message that sanitises to an already-used name gets a `-N` suffix
   inserted before the extension. No cross-message de-dup is needed — each
   message has its own directory.

4. **The manifest's `attachment_count`/`attachment_filenames` fields do
   not change meaning.** They always come from the existing heuristic,
   regardless of the flag. `--extract-attachments` is purely additive
   file-writing; it does not touch the manifest contract ADR-0064
   established as deliberately minimal and stable. A consumer wanting the
   exact on-disk file list for a message globs its deterministic
   `attachments/` directory directly.

Extraction failure (an unparseable message) never fails the message
fetch — it simply yields no attachment files for that message, since the
`.eml` remains the lossless source of truth regardless and extraction is
a convenience projection over it, never a new contract.

## Consequences

- **No retroactive backfill, for free.** `gmail sync` only ever fetches
  messages missing on disk — ADR-0064's presence-on-disk idempotence
  mechanism — and this holds even under `--full`. Turning on
  `--extract-attachments` therefore only affects messages actually fetched
  in that run; it never backfills an already-archived message. No
  special-casing was needed to get this property; it falls out of the
  existing design. As filed, an operator who wanted attachments for
  already-archived mail had no choice but to delete the affected `.eml`
  files (or the whole archive) and re-run `--full --extract-attachments`
  — since addressed by the local-only `gmail extract-attachments`
  subcommand (#1510), which parses the `.eml` bytes already on disk in
  place, no re-fetch required. See `docs/gmail.md`'s Extract attachments
  section.
- **A second, real MIME parser now lives in the crate.** `mail-parser`
  resolves RFC 2231 continuation parameters and decodes
  Content-Transfer-Encoding correctly — strictly more capable than
  `raw_message.rs`'s heuristic — but the two are deliberately not unified.
  This means a message's `attachment_count` and the number of files
  actually written under `--extract-attachments` can, in rare cases
  (e.g. a filename split across RFC 2231 continuation parameters, or a
  disposition line that fools the line-oriented heuristic), disagree.
  This is accepted: unifying the two would touch manifest output on every
  sync, flagged or not, which is exactly the blast radius ADR-0064's
  "deliberately minimal" manifest contract was meant to avoid.
- **Extra disk usage and I/O is opt-in only.** Off by default; existing
  archives and existing `sync` invocations are byte-for-byte unaffected.
- **Sync obligation.** `docs/gmail.md`'s Sync section documents the flag,
  the layout, and the no-retroactive-backfill caveat. Keep it in sync with
  this ADR.

See [ADR-0064](adr-0064.md) for the archive format and reconciliation
contract this extends.
