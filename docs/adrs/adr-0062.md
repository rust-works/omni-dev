# ADR-0062: Drop the VS Code Rebase Confirmation Modal

## Status

✅ Accepted (2026-08-01)

Supersedes [ADR-0059](adr-0059.md) **in part**: on *whether* the extension's
"Rebase on main" action confirms before executing. Everything else ADR-0059
decided — the two-phase check/execute split (§1), conflicts left in place (§2),
`resolve_git_binary()` (§3), the tree cue (§4), and the daemon requirement (the
first half of §5) — is unchanged and still governs. The affected passages are
marked inline.

## Context

`confirmRebase` in [`rebaseCommand.ts`](../../editors/vscode/src/rebaseCommand.ts)
fired a modal (`{ modal: true }`) before every rewrite phase 1 found something
pending for, unconditionally — a single clean fast-forward and a batch containing
a conflict got the identical dialog. The doc comment above it was explicit that
this was deliberate: "**Always** shown, even for a single row: a rebase rewrites
branch history, and a batch is one gesture over N branches — the modal is the only
place the user sees the full set (ADR-0049 §1's rule, as applied by 'Add to Merge
Queue')."

Issue #1458 asked to reconsider that always-confirm policy, pointing out that it
diverges from the sibling **Close Worktree** command: `close`'s phase 1 returns
`risks: []` when nothing would be lost, and in that case the extension proceeds
with **no** dialog at all ([ADR-0049](adr-0049.md) §1) — the modal only appears
when there is something to lose. Rebase never got that fast path.

### Risk-gating rebase like `close` does not actually work

The issue offered risk-gating (mirroring `close`) as one option. It does not hold
up: `close`'s `risks` enumerate things a **reflog cannot get back** — modified or
untracked files about to be deleted, and commits reachable only from a detached
HEAD that removal will let get garbage-collected. Those are real, asymmetric
hazards: some targets are safe to delete with nothing lost, others are not, and the
`risks` array tells them apart.

A rebase has no equivalent split. Every branch a rebase touches is a named ref,
and starting a rebase is itself what writes the pre-rebase `HEAD` into the reflog
— `git` does that unconditionally, before the extension ever asks the user
anything. A "clean fast-forward, no conflicts" target and a "will hit conflicts
and get left mid-rebase" target are **equally** recoverable, just via different
reflog entries (`git reset --hard ORIG_HEAD`, or `git rebase --abort` while the
conflict is still in progress). There is no tier of "riskier" rebase outcome the
way `close` has a tier of "riskier" deletion — so a `close`-style gate would either
never fire (defeating the point) or fire on an arbitrary proxy (e.g. "has a
conflict") that isn't actually about what can be lost.

### What the modal was protecting against was already covered elsewhere

Once the risk-gating premise falls away, the remaining case for confirming at all
is thin:

- **The pre-rebase state is already in the reflog**, independent of any UI
  gesture ([ADR-0059](adr-0059.md)'s own Consequences already said as much: "Both
  are still recoverable with ordinary git"). The modal was never the thing making
  the operation safe — git's own bookkeeping is.
- **A rebase never reaches a remote.** [ADR-0061](adr-0061.md)'s `push` op is a
  separate, explicit action, and it keeps its own confirmation modal untouched by
  this ADR. A locally-rewritten branch a user did not mean to touch is invisible
  to anyone else until they deliberately push it — so the moment a mistake becomes
  hard to walk back is still gated, just one step later than before.
- **Phase 1 still runs unconditionally.** A daemon-down error, an unreachable
  remote, and "nothing to rebase" (already up to date, dirty, detached, mid-
  operation) all still short-circuit before anything is rewritten — those are not
  confirmations, they are correctness/precondition checks, and none of them
  change.

Given that, the honest choice is not a gate that can't distinguish anything, but
no gate at all.

## Decision

### 1. `confirmRebase` is deleted; phase 1 flows straight into phase 2

`rebaseOnMain` (`rebaseCommand.ts`) still runs the phase-1 check (fetch once per
repository, classify every selected worktree), still bails out with an error or a
"nothing to rebase" toast exactly as before, but no longer pauses for a modal in
between. The `withProgress` notification goes straight from "Checking…" to
"Rebasing N…". Phase 2 still **re-plans from scratch** before executing
([ADR-0059](adr-0059.md) §1) — nothing about the daemon's own safety story
changes, only the client-side pause that used to sit between the two phases.

### 2. The now-unused reporting helpers are deleted, not left dormant

`confirmDetail` and `confirmTitle` (`rebaseReport.ts`) existed only to render the
modal's title and body. With no caller left, they are deleted outright along with
their unit tests in `rebaseReport.test.ts`, rather than kept as dead exports.
`pendingOutcomes`, `skippedOutcomes`, `nothingToRebaseMessage`, and `summarize`
are unaffected — they back the pre-flight short-circuit and the post-execute
toast, both of which are unchanged.

### 3. `push` keeps its confirmation; this ADR does not touch it

`pushCommand.ts`'s own `confirmDetail`/`confirmTitle` (`pushReport.ts`) are a
different, unrelated pair despite the similar names, and are untouched. Publishing
a rewrite to a remote is qualitatively different from writing it locally — once
pushed (especially a force-push under `--force-with-lease`), the reflog on the
user's own machine stops being the relevant recovery mechanism for anyone who has
already fetched the old tip. That is precisely the boundary ADR-0061 §1 already
drew; this ADR leaves it in place.

## Consequences

- **"Rebase on main" is now one gesture with no pause**, for a single row and for
  a batch alike. This is a deliberate loss of the one thing the always-confirm
  policy had over `close`'s risk gate: a moment to review the full target list
  before anything happens. The mitigation is that the operation is local and
  reflog-recoverable regardless, and the post-execute toast still names every
  worktree left mid-rebase.
- **The ADR-0049 §1 precedent is now explicitly not universal.** `close` and
  `merge-queue` still confirm because they enumerate genuine asymmetric risk (data
  loss, or an eligibility check that can go stale); `rebase` does not, because
  every one of its outcomes is equally reflog-recoverable. Future actions should
  ask "does this have a `close`-shaped risk tier, or a `rebase`-shaped uniform
  one?" rather than defaulting to a modal because a sibling action has one.
- **No change to the daemon, the wire protocol, or the tree cue.** This is a
  client-side UI change only — the `rebase` op's two-phase shape, `keep_conflicts`
  behaviour, and the `operation`/`rebasing` tree cues from
  [ADR-0059](adr-0059.md) are all untouched.
- [ADR-0059](adr-0059.md) keeps its status; only its restatement of the modal step
  in §5's summary and the "confirmation can show true behind-counts" bullet are
  superseded — everything else it decided about hosting rebase in the daemon is
  still the live design.

This amends [ADR-0059](adr-0059.md); leaves [ADR-0049](adr-0049.md)'s `close`
gate and [ADR-0061](adr-0061.md)'s `push` gate untouched. See
[docs/worktrees-service.md](../worktrees-service.md) for the operator guide.
