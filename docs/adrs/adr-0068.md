# ADR-0068: Concurrent Multi-Account Gmail Sync via `gmail-sync.yaml` and a Shared Fetch Semaphore

## Status

✅ Accepted (2026-08-06)

Extends [ADR-0064](adr-0064.md) (the `gmail sync` archive/engine contract)
and [ADR-0066](adr-0066.md) (named-account resolution) without amending
either — both are consumed unchanged. Filed as its own ADR rather than a
third decision folded into either, per the same reasoning ADR-0064 itself
gave for not becoming a fourth decision on ADR-0063: a new recognised
config file, a new CLI subcommand, and a concurrency primitive shared
across otherwise-independent sync runs is a substantial new decision, not a
natural extension of either existing ADR's scope.

## Context

`gmail sync` archives one mailbox per invocation. Syncing several accounts
today means an external wrapper script looping over `omni-dev gmail sync
--output-dir ... --account ...` once per account, serially. Two problems
with that shape:

1. **Serial for no reason.** Each account's sync — a `messages.list`
   pagination pass plus a throttled `messages.get` fetch fan-out, both
   quota-paced by a per-run `TokenBucket`
   (`src/cli/gmail/sync/engine.rs:118`) — runs to completion before the next
   starts. Wall-clock is the sum of every account's sync time even though
   each account has its own independent Gmail API quota
   (`GMAIL_QUOTA_UNITS_PER_SECOND = 250`, `src/gmail/messages_api.rs:48`,
   documented as per-**user**, not global) and nothing in the engine
   requires serialization: `TokenBucket` is a local stack variable created
   fresh inside `run_sync_with_progress`, borrowed (not `Arc`'d) through the
   fetch fan-out, never shared across `GmailClient` instances.
2. **Config lives in a bash loop.** Adding, removing, or redirecting a
   mailbox means editing a script rather than a config file, with no
   relationship to the project's own `.omni-dev/` configuration every other
   cross-cutting omni-dev feature (`scopes.yaml`, `commit-rules.yaml`, …)
   already uses.

ADR-0066 anticipated this directly, in its own Consequences section:
*"Cross-account fan-out (one command querying multiple accounts at once) is
deferred — nothing in this shape precludes it later, since each account
already resolves to an independent `GmailClient`."* That independence is
exactly what makes concurrent multi-account sync safe to add without
touching either the account-resolution or archive/engine contracts: this
ADR is additive on top of both.

The one thing standing between "each account is independent" and "safe to
run concurrently in one process" is credential resolution. `GmailCommand::
execute`'s existing account-selection path (`src/cli/gmail.rs:76-78`)
mutates the process-global `OMNI_DEV_GMAIL_ACCOUNT` env var once per
invocation — fine for one CLI process resolving one account, unsafe for N
concurrent tasks racing on the same env var within one process.
`helpers::create_client_for(Some(&name))` (`src/cli/gmail/helpers.rs:18-20`,
shipped for #1500 alongside ADR-0066) already exists as the non-env-mutating
alternative: it resolves a named account's credentials and builds a
`GmailClient` directly from an explicit parameter, with no process
environment involved. It was built for per-command `--account` selection,
but nothing about it is single-task-only — it is exactly the building block
concurrent multi-account sync needs.

## Decision

### 1. A new recognised config file: `.omni-dev/gmail-sync.yaml`

Located via the existing, filename-generic
`discovery::resolve_context_dir_with_source`/`resolve_config_file`
(`src/claude/context/discovery.rs`) — the same walk-up-to-repo-root
discovery, `local/` shadow tier, and `--context-dir`/`OMNI_DEV_CONFIG_DIR`
override chain already used for `scopes.yaml`/`commit-rules.yaml`. No
changes to discovery.rs itself: recognising a new filename is purely a new
caller, not new discovery machinery.

```yaml
concurrency: 20
accounts:
  - account: jky.greens
    output_dir: emails/jky.greens/
  - account: newhoggy
    output_dir: emails/newhoggy/
    query: "-in:spam"
    extract_attachments: true
```

`account` is a lookup key into `~/.omni-dev/settings.json`'s
`gmail.accounts` map (`src/utils/settings.rs:167-178`, ADR-0066) — this file
says *which* accounts to sync and *where*, never a second credential store.
`output_dir` resolves relative to the directory containing the discovered
`.omni-dev/` (the project root), matching the wrapper script's
`$repo_root/emails/$x/` convention it replaces.

Unlike `scopes.yaml`/`commit-rules.yaml` (which fall back to a safe default
on a missing or malformed file, `discovery.rs`'s `load_commit_rules`/
`load_project_scopes_only`), `gmail-sync.yaml` is loaded **strictly**: a
missing file, an empty `accounts` list, an unparseable file, or an
`account` name absent from `gmail.accounts` are all hard errors before any
network call is made — a config file this central to what `sync-all` does
has no safe silent default; a silently-empty account list would look like a
successful no-op.

### 2. Per-account client resolution goes through `create_client_for`, never the env var

`sync-all` iterates the configured accounts and calls
`helpers::create_client_for(Some(&entry.account))` once per account inside
its own concurrent task. `GmailCommand`'s existing `--account` flag is
rejected outright when paired with `sync-all` (it has no meaning against a
multi-account YAML list, and silently ignoring it would be more confusing
than refusing it) — `sync-all` never touches `OMNI_DEV_GMAIL_ACCOUNT` at
all, so nothing about this feature depends on, or risks, the env-var path
being safe for concurrent use.

### 3. Two-level concurrency: an unchanged per-account cap, plus a new shared cap underneath it

Each account's fetch fan-out already gates concurrency with
`buffer_unordered`/`FuturesUnordered` capped at `--concurrency`
(`engine.rs`'s `fetch_and_archive_messages`/`_streaming`) — a purely local,
per-invocation cap, unrelated to quota compliance (the `TokenBucket` is
that). To bound total in-flight fetch requests *across* accounts without
touching quota pacing, `SyncOptions` (`engine.rs:54-61`) gains:

```rust
pub(crate) shared_pool: Option<Arc<tokio::sync::Semaphore>>,
```

`None` for every existing single-account caller (`gmail sync`'s own
`SyncOptions` construction) — zero migration, byte-identical behavior.
`sync-all` builds one `Arc::new(Semaphore::new(effective_concurrency))`
(CLI `--concurrency` → YAML `concurrency` → the existing
`DEFAULT_SYNC_CONCURRENCY` default), clones it into every account's
`SyncOptions`, and each fetch task acquires a permit (`pool.acquire()`)
immediately before `fetch_and_write_one`, released on completion. This
sits *underneath* each account's own `--concurrency`
clamp, not instead of it: an account can have up to its own local
concurrency limit of fetches "in flight" (queued on the fan-out), but only
`effective_concurrency` of them across *all* accounts actually hold a
permit and do work at once — so one starved or slow-quota account can never
claim the whole shared pool for itself. Each account keeps its own
independent `TokenBucket`, entirely unaffected — the shared semaphore is a
purely local resource cap, orthogonal to per-account quota pacing, which is
what makes it safe to share across accounts whose Gmail-side quotas are
themselves independent.

`sync-all` drives the per-account tasks (`tokio::task::spawn`, one per
account, gated by the shared semaphore inside each) via
`FuturesUnordered<JoinHandle<_>>` rather than a `join_all` barrier, so a
per-account summary line prints as each account finishes rather than only
once every account has completed.

### 4. No live multi-account progress bars in v1

`SyncProgressBars::new()` (`src/cli/gmail/sync/progress.rs:41-57`)
constructs its own `indicatif::MultiProgress` per call. Running one per
account concurrently would mean N independent `MultiProgress` instances
fighting over one stderr. `sync-all` calls `engine::run_sync` (not
`run_sync_with_progress`) for every account and instead prints one summary
line per account as it finishes, reusing `sync.rs`'s existing
`format_summary_line`, prefixed with the account name, plus a trailing
combined-total line once every account has finished. A shared-
`MultiProgress` design (one bar pair per account, all registered on one
instance) is deferred to a follow-up rather than blocking this feature —
nothing here forecloses it, since `run_sync_with_progress`'s channel-based
signature is untouched.

### 5. Failure handling mirrors `gmail sync`'s own contract, aggregated across accounts

Each account's `SyncReport` (or task-level error — a credential failure,
`guard_output_dir` rejection, etc.) is collected and tagged with the
account name in both the text summary and any structured (`-o json`/`yaml`)
output. The process exits non-zero if **any** account either failed as a
task or returned a non-empty `report.errors` — one account's failure is
never silently swallowed because others succeeded, the same
compute-render-decide-last contract `gmail sync` already follows
(ADR-0064, Decision 4).

## Consequences

- **No changes to the archive format, watermark contract, or account
  resolution precedence.** This ADR is purely additive: it reuses
  `engine::run_sync`, `SyncReport`, and `create_client_for` exactly as
  ADR-0064 and ADR-0066 defined them. A `sync-all` run and N sequential
  `sync` runs against the same accounts produce byte-identical archives.
- **A new, narrow concurrency primitive.** `SyncOptions.shared_pool` is the
  only new cross-cutting mechanism this ADR introduces, and it is `None`
  by default — `gmail sync`'s behavior is unchanged and covered by the
  existing test suite without modification.
- **`--account` and `sync-all` are mutually exclusive**, enforced as a hard
  error rather than silently ignored — a deliberate small surface
  restriction to avoid a confusing no-op.
- **Deferred, not solved here:** a shared `MultiProgress` live-rendering
  layer for concurrent accounts (tracked as a follow-up); per-account
  `--concurrency` overrides in the YAML (the local per-account cap stays at
  the existing default in v1 — only the shared pool is configurable).
- **Sync obligation.** `docs/gmail.md`'s Sync and Multiple-accounts
  sections, and `docs/omni-dev-directory.md`'s recognised-files list, must
  describe `gmail-sync.yaml` and `sync-all`. Keep them in sync when this
  ADR's config shape or concurrency model changes.

See [ADR-0064](adr-0064.md) for the archive/engine contract this reuses
unchanged, and [ADR-0066](adr-0066.md) for the named-account resolution
`create_client_for` performs per account.
