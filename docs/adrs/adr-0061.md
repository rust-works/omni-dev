# ADR-0061: Daemon-Hosted Force-Push With a Lease

## Status

✅ Accepted (2026-07-30)

Extends [ADR-0059](adr-0059.md) (the `rebase` op this completes) and
**inverts** [ADR-0060](adr-0060.md) for one specific case — see §3. Neither is
superseded: both keep their status and everything else they decided still governs.

## Context

[ADR-0059](adr-0059.md) gave the worktrees tree view a batch **rebase**, and
[ADR-0060](adr-0060.md) widened it to every worktree of a repository. A rebase
rewrites history, so every already-published branch it touches is now diverged
from its upstream and a plain `git push` is rejected.

The batch rebase is therefore only half a workflow. The user rebases N worktrees
with one gesture, then opens a terminal in each one and force-pushes by hand. The
view *displays* the divergence it just created — `↑ahead ↓behind` on every row —
and offers no way to resolve it. There is no push action of any kind in the tree
today, on worktree rows or repo rows (#1443).

The obvious shape is "the rebase op, one verb over". Most of it is: two phases,
one batched op, re-plan before acting, a transient tree cue, an engine shared with
a local CLI. But a force-push is not a rebase, and the two places it differs are
the reason this needs an ADR rather than a paragraph in ADR-0059.

### This is the first op to *write* to a remote with the user's git credentials

`merge-queue` ([ADR-0056](adr-0056.md)) mutates the remote, but through `gh` and
its own token. `rebase` ([ADR-0059](adr-0059.md)) uses the user's ambient
`ssh-agent` credentials, but only to **fetch**. A credentialed,
history-publishing, non-fast-forward remote write is a genuine step beyond both:
it is the first daemon op whose failure mode is *other people losing work*.

## Decision

Add a two-phase **`push` op** to the `worktrees` daemon service, a **Push
(force-with-lease)** row action on both worktree and repo rows, and
`omni-dev worktrees push` for parity.

### 1. Two-phase, modelled on `rebase`

- **Phase 1** (`check: true`, or any un-`confirmed` request) runs
  `worktree_push::plan`, classifying every selected worktree against its
  upstream: `UpToDate`, `WouldFastForward` (ahead only — a plain push, **no force
  flag**), `WouldForce` (diverged), `WouldCreate` (no upstream — publishes with
  `--set-upstream`), or a skip. `WouldCreate` is included deliberately: a batch
  action that silently refused every unpublished branch would be worse than one
  that publishes it, and `--force-with-lease` is a no-op against a ref that does
  not exist yet.
- **Phase 2** (`confirmed: true`) **re-plans from scratch** and executes, as
  `close`, `merge-queue` and `rebase` all re-validate. A branch that moved
  between the phases is re-classified, not pushed on stale information.

Both phases reply in one shape (`{ worktrees }`); only which `PushResult`
variants appear differs. Phase 2 is serialized by a `push_lock` mirroring
`rebase_lock` — a successful push writes `refs/remotes/<remote>/<branch>` into the
ref store every linked worktree shares. It is a **separate** lock: a rebase and a
push touch different refs, and a push should not queue behind an unrelated
repository's rebase.

A **dirty worktree is not a skip**, unlike in the rebase engine. A push publishes
commits, not the working tree.

### 2. Always `--force-with-lease --force-if-includes`, never `--force`

This is the load-bearing detail, and it is not the obvious one.

Bare `--force-with-lease` leases against the *local* remote-tracking ref. Any
background fetch that refreshes `refs/remotes/<remote>/<branch>` **silently renews
the lease**, so a teammate's commit the user has never seen becomes overwritable.
`git-push(1)` (verified against git 2.50.1):

> Alternatively, specifying `--force-if-includes` as an ancillary option along
> with `--force-with-lease[=<refname>]` (i.e., without saying what exact commit
> the ref on the remote side must be pointing at […]) at the time of "push" will
> verify if updates from the remote-tracking refs **that may have been implicitly
> updated in the background** are integrated locally before allowing a forced
> update.

> If the option is passed without specifying `--force-with-lease`, or specified
> along with `--force-with-lease=<refname>:<expect>`, it is a "no-op".

So `--force-if-includes` is **not** implied — it must be passed explicitly, and
only the valueless / refname-only form of `--force-with-lease` activates it. The
engine therefore never emits the `=<refname>:<expect>` form, and a unit test pins
that.

The hazard is *elevated* in exactly the environment this ships into: the built-in
VS Code Git extension's `git.autofetch` is precisely such a background fetch, and
it updates every remote-tracking ref. Worth recording that our own `rebase` op is
**not** a source of it — `worktree_rebase::fetch_once` runs
`git fetch <remote> <branch>`, refspec-limited to the onto branch, so it never
refreshes a feature branch's lease. Users who already set
`push.useForceIfIncludes = true` are unaffected by passing it explicitly.

**`--force` is not exposed** — no engine option, no CLI flag, no modal escape
hatch. `PushOptions` has no field for it; `omni-dev worktrees push --force` is a
parse error; the wire payload has no force field for a socket client to set. A
rejected lease is the feature working: it is reported, distinguished from every
other rejection, and names `git fetch` plus a rebase as the fix.

### 3. Planning does not fetch

The rebase engine fetches in phase 1, because the fetch is what pins the snapshot
every worktree is measured against. The push engine deliberately does not, and
the reason is rule 2: a fetch refreshes the remote-tracking ref, which is the very
lease renewal that makes a bare `--force-with-lease` untrustworthy.

Classifying against the *unfetched* local ref means the plan the user confirms and
the lease `git` enforces are measured against the same tip, by construction. It
also means phase 1 costs zero network round-trips — which is why `plan` takes no
`git` binary at all, and why the reply has no `fetches` array.

The cost is honest and bounded: a teammate's unseen push reads as
`WouldFastForward` and is then refused by the remote. That is reported, never
forced.

### 4. The gate is the *branch*, not the worktree's structural role

[ADR-0060](adr-0060.md) dropped rebase's `is_main` gate: a main working tree is
rebased like any other target, because a rebase rewrites only local history and is
`git reflog`-recoverable, exactly as recoverable for the main tree as for a linked
one.

A force-push must **invert** that conclusion, and the asymmetry is the whole
point: a rebase is local, a force-push is *published*. So the engine **refuses to
force-push the repository's remote default branch**, whichever worktree it happens
to be checked out in.

Note precisely what changes and what does not:

- The gate is on the **branch name**, compared against the remote's default
  (`RemoteInfo::detect_main_branch_local`) on the *remote-side* name — never on
  `is_main`. A linked worktree that has `main` checked out is refused; a main
  working tree on a feature branch is not.
- It applies **only** to `WouldForce`. `WouldFastForward` onto the default branch
  is an ordinary push that destroys nothing and stays allowed, as does
  `WouldCreate`.
- ADR-0060 is not superseded. Its reasoning about rebase remains correct; this
  ADR adds a *different* operation with a *different* hazard, which is exactly the
  distinction ADR-0060 drew when it left `close`'s `is_main` guard untouched.

The refusal lives in the **engine**, so it holds for the CLI, the daemon op and
any future caller — the UI gating is not the only guard, matching ADR-0049's
posture for `close`.

### 5. The tree cue is transient-only

A `pushing` set in the registry mirrors `rebasing`: keyed by canonicalized
worktree path, marked and cleared by the op, bumping the change-notify **only on a
real change** (an unconditional bump defeats the server's snapshot diff and
re-pushes to every window on every tick).

Unlike the rebase cue there is **no durable half**. A rebase can leave
`.git/rebase-merge` on disk for `operation` to rediscover after a restart; a push
writes no state at all. The `pushing` flag is therefore the whole cue, and
`clear_pushing` running on *every* exit — including a panicked task — is load
bearing rather than tidy: nothing else could ever correct a leftover mark.

What makes a **completed** push visible is `upstream_sha` moving on the snapshot.
That field already rides the stream for exactly this reason (#1344), and the
extension re-fetches ahead/behind on every `getChildren` with no client-side
cache, so the counts settle on the resulting refresh with no extra invalidation.

Rendered as a **row icon** (`$(sync~spin)`) plus description text, not a file
decoration — a `FileDecoration.badge` holds two characters and both are claimed by
the PR-check verdict and the Claude-session cue (ADR-0059 §4).

### 6. Repo rows are expanded client-side

The action is offered on repo rows as well as worktree rows, since "publish
everything I just rebased in this repo" is the motivating gesture. `tree.ts`'s
existing `worktreeTargets` silently drops a repo node, so a new
`expandToWorktrees` expands a repo to its worktrees and dedupes against
explicitly-selected rows.

No new op and no daemon change: a repo node already carries its full `worktrees`
array on the snapshot, so this is a local read. Migrating `rebaseOnMain` /
`addToMergeQueue` onto the same helper is a deliberate follow-up, not part of this
change.

### 7. Confirm-by-default, and the CLI stays local

The modal is **always** shown, even for a single row (ADR-0049 §1), and lists each
branch with its classification so force and fast-forward are visually distinct —
forced entries first, because they are the ones with a consequence for other
people. The action button reads **Force Push** whenever the batch contains one, so
a rewrite can never be confirmed by a button that says merely "Push".

`omni-dev worktrees push` keeps its own local engine, like `worktrees rebase` and
for the same reasons (ADR-0059 §5): a batch push works with no daemon running, and
`--all` stays out of the wire protocol. It confirms by default
([ADR-0027](adr-0027.md)), with `--dry-run` to preview and `-y` to skip.

## Consequences

- **The daemon now publishes rewritten history using the user's ambient git
  credentials.** The largest escalation in this service's threat model to date. It
  remains same-user-bounded behind the `0600` socket, publishes only branches the
  client names, re-validates on execute, and reads or persists no secret. The
  mitigation that actually matters is not ours: the lease is enforced by `git`, so
  the daemon **cannot** overwrite a remote tip it has not seen, however wrong the
  client's request is.
- **A refused lease is a normal, expected outcome**, not an error condition to
  design away. It is surfaced distinctly at every layer — `stale` on the wire, its
  own toast sentence, its own CLI row text — always naming `git fetch` and a
  rebase as the fix. The one thing no layer offers is a way to push harder.
- **The default branch is protected by name, not by role**, which is a rule the UI
  cannot express and so must live in the engine. A user who genuinely needs to
  force-push `main` uses `git` directly; that is the correct amount of friction.
- **Not fetching is a real trade-off**, made deliberately. Classifications can be
  stale in the user's favour (a `WouldFastForward` that the remote then rejects),
  and the alternative — fetch first — would have renewed the lease on every run
  and left `--force-if-includes` as the only remaining guard.
- **Pushes stay sequential**, within a batch and across requests. Parallel push
  remains a follow-up, as it does for rebase.
- **Two engines now share `src/git/worktree_batch.rs`** (selection, worktree
  enumeration, HEAD reading, the `git` subprocess seam). Extracted rather than
  duplicated because the subprocess seam encodes a non-obvious environment-snapshot
  rule (#1022) that must not drift between them.
