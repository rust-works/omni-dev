# ADR-0090: Fetch Secrets On Demand with `<NAME>_COMMAND`

## Status

✅ Accepted (2026-09-30, #2011). Extends [ADR-0089](adr-0089.md).

## Context

[ADR-0089](adr-0089.md) gave every registered secret a `<NAME>_FILE` companion.
That keeps a secret out of `env` listings, `/proc/<pid>/environ`, shell history,
child processes and settings.json, which stops *accidental* leaks. It does not
stop a process running as the same user from reading the secret on purpose: the
file is plaintext on disk, and its path is in the environment or in
settings.json. That matters here because the workflow runs many concurrent agent
sessions as the user (Claude Code, Codex, pi), and the `claude-cli` backend's
`--claude-cli-allow-tools` escape hatch runs a tool-capable nested session driven
by untrusted prompt content. An injected payload can `cat` a secret file as easily
as it can read an environment variable.

Two designs were considered.

- **A: `<NAME>_COMMAND`**, a credential helper: the value names a command whose
  standard output is the secret, as with git credential helpers and AWS
  `credential_process`. It is store-agnostic (1Password `op read`, macOS
  `security find-generic-password -w`, `pass`, Vault, `secret-tool`) and can
  require biometric approval per use.
- **B: the native OS keychain**, read directly (for example with the `keyring`
  crate) under a fixed service name. It is simpler for users. It also adds a
  platform-specific dependency, and on macOS the keychain ACL is per binary while
  omni-dev installs unsigned, so every upgrade may re-prompt (the Accessibility
  grant of [ADR-0058](adr-0058.md) has the same problem). A headless Linux daemon
  has no Secret Service session at all.

B can be written as A (`security find-generic-password …`), and A cannot be
written as B, so A is the more general of the two.

Six questions shaped A:

- **What it protects.** A same-user process can read settings.json, see the
  command, and run it. Whether that succeeds depends on the store. An item made
  with `security add-generic-password` trusts `/usr/bin/security` by default, so
  any same-user process can read it; only an item whose ACL prompts on each
  access (`-T ""`), or 1Password's Touch ID approval, is a per-use gate. So
  `_COMMAND` reliably removes the secret from disk, the environment and
  settings.json, and raises the bar from "read a file" to "cause a prompt the
  user can see and refuse" only when the store prompts.
- **Shell or argv.** `sh -c` makes every settings.json writer a shell author and
  adds quoting hazards; splitting into argv has no such surface.
- **Where a secret can be resolved.** The daemon is started by launchd or
  systemd with a minimal environment, so a rule allowing `_COMMAND` only in the
  process environment would exclude the long-lived Snowflake and browser-bridge
  services. `settings.json` is home-only (`0600` in a `0700` directory, no
  repo-local file), so a cloned repository cannot plant a command there.
- **Repeated resolution.** One CLI invocation resolves a secret more than once
  (`preflight`, then the client build), and the MCP server rebuilds a client per
  tool call. Without a cache each would prompt.
- **What a login does.** ADR-0089 makes a login remove a `_FILE` companion and
  write the plaintext value. Doing that to a `_COMMAND` would silently replace a
  user's keychain-backed configuration with a plaintext one.
- **Async callers.** `secret_var` is synchronous and `create_default_claude_client`
  is `async`; a helper may block for as long as a human takes to approve a prompt.

## Decision

We will build A, and not B. We will read `<NAME>_COMMAND` through the same
resolver, `crate::utils::secret_env`, so every registered secret accepts it and no
call site changes.

1. **Sources and conflicts.** A secret is `NAME`, `NAME_FILE` or `NAME_COMMAND`.
   `EnvSource::var_pair` becomes `var_triple`, and the settings layer resolves the
   triple from one layer (`Settings::resolve_triple_with`). Two or more members
   set in one layer is an error naming each one set
   (`SecretEnvError::CommandConflict`; a bare `NAME`/`NAME_FILE` clash keeps
   `Conflict`). Between layers the normal precedence applies, so a
   `NAME_COMMAND` in the process environment overrides a `NAME` in settings.json.
   Empty values count as unset. Aliases keep their order, and a conflict is only
   ever within one name's triple. `EXEMPT_SECRET_ENV_VARS` entries stay exempt, so
   there is no `GMAIL_CLIENT_SECRET_COMMAND`.
2. **No shell.** The value is split into argv with `shlex` and run directly. An
   unbalanced quote or an empty command is an error. A pipeline is written
   `sh -c '…'` explicitly. `shlex` follows POSIX quoting, so a Windows path with
   backslashes needs quoting.
3. **Execution.** Standard input is `/dev/null`. Standard output is captured and
   capped at 64 KiB. Standard error is captured, not passed through. With no
   terminal attached (the daemon, the MCP server, a pipe) the child runs in its
   own process group, and the timeout (60 s by default, because a biometric prompt
   needs a human; `OMNI_DEV_SECRET_COMMAND_TIMEOUT_SECS`) kills the whole group.
   With a terminal it stays in the foreground group, since a background group is
   stopped by `SIGTTIN` when a helper prompts on `/dev/tty` (`pass`, `gpg`'s curses
   pinentry), and only the child is killed. The child inherits the environment minus every registered
   secret and its `_FILE` and `_COMMAND` companion (and
   `SNOWFLAKE_PRIVATE_KEY_PATH`), so a helper never receives sibling secrets. A
   bare program name resolves through `PATH`; the daemon's `PATH` is minimal, so
   the "not found" error advises an absolute path.
4. **Result rules.** A non-zero exit is an error. Exit 0 with output that is empty
   after trimming, or not UTF-8, is an error, as for `_FILE`. Exactly one trailing
   `\n` or `\r\n` is trimmed.
5. **Errors and logs never contain the secret or the arguments.** Errors name the
   variable, the program (`argv[0]`) and the exit code or signal. Arguments are
   omitted because they can embed a token (`--password=…`). On failure only, the
   first 512 bytes of standard error are appended, with control characters
   escaped, because it is the only diagnostic ("not signed in"). On success it is
   discarded. `tracing` logs the variable and the program at debug level.
6. **Caching.** A process-wide cache keyed by the command string, for 300 s by
   default (`OMNI_DEV_SECRET_COMMAND_TTL_SECS`; `0` disables it). Concurrent
   callers of one command share a single run and so a single prompt. Only
   successes are cached. The TTL also bounds how long a rotated secret can be
   stale in a long-lived process. The Snowflake configuration and the bridge token
   are read once at daemon start, so the daemon prompts once at start-up.
7. **Presence checks never run it.** `secret_var_is_set`, and so `auth status`,
   counts a `NAME_COMMAND` as configured without running it.
8. **Blocking.** The resolver stays synchronous. On a multi-thread tokio runtime
   it wraps the wait in `block_in_place`; on a current-thread runtime it blocks.
9. **Writers.** `Settings::upsert_env_vars_in` refuses, before writing anything,
   when the target map holds a non-empty `_COMMAND` for a registered secret it
   was asked to write, and says so and how to proceed. This departs from
   ADR-0089 point 8, which replaces a `_FILE`, because the command names a store
   the user chose to keep the secret out of settings.json. Interactive logins that
   would spend a browser flow first (`gmail auth login`, `drive auth login`) call
   `Settings::ensure_secrets_replaceable` before it, so a token is not lost; it
   also refuses a `_COMMAND` exported in the process environment, which would
   shadow the saved value.
   `remove_env_vars_in`, used by `auth logout`, removes all three members.
10. **`claude-cli` scrubbing covers `_COMMAND`.** When the tool escape hatch is on,
    `<NAME>_COMMAND` is scrubbed whenever `NAME` is a secret, including the
    `ANTHROPIC_*` names whose values are kept, and
    `OMNI_DEV_CLAUDE_CLI_KEEP_ENV` still overrides it. This is hygiene, not a
    boundary: the same command is still in settings.json, which the nested
    session can read.
11. **Grep guards.** The registry and the two existing read guards are unchanged.
    The collision guard also checks the `_COMMAND` companions, and a new guard
    fails if any file other than the resolver, the settings writers and the scrub
    names a `_COMMAND` companion, so no call site can run a helper itself and skip
    the timeout, the cap or the cache.
12. **Deferred.** Named-account `<field>_command` for Drive and Gmail
    (`accounts.<name>`): a refresh token is rotated on login, so a command-backed
    one needs its own write-back story. An `auth login --store keychain`
    convenience that writes to the OS store and sets `_COMMAND`. **B** stays
    unbuilt: we will revisit it if the release binary is signed and notarized, which
    removes the per-upgrade prompt.

## Consequences

- **Positive.**
  - Every registered secret can be fetched on demand from a store that keeps it
    off disk, without a call-site change.
  - With a store that prompts per use (1Password with Touch ID, a keychain item
    with `-T ""`), a prompt-injected same-user process must cause a prompt the user
    can see and refuse.
  - The native keychain (B) is available today as a recipe, without a dependency.
  - One implementation, one set of tests, and guards that stop a call site from
    bypassing it.
- **Negative.**
  - `_COMMAND` does not defend against a same-user process when the store does not
    prompt: it can read settings.json and run the command. The operator guide
    shows a prompting recipe first and says which recipes only keep the secret off
    disk.
  - A `_COMMAND` in settings.json executes on every command that needs the secret.
    Anyone who can write settings.json already runs as the user, but the file is
    now also a place that runs code.
  - A login for a command-fetched secret is refused instead of completing, and the
    user must store the new value themselves.
  - A rotated secret can be stale for up to the TTL in a long-lived process, and
    nothing flushes the cache when a request is rejected.
  - A failing helper's standard error is shown, so a helper that echoes its
    arguments there shows them.
  - `drive auth login` also writes the client secret, so a command-fetched
    `DRIVE_CLIENT_SECRET` blocks it until the command is removed.
  - The resolver can block for up to the timeout on the calling thread.
- **Neutral.**
  - `NAME_FILE` behaviour and the file rules of ADR-0089 are unchanged.
  - Windows works the same way except that only the child, not a process group, is
    killed on a timeout, and `shlex`'s POSIX quoting means a Windows path goes in
    single quotes.
  - The approval window of `op` (per command or per terminal session) is the
    store's, not omni-dev's, and is documented as such.
