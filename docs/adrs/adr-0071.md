# ADR-0071: Folder-Scoped Write Permissions for the Drive Integration

## Status

✅ Accepted (2026-08-25)

**Extends [ADR-0069](adr-0069.md) and [ADR-0070](adr-0070.md), reverses
neither.** ADR-0069 shipped Drive read-only; ADR-0070 added the
integration's first write capability — `drive rename`/`drive move` — under
an additive `drive.metadata` scope, metadata-only by design (no file-content
access). This ADR is purely additive over both: it adds real content
mutation (`drive create`/`drive upload`/`drive edit`) and a second,
independent, local safety gate to bound it, but changes nothing about how
`rename`/`move`/`search`/`read`/`dedupe` already behave.

Landed under this ADR so far (issue #1574, Phases 1–2): the pure
folder-permission resolution engine (`src/drive/write_gate.rs`), the
ancestor-chain fetcher (`src/drive/folder_ancestry.rs`), the
`write_permissions` settings schema, the `DriveScope`→`DriveGrantedScopes`
capability-set migration with `--write-file`/`--write-full` login flags, and
the read-only `drive permissions show/lookup-folder/check` diagnostics.
`drive create`/`upload`/`edit` themselves (Phase 3) are specified here and
land in the commits immediately following this ADR's acceptance, per this
issue's own stated sequencing: the ADR is written and accepted
before/alongside the mutating phase, not after.

## Context

Nothing in the Drive surface before this issue touches file *content* —
`drive.metadata` (the only write scope granted by ADR-0070) technically
cannot: Google's own scope definition restricts `files.update` under it to
the `name`/`parents` fields. Creating a file, pushing local content into
Drive, or changing an existing file's content needs a materially broader
OAuth grant than anything this integration has requested before.

That broader grant is also why this issue needs its own local safety layer.
Google's OAuth scopes are all-or-nothing across a user's *entire* Drive —
there is no Google-side way to express "this credential may only write
inside folder X." The folder-scoped permission gate this ADR specifies is
`omni-dev`'s own policy layer, filling exactly that gap, the same way
ADR-0070's visibility-diff gate exists because Google's `move` API itself
never warns that a move changed who can see a file.

Two Google OAuth scopes are relevant, and neither alone covers everything
asked for:

- `drive.file` — per-file access, restricted by Google to files this app
  itself created via this scope (a Drive file picker, the other route to
  `drive.file` access, doesn't apply to a headless CLI). Sufficient for
  creating files/folders and uploading new content, and for later editing
  those same, app-created files. **Not** sufficient to edit a file that
  already existed in the user's Drive before `omni-dev` touched it.
- `drive` (the unrestricted "full" scope) — the only scope that can edit
  arbitrary pre-existing file content. Substantially broader than anything
  requested before; unlike `drive.metadata`, it also subsumes read.

So "create, upload, edit" spans two different privilege tiers, kept as two
independent, additive opt-ins — mirroring how ADR-0070 kept `drive.metadata`
additive over `drive.readonly` rather than a replacement.

## Decision

### 1. An additive `DriveGrantedScopes` capability set, not a further enum split

ADR-0070 §1 generalized Drive's scope handling from Gmail's binary
`ReadOnly`/`Modify` split to an additive `drive.metadata`-over-`drive.readonly`
model, still a 2-variant enum. This issue needed a third and fourth tier
(`drive.file`, `drive`), and — critically — `--write`/`--write-file`/
`--write-full` are independent, *combinable* opt-ins (Google just grants the
union), not one of four mutually exclusive levels. `DriveScope` therefore
stops being an enum entirely: `DriveGrantedScopes` (`src/drive/auth.rs`) is a
4-bool capability set (`readonly`/`metadata`/`file`/`full`), with
`from_granted`/`as_str` generalized to set/render each flag independently,
and predicates (`allows_rename_move`, `allows_create_or_upload`,
`allows_edit_arbitrary_content`, `allows_write`) replacing the old
single-method `allows_write`. `drive auth login` gains `--write-file` and
`--write-full` alongside the existing `--write`, freely combinable.
`readonly` is always requested alongside every write tier, unchanged from
ADR-0070's additive posture.

### 2. No client-side scope pre-flight gate, for the new verbs either

Unchanged from ADR-0070 §2: `drive create`/`upload`/`edit` always attempt
their mutating call and translate a 403 `insufficientPermissions` into an
actionable hint via a generalized `append_write_scope_hint`, rather than
duplicating a scope check that would drift from Google's actual grant. The
one new wrinkle: which flag to name in the hint is genuinely ambiguous for
`edit` (an app-created file needs only `--write-file`; a pre-existing one
needs `--write-full`, and the client has no cheap way to know which a given
file id is) — the hint names both, letting the operator decide from what
they know about the file, rather than attempting per-file provenance
tracking (out of scope).

### 3. The folder-permission algorithm (this ADR's security-critical core)

`src/drive/write_gate.rs` is a pure module (zero `DriveClient`/network
dependency), mirroring `visibility.rs`'s contract exactly. A target — the
`--parent` folder for `create`/`upload`, or a file's current parent(s) for
`edit` — is identified by its **ancestor chain**: depth 0 is the target
folder itself, depth 1 its parent, and so on up to Drive's root. Configured
`FolderPermissionRule`s (`folder_id`, `recursive`, `allow`/`deny` operation
sets) are matched against that chain by `write_gate::resolve`:

```text
resolve(chain, op, rules):
    for each depth, folder_id in chain:
        for each rule matching folder_id (recursive, or depth == 0):
            record (depth, Allow) if op in rule.allow
            record (depth, Deny)  if op in rule.deny
    if nothing recorded: return default_policy(op)   // Allow for Read, Deny for Create/Upload/Edit
    take the record(s) at the closest (lowest) depth
    return Deny if any Deny among them, else Allow
```

Two tie-breaks, both security-relevant and each backed by a dedicated test:
**closest ancestor wins** (a rule on a subfolder overrides a broader rule on
its parent — the more specific grant/restriction is assumed the more
deliberate one), and **deny beats allow at equal depth** (the safe direction
wins a tie). `DriveOperation::default_policy` is where "disabled by default"
for writes actually lives: `Read` defaults `Allow`, every write operation
defaults `Deny` — there is deliberately no separate enabled/disabled toggle;
an absent or empty rule list already means "deny everywhere" via this table
alone.

`src/drive/folder_ancestry.rs` does the fetching `write_gate.rs` refuses to
(mirroring `file_move.rs`'s role relative to `visibility.rs`):
`resolve_ancestor_chain` walks a target's parent chain via repeated
`files.get` calls. **Any** failure — a fetch error, or exceeding a
defensive depth cap — is a hard `Err`, never a silently truncated `Ok`
chain, exactly the invariant ADR-0070 §3 established for `permissions.list`
fetch failures: a truncated chain could hide a deny/allow rule configured
above the truncation point, manufacturing a false "no rule applies here"
reading. This is asserted by a named regression test
(`ancestor_chain_fetch_failure_returns_err_not_a_truncated_chain`) — the
single highest-priority test in this ADR's whole test surface, since it is
the one place a silent fail-open would be catastrophic.

A legacy multi-parent file (rare — Drive no longer permits creating new
ones) is handled by resolving each current parent's chain independently and
combining the resulting decisions via `write_gate::combine_across_parents`
— deny wins across parents, the same fail-closed direction as every other
tie-break here. An orphan target with no parent at all degenerates to the
bare default policy, correctly, since its chain is empty.

Unlike `visibility.rs`'s diff (necessarily approximate — the documented
shadowed-grant limitation, ADR-0070 §3), this algorithm is a complete,
unambiguous total function over any well-formed chain and rule set: no
analogous accepted-approximation exists here.

### 4. Two independent, mandatory layers; no bypass

The OAuth scope is a technical ceiling ("could this credential ever do
this"); the folder-permission gate is this installation's own policy ("is
it allowed to, here, right now"). Both are required and neither is
sufficient alone — a leaked `--write-full` refresh token with an empty
`write_permissions` block still cannot create, upload, or edit anything,
because the local gate defaults closed independently of what Google
granted. There is no "always allow" bypass and no global on/off switch for
the write gate, mirroring ADR-0070 §4's identical posture for the
visibility gate.

### 5. Per-account settings, not top-level

`write_permissions` nests under `DriveAccountSettings`
(`drive.accounts.<name>.write_permissions.rules`), sibling to `client_id`/
`refresh_token`/`scope`, rather than a top-level field on `DriveSettings`.
The gate's *code* (`write_gate::resolve`) is deliberately account-agnostic —
a pure function over a caller-supplied rule slice — but its *data* is not:
a folder id is only meaningful inside the one Drive it was minted in, so a
rule authored for one account's Drive would be silent noise (never
matching, only hurting the "which rule decided this" auditability this ADR
otherwise prioritizes) if it were visible to every account. Every other
piece of per-account data in `DriveAccountSettings` already lives at this
same scope for the same reason.

### 6. Single-target semantics — no batch machinery

Unlike `drive move`'s N-file, one-shared-destination batch (ADR-0070 §5),
`create`/`upload`/`edit` each act on exactly one target per invocation. So
they use `rename.rs`'s simpler linear-function shape — one async function
per verb, mutating call gated by the classification and a `dry_run` branch
inline — rather than `file_move.rs`'s two-phase Plan/Execute split, which
exists specifically to amortize a shared-destination permission fetch
across a batch these verbs don't have. `--dry-run` and a real run therefore
share the exact same gate-classification code by construction (same
function, same early-return branch), not merely by convention.

### 7. No interactive confirmation, ever

Unchanged from ADR-0070 §6, for the same two reasons: full CLI/MCP parity
is a stated goal for this surface, and a TTY-only confirm would hang or be
silently skipped under a future MCP caller. The permission gate plus
`--dry-run` will be the entire safety surface for `create`/`upload`/`edit`,
exactly as they are for `move`/`rename` today.

### 8. Logging will reuse the existing `RecordKind::DriveMutation` (Phase 3, not yet landed)

No new `RecordKind` — `create`/`upload`/`edit` will route through the same
`kind: "drivemutation"` record ADR-0070 §7 introduced, with `operation`
becoming `"create"`/`"upload"`/`"edit"`. `DriveMutationOutcome` will gain
three new optional context fields (`resolved_folder_id`,
`decided_by_folder_id`, `decided_by_depth`), following its existing
omit-if-absent convention, so `omni-dev log --query decided_by_folder_id:X`
can filter directly on which rule decided a refusal. One correction against
a stale assumption worth recording here: `DriveMutationOutcome` itself has
no `Blocked` variant today — `status` is a plain `String`; the
`Blocked{reasons}` pattern lives on each verb's own local result enum
(`CreateResult`/`UploadResult`/`EditResult`) via a hand-written
`log_status()`, exactly mirroring `MoveResult`'s existing precedent of
keeping the log's `status` field decoupled from the wire
`#[serde(tag = ...)]` shape. Logging will happen inside each engine module,
not the CLI layer, for the identical reason ADR-0070 §7 gives: a future MCP
caller must not be able to bypass it by construction.

### 9. `drive edit` will refuse Google-native documents client-side (Phase 3, not yet landed)

`content_edit::edit` will refuse, before any network call and before the
permission gate itself (cheaper, and not a policy decision), any target
whose `mimeType` starts with `application/vnd.google-apps.` — reusing the
existing `DriveFile::is_google_native()` helper. A raw media PATCH has no
meaningful "content" to replace for a Doc/Sheet/Slide; editing them is a
Docs-API/Sheets-API problem, out of scope here, mirroring ADR-0069's
identical deferral of Docs export.

### 10. Upload size cap (Phase 3, not yet landed)

`drive upload`/`drive edit` will refuse to buffer local content larger than
Drive's documented simple-upload limit (5 MB) into memory, mirroring
`MAX_DOWNLOAD_BYTES`/`check_download_size`'s existing rationale on the read
side. Content above that cap needs a resumable upload session — chunked,
with its own restart/retry bookkeeping — explicitly out of scope for v1, the
same kind of documented boundary ADR-0070 §8 drew around folder-move
recursion rather than silently degrading or erroring unhelpfully.

### 11. CLI-first; MCP tools **and** read-path enforcement both deferred

Broader than ADR-0070 §9's MCP-only deferral: this issue's `Read` operation
and its allow-by-default policy exist in the schema and the resolution
algorithm from day one (so a `deny: ["read"]` rule written into config now
stays valid once the fast-follow lands), but nothing in this ADR's scope
calls `write_gate::resolve(..., DriveOperation::Read, ...)` from a real read
path — only `drive permissions check` exercises it, diagnostically. Wiring
live enforcement into `search`/`read`/`dedupe` needs its own batching/
caching design (resolving every result's ancestor chain is a real per-result
API cost) and is a deliberate fast-follow, not silently dropped. MCP tool
parity for `create`/`upload`/`edit` follows the identical CLI-first
precedent ADR-0070 §9 already set.

### 12. Exit code convention

Unchanged from ADR-0070 §10: exit 0 regardless of individual `Blocked`/
`Failed` outcomes, matching `worktree push`'s existing convention. Scripts
that need to detect a blocked/failed outcome must inspect the output, not
`$?`.

## Consequences

- **This is the largest privilege escalation in the Drive integration's
  history**, larger than ADR-0070's: `--write-full` requests unrestricted
  read/write over the account's entire Drive, where every prior scope
  (`readonly`, `metadata`) was either read-only or metadata-only. The
  folder-permission gate's fail-closed default (empty `write_permissions` =
  deny everywhere) is *load-bearing* against that scale of grant, not
  cosmetic.
- **Two independent layers, both required, neither sufficient alone** — the
  threat-model framing every decision above serves. A leaked `--write-full`
  token is inert against an account with no `write_permissions` configured.
- **No "always allow" bypass and no global on/off switch** for the write
  gate — consistent with ADR-0070's "default-deny, not default-allow-with-a-
  warning… no global config to disable it."
- **A refusal is exactly as auditable as a success** — every `create`/
  `upload`/`edit` attempt, whether it succeeds, is refused by the folder
  gate, or fails outright, produces a `kind: "drivemutation"` record with
  the same fidelity, even when zero Drive API calls were made.
- **`drive edit` cannot silently corrupt a Google-native document** — the
  client-side mimeType refusal exists because there is no sane way to "PATCH
  the content" of a Doc/Sheet, and a permissive implementation here would
  produce confusing, possibly destructive, results.
- **Read-path enforcement is a known, scoped gap, not an oversight.** The
  schema supports `deny: ["read"]` today; nothing enforces it in `search`/
  `read`/`dedupe` yet. Documented here and in `docs/drive.md` so it reads as
  a deliberate fast-follow, the same posture ADR-0070 §8 took for shallow
  folder moves.
- **Sync obligation.** [docs/drive.md](../drive.md) documents the two new
  login flags, the `write_permissions` config schema and its resolution
  algorithm, `drive permissions show/lookup-folder/check`, `drive create`/
  `upload`/`edit`, the upload size cap, and the native-document refusal;
  [docs/log.md](../log.md) documents the three new `drivemutation` context
  fields. Keep both in sync when this ADR's decisions change.
