# ADR-0064: Presence-on-Disk Idempotence and Immutable-`.eml`/Mutable-Manifest Split for `gmail sync`

## Status

✅ Accepted (2026-08-03)

Extends [ADR-0063](adr-0063.md) (Gmail OAuth2 authentication) — consumes its
`GmailClient`/`GmailSession` unchanged, adds no new scope, credential, or
trust surface. Filed as its own ADR rather than a fourth decision on
ADR-0063, per that ADR's own closing note leaving the choice open: a
filesystem archive format with its own atomicity and reconciliation
contract is a substantial new decision, not a natural extension of an OAuth
ADR's scope — the same reasoning that gave the worktrees service's
`rebase`/`push`/`reposition` operations their own ADRs
([ADR-0059](adr-0059.md), [ADR-0061](adr-0061.md), [ADR-0058](adr-0058.md))
rather than repeatedly amending [ADR-0048](adr-0048.md).

## Context

#1465 (ADR-0063) gave omni-dev live, on-demand Gmail access — good for "what
did that thread say", useless if the account disappears or someone wants to
run ordinary tools (`grep`, `mutt`, a mail indexer) across years of mail.
This repository has solved that class of problem twice before —
`transcript youtube sync` (#928/#976) and `ai claude history sync`
(`src/cli/ai/claude/history/sync.rs`) — but never for mail, and a third,
cautionary precedent exists in `src/browser/harvest/facebook.rs`: a
harvester whose resume-state handling contains a genuine data-loss bug (see
Decision 2 below) that this design must not repeat.

Three decisions in this design are load-bearing enough to need explicit
justification.

### Why the `historyId` watermark is an optimisation, not the correctness mechanism

The parent issue proposing this work (#1464) assumed Gmail's `historyId`
watermarks remain valid for roughly 30 days. That is wrong: Google
documents history availability as guaranteed only for approximately **one
week**, and a `startHistoryId` older than that returns `404`. A design that
treats the watermark as authoritative — "if it's missing or stale, we don't
know what changed, so we can't safely proceed" — would have to either leave
a gap or blindly re-download the whole mailbox on every watermark loss, and
would have no defined behavior at all for a first run (no watermark
exists yet). Both problems disappear if idempotence is derived from
**presence-on-disk** instead: "does `messages/<shard>/<id>.eml` already
exist for this id" is always answerable, requires no cursor, and survives
an interrupted run for free — the same principle `transcript youtube
sync`'s `plan_fetches` already established (`path.exists()` per id, no
stored cursor at all). The watermark then becomes exactly what its name
suggests: a fast path that avoids re-listing the entire mailbox when
recent history is still available, never the thing correctness depends on.

### Why `.eml` is immutable and the manifest is the only mutable state

`format=raw` returns the complete RFC 2822 message, base64url-encoded, at
the same 5-quota-unit cost as `format=full` — the right thing to persist
for an archive, since it is a standard format loadable by any mail tool
without omni-dev and requires no schema to stay useful. But Gmail labels
are mailbox-side metadata, not part of the RFC 2822 body: a
`labelsAdded`/`labelsRemoved` history event has nothing in the message
itself to rewrite. Two designs were available: (a) treat the archive as
fully immutable and represent a label change as a *new* record referencing
the same `.eml` (an append-only event log), or (b) keep exactly one mutable
record per message, decoupled from its `.eml`. (a) was rejected — it turns
"what are this message's current labels" into a fold over every event ever
recorded for that id, for no benefit (nothing in this issue needs the label
*history*, only the current label *state*). (b) is the manifest: one JSON
object per message id, holding everything that can change (`label_ids`,
`deleted_at`) alongside everything fetched once and never revisited
(`path`, `size`, `subject`, `from`). This makes the manifest **not** a
derived index that could be regenerated by rescanning the `.eml` files — it
is the sole record of a message's Gmail-side state, which is why its
corruption-handling deliberately differs from `state.json`'s (Decision 2).

### Why the Facebook harvester's resume-state machinery is not reused, and its bug matters here

`src/browser/harvest/facebook.rs` looks superficially like the same job
(list a remote source, persist to local files, resume across runs) but its
`ResumeState` is a private struct whose only load-bearing field is a
GraphQL `end_cursor` — nothing about it is a reusable abstraction. More
importantly, it contains a genuine data-loss bug worth naming explicitly
so this design is checked against it: `preload_prior()` unconditionally
reads every id out of an *existing* output file into a `seen` dedup set
**before** checking whether resume state (`end_cursor`) was actually
found, and `open_sink(resume.end_cursor.is_some())` then opens that same
output file in **truncate** mode whenever no cursor was present — so an
existing archive plus a missing or reset state file silently truncates the
archive to nothing, while the pre-populated `seen` set then suppresses
re-emission of everything just deleted. No error, no warning, a normal-
looking successful run. The design below is structurally incapable of this
failure mode: presence-on-disk is checked *before* every fetch decision
(Decision 1), and nothing in the fetch or reconciliation path ever opens
an existing `.eml` or the manifest in a mode that discards prior content
before confirming what should replace it.

## Decision

### 1. `historyId` in `state.json` is disposable; a 404 or a corrupt/missing file both trigger the same full-reconciliation pass a first run uses

`state.json` (`history_id`, `email_address`, `last_sync`, and the
`--query` last used) is loaded via a three-way outcome —
present-and-valid, absent, or corrupt — and **absent and corrupt are
handled identically**: both fall back to listing the whole mailbox
(`users.messages.list`, reusing the existing `MessagesApi::search_all`
pagination unchanged) and fetching only the ids not already present on
disk. A `404` from `users.history.list` against a present-and-valid
watermark falls back to that exact same code path. Backfill, `--full`, and
404-triggered reconciliation are therefore **one function**
(`run_full_sync`, `src/cli/gmail/sync/engine.rs`), not three — an
interrupted backfill needs no special resume logic because "already on
disk" and "needs fetching" is recomputed from scratch every time. The
`historyId` snapshotted for the next watermark is read from
`users.getProfile` **before** the listing begins, so mail arriving
mid-listing is simply observed as an ordinary `messagesAdded` event on the
next incremental run rather than a race to close.

One case is a hard failure, not a fallback: a `state.json` whose
`email_address` doesn't match the currently authenticated account
(`ProfileApi::get().email_address`) is rejected immediately
(`state::validate_identity`), never silently merged — this is the
account-mismatch bug class Decision 3 names, applied to the one field
where silent recovery would actively corrupt the archive rather than
merely cost an extra listing pass.

The watermark is also **never advanced on a run that recorded any
per-message error** (`SyncError`, Decision 4) — an advanced watermark past
a failed fetch would scroll that history event out of Gmail's retention
window permanently. Withholding the advance means the next run
re-examines the same range for free (already-fetched messages and
already-applied label/delete deltas are skipped via presence-on-disk and
idempotent mutation), at the cost of a full history re-scan rather than a
cheap incremental one until the underlying failure resolves.

### 2. `manifest.jsonl` is the one artifact that must never be silently reconstructed from empty

The manifest (`src/cli/gmail/sync/manifest.rs`) is loaded wholesale into
memory, mutated in place, and rewritten atomically in full on every run —
not appended-then-compacted, since a `labelsAdded` event needs to *update*
an existing record, which an append-only log can only do via a
last-write-wins reconstruction on every read. At realistic scale (tens of
thousands of messages at roughly 250 bytes/record) loading the whole file
is trivial, so the file stays one-JSON-object-per-line (greppable) purely
as a storage format, not a write strategy.

Unlike `state.json`, **a manifest that fails to parse is a hard error**,
never a silent "start from empty." Starting empty would orphan every
already-archived message's label state with no way to recover it (the
`.eml` files carry no label information at all — see Context). Soft-delete
is likewise conservative by construction: a message absent from a full
listing gets `deleted_at` set and its `.eml` is **never removed**; if a
later listing shows the id again, the marker is cleared. Nothing in this
design ever deletes a `.eml` file or truncates the manifest to fewer
records than it already held.

### 3. Every write is presence-checked or atomic, by construction, not by convention

Every fetch decision — backfill, incremental, reconciliation — checks
`messages/<shard>/<id>.eml`'s existence before deciding to fetch; nothing
is ever opened in a mode that discards existing content first and decides
what replaces it second (the inversion of Context's Facebook bug).
`state.json` is written via a sibling `.tmp` file + rename (the one part
of the Facebook harvester worth keeping, `facebook.rs:141-149`); the
manifest is written via the `tempfile` crate's `NamedTempFile::new_in` +
`persist` (already a dependency, the same pattern
`src/cli/ai/claude/history/sync.rs` uses for its own atomic writes,
additionally cleaning up the temp file if `persist` is never reached); each
`.eml` is written via a sibling dotfile + rename (the `transcript youtube
sync` pattern), so a crash mid-write can never leave a partial file that a
later presence check would mistake for a complete one.

### 4. Per-message failures accumulate into a report; they never abort the run

`SyncReport { actions: Vec<SyncAction>, errors: Vec<SyncError> }`
(`src/cli/gmail/sync/report.rs`) is modelled directly on
`src/cli/ai/claude/history/sync.rs`'s `SyncReport`/`SyncError`: every
per-item fallible step is captured into a local `Result` first and matched
once, so a single unfetchable message (a transient 500, a message too
large, whatever) becomes one `SyncError` and the run continues — the
opposite of the Facebook harvester's three whole-run-fatal `?`-propagation
sites. `run_sync` itself performs no stdout/stderr I/O (`engine.rs`); the
CLI layer (`src/cli/gmail/sync.rs`) renders the report and only then
decides the process exit code, turning a non-empty `errors` into a failing
exit **after** everything that could succeed already ran and was
persisted — mirroring `claude/history/sync.rs`'s compute → render → decide
split exactly.

Message fetches are bounded by both a `Semaphore`-equivalent concurrency
cap (`--concurrency`, default 20, clamped to
`1..=messages_api::MAX_CONCURRENCY`) and a proactive token-bucket rate
limiter (`src/utils/rate_limit.rs`) sized to Gmail's documented 250
quota-units/second budget — this is the load-bearing throttling decision
for making a multi-thousand-message sync tractable rather than either slow
or quota-exhausted, and is covered in the operator-facing detail in
`docs/gmail.md`'s Sync and Rate limits sections rather than repeated here.

## Consequences

- **Presence-on-disk, not the watermark, is what an operator can trust.**
  Deleting `state.json` never loses data and never duplicates it — at
  worst it costs one full-mailbox listing pass. This is a deliberately
  different reliability story from a cursor-only design, and is the
  single fact worth remembering when something looks wrong with a sync
  run: check the archive on disk before suspecting the watermark.
- **The manifest is the one file in this archive that is not disposable.**
  Its loss is equivalent to losing every archived message's label state
  (though not the messages themselves, which remain intact and readable as
  ordinary `.eml` files). Back it up like any other irreplaceable local
  state; this ADR does not add any redundant copy of it.
- **A known, documented scope limitation, not solved here:** `--query`
  scopes a backfill/reconciliation listing, but `history.list` has no
  query filter, so an incremental run cannot re-apply it — newly-arrived
  mail matching the original query is only picked up by a later `--full`
  pass. Documented in `docs/gmail.md`; not a correctness bug, since nothing
  is lost, only delayed until the next full pass.
- **Explicitly out of scope, and why:** a generic harvest/sync trait
  unifying this design with the Facebook harvester and `transcript youtube
  sync` is tempting — three divergent state models now exist for a similar
  problem shape — but unifying three shipped features is its own project
  with its own ADR, not something to couple opportunistically to a new
  feature. Full-text search over the archive and attachment **extraction to
  separate files** are likewise out of scope: the `.eml` + manifest contract
  this ADR establishes is deliberately minimal, and both are additive
  layers a future issue can build on top of it without changing anything
  decided here. Attachment *metadata* (a count plus whichever filenames can
  be parsed from `Content-Disposition: attachment` parts) is in scope and
  recorded in the manifest — a 24%-of-corpus prevalence measured against a
  real mailbox made "attachments are entirely invisible" the wrong default,
  but attachments themselves stay inline inside the `.eml`, never written
  out as separate files.
- **Sync obligation.** `docs/gmail.md`'s Sync section is the
  operator-facing description of the archive layout, the backfill/
  incremental/reconciliation contract, and the `--query` limitation. Keep
  the two in sync when this ADR's watermark or manifest contract changes.

See [ADR-0063](adr-0063.md) for the `GmailClient`/OAuth session this design
consumes unchanged, and [ADR-0046](adr-0046.md) for the `-o/--output`
convention `gmail sync`'s report rendering follows.
