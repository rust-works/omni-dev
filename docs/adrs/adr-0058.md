# ADR-0058: Repositioning VS Code Windows from the Daemon via the macOS Accessibility API

## Status

✅ Accepted (2026-07-25)

## Context

[ADR-0040](adr-0040.md) introduced the `worktrees` daemon service, [ADR-0048](adr-0048.md)
grew it into a live cross-window tree, [ADR-0049](adr-0049.md) added its first
**destructive** op (`close`), and [ADR-0056](adr-0056.md) its first op to mutate
**remote** state (`merge-queue`). Every capability so far reads git, reads the
registry, spawns `code`, deletes a directory, or calls GitHub.

The next thing a fleet of worktree windows needs is not another action on a
worktree — it is **arrangement**. With two dozen windows open, getting a chosen
subset to occupy the same screen slot is manual, per-window dragging, repeated
every time the set changes. The wanted gesture is: select N worktrees, act once,
and every one of their windows takes the position and size of the window you acted
from.

Four facts shaped the design.

1. **A VS Code extension cannot do this at all.** There is no API to read or set a
   window's OS-level position or size, and the request is long-standing and
   explicitly parked upstream (microsoft/vscode#28150, #83170, #195406). Extensions
   that resize windows shell out to native code; none uses a VS Code API. So the
   work *must* happen in a native process, and the daemon already is one — a
   LaunchAgent inside the user's GUI session, and (per ADR-0040) the only vantage
   point that knows every window.

2. **This is a new kind of privilege, not a bigger version of an old one.** Every
   previous op acted on files, processes, or network resources the user's own
   session already granted us. Moving *another application's* window is gated by
   macOS behind the **Accessibility** permission, which is coarse: a process that
   holds it can, in principle, drive any application's UI. That is a genuine
   escalation of the daemon's trust surface and the reason this ADR exists.

3. **The registry cannot identify an OS window.** `WindowEntry` stores
   `key, folders, repo, title, pid, last_seen` — no window id, no geometry. Worse,
   `pid` is the **extension-host** process, and in Electron every window's native
   `NSWindow` belongs to the single **main** process. So `pid` cannot locate a
   window, and the identification problem is the real engineering risk here, well
   above the permission.

4. **Z-order must not change.** The point of the gesture is to stack windows into
   one slot while leaving the invoking window exactly where it is in the stack.
   Anything that raises or activates a window destroys the result. This rules out
   the existing focus path (`focus_window`, which spawns `code <folder>` and lets
   VS Code raise the window) as an implementation route.

Two alternatives were considered and rejected. **Shelling out to `osascript` /
System Events** avoids `unsafe` entirely and mirrors the existing "shell out to
`code`" pattern; the issue proposed it as a de-risking spike. It was dropped
because it needs an *additional* Automation TCC grant on top of Accessibility
(and background-agent TCC prompts are unreliable), and because the read half of
the Accessibility API is needed regardless — so the spike would have been thrown
away. The de-risking it was meant to provide is instead delivered by a
side-effect-free `check` mode of the real op. **Embedding the window key in
`window.title`** would make identification exact, but at the cost of permanently
defacing every title bar and overwriting a user setting; it is recorded below as a
fallback should title matching prove insufficient.

## Decision

We will add a `reposition` op to the worktrees service that moves and resizes
target windows onto a reference window's frame using the macOS Accessibility API,
with a companion `reposition-undo`. Specifically:

### 1. The daemon does the geometry work; the extension only supplies keys

We will keep the extension a thin reporter, as ADR-0040 established. It resolves
the user's selection to window keys and sends one envelope; the daemon resolves
keys to OS windows, reads the reference geometry, and performs every write. The
CLI (`omni-dev worktrees reposition`) is a socket client on the same op, so it
inherits the daemon's permission rather than needing the terminal to hold one —
TCC attributes a grant to the *responsible* process, which for a terminal-launched
binary is the terminal.

### 2. Geometry only, never a raise — which is why AX, not a launcher

We will set only `kAXPositionAttribute` and `kAXSizeAttribute`. Setting these
neither raises nor activates a window, so Z-order preservation is a property of
the mechanism rather than something we maintain. We will **not** reuse
`focus_window` for any part of this: it exists to raise a window, which is the
exact opposite of the requirement. The Accessibility API is also what lets the
daemon *read* the reference frame, which an extension cannot do for its own window.

### 3. Windows are identified by root name, and ambiguity is refused

We will resolve a registered window to an OS window in two steps. First, its
owning application: the extension-host pid's parent is the VS Code main process
that owns every `NSWindow`, resolved with one batched `ps -o pid=,ppid=` — a
shell-out rather than more FFI, and one that correctly attributes each window to
its own variant (Stable / Insiders / VSCodium). Second, the window within that
application: match the registry's `title` (`vscode.workspace.name`) against
`AXTitle` through a cascade of progressively looser rules — exact equality, then
suffix, then substring — each requiring **uniqueness** before it is accepted.

A bare substring match is not merely imprecise but wrong: the root name
`omni-dev` is a substring of a window named `… — issue-198-omni-dev-coverage-check`.
The cascade separates those; where nothing can, the target is reported
`ambiguous` and **left alone**. Refusing to guess is the load-bearing property —
moving the wrong window is a worse failure than moving none, and it is not
obviously attributable when it happens. Every resolved window is also *claimed*,
so two targets can never be planned onto one window and no target can be planned
onto the reference. The reference alone may fall back to a focus tie-break, since
the window the user acted from is its application's focused window.

We accept that this is weaker than an exact identifier. It is sound for the
default `window.title` and breaks predictably — into a *reported skip*, never a
mis-target — under a custom title template, a non-default profile, or duplicate
root names. Embedding the window key in `window.title` remains available if that
proves too weak in practice.

### 4. No confirmation, but one level of undo

We will not make this two-phase. `close` and `merge-queue` confirm because they
destroy local files or mutate shared remote state; repositioning creates,
modifies, and deletes nothing durable, and a modal on a routine layout command
the user repeats would cost more than it protects. But the previous layout *is*
lost, so the daemon will record where each moved window was and expose
`reposition-undo` to put them back — surfaced both as an action on the summary
notification and as a palette command.

The record is deliberately **one level deep and in-memory**: it is replaced by the
next reposition, consumed by the undo, and dropped by a daemon restart. A deeper
stack would pose questions ("what does undoing an older batch mean once a newer
one moved the same window?") that one level cannot.

### 5. A dry run is the diagnostic surface, and it is the same code path

We will make `check: true` (`--dry-run`) resolve everything exactly as a real run
does and write nothing. Because identification is the fragile part, the ability to
ask "which OS window does each of these worktrees resolve to?" is not a debugging
afterthought but the primary operator tool — and it is trustworthy precisely
because it is not a separate code path.

### 6. `unsafe` is confined to one module, behind a trait, with a bounded blast radius

We will isolate every `unsafe` call in `src/daemon/services/worktrees/geometry/ax.rs`
behind a four-method `WindowBackend` trait, satisfying STYLE-0013's requirement
that an FFI exception be ADR-justified, isolated, and `SAFETY`-commented. All
matching, planning, and reporting live in the platform-independent parent module
and are unit-tested with a fake backend on any platform.

Within the FFI module: ownership of every Accessibility object is `CFRetained`,
so `CFRelease` is a destructor rather than hand-written cleanup; attribute values
are `downcast`-checked against their concrete CoreFoundation type instead of
blind-cast; and `AXUIElementSetMessagingTimeout` bounds every call, because
Accessibility is synchronous Mach messaging into another process and a
beachballing VS Code would otherwise wedge a daemon thread indefinitely. All of it
runs on a blocking thread, never the async worker and never under the registry
lock. We declare the seven C entry points inline rather than adding a generated
framework binding — the `launchd_listener` precedent — since seven plain-C
functions over `CFTypeRef` are a smaller reviewable surface than a whole
framework's bindings.

### 7. The permission is reported as data, and never prompted for

We will check `AXIsProcessTrusted()` once per op and return the answer as a
`trusted` **field** on the reply, not as an error, so a client can offer the user
the Accessibility settings pane instead of pattern-matching an error string. We
will **not** call the prompting variant: a permission dialog raised by a
background LaunchAgent is unreliable, and the extension's own notification with a
deep link is a better affordance.

### 8. macOS only for v1, with the seam already in place

We will ship macOS only, consistent with the tray. The non-macOS backend reports
itself untrusted, so the op degrades to the same "cannot move windows" reply a
macOS daemon without the grant produces, and the extension hides the menu item
off-darwin. Linux/X11 (EWMH title matching) and Windows (`SetWindowPos`) would
each be an implementation of the same four trait methods, leaving every caller and
the whole planner untouched; Wayland is generally not possible.

## Consequences

**Positive.** The gesture the issue asked for works: one action arranges N windows,
Z-order intact, with per-target outcomes rather than silent partial success.
Because the planner is pure and the platform sits behind a trait, the interesting
logic — matching, ambiguity refusal, skip classification — is unit-tested without
a window, a grant, or a display, and a second platform is an additive change. The
dry run makes the fragile part inspectable, and the undo removes the
irreversibility objection to skipping a confirmation. No new transport, no new
trust boundary in the socket sense: requests ride the existing `0600` Unix socket
and nothing is persisted.

**Negative.** The daemon now needs the macOS **Accessibility** grant, which is
coarse — it authorises far more than reading titles and writing rectangles, so the
*capability* the daemon holds is much broader than the capability it uses. The
grant is also friction: it cannot be self-granted (a process can only open the
settings pane), it takes effect only for a freshly-spawned process (so
`omni-dev daemon restart` is part of the setup), and because omni-dev installs
**unsigned** via cargo/homebrew, its code-signing identity changes on every
rebuild — so the grant is silently invalidated on every upgrade and must be
re-granted. A stable Developer ID would fix that and is a follow-up; it is the
biggest adoption wrinkle. Separately, identification is heuristic, so a user with a
custom `window.title` or duplicate root names will see targets reported
`ambiguous`/`not-found` instead of moving. And the crate's `unsafe_code = "deny"`
now has a second exception.

**Neutral.** The `objc2-core-foundation` dependency becomes non-optional on macOS
(it was already in the tree behind the `menu-bar` tray feature) because
repositioning must work in the default build. Windows on another macOS Space are
moved — the coordinates apply — but stay on that Space, which is invisible until
the user switches; native-fullscreen and minimized windows are detected and
skipped rather than being moved incorrectly. Undo state, like the close-pending
directive of ADR-0049, does not survive a daemon restart. The residual exposure on
the socket is unchanged in kind: a local socket writer could rearrange the user's
windows, which is annoying rather than dangerous, and already requires being the
owning local user.
