# ADR-0098: A Default-Closed Anthropic Messages Gateway with a Classed Field Policy

## Status

✅ Accepted (2026-10-14, [#2226](https://github.com/rust-works/omni-dev/issues/2226)).

## Context

Tools that speak the Anthropic Messages API, such as Claude Code, the
Anthropic SDKs and anything that honours `ANTHROPIC_BASE_URL`, cannot use
models served over the OpenAI protocol. omni-dev already calls OpenAI-protocol
servers as an AI backend (`src/claude/ai/openai.rs`), but it could not *serve*
the Anthropic protocol to other clients. [#2226](https://github.com/rust-works/omni-dev/issues/2226)
asks for that inbound direction. It names Fireworks AI as a first-class target
and requires that the translation track the current specifications.

Three forces shaped the design.

**A new listening surface.** A local HTTP server that relays to a paid
upstream is a credential deputy. Any local process, or any web page the
operator visits (by cross-origin request or DNS rebinding), that can reach
it can spend the operator's upstream key. The browser bridge
([ADR-0036](adr-0036.md)) faced the same threat and settled it: loopback
bind, a token on every request, Host and Origin guards.

**A moving specification.** In 2026 the Anthropic API added, among other
things, adaptive and `between_tools` thinking, the `xhigh` and `max` effort
levels, structured outputs under `output_config`, `refusal` stop details,
mid-conversation system messages, and request fields such as
`context_management`, `compaction`, `fallbacks` and `inference_geo`. Claude
Code also sends fields that appear in no SDK type. Running it through the
gateway on 2026-10-14 showed `safeguards` (context for a server-side
dangerous-tool-use classifier), `thinking.display: "updates"` and a
per-message `output_config`. A translator that ignores what it does not know
silently changes behaviour; one that rejects what it does not know breaks when
the client updates.

**No faithful equivalent for some features.** OpenAI-protocol upstreams
cannot run Anthropic's server tools or classifiers, produce no thinking
signatures, do not report cache writes, and do not say which stop sequence
matched.

We considered and rejected these alternatives:

- **Running `anthropic-proxy` beside omni-dev.** It works today, but it lags
  the specification: `tool_choice` is always `auto`, it has no `refusal` or
  `pause_turn`, and thinking is a model reroute rather than a translation. It
  also sits outside omni-dev's authentication, logging and secret handling.
- **Depending on a translation crate.** The candidates are young and have no
  reverse dependencies. Tracking the specification is the part that needs
  owning.
- **Fireworks' own Anthropic surface only.** That serves Fireworks but not
  Ollama, LM Studio, vLLM or OpenRouter. We keep it as a passthrough mode
  instead.
- **Accept-and-ignore unknown fields.** This is how most proxies work, and it
  is exactly the silent behaviour change #2226 forbids.

## Decision

We will add an Anthropic Messages gateway (`crate::gateway`). It serves
`/v1/messages`, `/v1/messages/count_tokens` and `/v1/models` in front of an
OpenAI Chat Completions or Responses upstream, or passes through to an
Anthropic-compatible one, or invokes native Claude on Bedrock using the
existing bearer-token/configurable-base-URL authentication contract (no SigV4
credential chain). The standalone `omni-dev ai gateway serve` and the
daemon's `anthropic-gateway` service host one engine.

**The surface is default-closed, following ADR-0036.** We will:

- bind `127.0.0.1` only, and fail closed when the port is taken;
- require the gateway token on every request, as `x-api-key` or
  `Authorization: Bearer`, compared in constant time;
- refuse a non-loopback `Host` and any browser-originated request (an `Origin`
  header, or `Sec-Fetch-Site` of `cross-site`, `same-site` or `same-origin`).

The token never comes from argv. It comes from `OMNI_DEV_GATEWAY_TOKEN` (with
`_FILE` and `_COMMAND` companions), else from a persisted `0600` token file,
so a client's configuration survives restarts. The upstream key is read only
through the secret resolver. It is never sent to the client, and the gateway
token is never sent upstream. Every upstream call is recorded in the request
log, with auth redacted. The daemon service binds nothing until an upstream is
configured, so a default daemon opens no new port.

**Every request field is classed in one tested table.** Each top-level
request field, message-level key, content-block type and tool field is
translated, ignored or rejected.

- An ignored field is reported to the client in an
  `x-omni-dev-gateway-ignored` header and logged.
- A rejected field returns an Anthropic `invalid_request_error`, and nothing
  is sent upstream.
- A field the table does not know is rejected by default. An operator can
  downgrade unknown fields to ignored with
  `OMNI_DEV_GATEWAY_UNKNOWN_FIELDS=warn`.
- A safety control is never ignored: `safeguards` is rejected, and Claude Code
  retries without it.

The operator guide carries the same table, held in sync by a test. A weekly
job compares the table with the official Python SDK's generated types and
opens an issue on drift.

**The gateway signs its own thinking blocks.** It signs each block with an
HMAC keyed from the gateway token. On the next turn it replays a block whose
signature verifies, as `reasoning_content` or as a Responses `reasoning` item.
It drops one that does not, which mirrors Anthropic's binding of thinking to
the account that produced it. The signed payload carries what a replay needs
(the Responses API's encrypted reasoning, or reasoning hidden by `display:
omitted`).

**What cannot be represented is stated, not faked.**

- `count_tokens` is an estimate, flagged as one by a response header.
- `stop_sequence`, `pause_turn` and `model_context_window_exceeded` are never
  produced.
- Server tools and PDF documents are rejected.
- An upstream context-length error is reworded to Anthropic's `prompt is too
  long`, so clients compact rather than fail.

## Consequences

**Positive**

- Claude Code and the Anthropic SDKs can use OpenAI-protocol models, and
  Fireworks' own Anthropic surface, with omni-dev's authentication, secret
  handling and logging, either as a daemon service or as a standalone command.
- The translated / ignored / rejected decision is explicit, reviewable and
  tested. A client sees what was ignored, and an operator sees it in the log.
- The drift check turns a new Anthropic field into an issue within a week,
  instead of a rejection users discover.
- Running a real client through the gateway found Claude Code-specific fields
  that no specification lists. They are now classed rather than mishandled.

**Negative**

- The listening surface is new. Any local process holding the token can
  spend the upstream key. This is the same trust boundary as the browser
  bridge's token, and it is bounded to the same user.
- Rejecting unknown fields means a client update can fail until the table
  learns the new field. The drift check and the `warn` downgrade bound that
  cost, but do not remove it.
- Rejecting `safeguards` costs Claude Code one failed request per session in
  auto permission mode, and auto mode runs without Anthropic's server-side
  classifier. That is inherent in using a model Anthropic does not serve.
- Thinking signatures stop verifying when the gateway token is rotated, so
  the next turn after a rotation goes without the earlier reasoning. The
  signed payload is signed, not encrypted: a client can read reasoning it was
  told was omitted.
- `count_tokens` can be off by a margin that matters near a context limit.

**Neutral**

- The standalone server and the daemon service share a default port and a
  token file, so an operator runs one or the other.
- Existing single-upstream configuration remains supported. Optional named
  upstreams and exact/glob model routes select a protocol, flavor and credential
  per request. Credential references must use the central secret registry so
  secret helper sanitation, visibility and redaction recognize their real names;
  no unregistered lookup aliases bypass that invariant. The native Bedrock
  bearer variable is registered as `AWS_BEARER_TOKEN_BEDROCK`.
  Custom routes take precedence over cached automatic discovery.
  Discovery fails closed on unavailable or ambiguous ownership, never performs
  inference, and never retries inference against a different provider. Catalog
  endpoints are explicitly configurable (especially for Bedrock control-plane
  catalogs); redirect following is disabled. Successful discovery is cached for
  60 seconds, failures for 5 seconds, with no stale ownership on failure.
- Native Bedrock preserves provider content and signatures and decodes AWS binary
  event streams into Anthropic SSE; it does not apply the lossy translation
  policy or create gateway thinking signatures. All upstreams share the same
  inbound auth guard and concurrency budget.
- The Responses API target and Fireworks passthrough are additions to the
  Chat Completions translator, not replacements; each upstream protocol keeps
  its own request builder behind the shared lowering and response layers.
