# ADR-0083: Permission-Gate Mapping for the Grid-Mutation `batchUpdate` Verbs

## Status

✅ Accepted (2026-09-21)

**Extends [ADR-0073](adr-0073.md), [ADR-0075](adr-0075.md),
[ADR-0077](adr-0077-sheets-deletion-via-batchupdate.md), [ADR-0078](adr-0078.md)
and [ADR-0081](adr-0081.md); reverses none.** Those
ADRs built the `DriveOperation` vocabulary this one reuses without change:
`SheetsWrite` (ADR-0073 §3) for cell values, `SheetsStructure` (ADR-0075 §1,
extended by ADR-0078 §1 and ADR-0081 §1–§4) for non-destructive structural
and cosmetic edits, and `SheetsDelete` (ADR-0077 §1) for grid-data deletion.
Like ADR-0081, this ADR is a pure gate-mapping design pass — issue #1831,
blocking issues #1839–#1845 under tracker #1830 — and ships no code. Every
capability it covers is still unimplemented; the operation each one resolves
to is decided once, here, so the seven implementing issues do not each
re-litigate it and none of them accidentally settle it seven different ways.

## Context

Issue #1830 is the tracker for the second follow-up audit of the
`spreadsheets.batchUpdate` request union. Its "additive/structural" group
(#1832–#1838: banding, dimension groups, `moveDimension`, sheet and workbook
properties, chart/slicer repositioning, `insertRange`) is clean
`sheets-structure` reuse on the same reasoning ADR-0081 §1 recorded for
filter views, and is not discussed further here. Its "grid-mutation" group
is different in kind: every request in it writes, moves or reorders cell
**values**, which is the question ADR-0081 §5 had to settle for pivot
tables and the one this ADR settles for the rest:

- `cutPaste` / `copyPaste` / `pasteData` (#1839) — write into a
  caller-chosen destination anywhere in the workbook, overwriting whatever
  is there; `cutPaste` also clears its source.
- `autoFill` (#1840) — writes a server-computed series into a range.
- `findReplace` (#1841) — overwrites matching cell content, and optionally
  formulas, across a range, a sheet, or every sheet.
- `sortRange` (#1842) and `randomizeRange` (#1845) — rewrite every cell in
  a range with reordered values; nothing is discarded.
- `textToColumns` (#1843) — splits one column's text into the adjacent
  columns, overwriting them.
- `trimWhitespace` (#1844) — edits values in place.
- `deleteDuplicates` (#1844) — removes the duplicate rows within a range,
  the survivors shifting up inside it; content outside the range is
  untouched.

Three facts already in the codebase decide most of this before any new
argument is needed, and are stated here so the Decision can lean on them:

1. **`sheets clear` sits under `sheets-write`.** `WriteVerb::Clear` in
   `src/drive/sheets/write.rs` issues `values.clear` on a caller-chosen range
   anywhere in the workbook, erasing every value in it, and resolves
   `DriveOperation::SheetsWrite` exactly as `sheets write` does
   (`docs/drive.md`'s default-policy table lists all three together). An
   operator who granted `sheets-write` therefore already consented to
   "discard the existing values of any range I name". A verb that does no
   more than that is asking for nothing new, however it phrases the
   overwrite.
2. **`sheets-delete`'s binding scope is removing grid cells, not discarding
   values.** ADR-0077 §1 and `SheetsDelete`'s own doc comment scope it to
   deleting "a sheet, a row/column range, or an arbitrary cell range" —
   `deleteSheet`, `deleteDimension`, `deleteRange` — operations that remove
   cells from the grid and shift what remains. The distinction between
   `sheets-write` and `sheets-delete` was never "does data get lost" (`clear`
   loses data) but "do cells cease to exist and the grid close over them".
3. **`sheets append` grows the grid under `sheets-write`.** `values.append`
   adds rows past the end of a table, so a write that extends the sheet's
   dimensions by writing past its edge is already within that grant. What
   `sheets-structure` owns in this area is `insert-rows`/`insert-columns` —
   a *shift* of existing cells, which is a different thing from growth.

Two questions survive those facts. The first is the one issue #1831 asks:
where `deleteDuplicates`, `sortRange` and `randomizeRange` belong, since
none is a plain value assignment. The second the issue does not ask, and is
the genuinely new decision in this tranche: the three paste requests take a
`pasteType`, and the Sheets API defines it as `PASTE_NORMAL` ("values,
formulas, formats, and merges"), `PASTE_VALUES`, `PASTE_FORMULA`,
`PASTE_FORMAT` ("the format only, excluding data validation"),
`PASTE_NO_BORDERS` ("like `PASTE_NORMAL` but without borders"),
`PASTE_DATA_VALIDATION` and `PASTE_CONDITIONAL_FORMATTING`. Only two of
those seven write cell content alone; three write only what
`sheets-structure` covers; two write both. And `cutPaste`'s documentation is
explicit that "all the source data will be cut, regardless of what is
pasted" — a cut always clears the source's values, formats, merges and
validation together. A paste surface gated on `sheets-write` alone would let
that grant restyle cells, which is precisely what ADR-0078 §3 made
`sheets-structure`'s formatting request type-incapable of doing in the
other direction (`RepeatCellData` carries no `userEnteredValue`); the
symmetric guarantee is worth keeping.

Two alternatives for the paste family were considered. Gating the whole
family on `sheets-delete`, on the grounds that a paste can destroy data, is
rejected by fact 1: `clear` already destroys data under `sheets-write`, and
`sheets-delete`'s scope is grid removal, which a paste never performs. A
curated surface offering only the value-carrying paste types, ADR-0078 §5's
precedent, is the cheaper alternative and would need no composition at all;
it is rejected because `PASTE_NORMAL` is the common case for a copy or a
cut, and because the two-operation composition it would avoid already
exists (`target_gate::resolve_all`, built for #1798), so the curated cut
would save nothing and lose the verb most callers want.

The remaining design question is what `--dry-run` can honestly say for
each verb. The codebase has settled three tiers already: `sheets write`'s
dry run reads no values and reports dimensions only (pinned by
`dry_run_reports_dimensions_and_calls_no_values_endpoint`); `merge-cells`
reads its range and lists the values it would discard (ADR-0078 §4);
`delete-named-range` reads and reports only the count and A1 locations of
what it affects (ADR-0081 §2); and for an effect the server computes,
ADR-0077 §5 and ADR-0081 §5 name the limit as a fixed caveat rather than
guess. Several verbs here have server-decided effects — `autoFill`'s
series detection, `findReplace`'s matching (the API specifies Java
`java.util.regex.Pattern` semantics for `searchByRegex`, with the
replacement allowed to reference capturing groups), and `deleteDuplicates`'
comparison — which the API documents in intent (rows "with identical
values but different letter cases, formatting, or formulas are considered
to be duplicates"; hidden rows are removed too; the first instance is kept)
but not at the fidelity a local reproduction would need, such as which
rendering of a numeric value is compared.

Every mutating verb in the existing Sheets surface also passes through
[ADR-0080](adr-0080.md)'s backup-lease gate (`gate_optional_leased_write`
in `src/drive/lease/check.rs`, honouring the deciding folder rule's
`require_lease`), and every dry run returns before it. Nothing in this
tranche changes that, but seven parallel implementing issues are the shape
of work that settles it seven ways unless it is stated once.

## Decision

### 1. Value-only mutation joins `sheets-write`

`copyPaste` and `pasteData` with a value-only paste type
(`PASTE_VALUES`, `PASTE_FORMULA` — §4 has the full mapping), `autoFill`,
`findReplace`, `textToColumns` and `trimWhitespace` all resolve
`DriveOperation::SheetsWrite` alone. Each writes ordinary cell content
into a range the caller named, or into a range the request determines from
the caller's input, and none does
anything a `sheets clear` followed by a `sheets write` of the same range
could not already do under the same grant. No `sheets-write` rule written
before this ADR is widened by it: the harm each verb can cause — the loss of
whatever values were in the destination — is exactly the harm `clear`
already permits.

`findReplace`'s scope options (`range`, `sheetId`, `allSheets`) change
nothing about the gate, which resolves against the spreadsheet as a file,
not against a range within it — the same footing on which `sheets clear`
already reaches any range in the workbook. `includeFormulas` changes
nothing either: `sheets write` can already overwrite a formula cell with
whatever the caller supplies.

`textToColumns` is the one verb here whose destination the caller does not
name: the API requires `source` to "span exactly one column" and writes
into however many columns to its right the split needs. That is still a
value write into the target sheet, and the implementing issue's preview
(§6) reports which cells it would reach.

### 2. `deleteDuplicates` joins `sheets-delete`

`deleteDuplicates` "removes rows within this range that contain values in
the specified columns that are duplicates of values in any previous row",
keeping the first instance of each; "content outside of the specified range
isn't removed". Cells cease to exist and the rows below them *within the
range* close over the gap. That is `delete-range`'s shape with an upward
shift — an existing `sheets-delete` verb, and fact 2's definition of the
operation — not `clear`'s, so it is the one verb in this tranche that needs
the stronger gate. The argument that it loses no *information*, since every
removed row duplicates a kept one in the compared columns, does not move it,
and the API's own equality rule makes it weaker still: rows "with identical
values but different letter cases, formatting, or formulas are considered
to be duplicates", so a removed row may differ visibly from the one kept,
and with `comparisonColumns` set it may differ in every column not
compared. The gate tracks a risk class (ADR-0077 §1), not an
information-theoretic loss.

What is new about it is not the shape but the selection: every existing
`sheets-delete` verb removes cells the caller named by address, whereas
`deleteDuplicates` removes rows the *server* selects from the data — a
`sheets-delete` grant used through this verb deletes whatever the equality
rule finds, including rows hidden by a filter. That is still within what
the grant consents to (rows removed from a range this tool was told to
act on), but it is the reason §6 has both the preview and the real run
state the rule the server applies.

`deleteDuplicates` ships in #1844 alongside `trimWhitespace`, which resolves
`sheets-write` (§1). Two verbs in one implementing issue taking two gates is
the established shape, not a special case: `StructureVerb::gate_operation`
(ADR-0077 §1) decides the operation per verb, and every call site reads it
from the verb.

`SheetsDelete`'s binding clause — "no other operation should later join
this variant without the same re-consent reasoning" — is honored rather
than reopened. An operator who granted `sheets-delete` consented to having
rows removed from a sheet by this tool; `deleteDuplicates` removes rows, and
adds no consent beyond that. #1844, which ships it, owns the matching
update to `SheetsDelete`'s doc comment and to `docs/drive.md`'s
`sheets-delete` row — named here because it is the only issue in the
tranche touching that operation, so no other issue can do it by accident.

### 3. `sortRange` and `randomizeRange` join `sheets-write`

Both rewrite every cell in a caller-named range with the range's own
values in a different row order. No value is discarded and no cell is
removed, so on facts 1 and 2 neither verb reaches the threshold of `clear`,
let alone of `sheets-delete`; a `sheets-write` grant already permits
replacing the range's contents with anything at all, of which a permutation
of the existing contents is a strict special case.

The residual that makes these verbs worth their own paragraph is not what
happens inside the range but outside it: a formula elsewhere that
references a cell inside the range by address now sees a different row's
value. That is a real, visible effect, but it is the same *shape* as the
one ADR-0077 §5 accepted for `delete-rows` — a reference-level consequence
that cannot be checked from the request — and it is handled the same way:
a fixed caveat in both `--dry-run` and the real run's output (§6), not a
stronger gate.

This section's "values in a different row order" is the API's documented
contract for what the two requests *reorder*. Two things it does not
document: whether the server also carries each row's cell formatting along
with it, as the Sheets UI does when sorting, and what it does with a
formula *inside* the range — moved with its row, with or without its
relative references rewritten, or left where it is. §5 makes both
live-verification items. The formatting one has a fixed gate consequence,
so the gate settled here holds only for the values-only reading and moves,
by rule rather than by a fresh decision, if the reading is wrong; the
formula one cannot move the gate, since every answer is a change to cell
content, and decides only the wording of §6's caveat.

### 4. Paste types compose the existing operations; `cutPaste` always needs both

`copyPaste` and `pasteData` resolve their gate from the `pasteType` the
caller asks for, with no new operation and no new consent:

| `pasteType`                                                  | Writes                              | Resolves                                        |
|--------------------------------------------------------------|-------------------------------------|-------------------------------------------------|
| `PASTE_VALUES`, `PASTE_FORMULA`                              | cell content only                   | `sheets-write`                                  |
| `PASTE_FORMAT`, `PASTE_DATA_VALIDATION`, `PASTE_CONDITIONAL_FORMATTING` | presentation or validation only     | `sheets-structure`                              |
| `PASTE_NORMAL`, `PASTE_NO_BORDERS`                           | cell content **and** formats/merges | **both** `sheets-write` and `sheets-structure`  |

The presentation-only row is consistent with `format-cells`,
`set-data-validation` and `add-conditional-format`, which already write
exactly those things under `sheets-structure`; a `sheets-structure` grant
gains no ability from a format-only paste it did not already have. The
both-row reuses ADR-0081 §5's symmetric composition unchanged: both
operations must independently resolve `Allow` against the same target via
`target_gate::resolve_all`, and an operator who holds both has, by
definition, already consented to arbitrary cell overwrites and arbitrary
cosmetic changes, which is all `PASTE_NORMAL` does. This is the second use
of that composition, which makes it a pattern rather than a pivot-table
special case.

`cutPaste` resolves **both** operations whatever its `pasteType`, because
the source is always cleared in full — values, formats, merges and
validation — and clearing formats and merges is `sheets-structure`'s
territory (`unmerge-cells`, `clear-data-validation`) just as clearing
values is `sheets-write`'s. A `cutPaste --paste-type values` that resolved
`sheets-write` alone would let that grant strip formatting from the source,
which is the guarantee this section exists to keep.

The `PasteType` enum is mirrored as a typed `--paste-type` flag on the
paste verbs, never forwarded as a free string, so the mapping above is a
`match` with no default arm. A paste type this tool does not model is
unrepresentable rather than a compile error — it simply cannot be asked
for — and the implementing issue keeps it that way (no `#[non_exhaustive]`
mirror, no serde passthrough), so adding one later is a deliberate choice
of row, never a silent fall-through to the weakest gate.

The flag defaults to `normal`, the API's own default and what "paste" means
to a Sheets user, which means a bare `copy-paste` under a `sheets-write`-only
grant is refused. That is the right way round: the refusal names the
operation that is missing and points at `--paste-type values`, whereas a
`values` default would make the common invocation silently paste less than
the user copied. `pasteData`'s `html` form is not in the first version:
pasted HTML carries formatting, colours and merges whose gate row would
depend on the markup, so the surface is `delimiter`-form only — ADR-0078
§5's curated-surface cut — and adding `--html` later is a §4 question, not
a flag.

### 5. No verb requires `sheets-structure` for extending the grid

Fact 3 answers issue #1831's "does `autoFill` or `sortRange` need both?"
directly: growth by writing past the grid's edge is what `sheets append`
already does under `sheets-write`, so a paste, fill or split that reaches
beyond the current dimensions asks for nothing `sheets-structure` owns.
`sortRange` and `randomizeRange` cannot extend anything: they operate
strictly inside their range.

Whether the API errors or expands the grid when a `copyPaste`, `pasteData`,
`autoFill` or `textToColumns` destination runs past its edge is not
documented for those requests (the `copyPaste` reference says only that a
source larger than its destination is copied in full "beyond the end of the
destination range"). Each implementing issue verifies the behaviour live
and records the answer in `docs/drive.md` — ADR-0081 §5's "a documented
limitation, not a claim the tool cannot back up" — and either answer leaves
the gate where this section puts it.

A second live-verification item does not leave the gate where it is, and
its consequence is fixed here so that no implementing issue decides it:
whether `sortRange`, `randomizeRange`, `autoFill` or `textToColumns` moves
or writes cell **formatting** as a side effect of moving or writing values.
The API documents none of them as doing so, and §1 and §3 gate them on the
values-only reading; but the Sheets UI carries a row's formatting with it
when sorting and propagates a source cell's format when filling, and if
the API does the same then a `sheets-write` grant would change which
format sits in which cell — the guarantee §4 exists to keep. The rule:
**a verb live-verified to move or write formatting resolves both
`sheets-write` and `sheets-structure`, §4's composition, and the
implementing issue records the finding in `docs/drive.md` and the
`SheetsStructure` doc comment.** A verb verified values-only stays under
`sheets-write` alone. Either way the operator-facing guarantee is the
same: nothing gated on `sheets-write` alone changes a cell's format.

The formula question §3 raises alongside it — whether a `sortRange` or
`randomizeRange` moves a formula inside the range with its row, and
whether it rewrites the formula's relative references when it does — is
verified in the same pass (#1842, #1845) and recorded in `docs/drive.md`,
but it does not move the gate: whichever the answer, only cell content
changes, which `sheets-write` already covers. It fixes the wording of §6's
reordering caveat, nothing more.

### 6. `--dry-run` reports counts and locations, never contents, and names what the server decides

Every verb in this tranche gets a `--dry-run` sharing its real run's gate
classification by construction (ADR-0073 §9), and no verb gets a
confirmation flag (ADR-0075 §3, ADR-0070 §6). What the preview can say
falls into three tiers, and the ADR fixes which tier each verb is in so the
implementing issues do not each choose:

- **Computable from the request plus one bounded read** — the `copyPaste`,
  `cutPaste` and `pasteData` destination (and `cutPaste`'s source), the
  destination of an `autoFill` given as `sourceAndDestination` (source,
  dimension and `fillLength`, which the API allows to be negative, so the
  bounds check is two-sided like ADR-0077 §6's), and the range
  `trimWhitespace` acts on. The preview reads the affected cells — a
  `values.get`, or a `values.batchGet` for `cutPaste`'s two disjoint
  ranges, on top of the light `spreadsheets.get` every `GridRange`-based
  verb already needs for its `sheetId` (ADR-0075 §5; the same read
  `structure.rs`'s dry runs make) — and reports the **count and A1
  locations** of the non-blank cells that would be overwritten, or, for
  `trimWhitespace`, of the non-blank cells in the range any of which *may*
  change: predicting which ones *would* change means reproducing the
  server's trim rule locally, which is the "preview that lies" risk the
  `findReplace` bullet below refuses, so the preview does not try. In both
  the CLI output and the `drivemutation` record, and never a cell's value.
  A `copyPaste` or `pasteData` with a presentation-only paste type (§4's
  `sheets-structure` row) overwrites no value, so its preview reads no
  values and reports only the destination range, as `format-cells`' does;
  the non-blank count appears only when the paste type writes cell content.
  This is ADR-0081 §2's posture, chosen over `merge-cells`' value listing
  (ADR-0078 §4) deliberately: `merge-cells` remains the one preview that
  prints contents, and the "no cell content ever appears" line ADR-0077 §5
  drew for every other destructive preview is the one every new verb holds
  to. Two destinations are computable only as an upper bound — the API
  decides how many columns a `textToColumns` split needs, and for an
  `autoFill` given as a bare `range` it "will examine the range and detect
  the location that has data" itself, so which cells are source and which
  destination is server-detected — and their previews name the span the
  write may reach and report the non-blank count within it.
- **Nothing discarded** — `sortRange` and `randomizeRange` issue no read.
  The preview names the range and, for `sortRange`, the sort specs, and
  states the §3 caveat that references into the range from elsewhere will
  see reordered rows.
- **Server-decided** — the preview names every input the request carries
  and states plainly what it cannot compute, as ADR-0081 §5 does for a
  pivot table's extent:
  - `autoFill`: the destination is known or bounded (previewed under the
    first tier) but the *values* the server will generate are not — series
    detection and `useAlternateSeries` are the server's, so the preview
    says the fill's content is unknown until the request is sent.
  - `findReplace`: matching is by Java `Pattern` semantics with
    `matchCase`/`matchEntireCell`/`includeFormulas` modifiers, and a local
    emulation that disagreed with the server's would be a preview that
    lies. The preview names the scope, the search and replacement terms
    and every modifier, and states that the match count is
    server-computed; the real run reports the API's `FindReplaceResponse`
    (`valuesChanged`, `formulasChanged`, `rowsChanged`, `sheetsChanged`,
    `occurrencesChanged`) verbatim.
  - `deleteDuplicates`: the equality rule is documented in intent
    (case-, format- and formula-insensitive; hidden rows included; first
    instance kept; duplicates need not be adjacent) but reproducing it
    locally would mean guessing which rendering of each value the server
    compares — the same fidelity gap as `findReplace`, with a false
    preview costing a row rather than a match. The preview therefore names
    the range and the compared columns and states the rule as the API
    gives it, including that filtered-out rows are removed too, rather
    than a row list it cannot vouch for; the real run reports
    `duplicatesRemovedCount` and, being a `sheets-delete` verb, ADR-0077
    §5's fixed recovery line (Drive's version history is the only undo).

`trimWhitespace`'s real run reports the API's `cellsChangedCount`; the other
verbs in the first two tiers return no response object and report what they
sent, as the existing structural verbs do.

### 7. No new `DriveOperation` variant; typed verbs, no raw passthrough; the lease gate unchanged

Every verb in this tranche resolves to `SheetsWrite`, `SheetsStructure`,
`SheetsDelete`, or — for `PASTE_NORMAL`/`PASTE_NO_BORDERS` pastes and every
`cutPaste` — `SheetsWrite` and `SheetsStructure` together. Each is a typed
subcommand with typed arguments, following ADR-0075 §2 and ADR-0077 §3;
there is still no `batch-update --requests` passthrough, and this tranche
adds none. `SheetsProtection`'s binding clause and doc comment are untouched.

Every mutating verb here also passes through ADR-0080's backup-lease gate
exactly as `write.rs` and `structure.rs` do — `gate_optional_leased_write`
after the operation gate and before the request, the dry-run return before
both — with no verb exempt and no new lease semantics. `findReplace` with
`allSheets` and `includeFormulas` is the widest single write in the Drive
surface under a `sheets-write` grant, which changes neither gate but does
mean its `drivemutation` record and CLI output state the scope in full.

## Consequences

- **No new OAuth grant and no new trust boundary.** Every request in this
  tranche rides the Drive scopes already covered, unchanged since ADR-0073.
- **`sheets-write` grows in meaning, but bounded by what `clear` already
  permitted.** An operator who granted it before this ADR is exposed, once
  #1839–#1845 land, to pastes, fills, find/replace, sorts, splits and trims
  — every one of which can be expressed as a `clear` plus a `write` of the
  same range, which that grant already allowed. Nothing gated on
  `sheets-write` alone removes a cell from the grid or changes a cell's
  format — the second half held by §5's verification rule, which moves any
  verb found to touch formatting into the two-operation composition rather
  than leaving it under `sheets-write`.
- **`sheets-delete` gains its first server-selected removal.**
  `deleteDuplicates` (§2) is `delete-range`'s shape and joins the operation
  on that precedent, but it is the first verb under it whose removed cells
  are chosen by the server from the data rather than named by the caller,
  hidden rows included; #1844 extends the variant's doc comment and
  `docs/drive.md`'s `sheets-delete` row to say so.
- **The two-operation composition becomes a pattern, with an always-both
  case.** ADR-0081 §5 built `target_gate::resolve_all` for one verb; §4
  reuses it for `PASTE_NORMAL`/`PASTE_NO_BORDERS` pastes and for every
  `cutPaste`. Future hybrid capabilities have two worked examples of the
  symmetric shape to follow before proposing a new variant, and one example
  (`cutPaste`) of a verb whose *side effect* rather than its primary write
  is what earns the second operation.
- **Preview posture is now fixed for every value-mutating verb**: counts
  and A1 locations, never contents, with a named "server decides" caveat
  wherever the effect is not computable (§6). `merge-cells` stays the
  single content-printing exception rather than a precedent that spreads.
- **Four questions are deliberately left to live verification** — the
  grid-edge behaviour of each destination-writing verb (§5), whether any
  `sheets-write`-gated verb moves or writes cell formatting (§5, with its
  consequence fixed in advance), what a sort does with a formula inside
  the range (§3 and §5; caveat wording only, never the gate), and the
  practical fidelity of the upper-bound previews for `textToColumns` and
  `autoFill --range` (§6).
  Each is stated as a documented limitation to be closed by the
  implementing issue, not as a claim this ADR makes.
- **Two surface defaults are settled here so seven issues do not settle
  them seven ways**: `--paste-type` defaults to `normal` and `pasteData`
  ships `delimiter`-form only (§4); every verb takes ADR-0080's lease gate
  unchanged (§7). All seven verbs are CLI-surface changes and share
  `SheetsSubcommands` and the help snapshot, so #1830's two-at-a-time
  concurrency rule applies to the whole tranche.
- **Sync obligation, deferred to each implementing issue.** This ADR ships
  no code. `docs/drive.md`'s default-policy table and `sheets-write`/
  `sheets-delete` prose, and `src/drive/write_gate.rs`'s `SheetsWrite`/
  `SheetsStructure`/`SheetsDelete` doc comments, all need the new verb
  names and the §4 paste-type mapping added once #1839–#1845 land — the
  same deferral ADR-0081's Consequences record.
