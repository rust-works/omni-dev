# ADR-0097: Per-Pull-Request Changelog Fragments

## Status

✅ Accepted (2026-10-07, [#2213](https://github.com/rust-works/omni-dev/issues/2213)).
Supersedes the released-section guard of #2129 (`scripts/check_changelog.py`).

## Context

omni-dev keeps two Keep a Changelog files that release independently: `CHANGELOG.md` for
the crate (tags `vX.Y.Z`) and `editors/vscode/CHANGELOG.md` for the VS Code extension
(tags `vscode-vA.B.C`). Until this decision every pull request added its bullet at the top
of a `## [Unreleased]` section, which had two consequences.

- **Every pair of pull requests in flight conflicted.** They all edit the same hunk. With
  `main` behind a rebasing merge queue, a conflict means a rebase, a push and a re-enqueue,
  and `docs/RELEASE.md` documented that loop as routine.
- **A bullet could land in a released section.** A branch forked before a release adds its
  bullet under `[Unreleased]`; the release renames that heading; git then applies the
  branch's hunk inside the now-released section (#2129). `scripts/check_changelog.py`
  detected this after the fact, on the merge ref and the queue branch, by diffing the parsed
  sections, but could not prevent it.

Both have one root cause: a shared, positionally-addressed hunk. `rust-works/succinctly`
had the same problem and solved it with changelog fragments (its #3920).

## Decision

**Pull requests do not edit either changelog. Each adds its own fragment file; the release
assembles the fragments into the changelog.**

1. **Fragment layout.** `changelog.d/<id>.<type>[.<n>].md` for the crate and
   `changelog.d/vscode/<id>.<type>[.<n>].md` for the extension. `<id>` is the issue number
   or `+<slug>`; `<n>` disambiguates a second entry of the same id and type. The body is
   the entry exactly as it reads in the changelog: one or more bullets, continuation and
   nested lines indented, no heading, no blank lines.
   The extension's directory sits under the crate's rather than in `editors/vscode/`, so a
   fragment is not itself an `editors/vscode/**` change (which would trip the
   user-visible-change rule and the extension workflow's path filter) and needs no
   `.vscodeignore` entry to stay out of the `.vsix`. `changelog.d/` is in `Cargo.toml`'s
   `exclude`.
2. **Types are omni-dev's sections, in omni-dev's order:** `added`, `changed`, `deprecated`,
   `removed`, `fixed`, `security`, then `ci` (`### CI/CD`) and `docs`
   (`### Documentation`), the two extra sections recent releases already use after Keep a
   Changelog's six. succinctly's `performance` is not adopted: no omni-dev release has used
   it.
3. **One script, `scripts/changelog.py`, standard library only,** with three subcommands:
   `check` (every fragment's name, type and body, so a typo cannot silently drop an entry),
   `check-pr` (the pull-request rules below), and
   `collect --component crate|vscode --version X.Y.Z` (render the section, update the
   crate's compare links, delete the consumed fragments). The rendered format matches the
   hand-written one: `### Heading` with its bullets directly beneath, a blank line between
   sections, entries by ascending issue number with `+slug` entries last.
4. **The pull-request rules** (`check-pr`, judged from the merge base):
   - a fragment is required (added, edited or renamed into place);
   - a user-visible `editors/vscode/` change requires a fragment under
     `changelog.d/vscode/` (the visibility rules of #2129 are kept unchanged);
   - neither changelog may be edited directly, unless the pull request is a release.
   A **release** is recognised structurally, by the new `## [X.Y.Z]` section it adds to the
   changelog it releases, never by its title, so naming a pull request cannot skip the gate.
5. **Waivers stay commit trailers.** `Changelog: none <reason>` waives the fragment
   requirements; `Changelog: amend-released <reason>` waives the direct-edit rule, for the
   one legitimate direct edit left: correcting a published section. Both keep the
   meaning and the trailer-block parsing they had under #2129. A pull request opened by a
   bot (Dependabot) is waived.
6. **CI.** The workflow file, its name and its job name `Changelog` (a required context)
   are unchanged. On `merge_group` it runs the tests and `check`; `check-pr` runs on
   `pull_request` only, because which files a pull request adds is a property of the pull
   request that a queue rebase cannot change.
7. **Legacy text.** Each changelog's hand-written `[Unreleased]` text is carried into its
   next release verbatim, after the fragment sections, leaving `[Unreleased]` empty. It is
   not migrated into fragments.

## Consequences

- Two pull requests that each add a fragment touch disjoint files and cannot conflict on
  the changelog. A fragment cannot be applied into a released section, since there is no
  shared hunk to misapply, so the released-section guard and its similarity heuristics are
  deleted with `scripts/check_changelog.py`, along with the `--base vX.Y.Z` release audit
  that existed only to find such misapplied bullets.
- **Every pull request now needs a fragment or a `Changelog: none` trailer.** Before, only
  the extension entry was enforced and crate entries were routinely missed (release prep
  began by reconciling `[Unreleased]` against the log). Docs-, CI- and refactor-only pull
  requests pay one trailer line for that.
- The changelog is no longer readable on `main` between releases: the pending notes are
  files in `changelog.d/`, and `collect --dry-run` renders them.
- Entry order within a section is by issue number, not by when the bullet was written.
- The release commit is the only place a changelog is edited by hand. Reconciling against
  the commit log is still a release step, since a trailer can be wrong.
- A `Changelog: amend-released` trailer also satisfies the fragment requirement, since the
  correction is itself the changelog change; it therefore also waives the extension
  fragment for any extension change in the same pull request, which is a reason to keep
  such corrections in pull requests of their own.

## Alternatives considered

- **Keep `[Unreleased]` and a stronger guard.** Treats the symptom: the conflict on every
  pair of pull requests remains, and the guard can only reject after the merge ref is
  built.
- **A `merge=union` git attribute on the changelogs.** Removes the textual conflict but
  silently interleaves bullets and still applies a stale hunk inside a released section.
- **Generating the changelog from commit messages or pull request titles.** omni-dev's
  entries are prose with measured numbers and links, written for users; a commit subject is
  not that, and generated notes would need the same per-pull-request authoring step in a
  less reviewable place.
- **Extension fragments in `editors/vscode/changelog.d/`, or a name prefix
  (`vscode-2213.fixed.md`).** The first makes every fragment a user-visible-looking
  extension change and a packaging concern; the second complicates the name grammar for no
  gain over a directory.
- **A pull-request label or body marker as the waiver** (succinctly's choice). Commit
  trailers were already omni-dev's convention, survive into the merge queue and are part of
  the reviewed history; a body marker is not.
