# ADR-0055: Batch Worktree Rebase onto Remote Main, Fetch-Once-Per-Repository, CLI-Side

## Status

✅ Accepted (2026-07-24)

**Superseded in part by [ADR-0059](adr-0059.md) (2026-07-26), on *where* a batch
rebase runs.** The claim below that the daemon lacks `SSH_AUTH_SOCK` and so could
not authenticate a fetch is **wrong**: launchd exports it into the per-user
session, so a LaunchAgent inherits the user's `ssh-agent`. The daemon now hosts a
two-phase `rebase` op, and the extension drives that rather than a terminal.
Everything else decided here — reads via git2 and the two mutations via the user's
`git` (§1), fetch-once-per-repository (§2), the selection rules (§3), the dirty
and conflict handling (§4, with conflicts now optionally left in place), and
confirm-by-default (§5) — is unchanged and still governs. The affected passages
below are marked inline.

**Superseded in part by [ADR-0060](adr-0060.md) (2026-07-28), on *whether* the
main working tree is a valid rebase target.** §3's claim that the main tree is
never rebased no longer holds: it is now classified — and, if eligible, rebased —
exactly like any other worktree, and `--all` now includes it alongside every
linked worktree. Everything else §3 decided (selection is explicit; the main
tree is identified by the structural `is_main` fact, never a branch-name
heuristic) is unchanged. The affected passage is marked inline.

## Context

The `worktrees` daemon service ([ADR-0040](adr-0040.md), [ADR-0048](adr-0048.md),
[ADR-0049](adr-0049.md)) tracks every repo + worktree open across all VS Code
windows and reports each worktree's divergence from its upstream (the
`ahead-behind` op). But keeping a fan-out of per-issue feature worktrees current
with `main` is still a manual, per-worktree chore: `cd` into each one, `git fetch`,
`git rebase origin/main`, resolve, repeat.

Issue #1400 asks for one command that rebases many worktrees onto the repository's
remote default branch. Its load-bearing requirement is that the remote default
branch is **fetched exactly once per repository, up front** — never once per
worktree. Two facts make that both natural and necessary:

1. **Linked worktrees share one object database.** A single
   `git fetch <remote> <branch>` updates the `refs/remotes/<remote>/<branch>`
   tracking ref that *every* worktree of that repo already sees. So one fetch pins
   the ref all worktrees rebase onto.
2. **Re-fetching per worktree is wasteful and *incorrect*.** N worktrees would mean
   N network round-trips, and if `origin/main` advances between fetches, different
   worktrees rebase onto **different** tips and stop sharing a base. A batch rebase
   must pin every worktree to one snapshot of `main`.

The open design question the issue itself raised was **where** this runs: a daemon
op (so the tray could offer "rebase all"), or a pure CLI-side operation. Research
made the answer decisive rather than a matter of taste:

- **git2 cannot fetch this project's remotes.** The vendored `libgit2` is built
  without a reliable SSH transport (no `libssh2`), and the repositories are cloned
  over SSH (`git@github.com:…`). A `git2` `Remote::fetch` would fail outright. This
  is exactly the constraint [ADR-0003](adr-0003.md) ("git2 for Reads, Shell for
  Complex Mutations") already codifies: remote/network mutations shell out to the
  user's `git` (see `GitRepository::run_git`, `push_branch`), so they work across
  SSH/HTTPS and honour the user's `ssh-agent` / `~/.ssh/config` / credential
  helpers (issue #903).
- **The daemon has no credential context.** It is spawned by launchd/systemd with a
  minimal environment that lacks the user's `SSH_AUTH_SOCK` and credential helpers —
  the same minimal-`PATH` problem [ADR-0049](adr-0049.md) §3 cites for the `code`
  launcher. A fetch initiated *from the daemon* could not authenticate to an SSH
  remote regardless of whether it used git2 or a shell-out.

  > **Wrong — corrected by [ADR-0059](adr-0059.md).** launchd exports
  > `SSH_AUTH_SOCK` into the per-user session, so a LaunchAgent inherits it
  > (`ps eww` on the resident daemon shows it, and a fetch under exactly that
  > reconstructed environment succeeds). Only the **`PATH`** half of this bullet
  > was true, and it is a binary-resolution problem — solved by
  > `resolve_git_binary()`, the twin of `resolve_gh_binary`.
- **`git rebase` is the right rebase engine.** ADR-0003 already notes libgit2's
  rebase API is too low-level; shelling out gets full conflict handling, hooks,
  rerere, and `--autostash` for free, and matches user expectations exactly.

A rebase rewrites branch history, so — like `close` — it is a mutating operation
beyond the read-only views, and [ADR-0027](adr-0027.md) ("Destructive CLI Commands
Confirm by Default") applies.

## Decision

Ship `omni-dev worktrees rebase` as a **pure CLI-side** command. It adds **no**
daemon op, no control-socket message, no protocol change — the `worktrees` daemon
service is untouched. The git work lives in a new engine module
`src/git/worktree_rebase.rs`; the thin CLI subcommand in `src/cli/worktrees.rs`
parses, confirms, and renders.

```
omni-dev worktrees rebase [<PATH>...] [--all] [--onto <ref>] \
                          [--autostash] [--dry-run] [-y|--yes] [-o table|json]
```

### 1. Reads via git2, the two mutations via the user's `git`

Per ADR-0003: enumerating the worktrees, resolving the onto ref, and classifying
each worktree (structural `is_main`, detached HEAD, repo state, dirty tracked
files, and behind-count via `graph_ahead_behind`) are `git2` reads. The **fetch**
and the **rebase** shell out to `git` through an `env_clear` + `envs` snapshot seam
(the #1022 race-safe idiom), so they run in the CLI process with the user's full
credential environment.

### 2. Fetch once per repository, up front

The selected worktrees are grouped by their shared repository root; the onto ref is
resolved and fetched **once per distinct repository** before any rebase. A repo
whose fetch fails has all its worktrees reported `fetch-failed`; other repositories
continue. A `--onto <remote>/<branch>` value is still fetched once; a local ref or
raw commit is used verbatim with no fetch. The one-entry-per-repository grouping is
a pure, unit-tested function — the fetch-once invariant is asserted directly (N
worktrees of one repo ⇒ exactly one fetch).

### 3. Selection is explicit; the main tree is never rebased

`--all` targets every **linked** worktree of the current repository; explicit
`<PATH>...` targets exactly those. A bare invocation with neither is a usage error,
not a silent mass-rebase. The main working tree is skipped on the structural
`is_main` fact (`!repo.is_worktree()`), never a branch-name heuristic — the same
guard `close` uses (ADR-0049) — so a linked worktree that happens to be on the
default branch is still eligible.

> **Reversed by [ADR-0060](adr-0060.md).** "Never rebased" was a default, not a
> structural necessity: `--all` now targets every worktree of the repository,
> main included, and the main tree is classified — and, if eligible, rebased —
> exactly like a linked one. The structural `is_main` fact is unchanged; only
> what happens once it's identified changed.

### 4. Dirty worktrees are refused by default; conflicts abort and report

A worktree with uncommitted changes to tracked files is skipped with a reason and
the batch continues; `--autostash` opts into stashing around the rebase instead. A
rebase that hits conflicts is `git rebase --abort`-ed so the worktree is left
**exactly as it was** and reported as `conflict` — never a silent half-rebased
state — and the batch continues for the rest. An in-progress rebase/merge (repo
state not `Clean`) is skipped, as is a detached HEAD.

### 5. Confirm by default; `--dry-run` previews

Because a rebase rewrites history, the command lists what it will do and confirms
before executing, unless `-y/--yes` is given (ADR-0027; matching the sibling
`worktrees close` CLI surface). `--dry-run` reports the plan and rebases nothing.
The fetch still happens under `--dry-run` — it is non-destructive (it only advances
the shared remote-tracking ref) and is what makes the behind-count preview accurate
and pins the snapshot; only the history-rewriting rebase is gated by the confirm.

## Consequences

- **A history-rewriting capability, but same-user-bounded and CLI-local.** Like
  `close`, this mutates beyond the read-only views. Unlike `close`, it never
  crosses the daemon's `0600` socket — it runs in the invoking user's shell with
  their credentials. (Still true of *this command*; since
  [ADR-0059](adr-0059.md) the same engine is also reachable over the socket via the
  `rebase` op.) It rewrites only branches the user names (or `--all` of their
  own repo's worktrees — main working tree included since
  [ADR-0060](adr-0060.md)), ~~refuses the main working tree defensively~~, and
  refuses/aborts rather than leaving a worktree in a dirty or half-rebased state.
  **Superseded by [ADR-0060](adr-0060.md):** the main working tree is now
  classified — and, if eligible, rebased — exactly like any other worktree.
- **The one `worktrees` subcommand that does not use the daemon.** Every other
  `worktrees` subcommand is a thin daemon client; `rebase` is deliberately local so
  it can authenticate to the remote and so it works even when the daemon is not
  running. (Since [ADR-0059](adr-0059.md), only the second half of that reason
  stands — the daemon can authenticate too.) The global `-C/--repo` flag is threaded in (resolved once in the CLI
  boundary), so nothing re-reads the ambient CWD.
- **No new dependency, no widened trust boundary.** Following ADR-0003's shell-out
  path avoids pulling `libssh2`/`openssl` into the build (a surface this project has
  deliberately kept minimal). No secret is read or persisted; the fetch relies
  entirely on the user's ambient `git` configuration.
- ~~**Tray "rebase all" is out of scope, and blocked for a concrete reason.** A
  daemon-hosted or tray-initiated rebase would fetch from the daemon's minimal
  environment, which lacks `SSH_AUTH_SOCK`, so it could not authenticate to an SSH
  remote. Revisiting a daemon op is a follow-up gated on solving that credential
  problem — not a v1 omission.~~
  **Superseded by [ADR-0059](adr-0059.md):** the credential premise was wrong, and
  the `worktrees` service now hosts a two-phase `rebase` op.
- ~~**A UI entry point is fine as long as it spawns this CLI, not a daemon op.** The
  companion extension's **Rebase on main** row action (#1409) shells out to
  `omni-dev worktrees rebase <paths> -y` in a VS Code integrated terminal — the
  user's own shell, and so their own credentials — after confirming with a modal
  that lists every branch it would rewrite.~~
  **Superseded by [ADR-0059](adr-0059.md):** the row action is a socket client like
  every other one, with no terminal. The CLI keeps its local engine so a batch
  rebase still works with no daemon running — now a choice rather than a necessity.
- **Sequential rebases; further ergonomics are follow-ups.** Rebases run one at a
  time for deterministic output and to avoid contention on the shared object
  database. Parallel rebase and consulting the daemon inventory to warn when a
  target worktree is open in a live window are possible follow-ups.
  (`--keep-conflicts`, which leaves a conflicted worktree mid-rebase for manual
  resolution, shipped in [ADR-0059](adr-0059.md).)
