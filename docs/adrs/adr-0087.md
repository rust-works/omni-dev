# ADR-0087: Codex as a Second Hook Feed of the Agent-Tagged Sessions Service

## Status

✅ Accepted (2026-09-25, implemented in #1907; proposed 2026-09-22, revised 2026-09-24 to build on #1901's `agent` tag)

Amends [ADR-0052](adr-0052.md), whose title and contract assume every tracked
session is a Claude Code session. Builds on #1901 (PR #1902), which already made
the agent a tag on every session for pi.dev.

## Context

The sessions service ([ADR-0052](adr-0052.md), [ADR-0057](adr-0057.md)) tracks
Claude Code sessions across every terminal and VS Code window. Codex (the OpenAI
CLI, its VS Code extension and the Codex Desktop app) now ships lifecycle hooks
whose stdin payload uses the same field names as Claude Code's — `session_id`,
`cwd`, `hook_event_name`, `model`, `transcript_path` — read from the same
`{ "hooks": { "<Event>": [ { "matcher"?, "hooks": [ … ] } ] } }` shape, in
`~/.codex/hooks.json`.

Issue #1861 asked whether those hooks can feed the existing service. The
investigation ([docs/plan/codex-sessions-feed.md](../plan/codex-sessions-feed.md))
found that they already do, by accident: pointing Codex's hooks at
`omni-dev sessions hook` makes Codex sessions appear in the registry, but as
Claude sessions, because nothing on the wire says otherwise, and because the sink
drops the two Codex-only events — `PermissionRequest` and `Interrupt` — that carry
the most useful state. Tested on `codex-cli 0.155.1`, the VS Code extension and
Codex Desktop, which fire the same events for the same scenarios:

- `PermissionRequest` is the one reliable "waiting on the user" signal; its
  resolution is inferred from the next `PostToolUse` (granted) or from the turn
  ending without one — `Interrupt` in the TUI, `Stop` in VS Code (denied).
  Automatic review ("Approve for me" / `--approve-for-me`) fires it too and
  resolves it seconds later, so a brief false "waiting" cue is unavoidable.
- `Interrupt` fires for Esc and Ctrl-C mid-turn and for the TUI's declined
  approval; `Stop` does not fire in any of those cases.
- `request_user_input` — the clarifying-question UI — is an ordinary
  `PreToolUse` with that `tool_name`, resolved by its `PostToolUse`. Desktop
  offers it by default; the TUI only behind a still-under-development feature.
- Subagents never create a session: `SubagentStart`/`SubagentStop` and the
  child's tool calls all carry the parent's `session_id`.
- `resume` reuses the session id with `SessionStart.source = "resume"`; `/new`
  opens a new id and the old thread's `SessionEnd` arrives only at exit.
- A signalled process (SIGHUP, SIGTERM, SIGKILL) fires no `SessionEnd`, and the
  documented 30-minute idle end did not fire in 32 minutes; the surface (CLI /
  IDE / Desktop) is not in the payload but is in the rollout file's head
  `session_meta.originator`.

Since the investigation, #1901 added pi.dev as a fifth feed and with it an
`agent` tag on `ObserveRequest` and `SessionEntry` (`claude` by default and
omitted on the wire, or `pi`), set by a session's first sighting and never
changed, plus an `AGENT` column in `omni-dev sessions list`. It kept the registry
keyed by `session_id` alone. Codex's session ids are UUID v7, like pi's.

Codex trusts a hook by **position and content**: `~/.codex/config.toml` stores a
`trusted_hash` under `[hooks.state."<hooks.json path>:<event>:<group>:<hook>"]`
(#1868 found the path half for project hooks). Verified on 0.155.1 with two
trusted groups A and B on one event: removing A shifted B to index 0 and B
silently stopped running; appending a third group left A and B running (the new
one is skipped until trusted); and replacing A with an empty `{ "hooks": [] }`
group kept B trusted and running. Changing a command string changes its hash
and likewise untrusts it.

Alternatives considered: the Codex **App Server** exposes exact thread status
(`activeFlags` `waitingOnApproval` / `waitingOnUserInput`), but the VS Code
extension and Desktop each run a *private* stdio app-server that no outside
process can reach, the shared daemon is opt-in, and prior art (codex-agents)
reports that subscribing to a thread duplicates its approval requests to every
client — so only `thread/list` polling is safe, and only for servers omni-dev can
reach. Screen scraping (Herdr) is the terminal-only authority and does not apply
to IDE or Desktop chats. Neither replaces hooks as the cross-surface feed.

## Decision

We will add Codex as a third agent of the existing sessions service and a second
hook feed of its engine, rather than a second service or a Codex-specific
registry, reusing #1901's `agent` tag instead of introducing a parallel
"provider" dimension.

- We will add `Agent::Codex` (`"codex"` on the wire). The omitted-means-`claude`
  rule is unchanged, so every existing sink, client and daemon keeps
  interoperating. The registry stays keyed by `session_id` alone and the tray
  action id stays `focus:<session_id>`. The version-nibble argument #1901 relied
  on no longer separates every pair (pi and Codex are both v7), so the `Agent`
  doc comment will rest single-key identity on v7's 74 random bits instead: a
  collision is improbable, not impossible, and not worth a re-key.
- We will extend `omni-dev sessions hook` with `--agent codex` and map Codex
  events onto the **existing** `SessionEvent`s so the engine's state machine is
  untouched: `PermissionRequest` → `Notification(PermissionPrompt)`;
  `PreToolUse` with `tool_name == "request_user_input"` →
  `Notification(AgentNeedsInput)`; `Interrupt` → `Stop`; `SubagentStart` →
  `PostToolUse`; `SubagentStop`, `PreCompact` and `PostCompact` → the
  state-preserving `TranscriptDiscovered` sighting (#1928: each can fire on an
  idle session — `/compact` is captured as `Stop · PreCompact · PostCompact` — and
  nothing afterwards would release a `working`; the thread lock, not a heartbeat,
  keeps an idle Codex session alive); the six shared names → themselves.
  The sink stays fail-open, exits 0 and writes nothing to stdout, which is a no-op
  for every Codex event including `PermissionRequest`.
- We will have `install-hooks` also install into `$CODEX_HOME/hooks.json`
  (default `~/.codex/hooks.json`) when Codex is present — its home directory
  exists or `codex` is on `PATH` — with `--codex-home` to force it, the pattern
  #1901 set for pi. The file has the same shape as Claude's `hooks` object, so
  the JSON merge helpers are reused. Entries get `timeout: 3` on `SessionEnd` and
  `Interrupt` (Codex caps those at 3 s). Because the agent tag is fixed by a
  session's first sighting, install **replaces** any untagged
  `omni-dev sessions hook` command already in that file, which would otherwise
  race the tagged one and could label the session `claude` for good.
- We will keep install and uninstall position-stable for Codex, so that neither
  ever untrusts a hook the user owns: install appends new groups and replaces an
  untagged sink entry in place; uninstall removes only our hooks and, where that
  empties a group that is not last in its event, leaves an empty
  `{ "hooks": [] }` group in its place instead of dropping it. Both commands
  print the one-time `/hooks` trust step, because an untrusted hook is skipped
  without a message.
- We will label the agent everywhere a session is shown that #1901 did not
  reach — the tray (whose "Claude Sessions" title already misdescribes pi), the
  VS Code tooltip and model family, the TUI summary — and leave the state glyphs
  and colours state-driven.
- We will keep `Source` as it is: the `cwd` join already places an IDE Codex
  session on its window. A Codex rollout watcher (the Feed 2 twin, which can
  decode `cwd`, surface and subagent-ness from `session_meta`) and an App Server
  observer for sessions omni-dev itself launches are recorded as follow-ups, not
  part of this decision.

## Consequences

**Positive.** Codex sessions show on the correct worktree row with the same
working / idle / waiting cues as Claude's, with `waiting_for_permission` driven by
a dedicated event rather than a message-text heuristic. No new op, service, trust
boundary or persisted secret: the feed rides the daemon's `0600` socket and the
sink still writes only the socket POST. The wire change is one new enum value on
an existing additive field, and no registry re-key is needed.

**Negative.** Hooks remain an inference feed: approval *resolution* is read off
the next tool event, automatic review flashes a false "waiting" for a few seconds,
a signalled or idle-abandoned process ages out on the TTL, and `waiting_for_input`
in the TUI depends on a feature Codex has not shipped by default. Users must
complete the `/hooks` trust step by hand, again whenever the installed command
string changes. `hooks.json` accumulates empty placeholder groups across
install/uninstall cycles; they are inert, and a user can drop them (and re-trust
what follows) by hand. Version skew is uneven: a daemon predating #1901 ignores the
field and shows Codex sessions as Claude's, but one with #1901's two-value
`Agent` fails to deserialise `"codex"`, so the fail-open sink silently drops
Codex sessions until the daemon is upgraded.

**Neutral.** ADR-0052's "Claude Code sessions" framing is now historical — the
service tracks agent sessions and the `agent` tag says which. The Codex feed is
opt-in like the Claude one. Trust is per hook entry in the one `~/.codex` store,
not per surface, so one CLI approval covers the extension and Desktop.

## Addendum: a hook-less session's turn state from its rollout (#2135)

The rollout watcher (#1909) was specified to read only a rollout's first line and
never to report a state, on the grounds that growth is not evidence of a turn: a
rollout keeps being written around a turn's `Stop`. That left a Codex session with
**no hook feed** (started before the hooks were installed and trusted; Codex skips
an untrusted hook silently) reading `idle` for good, even mid-turn.

**The contract change.** The watcher now also reads a bounded tail of the rollout
for its last turn marker: an `event_msg` whose `payload.type` is `task_started`
(open) or `task_complete` / `turn_aborted` (closed). Reading the tail is the
version-sensitive part of the file, so the read is schema-tolerant, keyed on those
`type` strings alone; a line that does not parse as such, a truncated tail and a
marker beyond the widest window (256 KiB, widened fourfold to 4 MiB, because one
line of tool output can run to several MiB) all change nothing. Only the marker's
kind leaves the read, and nothing is logged. The first-line-only and
no-conversation-content guarantees become "no conversation content is kept or
logged".

**The rule.** Only the *last* marker is evidence, never the counts: a measured
corpus of 784 rollouts held two turns left open by a crash and several with an
extra completion. And the marker is evidence only **while the thread lock is
held**, since a free lock means the session is gone whatever the marker says and a
Codex without locks makes no claim.

**It must not override a hook.** The report is a new passive `SessionEvent`,
`RolloutTurn(Open | Closed)`, that follows `TranscriptGrew`'s rule: an open turn
reads `working` unless a `starting`, `waiting_for_*` or `ended` state is held, and
a closed one moves `working` to `idle` and nothing else, so a reported wait is
neither overridden nor released (ADR-0052's reliable-over-inferred ordering). The
rule is deliberately asymmetric: an open turn starts `working` only from an `idle`
that nobody reported (the registry tracks whether the current state was asserted
by a hook or the wrapper, because `last_event` cannot say: the watcher's own
heartbeat overwrites it), since the marker can trail a `Stop` hook by a scan; a
closed turn may end any `working`, which also heals a `Stop` that never arrived.
The wrapper's authoritative `StreamState` is applied verbatim and re-asserted on
every poll, so it keeps the last word. Three details keep it from racing a hook:

- **It reports a change, not a level.** A level re-asserted each scan would read a
  session back to `idle` whenever a hook (`UserPromptSubmit`) lands before Codex
  has flushed `task_started`. The tail is re-read only when the rollout's size has
  changed.
- **The first read is asymmetric.** An open turn is reported; a closed one is only
  recorded, so a first sighting cannot say `idle` over a state a hook reported.
- **A stale open turn is not claimed.** An open marker in a rollout not written to
  within five minutes is ambiguous between a long silent turn and a crash, and
  `codex resume` of a crashed turn holds the lock again. Such a marker, and the
  one a session was ended in, are remembered by the byte offset of their line, and
  only a newer `task_started` is claimed; writing around the old marker is not
  evidence of a turn.

**Residual limits.** A turn shorter than the 5-second scan, or with its marker
beyond the tail, is missed and the session stays `idle`, as before; growth alone
is not taken as a turn, because that is the inference #1909 rejected. A turn that
is silent for five minutes when the daemon first sees it is not claimed either.
A wait a hook reported is released only by a hook, so an untrusted `Interrupt`
leaves a denied approval showing as waiting. None is a regression. No new trust
boundary, op or persisted state: the watcher already read this file, and the
change is one more field of it. The operator contract is in
[docs/sessions-service.md](../sessions-service.md#codex-hooks-feed-6).
