# ADR-0066: A Gmail-Specific Named-Account Store, Orthogonal to `--profile`

## Status

✅ Accepted (2026-08-05)

Extends [ADR-0063](adr-0063.md) (Gmail OAuth2 credential storage) without
amending it; is a sibling design to, and explicitly does not reuse,
[ADR-0045](adr-0045.md) (profile isolation).

## Context

`omni-dev gmail` authenticates against exactly one mailbox at a time.
Credentials (`GMAIL_CLIENT_ID`/`GMAIL_CLIENT_SECRET`/`GMAIL_REFRESH_TOKEN`/
`GMAIL_SCOPE`) are written by `gmail auth login` through
`Settings::upsert_env_vars_in` (`src/utils/settings.rs`) into either the base
`env` map of `~/.omni-dev/settings.json` or, when `--profile`/
`OMNI_DEV_PROFILE` selects one, that profile's isolated `env` map — the exact
mechanism [ADR-0045](adr-0045.md) built for multi-tenant credentials in
general, and which ADR-0063 deliberately reused rather than inventing new
storage.

That reuse now runs out of headroom. Two mailboxes side by side means one of:

1. Re-running `gmail auth login`, which overwrites the current bucket's
   refresh token — the other account's session is gone.
2. Using a second `--profile`, which is [ADR-0045](adr-0045.md)'s
   **isolation** decision working exactly as designed: an active profile's
   `env` map replaces the base `env` map wholesale, for every backend at
   once. That is the correct behavior for "I am a different tenant right
   now" (a different Atlassian site, a different Datadog org, a different
   Gmail account, all together) — the scenario ADR-0045 was written for. It
   is the wrong behavior for "I just want a second mailbox while everything
   else about my environment stays the same": picking a Gmail account by
   `--profile` would force duplicating every unrelated credential (Atlassian
   token, Datadog key, Claude API key, …) into a profile that exists only to
   carry a second `GMAIL_REFRESH_TOKEN`.

There is also no way for the MCP server (`src/mcp/gmail_tools.rs`) to
address more than one mailbox at all — every tool call resolves credentials
once, with no account parameter, and an MCP client cannot pass `--profile`
per call the way a CLI invocation can pass a global flag.

The two axes — "which tenant's whole environment" (`--profile`) and "which
Gmail mailbox" (this ADR) — are conceptually independent and need to compose
independently: switching Gmail mailboxes must never disturb which Atlassian
site or Datadog org is active, and vice versa. `--profile`'s isolation
semantics cannot be parameterized to deliver that; the two need separate
storage.

## Decision

### 1. A new top-level `gmail` settings block, sibling to `env`/`profiles`/`mcp`

We will add `gmail: { default_account, accounts: { <name>: {...} } }` to
`~/.omni-dev/settings.json`, read through new `GmailSettings`/
`GmailAccountSettings` structs on `Settings` (`src/utils/settings.rs`),
mirroring the existing `McpSettings` read-only-struct precedent combined
with the `HashMap<String, Profile>` shape `Settings.profiles` already uses.
It is **not** nested under `profiles.<name>` — switching `--profile` never
changes which Gmail accounts exist, and choosing a Gmail account never
changes which profile is active. Each account entry stores `client_id`,
`client_secret`, `refresh_token`, `scope`, and an optional `email_address`
(display-only, populated opportunistically by `gmail auth status`, never
used for auth or written by `login`/`import`).

The write side reuses [ADR-0063](adr-0063.md)'s existing hardened path
rather than duplicating it: the two-level path walkers backing
`Settings::upsert_env_vars_in`/`remove_env_vars_in` generalize to an
arbitrary path-segment slice, so the new `upsert_gmail_account`/
`remove_gmail_account`/`set_gmail_default_account` helpers go through the
same `write_settings` (0700 directory, 0600 file, unknown-fields-preserved
`serde_json::Value` round-trip) with no new file-handling code.

### 2. Resolution: explicit account, then default, then a zero-migration Legacy fallback

A new `--account NAME` CLI flag / `OMNI_DEV_GMAIL_ACCOUNT` env var selects
an account per invocation, AWS-CLI style — the same shape `--profile`/
`--instance` already establish in `src/cli.rs`, propagated to its own env
var so the two selectors never collide. Unlike `--profile`/`--instance`,
`--account` is **not** a CLI-wide global on the root `Cli` struct — it is
`global = true` scoped to `GmailCommand` (`src/cli/gmail.rs`), so it is
inherited by every `gmail` subcommand (usable before or after the leaf
subcommand name, within the `gmail` subtree) but by nothing outside it.
This was a deliberate correction during implementation: clap rejects two
args on the *same* command sharing a long flag string, and a CLI-wide
global is inherited by literally every subcommand — including Snowflake's
pre-existing, unrelated `snowflake query/cancel/disconnect --account`
(a Snowflake account identifier). Scoping the flag to where it's actually
meaningful avoids colonizing a word another subsystem already owned, at the
minor cost that `--account` isn't usable before the `gmail` subcommand name
the way `--profile` is. Precedence, in `src/gmail/account.rs::resolve_account`:

1. A literal `GMAIL_CLIENT_ID`/`GMAIL_CLIENT_SECRET`/`GMAIL_REFRESH_TOKEN`
   set directly in the **process environment** bypasses account resolution
   entirely — today's exact behavior, unchanged, and still the
   CI/script-friendly escape hatch.
2. `--account`/`OMNI_DEV_GMAIL_ACCOUNT` set → the named
   `gmail.accounts.<name>`; an unknown name is a hard error listing the
   configured accounts, mirroring `Settings::validate_profile`'s exact
   message convention.
3. No explicit account, `gmail.accounts` non-empty → `default_account` if
   still valid, else the sole configured account, else a hard error naming
   both remedies (`--account` or `gmail account set-default`).
4. `gmail.accounts` empty → falls through **unchanged** to today's exact
   resolution (process env → active `--profile` env → base env). This is
   the zero-migration guarantee: a single-account setup that never touches
   the new commands behaves identically forever.

We deliberately chose isolation, not merge, for rule 4 as well as rule 2 —
once any named account exists, a no-`--account` invocation resolves through
rules 2–3 only, never silently falling back to legacy credentials. The one
sharp edge that follows — the first `gmail auth login --account NAME` or
`gmail account import-legacy` transitions the store from empty to
non-empty, which shadows any un-migrated legacy credentials for future
no-`--account` invocations — is handled with a one-time stderr notice at
the transition point (pointing at `gmail account import-legacy` /
`gmail auth logout`) rather than a silent auto-migration, matching the
"fail loud, not silent-wrong-tenant" taste [ADR-0045](adr-0045.md) already
established for profile resolution.

### 3. New `gmail account` command tree; MCP tools gain an optional `account` parameter

`gmail account list` (settings.json only, no network, no secrets rendered),
`gmail account set-default <name>`, and
`gmail account import-legacy [--name NAME] [--remove-legacy]` (migrates
today's legacy credentials into a named account; non-destructive unless
`--remove-legacy` is passed) round out the CLI surface. `import-legacy`
takes `--name`, not `--account`, since `--account` is inherited (per
Decision 2's `GmailCommand`-scoped `global = true`) by every command in the
`gmail` subtree, `import-legacy` included, and clap rejects a subcommand
redefining an inherited flag — the two mean different things here anyway
(`--account` selects an existing account; this names the one being
created). `gmail auth status` gains `--all` to report every configured
account in one call.

Each of the five existing Gmail MCP tools gains an optional `account`
string parameter threaded through the same resolution path (explicit param,
then env/default/sole/legacy fallback — an MCP server process has no CLI
flag of its own, but can be launched with `OMNI_DEV_GMAIL_ACCOUNT` pinned).
A new `gmail_account_list` tool is added so an LLM client can discover
account names before calling the others with a specific `account` — the one
place this design adds new tool surface rather than only a parameter.
`gmail auth login`/`gmail account set-default`/`gmail account import-legacy`
stay CLI-only, consistent with [ADR-0063](adr-0063.md)'s decision that the
interactive login flow has no MCP equivalent.

## Consequences

- **Two independent multi-tenancy axes now exist by design, not by
  accident.** `--profile` continues to mean "which tenant's whole
  environment"; `--account` means "which Gmail mailbox, everything else
  held constant." A reviewer's first question — "why not just another
  profile?" — is answered structurally: profile switching was never meant
  to be cheap per-backend, and forcing Gmail through it would mean
  duplicating every unrelated credential for no benefit.
- **No new storage or permission model.** The new `gmail` block rides the
  same `write_settings` hardening (0700/0600) and unknown-field-preserving
  round-trip every other settings write already uses; multiple refresh
  tokens now live side by side in one file with the same trust posture as
  today, not a new one. `client_secret`/`refresh_token` stay `Secret`-wrapped
  in memory the moment they are read, inheriting [ADR-0043](adr-0043.md)'s
  redaction guarantee identically to the single-account path.
  `gmail account list` and the `gmail_account_list` tool render name/email/
  scope/default only, never secrets.
- **Zero-migration guarantee for existing single-account users.** An
  installation that never configures a named account sees no behavior
  change, ever — enforced by a regression test pinning byte-identical
  credential resolution and writes when `gmail.accounts` stays empty.
- **A deliberate, documented sharp edge.** The empty→non-empty transition
  shadows legacy credentials for no-`--account` callers. This is
  communicated via a one-time stderr notice at the transition, not
  auto-migrated, so a user is never silently left wondering which mailbox a
  bare `omni-dev gmail search` just queried.
- **Explicitly out of scope.** Cross-account fan-out (one command querying
  multiple accounts at once) is deferred — nothing in this shape precludes
  it later, since each account already resolves to an independent
  `GmailClient`, but it is not needed for per-command selection. A distinct
  `gmail account remove` command is also deferred in favor of extending
  `gmail auth logout --account NAME`. OS keyring storage for refresh tokens
  remains future/ADR-sized work, unchanged from [ADR-0063](adr-0063.md)'s
  own out-of-scope note.
- **Sync obligation.** `docs/gmail.md`'s Authentication section must gain a
  "Multiple accounts" subsection describing `--account`/
  `OMNI_DEV_GMAIL_ACCOUNT`, the `gmail account` commands, the shadowing
  notice, and the settings.json `gmail` block shape. Keep it in sync when
  this ADR's resolution precedence or storage shape changes.
