# ADR-0067: Automatic Chrome-Profile Resolution for Gmail Login, Opt-In Per Account

## Status

✅ Accepted (2026-08-06)

Builds on [ADR-0066](adr-0066.md) (Gmail named accounts) without amending
it — that ADR is scoped to the account *store*/selection axis, while this
one is scoped to a single account-level behavior of `gmail auth login`
(where it opens a browser), so it stands alone rather than folding in.

## Context

With several named Gmail accounts (issue #1500, [ADR-0066](adr-0066.md)),
each usually corresponds to a different local Chrome profile signed into
a different Google identity. `gmail auth login` always opened the OS
default browser (`BrowserConfig::default()`, hardcoded in `run_login`,
`src/cli/gmail/auth.rs`), so every login landed in whatever profile the
default browser happened to be on. The user then had to manually switch
Google identities on the consent screen — easy to get wrong, and it could
land the refresh token on the wrong mailbox entirely.

Two pieces already existed but weren't connected:

1. `BrowserLaunch::Command(Vec<String>)` (`src/gmail/auth.rs`) runs an
   arbitrary `{url}`-templated command to open the authorization URL — its
   own doc comment already gave "target a specific Chrome profile" as the
   motivating example.
2. `GmailAccountSettings.email_address` (`src/utils/settings.rs`) was
   write-only: populated opportunistically by `gmail auth status` after a
   successful login, documented as "never used for authentication."

Snowflake's external-browser SSO (`crate::snowflake`, #1229) already reads
a user-supplied browser command from settings/env
(`SNOWFLAKE_BROWSER_COMMAND`) and feeds it into the identical
`BrowserLaunch::Command` shape — a directly reusable precedent for the
manual half of this design, though not (per that type's own doc comment)
for sharing the `BrowserLaunch` enum itself.

Two requirements shaped the decision, given directly during scoping
(issue #1505):

- **Opt-in per account, never inferred.** Automatically launching a
  specific Chrome profile just because `email_address` happens to be set
  would surprise a user who set it only for display, or before this
  feature existed. It must be a separate, explicit choice.
- **Chrome-only for v1.** The manual escape hatch (below) already covers
  every other browser; building bespoke profile-detection for
  Chromium/Brave/Edge's forks of the same `Local State` format is
  deferred until there's real demand.

## Decision

### 1. Two new opt-in fields on `GmailAccountSettings`

`chrome_profile_from_email: bool` (default `false`) and
`browser_command: Option<String>`, both `#[serde(default)]` like every
existing field, so they round-trip through `Settings::upsert_gmail_account`
(`src/utils/settings.rs`) with no schema-version bump. `email_address` may
now be set by hand ahead of the first login (not only backfilled by
`gmail auth status`), and an explicit value is never overwritten by that
backfill (`record_account_email`, `src/gmail/auth.rs`).

### 2. `browser_command` — the manual escape hatch, promoted tokenizer

A per-account `browser_command` becomes `BrowserLaunch::Command`, parsed by
the same POSIX-style tokenizer Snowflake uses. Unlike `BrowserLaunch`
itself (a small, stable shape each consumer keeps duplicated — "extract
only on a third consumer"), the tokenizer is non-trivial escaping logic
worth sharing on its *second* consumer: it moved from `crate::snowflake` to
`crate::utils::browser_command::split_browser_command`, taking a `label`
parameter so each caller's error messages still name their own
setting/env var. A malformed `browser_command` is a hard login error,
mirroring Snowflake's `resolve_auth_method` — a user who typed an explicit
override is told immediately, not silently downgraded to the default
browser.

### 3. `chrome_profile_from_email` — automatic resolution, fail-open

New module `src/gmail/chrome_profile.rs`. Given an email address:

- Locates Chrome's `Local State` file for the current OS (macOS/Linux via
  `dirs::config_dir()`, Windows via `dirs::data_local_dir()` — matching
  where Chrome itself puts it on each platform).
- Parses `profile.info_cache.<dir>.user_name` and matches it against the
  configured email, case-insensitively.
- **Never guesses**: zero matches or more than one profile signed into the
  same email both resolve to "no automatic command," not a pick — the same
  refuses-to-guess posture the daemon's AX-based window matching already
  uses (`src/daemon/services/worktrees/geometry.rs`).
- **Always fails open**: a missing/unreadable `Local State`, unparseable
  JSON, or no unambiguous match all fall back to `BrowserLaunch::Auto`
  with a logged notice — automatic resolution failure is never a login
  failure, only the manual `browser_command` path can hard-error.
- On a match, builds an OS-specific command
  (`open -na "Google Chrome" --args --profile-directory=… {url}` on macOS;
  `google-chrome --profile-directory=… {url}` on Linux; a best-effort
  `chrome --profile-directory=… {url}` on Windows) and feeds it into the
  same `BrowserLaunch::Command` — no third `BrowserLaunch` variant.

### 4. Precedence in `run_login`

`src/gmail/auth.rs::resolve_browser_config_for`, resolved once per login
from the account already selected by [ADR-0066](adr-0066.md)'s
`--account`/`OMNI_DEV_GMAIL_ACCOUNT` machinery:

1. `browser_command` set (non-blank) wins outright — manual always beats
   automatic.
2. Else, `chrome_profile_from_email` **and** `email_address` both set →
   attempt automatic resolution; any failure falls back to `Auto`.
3. Else (including a `Legacy`, non-named account) → today's
   `BrowserLaunch::Auto`, unchanged — zero migration, matching
   [ADR-0066](adr-0066.md)'s own guarantee.

## Consequences

- **A new local trust surface, but a narrow one.** This is the first code
  in the repo that reads another application's own state file (Chrome's
  `Local State`) rather than the user's own settings or a network
  response. It is read-only, unauthenticated, needs no OS permission
  prompt (unlike [ADR-0058](adr-0058.md)'s Accessibility grant), and the
  worst outcome of a wrong read is picking the wrong (or no) browser
  profile — never a credential leak, since nothing in `Local State` beyond
  the profile directory name and its signed-in email is ever used.
- **Naming discipline.** The codebase already overloads "profile" for
  omni-dev's own `--profile`/`OMNI_DEV_PROFILE` tenant-isolation axis
  ([ADR-0045](adr-0045.md)), which [ADR-0066](adr-0066.md) deliberately
  keeps orthogonal to the Gmail account axis. Every identifier this ADR
  introduces says "Chrome profile" in full — `chrome_profile_from_email`,
  never a bare `profile` field — so a reader familiar with `--profile`
  never conflates the two.
- **Opt-in is structural, not just documented.** `chrome_profile_from_email`
  defaults to `false` and `email_address` alone never triggers automatic
  resolution — an account that only set `email_address` for display
  (pre-existing behavior) sees no change.
- **Explicitly out of scope.** No global `GMAIL_BROWSER_COMMAND` env
  fallback (unlike Snowflake's env-first resolution) — the per-account
  `browser_command` already covers the manual case, and adding a second,
  differently-scoped tier before there's a concrete need would answer a
  still-open precedence question prematurely. No Chromium/Brave/Edge
  support. No new `gmail account` CLI subcommand for setting these
  fields — `settings.json` is edited by hand, same as any other
  Gmail-account field today; a setter command is a natural fast-follow if
  that friction proves real.
- **Sync obligation.** `docs/gmail.md`'s "Multiple accounts" section
  (Browser profile targeting) and "Browser did not open" troubleshooting
  entry must stay in sync with this ADR's precedence order and fail-open
  contract.
