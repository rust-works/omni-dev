# ADR-0072: A Terminal UI for the Worktrees View

## Status

✅ Accepted (2026-09-05)

**Extends [ADR-0040](adr-0040.md), reverses nothing.** ADR-0040 made the
daemon's worktrees registry the rendezvous point that aggregates every VS
Code window's registrations into one view, and the VS Code companion
(`editors/vscode/`) its first client. This ADR adds a **second first-party
client** of that same registry — `omni-dev worktrees ui`, a full-screen
terminal UI — and, with it, the crate's first embedded terminal emulator
and first hosting of interactive child processes. It relates to three other
ADRs without changing them: [ADR-0057](adr-0057.md) (the TUI launches
`claude` through `omni-dev claude-wrap`, so those sessions report
*authoritative* state), [ADR-0049](adr-0049.md) (the TUI's close is the
daemon's two-phase `close`, re-validated on execute, unchanged), and
[ADR-0058](adr-0058.md)/[ADR-0059](adr-0059.md)/[ADR-0061](adr-0061.md)
(`reposition` has no TUI analogue and is omitted; `rebase`/`push` will drive
the daemon's ops, never the CLI's local-only path — deferred to a later
phase, see §9).

Landed under this ADR so far (issue #1585): Phase 1, the read-only live
tree (`src/cli/worktrees/ui/{wire,client,supervisor,view_model,hub,…}.rs`);
Phase 2, actions (`actions.rs`, `tree.rs`, `popup.rs`,
`src/sessions/relocate.rs`); Phase 3, one embedded terminal tab
(`terminal/{mod,pty,cells}.rs`, `keys.rs`, `clipboard.rs`, `app.rs`). Phases
4–5 (tabs, splits, the mouse/selection contract, polish) are specified in §6
and land in the commits following this ADR's acceptance, per the issue's own
sequencing — the ADR is accepted alongside the phase that first hosts a
child process, not after the whole surface ships.

## Context

Stripped of VS Code, the companion extension is three things: a two-level
tree rendered from a snapshot the daemon pushes over the `0600` control
socket; ~20 commands on that tree, nearly all thin clients for daemon ops
this binary already speaks; and two badge layers competing for the two
characters a `FileDecoration` allows. Everything the UI needs, the daemon
already serves; `DaemonClient::subscribe` already speaks the push protocol
the extension uses. The work is a *view*, not data.

What a TUI adds that VS Code cannot: it can spawn terminals itself. A tab
opened in a worktree row is bound to that worktree, so the row you act on
and the shell you act in are the same object — and a `claude` tab can be
launched through `omni-dev claude-wrap` automatically, so every session the
TUI starts reports authoritative state rather than the hook-inferred kind
(ADR-0057). That is also what makes this the crate's first process host: the
UI holds PTY masters for shells that may hold credentials.

Two facts constrained the stack, both checked against real lockfile output
and a real-PTY spike (issue #1585 §6): `ratatui` 0.30 resolves to the
`crossterm` 0.29 already pinned here (0.29 would have pulled a second,
non-overlapping crossterm into the binary), and `alacritty_terminal` 0.26
ships its own cross-platform PTY layer, so no separate `portable-pty`.
Together they raised the crate's MSRV to 1.88 — a deliberate decision, since
nothing in CI enforced the old floor. The spike also surfaced two
requirements invisible from the API surface, both now load-bearing (§3).

## Decision

### 1. The TUI is a read-only client of the daemon and does not register as a window

The daemon's `open`/`focus` action shells out `code <folder>`, and
`reposition`'s planner matches an `AXTitle` — both assume a VS Code window
and would be wrong for a TUI pane (launching VS Code on a TUI-held
worktree; refusing to resolve a window that has no OS frame). So the TUI
sends no `register`/`heartbeat`; "you are here" (`here`) is computed
**locally** from the UI's own tabs, which is strictly better information
anyway. Registration becomes opt-in later behind an additive `kind` field on
`RegisterRequest`, so the daemon can tell an editor window from a TUI tab
before it tries to focus or reposition one. No new daemon op, wire field, or
service is required for any phase.

### 2. PTYs live in the process, not the daemon

In-process is simple and the tabs die with the UI. Hosting them in the
daemon would make the whole thing detachable, tmux-style — and would put
long-lived interactive child processes inside a service manager's
supervision tree. In-process for v1; anyone who wants persistence runs the
TUI inside tmux. Daemon-hosted PTYs are their own issue.

### 3. Two PTY-plumbing invariants are load-bearing, and regression-tested against real children

- **`TERM`/`COLORTERM` are set explicitly per spawn.** `tty::Options.env`
  is applied additively over the inherited environment, so a parent with
  no `TERM` spawns a child that silently degrades to dumb-terminal
  rendering — reproduced directly: `vim` never entered the alt screen. They
  are set per spawn (`terminal/pty.rs::child_env`) rather than through the
  crate's process-wide `tty::setup_env()`, which mutates *this* process's
  environment via an `unsafe` `set_var`.
- **Every `Event::PtyWrite` is written back to the child.** The emulator
  answers cursor-position/device-attribute queries itself and hands the
  reply back as an event rather than writing it anywhere; a real
  interactive child blocks on that reply. This is the same "both stdio
  directions are teed" invariant `claude-wrap` treats as load-bearing
  (ADR-0057), now inside an embedded emulator.
- **A resize is two calls, neither sufficient alone:** `Term::resize`
  rewraps the in-memory grid and `Msg::Resize` is the
  `TIOCSWINSZ`/`SIGWINCH` that tells the child. A splitter drag (Phase 4)
  goes through this same path.

The regression tests spawn real children (`/bin/sh`, `vim -u NONE`), not
mocks — a mocked PTY could never catch the hang the second invariant
prevents.

### 4. PTY content is never logged, and the clipboard gains no new path

The UI process holds PTY masters for shells that may hold credentials. So:
no PTY bytes, `PtyWrite` replies, selection text, or clipboard text are
ever logged, traced, or persisted; the request log (`log.jsonl`) sees only
`UiCommand::execute()`'s invocation-level record, nothing from inside the
running loop. This is enforced by a grep-guard test over the terminal, key,
clipboard and app modules' code lines, not left to review alone. A child's
OSC 52 clipboard write is passed through — it could already ask the host
terminal for the same thing — but the emulator is left at its default
`Osc52::OnlyCopy`, so a child can never *read* the clipboard through the
TUI, and no path is added by which selection or child output reaches the
clipboard without a user gesture (`alt-c`).

### 5. Legacy key encoding; the kitty keyboard protocol is deliberately not advertised

The emulator's `kitty_keyboard` stays off, so a child never negotiates the
protocol and never expects `CSI u` sequences; only `APP_CURSOR` (arrow/Home/
End form) and `BRACKETED_PASTE` are consulted. This is what makes the
Phase 3 key table (`keys.rs`) sufficient rather than a partial kitty
implementation, and it matches what the child would see from
Terminal.app. Advertising the protocol is a follow-up, to be evaluated
against a live `claude` session — the one fidelity question the spike could
not answer without observing one.

Focus decides who receives a key: a focused terminal takes every key
verbatim — including `Esc`, which `vim`/`claude` depend on — except
`Alt`-chords, which are chrome. The chrome therefore needs no tmux-style
prefix; a configurable prefix remains the fallback for terminals without a
usable Meta key.

### 6. Selection belongs to a widget, not to the screen (the Phase 4 contract)

With mouse capture on, the host terminal stops doing its own selection and
the app models it. Three rules, specified here so Phase 4 lands them whole:
(1) a drag is hit-tested to the pane it started in and clamped there for
its whole lifetime, and **only a terminal grid has a selection model at
all** — borders, tab strips, the tree and the status bar cannot be
selected because there is no code that would produce a string from them,
a structural guarantee rather than a filter; (2) copy comes from the
emulator's grid via `Term::selection_to_string()` — soft-wrap-aware, and a
pane border is never in that buffer to begin with — never from the rendered
frame; (3) the host terminal keeps its shift-drag escape hatch, implemented
by *omission*: terminals that support the convention never deliver those
events to the app, so `mouse.rs` must not try to detect or special-case
shift. A child that has itself requested mouse reporting (`claude` does)
receives the events instead, with `⌥` held taking them back.

`Term::resize`'s selection semantics are pinned by test rather than
assumed: a rows-only resize rotates the selection, a column-changing one
clears it (rewrap invalidates every offset).

Phase 4a lands this as `mouse.rs`: a `RegionMap` rebuilt from the drawn
rects each frame hit-tests a mouse-down to exactly one region; a drag
records its origin (`DragOrigin`) and is clamped to that region for its
lifetime; tree clicks classify by button, modifier and multi-click count
(plain focus, `^` toggle-mark, `⇧` range-mark, double-click open); a
terminal drag drives the emulator's `Selection` (simple / word / line by
click count); and `forwards_to_child` / `encode_mouse` implement rule (3)'s
handoff (SGR and legacy `CSI M` encodings, `⌥` reclaiming the mouse). The
wheel routes child-first, then alternate-scroll arrow keys on the alt
screen, then the emulator's own scrollback. `alt-c` copy consumes the
selection, tmux-style. Nothing in `mouse.rs` inspects `Shift` on a drag —
the escape hatch stays an omission.

### 7. A stack of pane groups, not a split tree

The right-hand side is a `Vec<PaneGroup>` with weights — top-vs-bottom,
which is what was asked for — rather than a recursive split tree, which is a
strictly larger change that buys nothing the request needs. The type is
written so a nested variant is additive, not a rewrite. Phase 3 hosts
exactly one tab and no strip; Phase 4b adds the rest.

Phase 4b splits this across two modules on purpose. `layout.rs` is pure
`Rect`-over-weights arithmetic — proportional splitting, a minimum height
per group, the splitter's boundary row and its drag clamp — so the maths is
unit-tested with no terminal and no PTY. `panes.rs` owns the tabs: the
groups, their focus and lifecycle, event routing by `TabId`, and the tab
strip. A drag adopts the *rendered heights* as the new weight vector rather
than rescaling the old weights, which is what keeps a drag from being lost
to integer division when weights are small. Two precedence rules are
load-bearing and pinned by test: a tab strip out-ranks the splitter whose
hit box overlaps it (otherwise no group below the first could have its tabs
clicked), and the strip's click targets come from the same width
computation that renders them, so a click cannot land on a different tab
than the one under the pointer.

### 8. Row colours are a local, unsynced store for now

`omniDevWorktrees.rowColors` lives in VS Code's application-scope settings,
invisible to a TUI. Rather than block on moving it into the daemon (the
right fix — `show_closed` solved exactly this problem that way in #1301,
and it is its own issue since it changes the shipped extension's settings
surface), the TUI keeps its own copy at
`~/.omni-dev/worktrees-ui-row-colors.yaml`, keyed with the extension's own
`repo:<root>`/`wt:<path>` scheme so a future migration reads it unchanged,
written `0600` under a `0700` directory like every other per-user config
file in the crate.

### 9. `reposition` is out of scope; `rebase`/`push`/`merge-queue` drive the daemon

A TUI pane has no `NSWindow`; repurposing the verb to mean "arrange panes"
would be a different feature wearing the same name. The three batch git
actions always call the **daemon's** ops (which run the identical engines)
rather than the CLI's local-only path: the TUI already requires the daemon
for its subscriptions, so there is no local-only benefit, and it inherits
ADR-0061's guarantees intact — `--force-with-lease --force-if-includes`
only, no force escape hatch anywhere in the UI, the remote default branch
never force-pushed. The UI must not introduce a "yes to all" that bypasses
the phase-1 confirm.

**Landed in Phase 4d** as `ActionKind::{Rebase, Push, MergeQueue}`, each a
thin two-phase client of `rebase`/`push`/`merge-queue`: the daemon plans,
the plan is rendered verbatim into the same confirm modal `close` uses, and
only then does phase 2 run — where the daemon re-plans from scratch, so the
confirmed plan is advisory rather than a token to be replayed. The UI adds
**no** safety logic of its own, deliberately: the lease, `--force-if-includes`
and the never-force-the-default-branch gate all live in
`crate::git::worktree_push`, where `git` itself enforces the lease. What the
UI owes this ADR is the *absence* of a bypass, and that is what its
`no_force_escape_hatch_exists_in_the_ui_surface` guard test asserts —
grepping the action, client and wire modules so a `force` field cannot be
added to a payload without failing a test. The `push` client sends no
`remote` override and the `rebase` client no `onto` override, for the same
reason: every widening of that surface is a way around a guard that lives
elsewhere.

## Consequences

- **No new trust boundary and no new daemon capability.** Every action
  rides the existing `0600` socket via ops that already exist; the TUI adds
  no op, grants itself no credential, persists no secret. The destructive
  surface (`close`, and since Phase 4d `rebase`/`push`/`merge-queue`) is
  unchanged and daemon-re-validated: the TUI reaches exactly the same ops
  the VS Code companion already reached, so it widens *who can ask* by one
  first-party client and widens *what can be asked* by nothing at all.
- **The genuinely new exposure is process hosting** (§4). The mitigations —
  never logging PTY content, no clipboard→child path, `OnlyCopy` — are
  code and tests, not conventions. Anyone adding a `tracing::` call in the
  terminal/key/clipboard/app modules will meet the guard test.
- **First `Apache-2.0` core dependency** (`alacritty_terminal`) against the
  crate's BSD-3-Clause — permissive and compatible, noted here so it is a
  recorded decision rather than an accident of `cargo add`.
- **MSRV is 1.88.** Declared honestly rather than left false; nothing in CI
  enforced the old floor.
- **Two views of the same tree will drift** until the row-formatting rules
  (glyph precedence, description order, badge severity) share golden
  fixtures asserted by both `node --test` and `insta` — recommended in the
  issue, deferred to Phase 5, and the reason the Rust ports cite their
  TypeScript sources line by line.
- **One tab, in-process, no persistence** in this phase. Detach/reattach,
  daemon-hosted PTYs, a split tree, and moving `rowColors` into the daemon
  are each their own issue, none precluded by the shapes chosen here.
