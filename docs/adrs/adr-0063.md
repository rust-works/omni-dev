# ADR-0063: OAuth2 Authorization-Code + PKCE for Gmail, with Bring-Your-Own Google Cloud Project

## Status

✅ Accepted (2026-08-02)

Extends [ADR-0043](adr-0043.md) (credential redaction) and [ADR-0045](adr-0045.md)
(profile isolation); introduces no changes to either.

## Context

Every credentialed backend omni-dev talks to today — Atlassian, Datadog,
Snowflake's static-token path — authenticates with a **static bearer
credential**: an API key or token pair that a human generates once in a
provider console and that omni-dev reads from `~/.omni-dev/settings.json` or
the process environment (`src/datadog/auth.rs`, `src/atlassian/auth.rs`).
Snowflake additionally supports external-browser SSO
(`src/snowflake/client/auth.rs:38-94`): bind a loopback listener first so its
OS-assigned port is the redirect target, open the identity provider's URL in
a browser, capture the callback with a raw `TcpListener::accept`, then
exchange the captured token for a session. That flow is the closest existing
precedent to what Gmail needs, but it stops short in exactly the ways Gmail
cannot: it has no PKCE, no `state` nonce, no `access_denied` branch, and —
because Snowflake sessions are ephemeral per-connection — no long-lived
refresh-token persistence.

Gmail requires Google's OAuth2 **authorization-code grant**: there is no
API-key equivalent for accessing another user's mailbox. Greps for
`oauth|authorization_code|refresh_token|code_verifier|PKCE|redirect_uri`
across `src/` before this work return nothing but redaction-denylist entries
(`src/request_log.rs`) and prose warnings about *other* tools' tokens — this
is a genuinely new authentication modality for the project, not a variation
on an existing one, which is why it is recorded here rather than folded into
an existing ADR.

Three decisions in this design are load-bearing enough to need explicit
justification rather than being reverse-engineered from the diff:

### Why authorization-code + PKCE, and why a loopback listener specifically

A CLI has no server-side component to receive a redirect the way a web app
does, and it cannot embed a `client_secret` that stays secret (anyone can
extract a string compiled into or shipped alongside a binary). The two OAuth2
flows shaped for exactly this constraint are device-code (poll-based, no
redirect at all) and authorization-code-with-PKCE via a loopback redirect.
PKCE (RFC 7636) removes the need to protect the `client_secret` at the
token-exchange step by binding the authorization code to a per-flow
`code_verifier` the client alone holds — a code intercepted in transit (e.g.
from a shared machine's browser history) cannot be redeemed without it.
Device-code was rejected: it optimizes for headless/TTY-only environments
(smart TVs, CI runners) at the cost of a worse interactive UX (type a code
into a second device) for the common case — a developer running `omni-dev`
on their own machine with a browser available. Loopback-redirect
authorization-code + PKCE is Google's own documented recommendation for
installed apps and is the shape both the OAuth2 spec's "native app" guidance
(RFC 8252) and Snowflake's existing external-browser precedent already point
toward. Google also shut down its out-of-band flow
(`urn:ietf:wg:oauth:2.0:oob` — paste a code shown on a Google-hosted page
back into the CLI) in 2022, so loopback redirect is not merely the preferred
option among several — for an installed app targeting Google specifically,
it is the only one left.

### Why the refresh-token/access-token split, and why *not* rotating on-disk credentials

Nothing in this repository today rewrites a credential file as it refreshes.
`settings.json` credentials for every other backend are static tokens
written once by an `auth login` command; the browser-bridge session token is
0600-persisted but never rotates (`src/daemon/services/bridge.rs`); and
Snowflake's session tokens rotate but do so **only in memory**, keyed to a
single long-lived process (`src/snowflake/client/session.rs`). Introducing a
Gmail credential that both persists to disk *and* rotates on a schedule
would be new machinery this repository has never needed:
atomic-rewrite-on-refresh, a lock against concurrent CLI invocations racing
to write the same file, and a recovery story for a partially-written token
file — none of which has a working example anywhere in the codebase to build
from safely. A design that avoids inventing that machinery is worth
preferring on its own, independent of any Gmail-specific reasoning.

### Why bring-your-own Google Cloud project, and its consequence

A CLI cannot keep a `client_secret` secret regardless of how it obtains
one — whether the project ships its own OAuth client or not, the secret is
extractable from the installed binary or its distribution artifact. That
alone would be reason enough to make credential provisioning the user's
responsibility. But Gmail read scopes are also **restricted scopes** under
Google's API terms: an application distributed to third parties that
requests them must pass a **CASA (Cloud Application Security Assessment)**
with **annual recertification** — an ongoing compliance and cost burden
entirely disproportionate to an open-source CLI tool with no company behind
it to carry it. The honest design for this project is that each user
creates their own Google Cloud OAuth client and supplies its credentials;
omni-dev never distributes one that has (or claims) Google's verification.

## Decision

### 1. Authorization-code + PKCE via a loopback listener is a new, additive auth modality

We will implement Gmail authentication as OAuth2 authorization-code grant
with PKCE, following the same three-step shape as Snowflake's
external-browser SSO (`src/snowflake/client/auth.rs`) but closing every gap
that flow leaves open for an installed-app OAuth2 client:

1. **Bind the loopback listener first**, `127.0.0.1:0` (OS-assigned
   ephemeral port), so the port is known before constructing the
   authorization URL — the redirect target *is* the bound port, avoiding a
   race between "ask for a port" and "listen on it."
2. **Generate a PKCE `code_verifier`/`code_challenge` pair and a `state`
   nonce** using the existing `generate_token()` primitive
   (`src/browser/auth.rs`, 256-bit URL-safe base64) — no new randomness
   primitive is introduced. Open the authorization URL in the user's
   browser, reusing the existing `open_browser()` three-mode design
   (`Auto`/`Command`/`Manual`, `src/snowflake/client/auth.rs`) so a user can
   pin a specific browser profile — not optional for anyone who runs
   multiple Google accounts day to day, which is the common case for the
   audience this tool serves.
3. **Capture the callback** with the same raw `TcpListener::accept` +
   single `read()` approach Snowflake uses (no HTTP framework dependency),
   replying with a fixed 200 response body telling the user they can close
   the tab. `state` is compared against the expected value with a plain
   `==` — it is a CSRF nonce carried in a browser-visible URL, not a secret,
   so there is no timing side-channel for a constant-time comparison to
   guard against (unlike `constant_time_eq()`'s real use in
   `src/browser/auth.rs`, which guards a bridge auth token) — and an
   `?error=access_denied` (or any other `error=`) query parameter is
   treated as a distinct, actionable failure rather than falling through to
   "missing `code`."
4. **Exchange the authorization code for tokens** — the one step with no
   existing precedent to copy, implemented as a plain `reqwest` POST to
   Google's token endpoint carrying the `code`, `code_verifier`,
   `redirect_uri`, and client credentials.

This flow lives in `src/gmail/auth.rs`, is triggered only by
`omni-dev gmail auth login`, and is never invoked from an MCP tool handler —
an interactive browser flow has no meaningful non-interactive analogue, so
there is deliberately no `gmail_auth_login` tool.

The OS-assigned ephemeral port from step 1 also constrains which Google
Cloud OAuth client type works at all: a "Web application" client requires
every redirect URI to be pre-registered, port included, which is
incompatible with a port chosen fresh at bind time. The user-provisioned
client (Decision 3) must therefore be of type **Desktop app**, which Google
exempts from redirect-URI pre-registration for exactly this loopback case.
This is the single most likely first-run failure mode and is documented
prominently in `docs/gmail.md`'s prerequisites, not left to be discovered
via a bare redirect-URI-mismatch error.

### 2. Refresh token on disk, access token in memory only — no rotating on-disk credential

We will **not** introduce a credential file that rewrites itself as tokens
refresh. Instead:

- The **refresh token** is written **once**, at the end of a successful
  login, into the `env` map of `~/.omni-dev/settings.json` (or the active
  profile's `env` map, when one is selected) via the existing
  `Settings::upsert_env_vars_in` (`src/utils/settings.rs`) — the identical
  call `omni-dev datadog auth login` already makes
  (`src/datadog/auth.rs`). It inherits 0700-directory/0600-file hardening
  and [ADR-0045](adr-0045.md) profile isolation with no new code. Google
  issues a refresh token that itself does not expire on a fixed schedule
  under normal operation (only under the testing-mode 7-day policy
  described in Decision 3, or if explicitly revoked) — so "written once" is
  the correct steady-state model, not a simplification that will need
  revisiting once real usage arrives.
- The **access token** is held **only in memory**, for the lifetime of one
  CLI process (or one MCP server process), behind a `GmailSession` that
  refreshes on demand and mid-run — the same shape as
  `SnowflakeSession::renew()` (`src/snowflake/client/session.rs`). Every
  fresh CLI invocation exchanges the refresh token for a new access token,
  costing roughly one extra ~150ms POST — an acceptable, bounded price for
  never having to persist, lock, or atomically rewrite a rotating
  credential file.
- `client_secret`, `refresh_token`, and `access_token` are all wrapped in
  the existing `Secret` newtype (`src/utils/secret.rs`), so
  `Debug`-formatting the credential struct prints `<redacted>` by
  construction, and the struct implements no serde trait that could
  accidentally serialize a token into a log line or a debug dump —
  inheriting [ADR-0043](adr-0043.md)'s guarantee the same way every other
  credential struct in the codebase does. The wire side needs no new work:
  `request_log.rs`'s existing `Authorization`-header and `?access_token=`
  denylist entries already cover Gmail's HTTP traffic, and this
  implementation's own architecture additionally guarantees that `code`,
  `code_verifier`, `refresh_token`, and `client_secret` never travel in a
  URL query string in the first place — they are read from the loopback
  callback's request line only in-process, and sent to Google's token
  endpoint exclusively as a POST body.

We explicitly considered and rejected keeping the access token on disk
alongside the refresh token (simpler code, one file instead of a
memory/disk split) — rejected because it reintroduces exactly the
rotating-credential-file problem this decision exists to avoid, for a token
whose only purpose is being handed to `reqwest` immediately after being
obtained.

### 3. Bring-your-own Google Cloud project; scopes default to read-only

We will require each user to create their own Google Cloud project and
OAuth2 client, supplying its identifier and secret via `GMAIL_CLIENT_ID` /
`GMAIL_CLIENT_SECRET` environment variables (or the settings-file `env`
map, following the same resolution order as every other backend). omni-dev
will never ship or embed a shared OAuth client. This is a direct
consequence of two facts that hold regardless of engineering effort: a CLI
cannot keep a `client_secret` confidential, and Gmail read scopes are
Google *restricted scopes*, whose distribution to third parties requires an
annual CASA security assessment — a compliance burden with no owner for an
open-source tool.

The default requested scope is `gmail.readonly`. `gmail.modify` (required
for `gmail label add`/`remove`) is opt-in via
`omni-dev gmail auth login --modify`. We will **not** request Gmail's send
scope under any flag — there is no read-path use for it in this issue's
surface, and requesting it would widen the blast radius of a leaked refresh
token for zero functional gain (sending mail is explicitly out of scope for
this issue and its Phase 2 follow-up).

We considered whether the narrower `gmail.metadata` scope (headers and
labels, no message bodies) could cover `gmail search`'s default ids-only
path, since least-privilege is worth stating even when cheap. It does not:
`gmail read`/`gmail thread` need full body access unconditionally, so a
mailbox-wide client would still need `gmail.readonly` for those commands to
work at all, and splitting one login flow into scope-per-command would
multiply the number of consent screens and stored credentials for no
practical safety gain (`gmail.metadata` is *also* a restricted scope, so it
does not change the CASA conclusion above either). `gmail.readonly` as the
single default scope stands.

**Consequence that must be documented prominently, not left to be
discovered via a bare API error:** an OAuth client left in Google Cloud's
"Testing" publishing status (the default for a freshly created project, and
the state most individual users will leave it in, since "In production"
requires Google's own verification review for anything beyond 100 test
users) issues refresh tokens that **expire after 7 days**. A user who does
not explicitly push their project out of testing mode will need to re-run
`omni-dev gmail auth login` weekly. When the client library encounters
Google's `invalid_grant` error, the error message must name this as the
likely cause rather than surface the bare OAuth error string — this is a
testable requirement (`src/gmail/error.rs`), not just a documentation note,
and `docs/gmail.md`'s troubleshooting section must carry a dedicated entry
for it.

## Consequences

- **A genuinely new trust surface, scoped narrowly.** This is the first
  authorization-code OAuth2 flow in the project. Its blast radius is
  bounded to read access (plus, opt-in, label mutation) over one user's own
  mailbox via a credential they alone provision — there is no shared secret
  whose compromise affects more than one user, unlike a hypothetical shared
  OAuth client would be.
- **No new persistence machinery, at the cost of one extra network round
  trip per process.** By keeping the access token in memory only, this
  design adds no file-locking, no atomic-rewrite-on-refresh, and no
  partial-write recovery path to the codebase — genuinely simpler than the
  alternative, not merely deferred complexity. The cost is paid on every
  fresh CLI/MCP-server process: one refresh-token-exchange POST (~150ms)
  before the first real API call.
- **The 7-day testing-mode expiry is a real, recurring UX cost this
  project does not control.** It is Google policy, not something omni-dev
  can route around short of asking every user to submit their personal
  project for Google's app-verification review (disproportionate for a
  single-user tool) — the mitigation is entirely in clear error messages
  and documentation, not code.
- **Extends, does not amend, [ADR-0043](adr-0043.md).** The
  `Secret`-wrapped `client_secret`/`refresh_token`/`access_token` are new
  *instances* of that ADR's invariant, not a new mechanism — no change to
  `request_log.rs`'s denylists was needed, since this design's own
  architecture keeps every OAuth secret out of URL query strings entirely
  (never constructed as one, in either direction).
- **Extends [ADR-0045](adr-0045.md)'s profile isolation for free, with its
  fourth consequence already on record as the relevant constraint for any
  future change here.** Because the refresh token is written through the
  same `Settings::upsert_env_vars_in`/profile-aware path every other
  credential uses, a Gmail refresh token is isolated per active profile
  exactly like a Datadog API key is, with no Gmail-specific code.
  ADR-0045's fourth consequence — "the abstraction does not auto-cross the
  daemon boundary," since `OMNI_DEV_PROFILE` is a property of the invoking
  CLI process — is **not yet exercised** by this design (Gmail's session
  lives entirely inside the CLI/MCP-server process; see "Explicitly out of
  scope" below), but is the constraint any future daemon-hosted Gmail
  service must satisfy by resolving profile scope client-side, the same way
  the Snowflake daemon service was fixed to do.
- **Explicitly out of scope, and why.** A daemon-hosted Gmail refresh loop
  (the way `SnowflakeEngine::start_heartbeat` keeps a session warm,
  `src/snowflake.rs`) is a natural-looking next step and would be
  mechanical to add (`DaemonServiceKind::Gmail`), but the in-memory,
  per-process session this ADR specifies already covers every surface this
  issue ships. Introducing a daemon-hosted session now would be speculative
  generalization ahead of a concrete need, and — per the consequence above
  — would immediately have to solve the profile-boundary problem ADR-0045
  already flags as unsolved for any new daemon service. Revisit only if a
  future use case (e.g. Phase 2's incremental sync running unattended)
  needs a warm token shared across processes.
- **Sync obligation.** `docs/gmail.md`'s Authentication section is the
  operator-facing description of this design (environment variables, the
  `--modify` flag, the CASA/bring-your-own rationale in plain language, and
  the 7-day expiry). Keep the two in sync when this ADR's scope model or
  token handling changes.

See [ADR-0043](adr-0043.md) for the redaction invariant this design's
`Secret`-wrapped fields inherit, and [ADR-0045](adr-0045.md) for the profile
isolation the refresh-token write path inherits. Phase 2's `historyId`
watermark-persistence decision is not part of this ADR and will either amend
it or receive its own ADR when that follow-up is filed.
