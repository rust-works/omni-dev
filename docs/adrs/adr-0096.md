# ADR-0096: Persisted Closure History and Recreating Removed Worktrees

## Status

✅ Accepted (2026-10-07, [#2211](https://github.com/rust-works/omni-dev/issues/2211))

Extends [ADR-0049](adr-0049.md) (the `close` op, whose deletion this makes recoverable) and
[ADR-0040](adr-0040.md) (the worktrees registry, whose in-memory-only posture it relaxes for
one list). Neither is superseded: both keep their status and everything else they decided
still governs.

## Context

There was no way to get back to a worktree you had closed. The daemon derives the tree's
repos from **open windows**, so a closed window only survived as a sibling of one that was
still open, closing a repo's last window dropped the whole repo from the tree, and **Close
Worktree** ([ADR-0049](adr-0049.md)) pruned a linked worktree from disk and left no record
that it had existed. The registry is in-memory by design, and `unregister` just deletes the
entry, so a closure left no trace and any daemon restart lost what little there was.

The daemon is the one process that sees every window register and unregister, so it is the
natural owner of a "recently closed" list, in the spirit of VS Code's own *Reopen Closed
Editor* and *Open Recent*. Three choices needed deciding.

**Whether to persist it.** The registry is in-memory because every other fact in it can be
re-reported by a live window within one heartbeat. A closure cannot: the window that would
re-report it is gone. A list that vanished on a daemon restart would lose exactly the
closures a user is most likely to want back (a crash, a reboot, a login). The precedent is
the per-repo PR-poll enable set ([#1376](https://github.com/rust-works/omni-dev/issues/1376)),
persisted to a `0600` file in the `0700` runtime directory. What this list records is
paths, branch names and commit ids: no secret and no file or conversation content, but it
does name what the user was working on, so the file keeps the posture of the other runtime
state.

**What "reopen" does for a removed worktree.** Opening a window on a folder that is still on
disk creates nothing. Reopening a *removed* worktree runs `git worktree add`, which is a
write to the repository, and what comes back is only the committed history: uncommitted
changes went with the directory and git has no copy. Three shapes were considered for the
request. Letting the client name a branch, a base and a destination is the most flexible and
turns a socket writer into someone who can make git create a worktree anywhere. Re-deriving
the plan from the client's last view repeats the mistake [ADR-0049](adr-0049.md) already
rejected for `close`. Accepting only a path the daemon itself recorded closing gives up the
flexibility and nothing a user needs.

**Which closures count.** Every way a window leaves the registry is a closure: an
`unregister`, a TTL reap (a crashed window), and the `close` op's removal. A VS Code window
reload is an `unregister` followed by a `register` of the same folders, which is not a
closure the user wants listed, and nor is a worktree they reopen by hand.

## Decision

We will keep a bounded, persisted, daemon-owned list of recently closed worktrees, expose it
through the tree snapshot and two ops, and recreate a removed worktree only after a
two-phase confirmation of a plan the daemon computes itself.

1. **One record per path, newest first, bounded.** Each entry holds the worktree path, its
   repository's main working tree, repo name, GitHub identity, branch, head commit, whether
   it is the main working tree, whether it was **removed from disk**, and a closed-at time.
   A newer closure of a path replaces an older one, and an older one never replaces a newer.
   The list is capped at 50 entries and 30 days, evicting oldest first.
2. **A closure is recorded when a window leaves, and forgotten when the folder is open
   again.** The registry queues a departure on `unregister` and on every TTL reap. The
   adapter resolves each to a record with `git2` on a blocking thread (a folder that is not
   in a repository, or no longer exists, yields nothing), and skips one a live window still
   has open. `register` forgets the record of the worktree each folder is in, which is what keeps a
   reload and a hand-reopened worktree out of the list; `reopen` itself leaves the record
   for that `register` to drop, so a launcher that never produces a window loses nothing. The `close` op captures the worktree
   *before* pruning it and records it as removed afterwards. A window-closed record whose
   directory has since vanished, while its repository is still there, is marked removed when
   next seen, which is the only way a
   worktree pruned outside omni-dev is noticed: we record closures we observed, and we do
   not scan for removals we did not.
3. **Persisted to `worktrees-closed.json`** (`0600`, in the `0700` runtime directory),
   loaded at startup and rewritten on each change. Loading and saving are best-effort: a
   missing file is the first-run default, a corrupt or unreadable one is logged and treated
   as empty, and a failed write is logged and does not fail the operation. The registry owns
   this file itself rather than the adapter, because the tree snapshot reads the list
   without going through the adapter. Every mutation bumps the change-notify only when the
   list actually changed.
4. **Exposed additively.** The `tree`/`subscribe` snapshot gains `recently_closed`, omitted
   when empty so an older client and the common case are byte-identical. A `recent-closed`
   op returns the list on demand. Window-feed ops are unchanged.
5. **`reopen` takes only a recorded path.** It accepts no branch, base or destination. For a
   worktree still on disk it opens the window with the existing launcher. For a **removed**
   one it is two-phase, keyed off `confirmed` like `close`/`rebase`: phase 1 returns the plan
   and creates nothing; phase 2 **re-plans from scratch**, never trusting what the client
   saw, then creates the worktree and opens it.
6. **The plan decides restorability in one place.** A worktree is recreated on its recorded
   branch if that branch still exists; if only the recorded commit survives, the branch is
   recreated at that commit; otherwise the plan says it cannot be restored and why. It is
   refused for the main working tree, for a detached HEAD (there is no branch to restore it
   onto), when the destination already exists, when the repository is gone, and when the
   branch is checked out in another worktree. Every restorable plan carries the warning that
   uncommitted changes are not recovered. A branch the op created is deleted again if the
   worktree then fails to appear. Creation is serialized with `close`'s prune, since both
   write `.git/worktrees`, and uses `git2` rather than a shell, as `close` does.
7. **No new socket capability beyond that.** The op rides the same `0600` socket, and what it
   can make git write is bounded by what the daemon itself saw close.

## Consequences

**Positive.** A closed window, a closed repo's last window, and a removed worktree can each
be reopened, from the tree view, the palette and the CLI, and they survive a daemon restart.
The destructive `close` becomes recoverable for everything but uncommitted work, and the UI
says so before it creates anything. Because `reopen` accepts only a recorded path, a socket
writer gains no way to create a worktree somewhere new. The list is bounded in size and age,
so it cannot grow without limit or keep a stale record indefinitely.

**Negative.** The daemon now persists a second file, and it names the user's repositories
and branches. It is `0600` in a `0700` directory like the rest of the runtime state and holds
no secret, but it is state an uninstall has to remove. A window reload briefly records and
then forgets a closure, so a snapshot taken in that gap can show it. Uncommitted changes in a
removed worktree are lost for good, and a removed worktree on a detached HEAD cannot be
restored at all. A worktree removed outside omni-dev that the daemon never saw close is not
discovered.

**Neutral.** A VS Code quit unregisters every window at once, so a restart fills the list
with that session's windows, which is the behaviour of VS Code's own *Reopen Closed Editor*.
Surfacing every on-disk worktree of a repository that has no open window, and showing the
list in the terminal UI, are separate designs and are not part of this decision.
