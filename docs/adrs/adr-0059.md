# ADR-0059: Daemon-Hosted Worktree Rebase, Conflicts Left In Place

## Status

✅ Accepted (2026-07-26)

Supersedes [ADR-0055](adr-0055.md) **in part**: on *where* a batch rebase runs.
ADR-0055's fetch-once-per-repository core (§2), its git2-for-reads /
shell-for-mutations split (§1), its selection rules (§3) and its confirm-by-default
posture (§5) are unchanged and still govern.

## Context

[ADR-0055](adr-0055.md) shipped `omni-dev worktrees rebase` as a **pure CLI-side**
command, and #1409 gave the companion extension a **Rebase on main** row action
that shells out to it — `omni-dev worktrees rebase <paths> -y` in a VS Code
integrated terminal. Everything else in the tree view is a socket client; this one
action was not.

Three problems with that, in increasing order of importance (#1415):

1. **A terminal opens at all.** Every sibling action reports through a modal and a
   toast; this one hijacks the panel.
2. **A multi-worktree rebase is one invocation in one terminal**, so N results
   arrive as a single scrolling blob rather than a per-worktree summary.
3. **On conflict the engine ran `git rebase --abort`.** That discards every
   conflict `rerere` already resolved and every hunk that applied cleanly before
   the collision — work the user then reproduces by hand. The worktree should be
   left mid-rebase so the conflict can be resolved *in place*.

### The premise ADR-0055 rested on was wrong

ADR-0055 blocked a daemon-hosted rebase on one specific claim:

> A daemon-hosted or tray-initiated rebase would fetch from the daemon's minimal
> environment, which lacks `SSH_AUTH_SOCK`, so it could not authenticate to an SSH
> remote.

Inspecting the resident daemon directly falsifies it:

```
$ ps eww -p <daemon pid>
SSH_AUTH_SOCK=/var/run/com.apple.launchd.XXXXXXXX/Listeners
PATH=/usr/bin:/bin:/usr/sbin:/sbin
HOME=/Users/...
```

launchd exports `SSH_AUTH_SOCK` into the **per-user session**, so a LaunchAgent
inherits the user's `ssh-agent` like any other process they start. A fetch under
exactly that reconstructed environment succeeds:

```
$ env -i HOME=$HOME PATH=/usr/bin:/bin:/usr/sbin:/sbin SSH_AUTH_SOCK=... \
    git fetch origin main
From github.com:rust-works/omni-dev
 * branch              main       -> FETCH_HEAD      # exit=0
```

What the daemon genuinely lacks is a useful **`PATH`** — the same minimal-`PATH`
problem [ADR-0049](adr-0049.md) §3 already solves for the `code` launcher and
`pr_status.rs::resolve_gh_binary` solves for `gh`. That is a *binary-resolution*
problem, not a credential one, and it has a known, boring fix.

The in-tree precedent settles the trust question: [ADR-0056](adr-0056.md)'s
`merge-queue` op **already** performs credentialed remote mutations from the
daemon through the user's own `gh`. Doing the same with `git fetch` widens no
trust boundary.

### What hosting it in the daemon buys, beyond removing the terminal

- **Conflicts can be left in place.** This is the real motivation. A terminal
  invocation that leaves N worktrees mid-rebase and scrolls away is worse than
  useless; a structured per-worktree reply plus a durable tree cue makes the same
  state legible.
- **The confirmation can show true behind-counts.** #1409's modal deliberately
  showed none: the only number the extension had was the tree's `behind`, which
  measures divergence from the branch's *upstream*, not from the rebase target. A
  phase-1 plan measures against the freshly fetched target, so the counts are real.
- **The run is auditable** in `omni-dev daemon logs`, like every other op.

## Decision

Add a two-phase **`rebase` op** to the `worktrees` daemon service, move the
extension action onto it, cue rebase state in the tree, and keep the CLI local.

### 1. Two-phase, modelled on `merge-queue`

- **Phase 1** (`check: true`, or any un-`confirmed` request) runs
  `worktree_rebase::plan`: fetch each repository's target ref **once**, then
  classify every selected worktree. This *is* the "only rebase if it makes sense
  from the current git state" gate — the classifier already skips the main working
  tree (structural `is_main`), a detached HEAD, a dirty tree, an operation already
  in progress, a non-worktree path, an unresolvable onto ref, and anything already
  up to date. Side-effect-free apart from the fetch, which only advances a
  remote-tracking ref.
- **Phase 2** (`confirmed: true`) **re-plans from scratch** and executes. A
  phase-1 result the client sends back is never trusted — exactly as `close`
  re-runs its safety check and `merge-queue` re-runs its eligibility evaluation. A
  worktree that went dirty between the phases is skipped, not rebased.

Both phases reply in one shape (`{ fetches, worktrees }`); only which
`RebaseResult` variants appear differs. One batched op over `paths`, not a
client-side fan-out — that is what preserves fetch-once-per-repository, since the
engine can only group by repository if it sees the whole selection at once.

Phase 2 is serialized by a `rebase_lock` (the `prune_lock` precedent): linked
worktrees share one object database, and the engine's within-batch sequencing
would be defeated by two concurrent requests.

### 2. Conflicts are left in place

A new `RebaseOptions.keep_conflicts` skips the `git rebase --abort`. The
conflicted worktree stays mid-rebase with its markers on disk, to be resolved and
finished with `git rebase --continue`; the batch continues with the rest, and the
outcome records `left_in_place: true` so a client can say something different
about it than about a rollback.

It stays a **client choice**, defaulting to the conservative abort. The tree view
always sends `true` — it is the point of the change — while an unattended or
scripted caller keeps the pre-existing behaviour unless it asks otherwise. The CLI
exposes it as `--keep-conflicts`.

### 3. `resolve_git_binary()`, mirroring `resolve_gh_binary`

`OMNI_DEV_GIT_BIN` → the first existing well-known absolute path (Homebrew, then
`/usr/local`, then Linuxbrew, then `/usr/bin`) → bare `git`. Resolved **once** per
plan/execute and threaded down, never re-read per subprocess. macOS's minimal
launchd `PATH` does contain `/usr/bin/git`, so the fallback would have worked —
but silently picking a *different* `git` than the user's shell does, for a
history-rewriting operation, is precisely the divergence worth ruling out.

### 4. The tree cue is two orthogonal facts, and not the badge layer

- **`operation`** — the worktree's own `repo.state()`, read fresh off disk into
  every snapshot. Durable: it survives a daemon restart and keeps showing a
  left-in-place conflict until it is resolved. Costs a handful of `stat`s, nothing
  beside the `Repository::discover` the enrichment already does, so it clears
  [#1306](https://github.com/rust-works/omni-dev/issues/1306)'s
  every-worktree-every-tick bar.
- **`rebasing`** — an in-memory registry set the op marks and clears. Transient,
  and *not* redundant: a rebase that applies cleanly never writes an on-disk state
  for `operation` to report, and even a conflicting one only writes it at the
  moment of collision — so without this a multi-second rebase renders as nothing
  happening.

Both are additive `skip_serializing_if` fields, so an older client sees a
byte-identical snapshot (the ADR-0053 convention). Marking and clearing bump the
change-notify **only on a real change**; an unconditional bump would defeat the
server's snapshot diff and re-push to every window on every tick.

They render as a **row icon** (`$(sync~spin)` / `$(warning)`) plus description
text — deliberately *not* a file decoration. A `FileDecoration.badge` holds only
two characters and both are already claimed, one by the PR-check verdict and one
by the Claude-session cue (#1406), so a third would have to evict one of them. The
icon override costs the row its open-state glyph while a rebase is in flight; the
tooltip and `contextValue` still carry open state, which is the cheaper loss.

### 5. The extension action requires the daemon; the CLI stays local

`rebaseCommand.ts` becomes a socket client — modal → `withProgress` → summary
toast — and the terminal path (`omniDev.ts`, the binary resolver and command-line
builders) is deleted rather than kept as a fallback. Two divergent code paths with
*different conflict semantics* would be worse than one, and a daemon-down rebase
now reports the same way every other tree action does, naming the CLI as the way
out.

`omni-dev worktrees rebase` keeps its own local engine. That is now a **choice,
not a necessity**: it means a batch rebase works with no daemon running at all,
and it keeps `--all` and `--onto <ref>` — CLI-shaped concerns — out of the wire
protocol.

## Consequences

- **The daemon now rewrites git history.** A genuine escalation beyond `close`'s
  file deletion, and the second op (after `merge-queue`) to use the user's ambient
  credentials. It remains same-user-bounded behind the `0600` socket, rewrites
  only branches the client names, refuses the main working tree on the structural
  `is_main` guard, and re-validates everything on execute. No secret is read or
  persisted; the fetch relies entirely on the user's ambient `git` configuration.
- **A worktree can now be left in a conflicted state by a UI gesture.** That is
  the intent, but it is a real change in what a click can leave behind — hence
  the durable tree cue, the named-in-the-toast warning, and the audit line. Both
  are still recoverable with ordinary git (`--continue` or `--abort`).
- **Off macOS the premise may not hold.** A systemd user unit does not get
  `SSH_AUTH_SOCK` unless it is imported into the user manager's environment. That
  degrades honestly through the existing `FetchOutcome` / `fetch-failed` shape —
  the repo's worktrees are reported unrebased with the fetch error — and the local
  CLI remains the fallback. Nothing silently half-happens.
- **Rebases stay sequential.** Within a batch by design (one shared object
  database, deterministic output), and across requests by the new lock. So #1415's
  second complaint is only partly addressed: N rebases still run one at a time,
  but the result is a structured per-worktree summary rather than one terminal
  blob. Parallel rebase remains a follow-up.
- **"Abort Rebase" / "Continue Rebase" tree actions are an obvious next step** now
  that the tree can *see* a left-in-place conflict, and are deliberately out of
  scope here.
- **ADR-0055 keeps its status.** Only its credential premise and the two
  consequences that followed from it are amended; everything else it decided is
  still the live design.
