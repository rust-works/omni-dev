# ADR-0092: Gated Trash and Restore for Individual Drive Files

## Status

✅ Accepted (2026-10-02, #1617).

## Context

The Drive integration can create and modify files but cannot clean up arbitrary
files. `drive lease prune` already uses `FilesApi::trash` to discard backup copies;
there is no public command for scratch-file teardown. A Sheets or Docs create
that fails while seeding content leaves a file whose ID must be reported
([ADR-0073](adr-0073.md) §11, [ADR-0076](adr-0076.md) §9).

Drive offers reversible trash and immediate permanent deletion. Trash covers
teardown without introducing permanent deletion. Reusing an existing `create`,
`edit` or `sheets-delete` grant would silently expand consent from writing a file
to removing it. A folder's trashed state affects descendants, so an ancestor
allow could bypass an explicit descendant deny. The shallow-move warning in
[ADR-0070](adr-0070.md) §8 is insufficient for that permission boundary.

Requiring a write lease would add a backup and Touch ID prompt to an operation
whose recovery mechanism is already Drive Trash. Exempting it follows the
reversible metadata precedent in [ADR-0080](adr-0080.md) §9, with the caveat that
Trash is normally purged after 30 days and can be emptied sooner. Automatic
rollback after create would also require a separate permission nobody necessarily
granted. Both alternatives therefore impose costs or widen consent.

## Decision

We will expose `drive trash <FILE_ID>` and `drive untrash <FILE_ID>` with
`--dry-run` and the existing output formats. Both use a new, default-deny
`DriveOperation::Trash` (`trash`). Permanent deletion must use a separate
operation or explicit re-consent; it must never join this grant.

We will refuse folders for both verbs, even with a matching file-ID allow.
Individual binary files, Google-native documents and shortcuts are supported;
changing a shortcut's state changes the shortcut itself. Recursive folder
operations and permanent deletion are deferred. The commands are CLI-first;
MCP writes remain deferred under ADR-0070 §9.

We will evaluate the same file-ID/current-parent permission resolver as `edit`
([ADR-0071](adr-0071.md), issue #1612). File-ID rules can grant files
without visible parents; otherwise such targets are refused. Default and
explicit denies apply before no-op detection. Multiple parents use the shared
resolver's combined verdict. A dry run fetches metadata and evaluates the gate
but never sends a PATCH. It previews local permission, not Drive's server-side
ownership/capability verdict.

We will extend ADR-0080 §9's lease exemption list with Trash and restore. Neither
command reads the lease ledger, requires a lease token or prompts for Touch ID,
even when a deciding rule has `require_lease: true`. Restore uses the same
`trash` consent and resolves the trashed file's current visible parents. It does
not bypass a revoked grant or restore a parent folder implicitly.

We will use `files.update` with `trashed: true` or `false` and
`supportsAllDrives=true`, requesting trashed metadata for idempotent no-ops.
Missing trashed metadata and PATCH responses that do not confirm the requested
state are failures, including a restore still affected by a trashed parent.
Metadata write access (`drive auth login --write`) is required. Google retains
its own ownership and shared-drive role checks; API refusals are reported as
failures. Real attempts, including refusals and no-ops, write the existing
best-effort Drive mutation log; previews do not. These are not the fail-closed
lease audit records of ADR-0080 §11. Exit status follows ADR-0070 §10: mechanical
completion returns zero and structured output carries the operation result.

We will keep `CreatedValuesFailed` and `CreatedTextFailed`. Their messages will
name the new file ID and an explicit trash command requiring a trash grant.
Create never initiates a rollback mutation.

## Consequences

Scripts can clean up individual scratch files and operators can undo trash
before Drive purges them. Existing grants retain their meaning and descendant
denies cannot be bypassed by folder mutations. Dry runs and structured results
follow the existing mutation surface.

Trash is temporary recovery, not a durable backup. Trashed files can still be
accessible to collaborators until permanently deleted. Restoring a file whose
parent is trashed may fail or leave it effectively trashed; the command does
not restore the folder. Untrash can be blocked by later rule changes. Google
permission failures remain possible even after a locally allowed preview.

Folder teardown, permanent deletion and MCP writes need future designs. Every
new permission operation adds config vocabulary, CLI help and tests. Live API
verification is distinct from mocked protocol tests and must use disposable
files rather than arbitrary user data.
