# ADR-0073: Google Sheets API Support for the Drive Integration

## Status

✅ Accepted (2026-09-06)

**Extends [ADR-0069](adr-0069.md), [ADR-0070](adr-0070.md) and
[ADR-0071](adr-0071.md), reverses none.** ADR-0069 shipped Drive read-only;
ADR-0070 added metadata writes; ADR-0071 added content mutation behind a
folder-scoped permission gate. This ADR adds the first *second-host* Google
API to the integration and the first cell-level access to a Google-native
document. It answers ADR-0071 §9's explicit deferral — "editing them is a
Docs-API/Sheets-API problem, out of scope here" — for Sheets specifically.

Landed under this ADR so far (issue #1589, Phases 1–2): the shared
`GoogleApiClient` transport core (§1), `SheetsClient`, the pure A1-notation
module, `spreadsheets.get` / `values.get` / `values.batchGet`, and
`drive sheets info` / `drive sheets read`. The mutating verbs (§3–§5, §10–§11)
are specified here and land in the commits following this ADR's acceptance —
the same sequencing ADR-0071 used, where the ADR is written and accepted
before, not after, the mutating phase.

## Context

The Drive API treats a Google Sheet as an opaque native document. `files.export`
renders it to a foreign format; a media `files.update` replaces the whole
document by re-importing one. There is no Drive-level notion of a range, a row
or a cell. Two consequences shaped this issue:

- `drive read --content` on a Sheet exports the **first sheet only** as CSV,
  because Drive's export API has no multi-sheet CSV format.
- `drive edit` refuses every Google-native document client-side, before the
  permission gate runs, because a raw media `PATCH` has no meaningful content
  to replace.

Anything cell-level has to go through `https://sheets.googleapis.com/v4/...`.
That is a **different host** from the `https://www.googleapis.com/drive/v3/...`
prefix `DriveClient` was built around — not a different path on the same host,
which is what makes it an architectural change rather than a new façade
method.

Two alternatives were considered and rejected. **Round-tripping through
export/import** (export xlsx, edit locally, re-upload with convert-on-import)
loses formulas, formatting and multi-sheet fidelity, rewrites the whole
document for a one-cell change, and gives the gate and the request log nothing
finer than "the file changed". **A top-level `omni-dev sheets` tree** would
need its own `auth`/`account` commands or a cross-tree reference to Drive's,
and — decisively — could not call `FilesApi`'s `pub(in crate::drive)` mutating
methods without widening the visibility fence that makes gate bypass
impossible by construction.

## Decision

### 1. A shared transport core, and two distinct client types over it

The host-agnostic half of `DriveClient` — OAuth session, one-shot 401
refresh-and-retry, 429/quota backoff, the request-log hook, and error-envelope
parsing — moves into `GoogleApiClient` (`src/drive/api_client.rs`).
`DriveClient` and `SheetsClient` are thin wrappers over it, each owning only a
default host and an env override (`DRIVE_API_URL` / `SHEETS_API_URL`).

They stay **distinct types** rather than one client re-based onto a second
URL. `FilesApi::new` takes a `&DriveClient`, so a Sheets-hosted client cannot
be handed to it and silently issue `/drive/v3/files` against
`sheets.googleapis.com`. A shared type would make that a runtime bug; two
types make it a compile error.

The session is held behind an `Arc` and **shared** by a derived client. A
`sheets write` necessarily talks to both APIs — Drive for the `files.get` and
ancestor-chain walk that feed the gate, Sheets for the cells — and two
independent sessions would refresh the same refresh token twice for one
command.

Gmail (`GmailClient`) is a near-verbatim twin of the pre-extraction
`DriveClient` and is deliberately **not** migrated onto the core. It carries
its own `GmailSession`, so sharing would need a `TokenSource` abstraction that
nothing in this issue requires.

### 2. Both Google error envelopes, because one of them is silent

Drive v3 returns the legacy envelope, whose machine-readable code lives at
`error.errors[0].reason`. Sheets v4 — like other newer Google services —
returns the `google.rpc` envelope instead:

```json
{"error":{"code":403,"message":"...","status":"PERMISSION_DENIED"}}
```

with **no `errors[]` array at all**. Reading only the legacy shape yields
`reason: None` for every Sheets failure, which disables both
`append_write_scope_hint` (it matches on the reason string) and the quota
retry. Neither fails loudly; they simply never fire. `error_reason` therefore
reads legacy-then-`status`, and the scope hint matches `PERMISSION_DENIED`
alongside `insufficientPermissions`.

This is recorded as a decision rather than a bug fix because it is a standing
constraint: every future Google API added to this transport must be checked
against both envelope shapes, and a new one that invents a third will fail the
same silent way.

For the same reason `DriveError::ApiRequestFailed` carries the API name rather
than hardcoding `"Drive"`: both APIs share one transport and one error type, so
a Sheets 403 that announced itself as a *Drive* failure sent the reader to the
wrong API's documentation. That is not hypothetical — a `drive.file` grant
cannot write a Sheet created in a browser, so it is the first error many users
will meet. The request-log `service` tag stays `"drive"` for both (§1); only the
human-readable message differs.

### 3. A new `DriveOperation::SheetsWrite`, not a reused `Edit`

Reusing ADR-0071's `Edit` for cell writes was the issue's original proposal
and is **rejected**. Anyone who wrote `allow: ["edit"]` on a folder did so when
`drive edit` categorically refused every Google-native document. Reusing
`Edit` would retroactively convert that existing grant into "may rewrite cells
in every Sheet in this folder" — no config change, no re-consent, no way for
the operator to have anticipated it. That is precisely the shape of silent
privilege widening ADR-0071's default-deny posture exists to prevent.

A new variant is fail-closed in both directions. Forwards: it defaults `Deny`
like every other write, so cell writes are off until explicitly granted.
Backwards: an older binary reading a config naming the new operation fails
`Settings::load()`, and `active_account_rules` degrades to an empty rule set,
which denies everything.

The cost — one enum variant, its `Display` arm, the `OperationArg` clap
mirror, a snapshot line and a docs table row — is small, and the gate's rule
vocabulary growing alongside genuinely new capability is correct, not
fragmentation.

### 4. A parentless shared Sheet is refused distinctly, not generically

`files.get` returns only the parents the caller can see. A Sheet shared by
link or email — the most common way anyone obtains one — comes back with
`parents: []`. The ancestor chain is then empty, `write_gate::resolve` falls
through to `default_policy`, and the write is denied with `decided_by: None`.

That is correct and fail-closed, but it is **not explicable** to the operator:
`decided_by: None` today means "no configured rule matched", and there is no
folder id anywhere they could name in a rule to fix it. The two cases must not
be conflated, so a target with no visible parents produces its own
`RefusedNoVisibleParents` outcome, whose message says what happened and what
would resolve it (add the Sheet to a folder in your own Drive, then grant that
folder).

Granting a rule against a **file id** rather than a folder id would solve this
properly. It changes ADR-0071's rule schema and its resolution algorithm, so
it is deliberately a follow-up with its own design pass, not a clause smuggled
in here.

### 5. Reading is ungated, exactly as the rest of the Drive read surface is

`sheets info` / `sheets read` consult no permission gate, matching
`search`/`read`/`dedupe`. ADR-0071 §11 records read-path enforcement as a
known, scoped gap across the whole integration, pending a batching/caching
design; these commands inherit that gap rather than opting out of it, and will
inherit its resolution.

### 6. `-o table` renders CSV; no second output flag

`sheets read` uses the tree's single `-o/--output` selector, and its `Table`
branch emits CSV. A command-local `--format csv|json|yaml` was considered and
rejected: it would make `sheets read -o json --format csv` expressible and
contradictory, and would fork the output convention (issue #1125) on its first
exception. Rendering CSV under `Table` follows the in-tree reading that
`Table` means "one command, one rendering", not a literal grid.

Two rendering rules follow from the API's shape and are chosen explicitly:

- **CSV pads rows** to the widest row in that sheet. The API truncates
  trailing empty cells per row, so raw rows are ragged and a ragged CSV is
  malformed. `-o json`/`-o yaml` preserve raggedness, which is the truthful
  shape.
- **Cell values are not sanitized; sheet titles are.** `sanitize_for_terminal`
  strips all control characters including newlines, which would silently
  destroy legitimate multi-line cell text and make the CSV non-round-trippable
  — data corruption in a data-extraction tool. Cell values are *content*, and
  `drive read --content` already prints file content verbatim; `output_as`
  likewise does not sanitize the JSON/YAML paths. Sheet titles rendered as
  chrome (the `# <title>` header, `sheets info`'s listing) **are** sanitized.

Multi-sheet JSON/YAML emit an ordered **list** of `{title, values}` objects
rather than a `{title: rows}` map: workbook order is meaningful and a map's key
order is not guaranteed.

### 7. A1 quoting is ours; A1 grammar is the server's

`src/drive/sheets/a1.rs` is pure, with no network dependency, mirroring
`write_gate.rs`/`visibility.rs`. It owns quoting, which is not optional — a
title containing a space, an apostrophe or a `!` produces a silently wrong
range otherwise. Titles are therefore **always** quoted with inner
apostrophes doubled, which is also the only rule that disambiguates a sheet
literally titled `A1`.

It deliberately does **not** validate A1 grammar, resolve defined names,
reject unbounded forms or check that a sheet exists. `Sheet1!A:A`,
`Sheet1!1:2`, a bare `Sheet1` and a bare defined name are all legal, and a
naive validator rejects all of them. Rejecting a legal range client-side is a
worse failure than forwarding an illegal one, and the server already returns a
clear error — the identical stance `resolve_export_mime_type` takes for export
MIME types.

Supplying `--sheet` alongside a `--range` that already names a sheet is an
error rather than a precedence rule: the two can disagree, and guessing writes
to the wrong sheet.

### 8. Ranges are percent-encoded into the URL path

Sheets puts the range in the URL *path* (`/v4/spreadsheets/{id}/values/{range}`),
and a range embeds a caller-influenced sheet title. A `#` truncates the path
into a fragment, a `?` starts a query string, a `/` invents a path segment, a
space is invalid — each silently reading or writing the wrong cells. Range URLs
are therefore built through `path_segments_mut()`, never string interpolation.
`files_api.rs`'s `format!("/drive/v3/files/{file_id}")` sites are safe only
because Drive ids are `[A-Za-z0-9_-]`; that is not a pattern to generalise
from.

A whole-workbook read is capped two ways, both erroring rather than
truncating: `values.batchGet` chunks at a fixed number of ranges per request
(each is a percent-encoded quoted title in the query string), and a workbook
beyond a hard sheet count is refused outright. Silently returning part of a
workbook is indistinguishable from a workbook that small.

`spreadsheets.get` is always sent with an explicit `fields` mask. Unmasked, it
returns every cell of every sheet — an out-of-memory failure on a large
workbook, not a slow request.

### 9. Single-target linear verbs, with `--dry-run` parity by construction

The mutating verbs use `rename.rs`/`content_edit.rs`'s linear shape — one
async function per verb, gate check then a `dry_run` early return then the
mutating call — not `file_move.rs`'s Plan/Execute split, which exists to
amortize a shared-destination fetch across a batch these verbs do not have.
`--dry-run` and a real run share the same gate classification because they are
the same code path, not by convention. There is no interactive confirmation,
unchanged from ADR-0070 §6 and ADR-0071 §7.

The mimeType refusal mirrors `drive edit`'s inverted: anything that is **not**
`application/vnd.google-apps.spreadsheet` is refused before the gate and
before any Sheets call, since the operation is nonsensical rather than
disallowed. A shortcut *to* a spreadsheet gets its own refusal message rather
than the generic one, matching `drive read`'s existing treatment.

### 10. Logging reuses `RecordKind::DriveMutation`

No new record kind, following ADR-0070 §7 and ADR-0071 §8. `operation` becomes
`"sheets-write"` / `"sheets-append"` / `"sheets-clear"` / `"sheets-create"`,
and `DriveMutationOutcome` gains omit-if-absent context fields for the range
and the API's reported `updatedRows`/`updatedColumns`/`updatedCells`. Logging
happens inside the engine module, never the CLI layer, so a future MCP caller
cannot bypass it by construction.

### 11. `sheets create` owns its verb; the seeding write only checks for an explicit deny

`sheets create` does not compose `drive create`'s public engine, which logs
internally and unconditionally — composing it would emit a phantom
`["drive","create"]` record for a command the user never typed, alongside the
`sheets-create` one. It calls `FilesApi::create` directly, so one user-visible
verb produces exactly one gate check for `Create` and one log record.

The optional `--values` seed is a `values.update` on the id `files.create`
just returned, never a caller-supplied id. Routing it through the ordinary
`sheets write` engine (which honors default-deny like every other write)
would re-run the gate under `SheetsWrite` against the new file's parents,
which defaults to `Deny` when no rule mentions `sheets-write` at all — so
`sheets create --values` would create an empty spreadsheet and then report
itself blocked on every folder that only grants `create`. The `Create`
verdict alone authorises the pair, *unless* an operator has gone out of
their way to add an explicit `deny: ["sheets-write"]` rule on this folder —
the seed step resolves that operation too and refuses the seed when
`Decision::decided_by` is `Some` (an explicit rule matched), never when it's
`None` (the bare default policy). This preserves the "no `sheets-write` rule
needed to seed" behavior for the common case while still honoring a
deliberate deny. It costs a second `files.get` on the same folder when
`--values` is given; this is defensible only because the target id is one
this same invocation just created inside an already-cleared folder, and
`drive upload` sets the precedent of writing content under `Upload` rather
than `Edit`.

There is no `files.delete` anywhere in the integration, so a seed that fails
after a successful create cannot be rolled back. That outcome gets its own
result variant carrying the new file id, so a created-but-empty spreadsheet is
never reported as a clean success and is never left unfindable.

### 12. CLI-first; MCP tools deferred

`drive_sheets_read`/`drive_sheets_write` follow the identical CLI-first
deferral ADR-0070 §9 and ADR-0071 §11 already set. Structural edits via
`spreadsheets.batchUpdate` — adding, deleting and renaming sheets, inserting
and deleting rows and columns, formatting, protected ranges — are out of scope
entirely and need their own safety analysis; row and column deletion is the
sharp edge, where one call destroys far more than its arguments suggest.

### 13. Exit code convention

Unchanged from ADR-0070 §10 and ADR-0071 §12: exit 0 regardless of individual
`Blocked`/`Failed` outcomes. Scripts detecting a refusal must inspect the
output, not `$?`.

## Consequences

- **No new OAuth grant and no new trust boundary.** The Sheets API accepts the
  Drive scopes, so `drive.readonly` already covers reading and ADR-0071's
  `--write-file`/`--write-full` tiers already cover writing, with the same
  ownership split (`drive.file` reaches only app-created Sheets). The Sheets
  host is a second endpoint the same bearer token is presented to. The
  narrower `spreadsheets` scope was considered and rejected: it is narrower
  than `drive` on one axis but *broader* than `drive.file` on another, and the
  local gate bounds writes better than either.
- **Blast radius per call is smaller than `drive edit`'s**, not larger.
  `drive edit` replaces an entire file; `sheets write` touches one declared A1
  range whose dimensions `--dry-run` reports. `sheets clear` is the
  destructive one and gets the same gate and `--dry-run` treatment, with no
  `--force`.
- **An existing `write_permissions` config keeps meaning exactly what it
  meant.** This is the direct consequence of §3, and the reason a new
  operation was worth its cost.
- **A shared Sheet cannot be written to until it lives in a folder**, and the
  refusal says so. This is a real usability limitation, recorded as such
  rather than worked around, with file-id-keyed rules as the scoped
  follow-up.
- **A refusal stays exactly as auditable as a success** — a gate-refused write
  produces a `drivemutation` record with zero Sheets calls made, matching
  ADR-0070 and ADR-0071.
- **Sheets responses contain user data.** `OMNI_DEV_LOG_BODIES` stays opt-in
  and off by default, unchanged; only the range and the API's own counts are
  recorded as context.
- **Sync obligation.** [docs/drive.md](../drive.md) documents the `drive
  sheets` command tree, the CSV/JSON rendering rules, the `SheetsWrite`
  operation in the write-permission table, and the shared-Sheet limitation;
  [docs/log.md](../log.md) documents the new `drivemutation` operations and
  context fields. Keep both in sync when this ADR's decisions change.
