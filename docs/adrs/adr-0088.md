# ADR-0088: Exact Codex Session State from a Private, Poll-Only App-Server

## Status

✅ Accepted (2026-09-25, #1910)

## Context

[ADR-0087](adr-0087.md) made Codex's hooks a feed of the sessions service. Hooks
only *infer* a Codex session's state. An approval's resolution is read off the
next tool event. Automatic review ("Approve for me") fires the same
`PermissionRequest` a human prompt does, so the tree flashes a false "waiting"
for a few seconds. And the TUI's clarifying-question UI needs a feature Codex has
not shipped by default.

Codex's **app-server** knows the exact state. Its JSON-RPC API has
`thread/loaded/list` (the threads in memory) and `thread/read` (one thread's
metadata), whose `status` is `idle`, `systemError`, `notLoaded`, or `active` with
`activeFlags` `waitingOnApproval` / `waitingOnUserInput`. #1861 found it
unreachable for the sessions users actually run. The VS Code extension and Codex
Desktop each spawn a **private stdio** app-server, and the shared daemon
(`codex app-server daemon`) is opt-in and absent by default. Prior art
(codex-agents) warns that a client *subscribed* to a thread receives that
thread's actionable approval requests, so a naive observer could duplicate, or
even answer, an approval.

Measured on `codex-cli 0.155.1` for this decision:

- `codex app-server --listen unix://PATH` serves the protocol as a WebSocket over
  a Unix socket, and `codex --remote unix://PATH` runs the normal TUI against it.
- A second connection that only calls `initialize`, `thread/loaded/list` and
  `thread/read` saw the TUI's thread go `active[]` →
  `active[waitingOnApproval]` → `idle` (declined) in step with the screen, and
  received broadcast *notifications* but **no server request** — approvals go
  only to the connection that owns the thread.
- The server also loads side threads: an `ephemeral` one with
  `threadSource: "system"` (it titles the chat), next to the user's
  `threadSource: "user"` thread.
- When the remote TUI exits, the server keeps running ("Any running work
  continues"), so whoever starts the server must stop it.

[ADR-0057](adr-0057.md) solved the same problem for Claude with a process
wrapper in the launch path, which fails open and reports authoritative state.

## Decision

We will add `omni-dev codex-wrap -- codex [args…]`, the Codex analogue of
`claude-wrap`. It gives exact state to the Codex sessions **omni-dev launches**,
and only those.

- **A private server per wrapper.** The wrapper starts
  `codex app-server --listen unix://<runtime-dir>/codex-wrap-<pid>.sock`, in the
  daemon's `0700` runtime directory, waits for it to accept connections, and runs
  `codex --remote unix://… <args>` in the foreground on the caller's terminal.
  When the TUI exits it ends the sessions it reported, stops the server
  (`SIGTERM`, then a kill after 2 s) and removes the socket. It attaches to no
  server it did not start: not the IDE's, not Desktop's, not the shared daemon.
- **Poll, never subscribe, never answer.** The observer connection calls only
  `initialize`, `thread/loaded/list` and `thread/read` (without turns), once a
  second. It never starts, resumes or subscribes to a thread, and any server
  request that reaches it is dropped unanswered. It cannot approve, deny or
  duplicate an approval.
- **Exact state, the Feed 4 form.** `active` maps to `working`, or to
  `waiting_for_permission` / `waiting_for_input` by flag (approval first). `idle`
  and `systemError` map to `idle`. The state is sent as the existing
  authoritative `{ "stream_state": … }` `observe`, tagged `agent: codex`, on
  every poll rather than only on a change: the same session also gets inferred
  hook and rollout-watcher reports, and re-asserting the exact state overrides
  them within a second (a repeat sighting does not bump the registry). That also
  keeps an idle session inside the TTL. A thread that unloads, or that reports
  `notLoaded`, is ended; one whose read fails is skipped for that poll.
  Subagent, ephemeral and `threadSource` ≠ `"user"` threads are not sessions and
  are not reported.
- **Fail-open**, as ADR-0057. An invocation the remote TUI does not serve (a
  non-interactive subcommand such as `exec`, no terminal, or a caller's own
  `--remote`) is exec-replaced by plain `codex`, as is one whose server does not
  come up within 10 s. If the observer cannot connect, the TUI still runs,
  unobserved. Reports are bounded, fire-and-forget, and never block the TUI.
- **A Codex tab.** `worktrees ui` gains a Codex tab kind (`alt-⇧x`, and the
  menus), launched as `omni-dev codex-wrap -- codex`, as the Claude tab is
  launched through `claude-wrap`.

## Consequences

**Positive.** Codex sessions started from omni-dev report exactly when they are
waiting on an approval or on input, with no hook inference, no false flash under
automatic review, and no dependence on the TUI's under-development
`request_user_input` feature. The observer is structurally unable to act on a
thread. No new daemon op, wire field or trust boundary: reports ride the
existing `observe` op over the daemon's `0600` socket, the private server's
socket lives in the `0700` runtime directory, and nothing is logged or
persisted.

**Negative.**

- It covers only sessions launched through the wrapper. IDE and Desktop chats,
  and a `codex` started by hand, stay on the hooks.
- A wrapped session runs on a second Codex process (the private server). Its
  hooks still fire, from that server, so the same session also gets the
  inferred hook reports; the wrapper's authoritative report corrects them within
  a second.
- If the wrapper is killed with `SIGKILL`, its server is orphaned until killed by
  hand. The server shares the terminal's process group, so closing the terminal
  (`SIGHUP`) takes it down too.
- On exit the TUI prints a "Reconnect: codex --remote …" hint for a server the
  wrapper has already stopped.
- It depends on an app-server API Codex marks experimental; a change to it
  degrades to "no reports", never to a failed launch.

**Neutral.** The mapping reuses the Feed 4 `StreamState` form, so the engine's
state machine and every consumer are unchanged. The ADR-0087 hook feed and the
#1909 rollout watcher still cover every Codex session, wrapped or not.
