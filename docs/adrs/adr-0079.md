# ADR-0079: Restoring an Archive into a Mailbox via `messages.insert`

## Status

✅ Accepted (2026-09-08)

**Extends the Gmail-archive lineage** — [ADR-0064](adr-0064.md) (presence-on-disk
idempotence, immutable `.eml`/mutable manifest), [ADR-0065](adr-0065.md)
(`--extract-attachments`), [ADR-0068](adr-0068.md) (concurrent multi-account
sync) — with the archive's missing direction. Those ADRs cover capturing and
reading a mailbox; this one covers restoring it. Reverses none of them: the
archive format (`manifest.jsonl` + sharded `.eml` files) is read-only input
here, unchanged.

## Context

`gmail sync`/`sync-all` produce a durable local archive; `render`/
`extract-attachments` read it back. Nothing puts messages *into* a mailbox —
the Gmail write surface was `messages.batchModify` only (label mutation on
already-present messages). Issue [#1655](https://github.com/rust-works/omni-dev/issues/1655)
closes that gap with `gmail insert`, motivated by mailbox consolidation
after an address change: an archived legacy mailbox needs to become
searchable, in-order, and (for sent mail) complete inside a current account.

Two premises in the issue turned out to be wrong during design, and both
shaped the decisions below:

- **`render` has no filtering to reuse.** Its entire selection is `--all`
  over non-deleted records; there is no date/query/id filtering anywhere in
  `src/cli/gmail/**`. Selection (`src/cli/gmail/selection.rs`) is net-new,
  factored so `render` can adopt it later — a follow-up, not part of this
  change.
- **`manifest.jsonl` already carries the dedupe key** (`rfc822_msgid`, set by
  `sync` from the raw headers) — no `.eml` re-parsing is needed to compute
  it, only whitespace/angle-bracket stripping.

Four decisions here are load-bearing enough to record.

## Decision

### 1. Idempotency is a local ledger, not a per-message remote probe

Gmail assigns a **new** id to every inserted message, so — unlike `sync`/
`extract-attachments`, which check presence-on-disk against the *source*
mailbox's own id (ADR-0064) — there is no id to check presence against
before insertion happens. Two designs were available: probe the destination
before every insert (`rfc822msgid:` search, 5 quota units), or maintain a
local `insert-ledger.jsonl` (a sibling of `manifest.jsonl`) recording what
has already been sent.

**The ledger wins.** A probe costs 5 units and a network round-trip *on top
of* the 25-unit insert itself, so a 5,000-message run would issue 10,000
API calls instead of 5,000 — and Gmail's search index can lag a real insert
by seconds to minutes, so the probe isn't even reliably correct for a run's
own just-inserted mail. The ledger costs nothing per message and makes a
re-run of a completed batch free. The probe survives as **`--verify-remote`**,
an opt-in supplement for the one case the ledger can't help with: a first
run into a mailbox that may already hold some of this mail from another
source, or recovery after the ledger itself is lost.

**The ledger's key is `(destination address, archived Message-ID)`, not
Message-ID alone.** The archive's own `state.json` names the *source*
mailbox (ADR-0064) — for the consolidation use case, precisely not where
mail is going. A ledger keyed only on Message-ID would make a completed
restore into account A silently suppress every insert into account B, the
opposite of what a multi-destination restore tool needs. Consequently
`sync::state::validate_identity` is **deliberately not called** anywhere in
`gmail insert` — that check exists to keep one archive tied to one source
mailbox, a different job than this command's.

A missing/unparseable `Message-ID` falls back to an `archive-id:<source
id>` sentinel key, scoped by the source archive's own id — collision-free
within one archive, though (having no real Message-ID) it can never be
confirmed via `--verify-remote`'s probe.

### 2. Transport is `uploadType=multipart` exclusively — no JSON `raw` path

`messages.insert` exposes two request shapes: a JSON body with a
base64-encoded `raw` field, or a `multipart/related` media upload with the
`.eml` bytes verbatim. Only the second is implemented. The JSON path costs a
33% size inflation from base64 and a correspondingly lower effective size
ceiling for no offsetting benefit — there is no scenario where an archived
`.eml` is small enough for the JSON path but too large for multipart and
not the reverse. Supporting both would mean two code paths that differ only
in how they fail on large mail, for a size class multipart already
handles. `MessagesApi::insert` therefore has one call shape, splicing the
`.eml` in byte-exact via the multipart encoder shared with
`crate::drive::files_api::FilesApi::upload` (`src/utils/multipart.rs`,
promoted for this reason).

### 3. Label replay is a system-label allow-list, with `--drop-label` as the escape hatch

An archived message's Gmail labels are replayed onto its inserted copy by
default, filtered through a fixed allow-list
(`INBOX`/`SENT`/`UNREAD`/`STARRED`/`IMPORTANT`/`SPAM`/`TRASH`/`CATEGORY_*`)
rather than a heuristic (e.g. "looks like a system label") or a full
passthrough. Three consequences follow directly from that shape:

- **This is what satisfies the issue's "preserve sent mail" requirement for
  free.** `messages.batchModify` (the only pre-existing write) *forbids*
  adding `SENT` — Gmail's own asymmetry, not this tool's — so `insert` is
  the only mechanism able to restore mail the source mailbox sent rather
  than received.
- **`DRAFT` is a real Gmail system label but is excluded from the
  allow-list.** Inserting a message carrying it creates a row in Drafts
  with no backing Draft resource, which the destination account cannot
  properly edit or send — a state worth refusing outright rather than
  producing.
- **User labels never replay.** A source mailbox's user-created label ids
  are foreign to the destination — they don't exist there, or collide with
  an unrelated label sharing that id in the new mailbox. Only the fixed
  system set is safe to carry across mailbox boundaries unmodified.

`--drop-label` (repeatable) is applied *after* the allow-list filter, so it
can only ever remove a label that would otherwise have replayed — most
usefully `--drop-label INBOX --drop-label UNREAD`, since faithful replay
would otherwise dump the entire restored archive into a live Inbox with no
warning. `--label NAME` (resolved against `labels.list`, never
auto-created) unions on top, as the one reliable handle for "what came from
the archive" once inserted — the raw headers still name the original
recipient, so `to:` searches on the destination won't find it.

### 4. The ledger is written after the 2xx, accepting duplicates over gaps

Two orderings were available for one insert: write the ledger entry first
(an intent log), or write it after Gmail confirms success. Writing first
converts a crash between the write and the request into *silently missing
mail* — the run believes a message was inserted when it never was, and
`--verify-remote` cannot rescue this case since there is genuinely nothing
on the destination to find. Writing after risks the opposite: a crash
between Gmail's 2xx and the local flush leaves a bounded number of messages
(at most `concurrency` in flight, plus up to
`INSERT_LEDGER_CHECKPOINT_INTERVAL - 1` completed-but-uncheckpointed)
inserted on Gmail's side but unrecorded locally, so a following run inserts
them again.

**Write-after is the decision**, because a duplicate is the strictly better
failure mode for a restore/backup tool: it is visible in the destination
mailbox, and deletable (the ledger's `inserted_id` field doubles as an undo
list — `gmail label add --label TRASH` over the affected ids, since
`batchModify` permits adding `TRASH`). A silent gap defeats the entire
purpose of a restore and offers no way to discover it occurred short of a
manual audit against the source archive. `--verify-remote` is the
documented recovery path after an interruption.

## Consequences

- **A ledger corrupted or discarded is a hard failure, never a silent
  reset** — `InsertLedger::load` follows `manifest.rs`'s posture
  (ADR-0064), not `state.rs`'s: losing this file doesn't lose recoverable
  metadata, it risks duplicating thousands of messages into a live mailbox
  on the very next run.
- **Default `--concurrency` is 4, not `sync`'s 20.** `messages.insert` costs
  25 quota units against the same 250-units/second bucket `sync` paces
  against (5x a `messages.get`'s 5 units), so the limiter admits roughly 10
  requests/second regardless of fan-out width — a wider window buys no
  throughput and only enlarges the crash-duplication window §4 accepts.
- **Selection (`src/cli/gmail/selection.rs`) is local-only and not Gmail
  query syntax** — a deliberate scope cut, not an oversight; it exists to
  filter an already-synced `manifest.jsonl`, not to replicate Gmail's
  search grammar. `render` has no selector today and could adopt this one
  later without any change to this ADR's decisions.
- **`--dry-run` makes exactly two read-only calls** (`getProfile`,
  `labels.list`) **and zero writes** — no `messages.insert`, no ledger file
  created — so a `--dry-run` preview never itself contributes to §4's crash
  window.
- **Sync obligation.** [docs/gmail.md](../gmail.md#insert) documents the
  full command surface, the archive layout gains `insert-ledger.jsonl`, and
  the `--verify-remote`-after-interruption recovery guidance. Keep it in
  sync when any decision above changes.
- **Known, accepted limitations, not follow-up work**: a message with a
  missing/unparseable `Date:` header is stamped with the insertion moment
  (Gmail's own default) with no override — `insert` has no equivalent to
  IMAP `APPEND`'s explicit `INTERNALDATE`, and synthesising a `Date:` header
  is rejected outright, since it would break byte-exactness and invalidate
  DKIM, turning a faithful archive into a forged one. Threading
  reconstruction is best-effort (no `threadId` is ever sent — source
  thread ids are foreign to the destination; Gmail reconstructs from
  `In-Reply-To`/`References` already in the raw bytes) and not
  machine-verifiable by a wiremock test — confirmed by manual verification
  against a real mailbox only.
