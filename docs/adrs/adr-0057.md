# ADR-0057: Authoritative Claude Session State via a Stream-Tee Process Wrapper

## Status

✅ Accepted (2026-07-25; amended 2026-07-30 to rewrite Claude's own OSC
terminal-title sequence with a colour-coded model identity, #1445)

## Context

[ADR-0052](adr-0052.md) built the sessions tracker on three feeds and accepted a
ceiling: session state is **inferred**. `waiting_for_permission` arrives only if
the user has installed the `Notification` hook, and `working`/`idle` is guesswork
from `PreToolUse`/`Stop` plus transcript growth. Anthropic closed the request for
dedicated session-state events as *not planned*
(anthropics/claude-code#43058), so nothing better was expected to arrive.

The cue this unblocks — per-worktree busy/idle/waiting badges in the Worktrees
tree (#1406) — is only worth building on state good enough to trust. The
high-value signal is precisely the one the inference cannot see: **a session
blocked on a permission prompt in a window you are not looking at**.

A reverse-engineering pass over the installed `anthropic.claude-code` extension
(v2.1.220) established where that state actually lives, and every alternative
route to it was checked and rejected:

| Route | Verdict |
|---|---|
| The extension's own 3-state model (`idle`/`running`/`waiting_input`) | ❌ Held in extension memory and a private webview channel; no extension API, context key, command, or `.exports` (the [ADR-0052](adr-0052.md) finding, still true) |
| The IDE websocket, the DOM, any on-disk file | ❌ None carries it |
| The transcript files | ❌ `session_state_changed`, `init`, `result` and `can_use_tool` are **stream-only** and never persisted, so watching transcripts recovers working/idle at best |
| Claude Code hooks | ⚠️ `Notification` gives `waiting_for_permission`, but only when the user installs it, and the rest stays inferred |
| The `claude --output-format stream-json` **stdout stream** | ✅ The ground truth the extension itself reads |

The stream is reachable without patching anything: the extension's supported
`claudeCode.claudeProcessWrapper` setting names an executable it launches Claude
through. Decoding its `resolveClaudeBinary` shows the exact contract — with the
setting present, it spawns `<wrapper> <real-cmd> <real-args…>` where `real-cmd` is
either `<node> <cli.js>` or the native binary, always with
`--output-format stream-json --verbose --input-format stream-json`. The spawn is
`child_process.spawn(cmd, args, {stdio:["pipe","pipe","pipe"]})` with **no shell**,
so the setting must name a single executable file: it cannot carry arguments, and
a wrapper is not something a user should have to hand-write.

One protocol detail shapes the design. A permission prompt is a
`control_request` with subtype `can_use_tool` that travels **CLI → editor on the
child's stdout**; the answer is a `control_response` that travels **editor → CLI on
the child's stdin**. Seeing only stdout would show a session entering
`waiting_for_permission` and never leaving it.

Sitting in Claude's launch path is the risk this decision has to buy down: a
wrapper that misbehaves does not degrade a badge, it stops Claude from running.

## Decision

We will add a fourth, **authoritative** feed to the sessions service: a
transparent process wrapper, `omni-dev claude-wrap`
([`src/cli/claude_wrap.rs`](../../src/cli/claude_wrap.rs)), that the Claude
extension launches Claude through and that tees the stream-json stdio to the
daemon.

**We will keep the wrapper structurally fail-open.** The byte-forwarding path
never depends on the observer, the parser, or the daemon: each direction is
pumped write-then-flush *before* the tee is attempted, the tee is a bounded
channel written with a non-blocking `try_send` that drops lines when full, and
every daemon error is swallowed exactly as the `sessions hook` sink swallows its
own. The wrapper drains the child's stdout to EOF before reaping, so forwarding is
lossless, and it exits with the child's own status (`128 + signo` when signalled),
forwarding `SIGINT`/`SIGTERM` on. It does not put the child in a new process
group, which would break job control. When stdout is a terminal there is no
stream-json to observe, so it `exec`-replaces itself with the child outright. The
worst case is *losing visibility*, never *Claude failing to launch*. One narrow,
deliberate exception to "never depends on the observer" — the terminal-title
rewrite — is described below, [added by amendment](#rewriting-claudes-own-terminal-title-sequence).

**We will tee both directions.** The pure state machine
([`src/sessions/stream.rs`](../../src/sessions/stream.rs)) takes the direction a
line was seen in, correlates `can_use_tool` requests with their responses by
`request_id`, and treats an outstanding request as outranking whatever the content
messages last implied — so a reply still streaming while the user is being asked
cannot mask the prompt. A completed turn (`result`) clears any stranded request, so
protocol drift can only ever end the wait early, never pin a session on
`waiting_for_permission` forever.

**We will reuse the existing ingest path rather than add one.** The engine gains a
single event variant, `SessionEvent::StreamState(SessionState)`
([`src/sessions.rs`](../../src/sessions.rs)), whose `for_event` arm returns the
carried state verbatim — the "authoritative versus inferred" distinction, expressed
in one line. It rides the existing `observe` op and `ObserveRequest` wire shape, so
there is no new op, no new engine method, and no adapter change; the adapter's
`cwd`→`repo` git enrichment and the `cwd`→window `source` join apply unchanged.

**We will never log or persist conversation content.** The wrapper reads only the
message `type`/`subtype`, the identity fields (`session_id`, `cwd`, `model`) and
outstanding permission ids out of each line. Nothing else is materialized, and
reports go to the daemon's existing `0600` Unix socket.

**We will ship the shim, because the setting cannot carry arguments.**
`omni-dev sessions install-wrapper` writes a `0700` one-line `exec` shim beside the
daemon socket and idempotently points `claudeCode.claudeProcessWrapper` at it;
`uninstall-wrapper` reverses both, clearing the setting only when it still points
at our own shim. VS Code settings files are JSONC, and a file with comments or
trailing commas cannot be rewritten safely — that case fails with the exact line to
paste rather than a bare parse error, with the shim already written so the hint is
actionable.

**We will re-report the current state every 30s while the child lives.** Comfortably
inside the registry's 300s TTL, this makes the wrapper the one feed with real
liveness: bounded by the process's actual lifetime rather than by observed
activity, so a session idle at the prompt for an hour no longer ages out.

### Rewriting Claude's own terminal-title sequence

*Added by amendment (2026-07-30, #1445).*

Concurrent Claude sessions in separate VS Code terminal tabs are visually
indistinguishable: Claude asserts, and continuously re-asserts, an OSC `0`/`2`
title sequence carrying only its own version string
(anthropics/claude-code#56933 confirms this live), and there is no other
channel to tell tabs apart — the terminal API only lets the *creating*
extension set `iconPath`/`color`, and only at `window.createTerminal()` time,
with no way to change either afterward or from an extension that did not
create the terminal (anthropics/claude-code#56925, closed not-planned by
Anthropic itself). A tab title is the only per-session surface left.

We will rewrite that sequence in flight, inside the pump's `FromClaude`
direction only, prepending a colour-circle-emoji-and-family prefix —
`🟠 Fable`/`🟡 Opus`/`🟢 Sonnet`/`🔵 Haiku`, or `⚪ Claude` for anything else —
classified from the session's model id via `ModelRegistry::get_model_family`
([`src/claude/model_config.rs`](../../src/claude/model_config.rs)), which
normalizes Bedrock/region-prefixed and versioned identifiers the same way
every other registry lookup does. A tab title is plain text with no
ANSI/theme-colour channel, so the emoji stands in for real colour. Since a
model can change mid-session (`/model`), `StreamTracker::absorb_identity`
([`src/sessions/stream.rs`](../../src/sessions/stream.rs)) no longer latches
`model` after its first sighting — unlike `session_id`/`cwd`, which are
genuinely fixed for a session's lifetime and stay latched — so a later change
is picked up and re-titled.

This is a deliberate, narrow exception to two things this ADR otherwise
guarantees: the pump gains a dependency on a value the parser produced, and it
mutates one specific, tightly-matched byte span instead of forwarding every
`FromClaude` byte verbatim. The exception is kept narrow on both counts. The
dependency is non-blocking: the observer publishes the classified prefix over
a `tokio::sync::watch` channel on every model change, and the pump does one
`watch::Receiver::borrow()` per chunk — never an `.await` on the observer or
the daemon, so "never depends on the daemon" still holds, and "never depends
on the observer" narrows to "never *blocks* on the observer." The byte
mutation is fail-open the same way the rest of the wrapper is: a small state
machine (`TitleRewriter`) recognizes exactly OSC `0`/`2` sequences terminated
by `BEL` or the two-byte ST (`ESC \`) form, bounded to 8 KiB of buffering
across any number of `read()` calls; a sequence that is any other OSC code,
is malformed, is not UTF-8, exceeds that bound before terminating, or arrives
before any model is known is forwarded byte-for-byte unchanged rather than
guessed at. Setting `OMNI_DEV_CLAUDE_WRAP_NO_TITLE_REWRITE=1` disables the
rewrite outright, forwarding Claude's title exactly as before this amendment —
an escape hatch for the terminal/font where the rewritten title misrenders,
consistent with this project's other user-visible-behaviour opt-outs (e.g.
`OMNI_DEV_LOG_DISABLE`).

This introduces no new trust boundary or capability: the model id already
crossed the same daemon socket before this amendment (it rides `ObserveRequest`
into `SessionEntry.model`, unread by any consumer); what changes is that the
wrapper *also* uses its own already-tracked copy locally, in-process, to decide
what to write to its own stdout.

## Consequences

- **No new trust boundary, and a narrow new exposure.** Reports ride the daemon's
  existing `0600` socket ([ADR-0039](adr-0039.md)); nothing is persisted. The new
  fact is that omni-dev code now runs inside Claude's launch path and *sees* the
  conversation as it streams. It extracts state and identity only, but "sees it"
  is a real change from the other three feeds and is why the no-content rule is a
  design constraint rather than a convention.
- **State becomes exact where the wrapper covers, inferred elsewhere.** A wrapped
  session reports the state the extension itself computes, permission prompts
  included, with no hooks installed. Terminal-TUI Claude and any non-VS-Code
  session keep the [ADR-0052](adr-0052.md) feeds and their limits. Consumers must
  therefore treat state as *best available*, not uniformly reliable — the tree cue
  renders both the same way on purpose, because a badge that changed meaning per
  session would be worse than one that is occasionally approximate.
- **Coverage is prospective.** Only sessions started after the setting is applied
  are wrapped; open tabs cycle in as they are reopened, and a window reload covers
  them all at once. There is no workflow change — tabs are launched exactly as
  before.
- **It depends on an undocumented protocol.** The stream-json message shapes are
  Claude Code's internals and may change. The parser is written to degrade rather
  than break: every field is optional, an unparseable or unrecognized line is
  ignored, and the worst outcome of a schema change is a session that stops
  updating and falls back to the other feeds. The launch contract itself
  (`claudeCode.claudeProcessWrapper`) is a supported setting.
- **The wrapper writes no request-log record.** It calls `std::process::exit` to
  propagate the child's status, which the framework's `Result`-to-0/1 collapse
  cannot express, and that bypasses the invocation record. It is a process shim,
  not a user command.
- Like the rest of the daemon surface, the wrapper and its installer are
  `#[cfg(unix)]` (Windows tracked with the broader daemon work, #1363).

This extends [ADR-0052](adr-0052.md) rather than replacing it: the service, its
three original feeds, and their inference all stand unchanged, and remain the only
coverage for anything this wrapper does not launch. See [ADR-0039](adr-0039.md)
for the daemon framework, and
[docs/sessions-service.md](../sessions-service.md) for the operator-facing guide
and the wrapper's setup.
