# ADR-0074: File-Id-Keyed Write-Permission Rules

## Status

✅ Accepted (2026-09-06)

**Extends [ADR-0071](adr-0071.md) and [ADR-0073](adr-0073.md), reverses
neither.** ADR-0071 §3 established the write-permission gate and keyed every
rule on a *folder* id, resolved against a target's ancestor chain. ADR-0073 §4
then recorded, honestly, that this leaves one class of target ungrantable —
and closed by parking the fix:

> Granting a rule against a **file id** rather than a folder id would solve
> this properly. It changes ADR-0071's rule schema and its resolution
> algorithm, so it is deliberately a follow-up with its own design pass, not a
> clause smuggled in here.

This ADR is that design pass (issue #1612). It does not weaken ADR-0071 §4's
two-independent-layers model or its default-deny posture; it adds a second way
to *name* a target inside the same gate.

## Context

The gate identifies a target by its **ancestor folder chain**: depth 0 is the
target folder itself (`create`/`upload`'s `--parent`) or the file's immediate
parent (`edit`/`sheets write`), then its parent, and so on to Drive's root.

Drive's `files.get` returns only the parents **the calling account can see**.
A file shared with you by link or by email — the most common way anyone
obtains one — is not in a folder you can see, so it comes back with
`parents: []`.

The consequences compound:

1. There is no chain, so no rule can match at any depth.
2. Resolution falls through to `DriveOperation::default_policy()`, which
   denies every write.
3. **There is no folder id an operator could name in a rule to change that.**

This is fail-closed, so it was never a security hole. But it made the
`sheets write`/`append`/`clear` surface unusable for its headline case, with
no configuration change able to fix it, and the same gap sits latently under
`drive edit` for a link-shared binary file. ADR-0073 §4's mitigation —
a distinct `RefusedNoVisibleParents` outcome naming the "move it into your own
Drive" workaround — stopped operators hunting for a rule bug, but the
workaround is often not what they want, and moving someone else's file is not
always possible.

## Decision

### 1. One rule list, with an optional `file_id` — not a second list

A rule now keys on **either** `folder_id` or `file_id`, exactly one of the two,
in the same `write_permissions.rules` array:

```jsonc
{ "folder_id": "1AbC...Workspace", "recursive": true, "allow": ["create", "edit"] },
{ "file_id":   "1Sh4r3d...Plan",                      "allow": ["sheets-write"] }
```

The obvious alternative — a sibling `file_permissions` (or `file_rules`) key —
keeps the name `FolderPermissionRule` honest and was tempting for that reason.
It is **rejected on compatibility grounds**, and the argument is asymmetric in
a way that decides it:

`WritePermissionsSettings` carries no `deny_unknown_fields`, so an older binary
reading a config with a sibling key **silently ignores it**. For a file
`allow` rule that is harmless — the grant merely fails to apply, and the write
denies. For a file **`deny`** rule it is not: the deny vanishes while a
folder-level `allow` higher in the chain survives, so the older binary permits
a write the operator had explicitly forbidden. Silently widening a permission
is precisely the failure this gate's default-deny posture exists to prevent
(the same argument ADR-0073 §3 used to refuse folding `sheets-write` into
`edit`).

Making `folder_id` optional instead means an older binary hits a **missing
required field** and fails `Settings::load()`. See §7.

### 2. Validated at the settings boundary, not left inert

`FolderPermissionRule` deserializes through a private `RawPermissionRule` via
`#[serde(try_from = ...)]`. Three shapes are hard errors rather than
silently-inert rules:

- neither `folder_id` nor `file_id` — a rule that would match nothing;
- both — a rule with two identities;
- `recursive: true` alongside `file_id` — a file has no descendants, so this
  is a *misunderstanding*, and accepting it would let an operator believe they
  had granted a subtree when they had granted one file. (`recursive: false` is
  merely redundant and is accepted.)

Erroring is the fail-closed direction here: `active_account_rules` turns a
load failure into an empty rule set, which denies every write.

The type keeps its name. It is `pub` and reachable from `settings.rs`, both
`permissions` subcommands and every engine module; a rename to
`PermissionRule` would read better but buys nothing the doc comment cannot
say, and `FolderPermissionRule`'s field list already changed shape in this
release.

### 3. A file rule sits at depth −1

A file rule names the target *itself*, which is strictly more specific than
the target's immediate parent at depth 0. ADR-0071 §3's **closest-ancestor-wins**
tie-break therefore settles precedence without a new rule: a file rule beats
every folder rule, in **both** directions.

- A file `deny` overrides a recursive folder `allow` — the restrictive case,
  and the obvious one.
- A file `allow` overrides a folder `deny` — the permissive case. This is not
  a hole: it is the same principle as ADR-0071's existing
  `closest_ancestor_wins_allow_over_broader_deny`, which already lets a
  subfolder `allow` beat a parent `deny`. A file rule is simply the most
  deliberate statement an operator can make about one object.

Deny-beats-allow still applies *among* file rules naming the same id.

Two consequences are worth stating outright, because both look like exceptions
and neither is:

- **The short-circuit is exact, not an optimization.** Since nothing in any
  chain can beat a file rule, a decisive one returns before a single
  `files.get` on any parent. That is what makes a parentless target grantable
  at all — there is no chain to walk.
- **`combine_across_parents`' "deny wins across parents" is unaffected.** That
  is a tie-break among a target's several legacy parents, which are *peers of
  each other*. A file rule is not one of them, so a file `allow` still beats a
  denying parent.

### 4. `DecidingRule` becomes a sum type, and a file id never enters the folder field

`DecidingRule` was `{ folder_id, depth }`. It is now:

```rust
#[serde(tag = "kind", rename_all = "kebab-case")]
pub enum DecidingRule {
    Folder { folder_id: String, depth: usize },
    File { file_id: String },
}
```

A file rule has no depth and a folder rule has no file id, so "a file rule at
depth 3" should not be expressible. Two alternatives were rejected:

- **One struct with three `Option` fields** — keeps every illegal combination
  representable and makes each of the six render sites re-decide what to do
  about them.
- **Widening `depth` to `isize` and using −1** — this would put a **file** id
  into the request log's `decided_by_folder_id`, so an existing
  `omni-dev log --query decided_by_folder_id:<id>` would start matching a
  different kind of id. That is an audit lie, and it silently reinterprets a
  shipped key. Rejected outright.

The log instead gains a **new** `decided_by_file_id` context field, mutually
exclusive with `decided_by_folder_id`. No existing key changes meaning,
disappears, or gains a new value domain. `-o json` for a `Blocked` result
gains a `kind` discriminator alongside the existing fields; a consumer reading
`.decided_by.folder_id` is unaffected.

Three accessors (`id`, `kind_label`, `depth_suffix`) exist so all six
`describe`/`print_report` sites are one identical line and cannot drift into
disagreeing about how a file rule is worded. Rendering stays in the CLI layer,
where terminal sanitization belongs; `write_gate` stays dependency-free.

### 5. Uniform across every operation

File rules apply to every `DriveOperation`, not only the Sheets verbs. The
reason is structural rather than a preference for uniformity: `create`,
`upload` and `sheets create` gate on their `--parent` **folder**, and the file
they are about to create has no id yet — so there is nothing for a `file_id`
rule to match, and no restriction is needed to keep them out.

Restricting the vocabulary per rule (rejecting `allow: ["create"]` on a file
rule) would mean a hard settings-load failure over a config that is merely
inert, which is disproportionate; and scoping the feature to Sheets alone
would leave `drive edit` broken for exactly the shared-file case that
motivates this ADR.

### 6. A file rule does not apply to a folder target

`drive permissions check <folder-id>` and the `create`/`upload` gate evaluate a
*folder* target and never consult `file_id` rules — even one naming that
folder's own id. A folder target means "create or upload something inside
this", and a `file_id` rule naming a folder id would just be a worse spelling
of a non-recursive `folder_id` rule. Keeping the two id spaces disjoint means
"which rules can decide this?" has one answer per target kind, and it is
pinned by a test in both directions.

### 7. Backward compatibility is fail-closed, and blunt

An older binary has `folder_id: String` as a **required** field. Reading a
config containing any file rule, it fails `Settings::load()`. `active_account_rules`
degrades that to an empty rule set: every write denied, nothing widened.

This is the same mechanism ADR-0073 §3 already accepted for an unrecognised
`DriveOperation`, so the feature inherits a documented failure mode rather
than inventing one. It is honest to record that it is **blunt**: the whole
settings file fails to parse, so that account's credentials are lost too and
Drive commands report themselves unconfigured rather than naming the real
cause. Two things bound the damage — credential resolution still falls back to
`OMNI_DEV_DRIVE_*` env vars, and settings *writes* go through an untyped
`serde_json::Value` merge, so an older binary running `drive auth login`
cannot silently drop the file rules it failed to parse. Improving the
diagnostic (propagating the load error instead of `unwrap_or_default()`)
affects every malformed settings file, not just this one, and is left as its
own change.

Forwards, a new binary reading a pre-#1612 config behaves identically: absent
`file_id` yields a folder rule, absent `recursive` yields `false`. No
migration.

### 8. The parentless refusal is now reached only after the file lookup

The ordering bug this issue is really about lived in `sheets/write.rs`: it
refused on `parents.is_empty()` **before** the gate ran, so a `file_id` rule
could never have been consulted. That ordering now lives in exactly one place,
`folder_ancestry::resolve_decision_for_file_target`, and
`resolve_decision_for_parents` is **private**, so a future fourth caller cannot
reach the primitive and forget the file-rule step — it is a compile error, not
a convention.

`RefusedNoVisibleParents` survives, with its meaning narrowed to "no file rule
named it *and* it has no visible parent", and its message now names the
`file_id` rule as the fix with the folder workaround as the alternative.
`drive edit` gains the same outcome, closing the latent gap ADR-0073 §4 named:
that case previously reported `Blocked { decided_by: None }`, which reads as
"fix your rules" when no folder rule would have helped.

Crucially, `NoVisibleParents` carries the **default-policy decision**, not a
forced refusal. `Read` defaults to allow, so a parentless shared file must
still read fine; the refusal is the *caller's* rendering choice for write
verbs, not the resolver's verdict.

## Consequences

- **A file shared by link or email is grantable.** The headline case works,
  and the fix is one line of config the error message spells out.
- **The gate gains no new bypass.** A file rule is still a local allow/deny
  evaluated before any mutating call, still layered under the OAuth scope
  ceiling, still default-deny. The only thing that changed is which ids a rule
  may name.
- **A file rule is the most powerful statement in the config**, since it beats
  every folder rule including a recursive `deny`. That is intended, and it is
  symmetric — the same specificity that lets it grant a shared file lets it
  revoke one file inside an otherwise-permitted tree.
- **Two ways to express one grant now exist** for a file that *is* in a
  visible folder. `drive permissions check` reports which one decided, so the
  ambiguity is observable rather than silent.
- **An old binary meeting a new config loses that account's Drive
  configuration entirely**, not just its rules. Fail-closed, precedented, and
  documented above — but a real cost, and the reason §7 exists as its own
  section rather than a footnote.
- **The public API broke.** `FolderPermissionRule::folder_id` is now
  `Option<String>` and `DecidingRule` is an enum; `omni-dev` is a published
  crate, so this is at least a minor bump.
- **Sync obligation.** [docs/drive.md](../drive.md) documents the `file_id`
  key, the depth −1 resolution rule, "Granting a file shared with you", the
  `permissions show`/`check` output, and the parentless-refusal troubleshooting
  entry; [docs/log.md](../log.md) documents `decided_by_file_id`. Keep both in
  sync when this ADR's decisions change.
