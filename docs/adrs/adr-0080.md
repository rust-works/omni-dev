# ADR-0080: Touch ID-Authorised Backup Leases and a Fail-Closed Audit Log for Drive Writes

## Status

✅ Accepted (2026-09-10)

**Extends [ADR-0071](adr-0071.md), [ADR-0073](adr-0073.md), [ADR-0075](adr-0075.md)
and [ADR-0077](adr-0077-sheets-deletion-via-batchupdate.md); will supersede
[ADR-0077](adr-0077-sheets-deletion-via-batchupdate.md) §5's "there is still no
recovery path but Drive's own version history" once Phase 3 below lands — not
yet, since native-file leases haven't shipped.**
Borrows the lease-with-staleness-check framing from
[ADR-0061](adr-0061.md) (`--force-with-lease`) and, at a smaller grain,
[ADR-0076](adr-0076.md) (the Docs revision lease) — see §1 for why this is a
**different** lease from ADR-0076's and the two coexist rather than one
replacing the other. Follows the OS-trust-surface precedent of
[ADR-0058](adr-0058.md) for a new `#[allow(unsafe_code)]` module.

Landed under this ADR so far (issue #1664): **Phase 1** — the fail-closed
audit sink (`RecordKind::Audit`, `audit.jsonl`, `omni-dev log --audit`; §11 —
nothing writes to it yet, that is Phase 3's job alongside native-file
leases). **Phase 2** — binary-file leases end to end: `drive lease acquire`,
the lease ledger, the macOS `LocalAuthentication` authenticator (§7), the
byte backup (§3), and `--lease` wired into `drive edit` (§9), including the
`require_lease` per-rule opt-out (§13) and the `decided_rule_requires_lease`
lookup that resolves it against whichever rule the folder-permission gate
already picked. Not yet landed: native-file (`files.copy`) leases, `drive
lease restore`, and wiring leased writes into the Phase 1 audit sink —
Phases 3 and 4, per the sequencing below.

## Context

Every write this integration has shipped since ADR-0070 is gated by an
explicit, auditable permission decision — folder-scoped (ADR-0071), later
file-scoped (ADR-0074) — and every one of those ADRs' Consequences repeats the
same honest caveat: a refusal is fully auditable, a **success is not
recoverable**. ADR-0077 §5 states it most directly, after shipping sheet and
row deletion behind the gate: "there is still no recovery path but Drive's own
version history, and every real destructive outcome says so." Drive's version
history is a whole-document restore a human performs by hand in the Drive UI;
Google merges older versions together over time; no API call can reinstate
one. That gap is also the stated reason issue #1663 (further Sheets
protection/formatting verbs) stalled: reviewing a wider destructive surface
without an undo story is the wrong order to ship things in.

This ADR is the recovery story. Its shape is set by two requirements the
issue is explicit about, and neither is satisfied by simply adding a
`--backup` flag to each write:

- **The backup must be structurally mandatory.** A flag is something a
  caller — human or agent — can omit, by habit or by accident. A write that
  refuses outright without a token cannot be run backup-free. This is
  [ADR-0061](adr-0061.md) §2 and [ADR-0075](adr-0075.md) §2's "no escape
  hatch anywhere in the surface" stance, applied to *omission* instead of a
  force flag.
- **The token must carry a staleness check.** Recording *that* a backup was
  taken is not enough; the backup must be provably taken from a known point,
  and every write against it must refuse once the file has moved past that
  point. Otherwise a later restore silently discards a collaborator's edit
  made in between — `--force-with-lease` for Drive, per ADR-0061.

Both requirements point at the same mechanism: a token, bound to a specific
backup and a specific Drive `version`, that a write must present and that a
staleness check can be run against. That is the lease.

### This is a different lease from ADR-0076's, and both are needed

ADR-0076 already put the word "lease" on something in this codebase:
`writeControl.requiredRevisionId`, sent with every Docs `batchUpdate`,
refusing the call if the document moved since the `documents.get` that
computed it. It is important to be precise about how the two differ, because
a reviewer who knows ADR-0076 will otherwise read this ADR as redundant with
it.

| | ADR-0076's revision lease | This ADR's backup lease |
|---|---|---|
| Scope | One API (Docs only) | Every content-mutating Drive/Sheets/Docs op |
| Lifetime | One request | Minutes (configurable), multi-use |
| Consent | None — silent, automatic | Touch ID (or the account password), once per acquisition |
| Backup | None | Mandatory, bytes or a Drive copy |
| Presented as | A field inside the request body | A `--lease <TOKEN>` CLI argument |

They are not competing designs for the same problem; they solve different
problems and compose. ADR-0076's lease is **unconditional and silent** — a
correctness guard against writing over the wrong version of a document,
paid for with a network round-trip already in flight. This ADR's lease is
**a human consent and recovery-point mechanism** — the two are checked
independently, in sequence, on the same Docs write: this ADR's lease first
(§9), then ADR-0076's `requiredRevisionId` as it always has. Nothing in
ADR-0076 changes.

One consequence worth naming up front: Sheets v4 has **no** per-call revision
field at all (ADR-0073/0075/0077 never had a staleness mechanism to add one
to — there is nothing analogous to `writeControl` in the Sheets API). So for
Sheets, the pre-write `files.get` this ADR requires (§6) is not a second
staleness check layered on an existing one — it is the **first staleness
check Sheets writes have ever had**. That is a genuine new safety property
this ADR buys for the Sheets surface, not merely bookkeeping.

## Decision

### 1. A third independent, mandatory gate — still no bypass, still no OR logic

[ADR-0071](adr-0071.md) §4 established two independent, mandatory layers for
Drive writes: the OAuth scope (a technical ceiling) and the folder-permission
gate (this installation's own policy). This ADR adds a third: the lease. All
three are required and none is sufficient alone — a valid `--lease` token
does not bypass the folder-permission gate, and a folder rule granting an
operation does not exempt it from needing a lease. There remains no
"always allow" bypass and no global on/off switch for either existing gate;
this one gets the identical posture (§13's `require_lease: false` is a
per-rule *opt-out*, set deliberately by the operator, never a default).

### 2. `drive lease acquire`: authenticate, then back up, then record, then mint

`drive lease acquire <FILE>` performs, in this order, aborting at the first
failure with nothing further attempted:

1. **Touch ID** (§7) — device-owner authentication via `LAContext`. Refused
   or cancelled authentication ends the command here: no backup is taken and
   no ledger entry is written. A backup nobody consented to is not a
   safer state than no backup.
2. **Backup** (§3) of the file's current content.
3. **Ledger record** (§4) — the backup location, the file's `version`/
   `modifiedTime` at this moment, and a fresh opaque token.
4. **Print the token** and exit 0.

The order matters: consent gates the *action*, not merely possession of the
resulting token, and it is why the token needs no secrecy (§7's "an
identifier, not a bearer credential" framing). A token authorises nothing by
itself: a write under it still needs this user's ledger, this user's OAuth
credentials and a folder-permission grant, so any principal holding all of
those is, by definition, the same local user the human authorised at the
prompt — which is the agent, by design. It is inert to anyone else.

### 3. Backup fidelity split: bytes for binary files, a Drive copy for native files

A binary file (anything without a `application/vnd.google-apps.*` mimeType)
is backed up as **raw bytes to a local backup directory** via `files.get`
with `alt=media`. A native Sheet, Doc or Slide has no bytes to copy at all,
and every export format (`xlsx`/`docx`) is lossy in ways that matter for a
recovery tool specifically — bound Apps Script, comments and suggestions,
protected-range editor lists, and developer metadata all fail to round-trip,
and the Sheets/Docs JSON models ADR-0073/0076 already read have no
`import`-shaped API to reconstruct a document from. So a native file is
backed up as a **`files.copy` into a configured backup folder in the same
Drive** — lossless, and restorable by a human in the Drive UI even without
this tool, which a byte-identical export copy would not be.

Backup naming, both targets: `<YYYYMMDDTHHMMSSZ>-<fileId>-<name>` — UTC,
seconds precision (collisions inside one second are vanishingly unlikely for
a single-operator CLI and, if they occur, only affect which of two
near-simultaneous backups a human picks by eye); the file id, because Drive
names collide freely and may contain `/`, which a bare name-based filename
cannot survive.

Both the local backup directory and the Drive backup folder id are
configurable (CLI flag → env → settings, the resolution order every other
per-invocation override in this codebase uses); the ledger records which one
each backup actually landed in, so a restore never has to re-derive it from
current settings that may have since changed.

The `files.copy` is itself a Drive write — a `Create` in the backup folder —
and it is **not** evaluated by the folder-permission gate. The backup folder
is named by the operator in the same per-account settings the gate's own
rules live in (§13), so naming it *is* the consent; routing the copy through
the gate would require a matching `allow: ["create"]` rule on the backup
folder, turn a missing one into a confusing refusal inside `lease acquire`,
and let a `deny` on the backup folder block the backup of a write the gate
has otherwise permitted. The copy is still logged as a `drivemutation`
record like every other mutation, and is part of the acquire's audit record
(§11). It needs the full `drive` OAuth scope, since `drive.file` cannot read
a file this app did not create — the same scope `drive edit` on a
pre-existing file already requires (ADR-0071 §1), so the lease adds no scope
escalation.

### 4. Two records, one purpose each: the ledger is operational state, the audit log is forensic history

It would be possible to make the audit log (§11) double as the lease's
operational store — it already records the full lifecycle per the issue's
own description. That is rejected. The two serve different jobs and must not
be conflated:

- **The ledger** is *read* by every leased write, to decide whether a
  presented token is valid, unexpired, bound to the right file, and not
  stale — a live, queryable store a program's own logic depends on to make a
  security decision.
- **The audit log** is *never* read to authorize anything. It is a
  fail-closed, append-only forensic trail — write-only from the gate's
  perspective, consulted later by a human or a `omni-dev log` query, never
  by the gate itself.

Collapsing them would mean the code path that decides "is this write
allowed" and the code path whose only job is "record what happened" share
one file and one failure mode, which is exactly the coupling that makes a
security-critical decision hard to reason about in isolation. They overlap
in *content* (both know about acquire/write/expire/restore) but never in
*role*.

The ledger (`lease-ledger.jsonl`, state dir, `0700`/`0600` — the same posture
[`crate::request_log`](../../src/request_log.rs) already uses) follows
`gmail insert`'s `InsertLedger` precedent exactly
(`src/cli/gmail/insert/ledger.rs`), not an append-only log: an in-memory
`BTreeMap<token, LeaseRecord>` is the source of truth, and every state
change (a successful acquire, a write updating the recorded `version`, an
expiry or release) upserts its entry and **atomically rewrites the whole
file** — `tempfile::NamedTempFile::new_in` plus `persist`, the same
temp-file-in-the-same-directory-then-rename `sync::manifest::Manifest::save`
and `InsertLedger::save` both already use. An expired, released or
restored-from lease's row is **kept**, marked with the transition and its
time, never dropped on rewrite: the gate treats only a live row (unexpired,
unreleased) as valid, but `drive lease restore <TOKEN>` (§10) locates the
backup through that same row, and a restore is almost always wanted *after*
the expiry window, once a bad write has been noticed. Dropping the row on
expiry would make every backup unreachable by token exactly when it is
needed. The ledger therefore grows with the number of leases ever acquired,
bounded only by the `lease prune` fast-follow (see Consequences), which
drops a row together with the backup it points at, never one without the
other. Concurrent access —
two overlapping `drive lease acquire`/write invocations against the same
ledger — is guarded by an advisory `create_new` lock file for the
lifetime of each mutating call, mirroring `InsertLedger`'s `LedgerLock`
exactly, since a naive full-file rewrite racing another one would silently
discard whichever lease state lost the race.

A corrupt or discarded ledger is a hard error on load, never a silent
reset — following that same module's posture (itself modelled on
`sync::manifest`'s, per [ADR-0064](adr-0064.md)) rather than
`sync::state`'s: losing this file doesn't lose recoverable metadata, it loses
the *only* record of which tokens are still valid, against what version, and
which backups they point at.

### 5. Expiry is absolute from acquisition; a write never silently extends it

Default expiry is 30 minutes, configurable. A lease is **multi-use** until
expiry: each successful write updates the ledger's recorded `version` for
that token (§6), so a second write under the same lease is checked against
the file's state *after* the first write, not against the original backup
point.

Expiry itself does **not** move. A write never extends it, silently or
otherwise. This resolves one of the issue's open questions directly: the
only way to get a fresh expiry window is a fresh `drive lease acquire` call —
which means a fresh Touch ID prompt. The whole point of the mechanism is that
a human is present at the moment consent is given; letting a long-running
agent session refresh its own leash by writing to it would let one Touch ID
prompt cover an unbounded session, which defeats that purpose. Re-acquiring
is a single, cheap command — there is no need for a separate "extend" verb
to make this bearable.

### 6. The staleness check differs by surface, and one of them is genuinely new

- **Binary files**: Drive's `version` field is monotonic and present on
  every file. The lease records it at acquire/last-write time; a write
  refuses if the live `version` differs.
- **Docs**: `documents.batchUpdate` already carries ADR-0076's
  `requiredRevisionId`, taken from the same `documents.get` a leased write
  performs anyway. This ADR's check is a **second, independent** comparison
  — the file's Drive `version` against the lease's recorded value — run
  before that call is even built. Both checks exist; neither replaces the
  other, per §1's box above.
- **Sheets**: v4 has no revision field of any kind. The check is a
  `files.get` immediately before the `batchUpdate` (already proposed by the
  issue for exactly this reason) comparing Drive `version`. As the Context
  section notes, this is Sheets' first staleness check of any kind — not
  redundant with anything ADR-0073/0075/0077 shipped.

The pre-write `files.get` is one extra round-trip per leased write, on
every surface. The multi-use lease (§5) then needs the file's *new*
`version` after a successful write, and where it comes from differs again:
`files.update` returns it in its response when `version` is in the requested
`fields`, so a binary write refreshes the ledger race-free from the write's
own reply; Sheets and Docs `batchUpdate` return no Drive metadata at all, so
those need a **second** `files.get` after the call — two extra round-trips
per leased write — and a collaborator's edit landing between the write and
that read is absorbed into the lease as if it were ours. That is a stated
limit of the same class as the pre-write race, not a hidden one. The cost is
accepted as the price of the property; it is the same trade-off ADR-0076 §3
already accepted for Docs ("the lease window is a network round-trip, not
human think time").

### 7. Touch ID via the generated `objc2-local-authentication` binding, not hand-rolled FFI

Acquiring a lease on macOS calls `LAContext.evaluatePolicy(_:localizedReason:reply:)`
with the **`deviceOwnerAuthentication`** policy: Touch ID where it is
available and enrolled, otherwise the account password, both collected by
the system's own dialog — this tool never implements or sees a password
path itself. The policy is chosen deliberately over
`deviceOwnerAuthenticationWithBiometrics`, which is biometrics-*only*: it
fails outright when Touch ID is absent, not enrolled or locked out, which
would fail every Mac without Touch ID hardware (Mac mini, Mac Studio, Mac
Pro, an iMac on a plain keyboard, a MacBook running clamshell) closed by
default — a regression far wider than §8's genuinely headless cases. A
global `lease.authentication: biometrics-only` setting (§13) selects the
stricter policy for operators who want it. Either way the prompt is
system-modal, rendered by `LocalAuthentication.framework` in a process the
caller does not control, so consent is human-present by construction: an
agent holding a token cannot answer a prompt it never sees, and a script
driving the CLI's own stdin or PTY cannot answer a prompt that is not stdin.

One residual is named rather than assumed away. A password dialog is a text
field, and synthesised keyboard events from a process holding the macOS
Accessibility grant can in principle reach one; this ADR does not claim the
system dialog is immune to that. What bounds it: the grant is per-binary and
user-granted (ADR-0058), the one omni-dev module that holds it reads
geometry and writes position and size and **never synthesises input**
(ADR-0058 §6), and the `biometrics-only` policy closes the path entirely for
an operator who wants no keyboard-answerable prompt at all, at the cost of
the hardware requirement above.

ADR-0058 §6 hand-rolled seven `extern "C"` declarations for the Accessibility
API rather than pulling in a whole generated framework binding, because that
API is a small, plain-C surface over `CFTypeRef`. `LAContext` is not that
shape: it is an Objective-C **class**, `evaluatePolicy` dispatches through
Objective-C message sending, and its result arrives via a **block-based**
completion handler — reimplementing correct `objc_msgSend` call-argument
marshalling and the block ABI by hand is a materially larger and more
failure-prone undertaking than seven C function declarations, for no benefit
this codebase needs. So this ADR makes the opposite call from ADR-0058, for
a reason specific to the shape of the API being wrapped: use the
already-upstream, machine-generated `objc2-local-authentication` crate
(alongside `objc2`/`block2`, siblings of the `objc2-core-foundation` already
in the dependency tree per ADR-0058) rather than hand-rolled bindings.

`evaluatePolicy` is asynchronous by API design; `drive lease acquire` is a
synchronous CLI command that must block until the human answers. The bridge
is a one-shot channel: the completion block captured by the async call sends
its `(bool, Option<NSError>)` result across a `std::sync::mpsc` channel (or
equivalent), and the calling thread blocks on a `recv_timeout()` of **two
minutes** — long enough for a human to reach the machine, short enough that
an unattended `lease acquire` cannot hang a script indefinitely — after
which the context is invalidated (`LAContext.invalidate()`, which dismisses
the dialog and fires the reply with a cancellation error) and the command
fails as cancelled, taking no backup and writing no ledger row (§2). All of
this lives in one module
(`src/drive/lease/authenticate/macos.rs`, mirroring ADR-0058 §6's placement
convention) behind a small trait so the ledger/backup/gate logic above it
stays platform-independent and unit-testable with a fake authenticator —
the same shape ADR-0058's `WindowBackend` trait established. Every
Objective-C/block boundary crossing carries the `// SAFETY:` comment
STYLE-0013 requires; this is the crate's **third** unsafe-code exception
(after the Accessibility FFI and the `launch_activate_socket` FFI), and each
new one narrows the argument that they should be rare, not that a fourth
would be fine by precedent.

Per ADR-0058's own open item for the Accessibility grant, this needed its own
verification before Phase 2: **confirm that an unsigned binary can present
the LocalAuthentication prompt at all** (omni-dev installs unsigned via
cargo/homebrew).

**Confirmed (2026-09-11).** A throwaway `cargo build` binary linking
`objc2-local-authentication` 0.3.2 (the same version pinned in this ADR),
signed only by the linker's automatic ad-hoc signature (`codesign -dv` shows
`flags=0x20002(adhoc,linker-signed)`, `TeamIdentifier=not set` — the same
posture `cargo install`/Homebrew produce, not a stronger stand-in for one),
called `evaluatePolicy` under both `DeviceOwnerAuthenticationWithBiometrics`
and `DeviceOwnerAuthentication`. Both calls rendered a real system dialog: a
human watching the screen saw it and authenticated via Touch ID, and both
replies landed roughly 2.1-2.2 seconds later — consistent with an actual
prompt-and-respond round trip through `securityd`/`biometrickitd`, not an
instant stub. The assumption holds; nothing here is speculative for Phase 2.

### 8. Off-macOS and headless: fail closed, with a documented opt-out — never a TTY fallback

`lease acquire` requires a working authenticator. On any platform or context
without one — non-macOS today, or a macOS process with no attached GUI
session (SSH, a bare launchd job, CI) — the default is to **refuse to
acquire a lease at all**, which by §1 means every gated write also refuses.
This is a real capability regression for those contexts — and only those:
a macOS GUI session without Touch ID hardware is *not* headless, since §7's
policy falls back to the account password there. It is accepted
deliberately rather than silently: an operator can set an explicit
per-installation opt-out (analogous in spirit to §13's per-rule
`require_lease: false`, but global — see §13) that documents, in the
settings file itself, that leased writes on this installation proceed
without the human-presence guarantee.

A TTY prompt ("type yes to confirm") is explicitly **not** an acceptable
substitute default, for the same reason ADR-0070 §6/ADR-0071 §7 give no
integration-wide interactive confirmation at all: an agent driving a
terminal or a PTY can answer a TTY prompt as easily as it can set a flag,
so it would provide the appearance of the human-presence property this ADR
exists to deliver without the substance.

### 9. Where the lease check sits in each engine, and what is exempt

Every `DriveOperation` that mutates a file which existed before the
invocation — `Edit`, `SheetsWrite`/`SheetsStructure`/`SheetsDelete`/
`SheetsProtection`, `DocsWrite` — gains a required `--lease <TOKEN>`
argument. Exempt, per the issue's own reasoning:

- **`Create` and `Upload`** — both make a *new* file (`drive upload` creates
  a file from local content, [`src/drive/upload.rs`](../../src/drive/upload.rs);
  it never replaces an existing one — that is `edit`), so nothing exists yet
  to back up.
- **The seed write of `docs create --text` and `sheets create`** — a
  `DocsWrite`/`SheetsWrite` on the file the same invocation just created,
  authorised by the `Create` verdict (ADR-0073 §11, ADR-0076 §9). No file id
  exists before the command runs, so no lease *could* be presented, and
  there is no pre-existing content to lose. ADR-0076 §9's "its seed pays for
  its own lease" is the *revision* lease and is unchanged.
- **`move`/`rename`** (metadata-only, ADR-0070; not gated by `DriveOperation`
  at all today) — reversible, and already guarded by ADR-0070's visibility
  diff.
- **`Read`**, and **`--dry-run`** on every verb — nothing is mutated.

The lease check slots into the existing linear engine shape
(ADR-0073 §9/ADR-0075 §5/ADR-0076 §8: pre-gate refusals → folder-permission
gate → `dry_run` early return → mutation) as a **new step immediately before
the mutating call**, after the `dry_run` branch — so a `--dry-run` invocation
never needs `--lease` and a missing/invalid token is reported the same way
regardless of which verb hit it (`RefusedNoLease`/`RefusedLeaseExpired`/
`RefusedLeaseStale`/`RefusedLeaseWrongFile`, mirroring the existing
`Refused*` family's per-cause granularity). Placing it after the permission
gate, not before, preserves ADR-0071 §4's "a refusal stays exactly as
auditable as a success" property in the direction that matters most here: a
folder-permission refusal still makes zero Drive API calls and never touches
lease state, so denying access to a folder never even reveals whether a
presented token was otherwise valid.

### 10. `drive lease restore <TOKEN>`

A binary file's backup restores via `files.update`, re-uploading the backed
up bytes. A native file has no equivalent restore call — its backup is a
Drive copy, restorable today by a human via the Drive UI — but where a typed
path exists, `restore` uses it: a deleted sheet's backup copy still contains
that sheet, so `restore` on a file that had a sheet deleted from it under
lease offers `spreadsheets.sheets.copyTo` from the backup spreadsheet into
the live one, reusing exactly the typed-request discipline ADR-0075 §2/§4
and ADR-0077 §3 established (no raw `batchUpdate` passthrough gains an
exception here either). Where no typed path exists, `restore` reports the
backup's location and stops — an honest limitation in the same spirit as
ADR-0077 §5's original admission, not something this verb pretends to paper
over.

`restore` is itself a write, and it acquires its own lease **internally**
rather than taking a second `--lease` argument: it runs §2's sequence in
full — Touch ID, a backup of the file's *current* state, a new ledger row —
and only then performs the restore write, printing the new token so the
restore is itself reversible by the same verb. One command, one prompt. The
`<TOKEN>` it takes is the *backup* lease, expired or not (§4 keeps the row);
it locates the backup and authorises nothing — the fresh prompt does. The
restore is audit-logged carrying both tokens, per §11.

### 11. The audit log: a new `RecordKind`, its own fail-closed sink

`audit.jsonl` is a sibling of `log.jsonl` under the same state directory,
sharing `crate::request_log`'s `LogRecord` shape and low-level line-append
primitive, but with its own path resolution
(`OMNI_DEV_AUDIT_LOG_FILE` → state dir default) that is **not** subject to
`OMNI_DEV_LOG_DISABLE`, rotation, or `prune` — none of `log.jsonl`'s
availability-favoring properties are appropriate for a forensic record.

A new `RecordKind::Audit` (not a reuse of `RecordKind::DriveMutation`, which
stays exactly what it is — the best-effort record already written to
`log.jsonl` for every `create`/`upload`/`edit`/Sheets/Docs mutation) carries
an `integration` field (`"drive"` today) so a later Gmail or Atlassian audit
need is additive rather than a rename, plus `lease_id`, the verdict
(`allowed`/`refused`/`stale`/`expired`), and the `version`/`modifiedTime`
before and after. The acquire record additionally carries the backup's
location and, for a byte backup, its SHA-256 and size — the fields a later
restore is checked against — plus which authentication policy (§7) was
satisfied; the restore record carries the backup token it restored from and
the fresh token it minted (§10). A leased write therefore produces records in **two**
files: its normal `invocation`/`http`/`drivemutation` records in `log.jsonl`
as today, and a fail-closed audit record in `audit.jsonl` carrying the same
`invocation_id` — either side finds the other, and the HTTP body stays
recorded exactly once.

Reading it is `omni-dev log --audit`: the flag switches the reader to
`audit.jsonl` (honouring `OMNI_DEV_AUDIT_LOG_FILE`) and changes nothing
else — the filter matrix, the `--query` mini-language, the three renderers
and `-f/--follow` all apply unchanged, so `omni-dev log --audit --query
'lease_id:<token>'` works the day the sink lands. `log prune` refuses
`--audit`, since exemption from pruning is the point. This is a CLI-surface
change and lands under `update-snapshots` in Phase 1.

**Fail-closed inverts this codebase's usual ordering.** `request_log`'s
existing writers are deliberately best-effort and non-blocking — a logging
failure must never change the caller's exit code (module doc,
`src/request_log.rs`) — and ADR-0079 §4 chose to write its ledger record
*after* the Gmail API call succeeds, explicitly preferring a duplicate over
a silent gap for a restore tool's own recoverability. The audit sink takes
the opposite stance for a different reason: **the write-ahead audit record
must be durably written *before* the mutating API call is attempted**, and
if it cannot be written, the write does not happen. This is not a
correctness trade-off the way ADR-0079's was; it is the definition of
"fail-closed" for a forensic log — a mutation with no accompanying intent
record would be exactly the gap the audit log exists to make impossible.
The **outcome** half of the pair is then written after the call returns,
succeeding or failing independently of the intent half already having
landed — so a process that dies mid-write still leaves a trace: an intent
record with no matching outcome is itself the signal that something was
interrupted. This inverted contract lives in its own writer
(`request_log::record_audit`, returning `Result`), never as a flag on the
best-effort `record`, so the module doc's "a logging failure never changes
the exit code" invariant stays literally true of `record` and the one
function that breaks it says so in its signature.

### 12. What the audit log proves, and what it does not

The ledger, the audit log and the backup directory/folder are all owned by
the same local user account the agent runs as. An agent with shell access to
that account can, in principle, edit or truncate any of them; a hash chain
across audit records makes tampering *detectable* but does not make it
*impossible*. This is recorded rather than glossed over, in the same spirit
as ADR-0077 §5's original admission: the local audit log is evidence,
checkable against Drive's own revision history (which the account holder
cannot rewrite from this tool), not a tamper-proof ledger in its own right.

### 13. Config surface: global authenticator/expiry policy, per-account backup targets, per-rule opt-out

Three settings live at three different scopes, and the reason for each
mirrors [ADR-0071](adr-0071.md) §5's reasoning for `write_permissions`
itself:

- **Global** (top-level, sibling of `drive` in `settings.json`): default
  lease expiry, the local backup directory default, the authentication
  policy (§7: `deviceOwnerAuthentication` by default, `biometrics-only`
  opt-in), and the headless/
  off-macOS opt-out (§8) — none of these are meaningful per-Drive-account,
  they describe *this machine's* policy.
- **Per-account** (`DriveAccountSettings`, sibling of `write_permissions`):
  the native-file backup folder id — meaningless outside the one Drive it
  names, for the identical reason ADR-0071 §5 gives for `folder_id` in a
  permission rule.
- **Per-rule** (`FolderPermissionRule`): a new `require_lease` field,
  defaulting to `true`, lets an operator relax the requirement for a
  specific folder — mirroring `allow`/`deny`'s existing per-rule
  granularity rather than adding a second, parallel rule system. Per the
  issue's own open question, `require_lease: false` skips **both** the
  backup and the Touch ID prompt for that folder, not merely one of them —
  a rule that skips the prompt but still silently takes a backup would
  surprise an operator who explicitly asked to relax this, and a rule that
  skips the backup but still prompts would ask for consent to a guarantee
  it then doesn't provide.

### 14. Sequencing

Unchanged from the issue's own plan: this ADR, then Phase 1 (the audit sink,
buildable today since the write gate already produces the verdicts it would
log — and the moment to fix `RecordKind::DriveMutation`'s doc comment,
which still names only `rename`/`move` although every Drive mutation writes
it), Phase 2 (binary-file leases end-to-end against the test folder — also
where `version` joins the `files.get` field lists in
`src/drive/files_api.rs`, which do not request it today, and where the
`files.copy` client, which does not exist today, is added), Phase
3 (native-file leases, `require_lease` wired into every Sheets/Docs
operation, ADR-0077 §5's recovery message updated to point at `drive lease`),
Phase 4 (`restore`, operator guide, `update-snapshots`), then #1663 resumes
under the lease regime.

## Consequences

- **This closes the recovery gap ADR-0077 §5 admitted.** Once Phase 3 lands,
  every content-mutating Drive/Sheets/Docs operation has a mandatory
  pre-write backup and a documented restore path — the stated blocker for
  #1663.
- **A third OS trust surface, of a different kind than the first two.**
  Unlike Accessibility (ADR-0058, a broad, silent background-automation
  grant) and `launch_activate_socket` (a narrow, one-shot FFI),
  LocalAuthentication is a **user-facing, per-acquisition consent** surface
  — its whole purpose is that a human sees and answers a prompt, so its
  risk profile is the inverse of the other two: the danger is a prompt that
  can be silently bypassed or answered by non-human means, not one that is
  overly broad once granted. Its unsigned-binary concern is confirmed
  resolved (§7, 2026-09-11): an ad-hoc-signed build renders a real,
  human-answered prompt.
- **A third independent, mandatory gate.** No bypass exists across all
  three (OAuth scope, folder permission, lease) — a leaked `--write-full`
  token with a permissive `write_permissions` config is still inert against
  a folder with no valid lease, and vice versa.
- **Sheets writes gain their first staleness check ever**; Docs writes gain
  a second, independent one layered on ADR-0076's existing per-call check —
  deliberate redundancy for Docs, a wholly new property for Sheets.
- **Headless/off-macOS Drive writes regress by default**, a real capability
  cost accepted deliberately (§8) rather than papered over with a TTY
  prompt that would defeat the whole mechanism. A macOS session without
  Touch ID hardware does *not* regress: §7's policy falls back to the
  account password, still in a system dialog.
- **A refusal stays exactly as auditable as a success, extended to the
  lease**: a lease-refused write produces a `drivemutation` record in
  `log.jsonl` (as every refusal already does) *and* an audit record in
  `audit.jsonl`. A missing, expired or wrong-file token is refused with zero
  Drive API calls made — matching ADR-0070/0071/0073/0075/0077's identical
  property for the folder-permission gate; a *stale* token is the one
  refusal that costs exactly the `files.get` that detected it.
- **Fail-closed audit logging is a deliberate departure from this
  codebase's usual best-effort logging posture** (§11), justified because a
  forensic log that can silently drop the one record proving a write
  happened is not a forensic log.
- **All three local artifacts grow unboundedly until pruned.** `audit.jsonl`
  is append-only by design (§11), nothing here deletes an old backup, and
  the ledger keeps every row so that `restore` can find a backup by token
  after expiry (§4). A `lease prune` that drops a ledger row *and* the
  backup it points at together (never one without the other), mirroring
  `log prune`, is a known, deliberate
  fast-follow — the same posture ADR-0071 §11 took for read-path
  enforcement — not a silently dropped requirement.
- **Tamper-evident, not tamper-proof** (§12): all three local artifacts are
  owned by the same account an agent could compromise. The audit log's
  value is as a checkable trail against Drive's own revision history, never
  as a security boundary in its own right.
- **Sync obligation.** [docs/drive.md](../drive.md) documents `drive lease
  acquire`/`restore`, the `--lease` requirement per verb, the exemption
  list, the config surface (§13) and the headless opt-out; ADR-0077's
  recovery-message language in the codebase (not this document) points at
  `drive lease restore` once Phase 3 lands; [docs/log.md](../log.md)
  documents `RecordKind::Audit`, its fields, `omni-dev log --audit`, and
  `audit.jsonl`'s location
  and exemption from `OMNI_DEV_LOG_DISABLE`/rotation/`prune`. Keep all three
  in sync when this ADR's decisions change.
