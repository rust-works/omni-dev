# ADR-0094: Anchor-Addressed Docs Insertion and Deletion

## Status

✅ Accepted (2026-10-02, #1642). Extends [ADR-0076](adr-0076.md).

## Context

ADR-0076 deliberately avoided computing Docs indices: append uses the server's
`endOfSegmentLocation`, and replace matches text server-side. Insertion and
range deletion require the crate to own UTF-16 addressing. A user-supplied
index from an earlier read would not share provenance with this invocation's
revision lease, even if both reads succeed. Astral characters, pending
suggestions, inline objects and structural terminators make naïve indexing
silently unsafe.

## Decision

### 1. Resolve content anchors in the leased snapshot

Expose `docs insert --before TEXT | --after TEXT` and
`docs delete --match TEXT | --from TEXT --to TEXT`. The latter range includes
both anchors. No numeric `--index`, externally supplied revision, or occurrence
selector is exposed. Each anchor must occur exactly once across all tab bodies,
including nested tabs and table cells. Overlapping matches count separately.
Anchors cannot span paragraphs or inline objects. Headers, footers, footnotes
and tables of contents are outside this addressing surface.

Matching defaults to case-sensitive literal text. `--ignore-case` uses Unicode
simple case folding through an escaped regex over the original text. It does
not lowercase a copy and then reuse its byte offsets: lowercasing can change
length, which would invalidate the mapping. There is no regex input surface.

Index-addressed writes read explicitly with `SUGGESTIONS_INLINE`, then resolve
against that same response's `revisionId`. Pending insertion/deletion text in
an anchor or deletion range is refused, rather than changing unaccepted prose.

### 2. Confine index arithmetic to a pure resolver

`src/drive/docs/anchor.rs` maps original UTF-8 byte boundaries to each text run's
server start index plus a UTF-16 prefix length. It validates the server's run
bounds. Adjacent text runs may contribute to one anchor, but inline objects
and gaps break the text stream. A missing index or tab identity is a refusal,
not an inferred index. Tests include randomized Unicode prefixes and run splits.

Insertion must remain inside its anchor's paragraph: an index equal to
`endIndex` is refused; insertion immediately before the trailing newline is
valid. Deletion never removes the last newline of a body or table cell, nor a
newline immediately preceding a table, table of contents or section break.
A range may span contiguous ordinary paragraphs within the same body or table
cell, but cannot cross tab/cell boundaries, structural elements, non-text
inline elements, missing index space or pending content suggestions. These
conservative restrictions keep dry-run resolution meaningful without
reimplementing Google's full structural-edit validation.

These boundaries follow the [Docs request reference](https://developers.google.com/workspace/docs/api/reference/rest/v1/documents/request#DeleteContentRangeRequest).

### 3. Separate consent to remove content

Anchored insertion joins `DriveOperation::DocsWrite`: like append, it adds text.
Deletion has a new `DriveOperation::DocsDelete` (`docs-delete`), deny-by-default
and requiring a lease by default. An existing docs-write grant does not permit
the new deletion verb; a docs-delete grant does not permit insertion or replace.
This follows ADR-0077's separation of destructive Sheet operations.

The existing `replace --replace ""` semantics are retained: that is the existing
text-replacement consent, not a new range-deletion grant. Older binaries reject
configuration naming the new operation rather than interpreting it differently.

### 4. Preserve one request and both lease checks

Every invocation emits one typed `DocsRequest` in one batch, carrying mandatory
`writeControl.requiredRevisionId`. No rebasing control, force flag, unleased
batch or multi-request ordering is added. The permission gate remains before
`documents.get`; ADR-0080's optional ledger lease check remains before mutation.
Resolve anchors and build the request before the ledger grants an intent, so
fallible preparation cannot strand a pending mutation record. A stale Docs
revision remains a distinct refusal without an automatic retry.

The source guard covers the Docs modules and CLI write entry point. It allows
`deleteContentRange` only at its single typed serde rename, and continues to
ban rebasing/force and unmodelled destructive requests. It is a unit test,
not a compiler-enforced theorem; any new request path must join this guard.

### 5. Preview metadata and logging

Dry runs and successful outcomes share an `EditPreview`: explicit UTF-16
`[start_index, end_index)`, tab identity, touched paragraph count, Unicode scalar
count and UTF-8 byte count. An insertion has an empty range. No preview echoes
anchor text or document contents. Refusals carry typed reasons and ambiguity
counts. Existing append/replace outcome shapes are preserved.

Mutation logs use `docs-insert` and `docs-delete` with existing status, revision
and decision metadata; successful insertion also records `inserted_chars`.
Ranges/counts remain in structured command outcomes; no new request-log schema
fields are added. User prose is never included in these new metadata fields.

## Consequences

The crate now owns a small, deliberately bounded index model. Conservative
refusals may reject edits Google could accept, such as deleting an entire
structural object. One-request batches keep index shifting within batches
absent. Styling, lists, table structure, non-body segment writes and named-range
mutations require separate follow-ups and explicit gate decisions. No MCP write
tools are added here.
