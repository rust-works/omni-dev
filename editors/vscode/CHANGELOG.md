# Changelog

All notable changes to the **omni-dev** VS Code extension are
documented in this file. The extension versions independently of the omni-dev
Rust crate — the crate's own changelog lives in the
[repository root](https://github.com/rust-works/omni-dev/blob/main/CHANGELOG.md).

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **Reload Window** ([#1417](https://github.com/rust-works/omni-dev/issues/1417)): a new context-menu action in the **Worktrees** view reloads the VS Code window each selected worktree is open in — the batch form of `Developer: Reload Window`, which otherwise has to be run by hand in each window in turn. It is the usual fix after an extension update, a setting that needs a restart, a language server that has wedged, or a `git` operation that left the SCM view stale, and with a fan-out of per-issue windows open that was one manual sweep per fix. Select any number of rows and act once. Selected worktrees with **no open window** are simply skipped — there is nothing to reload — and the count is included in the summary, so a batch is never *quietly* narrowed; selecting only closed worktrees says "nothing to reload" and does nothing else. There is **no confirmation prompt**: a reload creates, modifies and deletes nothing, and VS Code's hot exit preserves your unsaved editors, so it behaves like **Reposition Windows to Match** rather than like **Close Worktree**. There is correspondingly nothing to undo. Two things to expect: windows other than the one you act from reload over the **next ten seconds or so** rather than instantly, and a batch will visibly stagger — the daemon can only reach another window when that window next checks in, which is the same delay **Close Window** already has — and the window you act *from* reloads **last**, after the others have been signalled and the summary shown, because reloading it ends the extension host that is running the command. The summary therefore says how many windows were *signalled*, not how many reloaded. Also available as **`omni-dev worktrees reload <PATH>…`** from the command line. **Requires** a daemon built with this release.
- **Rebase on main** ([#1409](https://github.com/rust-works/omni-dev/issues/1409), reworked in [#1415](https://github.com/rust-works/omni-dev/issues/1415)): a new context-menu action on any **linked** worktree row in the **Worktrees** view rebases that worktree's branch onto the repository's **remote default branch**. It is built for a multi-selection: pick any number of worktrees — across as many repositories as you like — act once, and each repository's default branch is **fetched exactly once** for the whole batch, so keeping a fan-out of feature branches current with `main` is one gesture instead of one `cd` and one `git pull --rebase` per worktree. A main working tree is **never** a target: the action does not appear on one, and a main tree caught up in a multi-selection is **named as skipped** in the confirmation rather than silently included. Because a rebase rewrites branch history it **always** confirms first, listing exactly which worktrees will be rewritten, even for a single row. A worktree with uncommitted changes, a detached `HEAD`, or a rebase already in progress is reported and skipped rather than touched — the rest of the batch continues either way.
  - **Conflicts are left in place to resolve.** A worktree whose rebase hits conflicts stays **mid-rebase**, with its conflict markers on disk, so you can resolve them where you are and finish with `git rebase --continue` — instead of the rebase being rolled back and every already-resolved hunk thrown away. The summary tells you which worktrees are waiting, and their rows keep showing it until you finish.
  - **Rebase state shows in the tree.** A row spins while its rebase is running, and shows a `⚠ rebase in progress` until an unfinished one is resolved — including after a restart, since that half is read from the worktree itself.
  - **No terminal; it goes through the daemon like every other action.** It originally shelled out to `omni-dev worktrees rebase` in an integrated terminal, on the belief that a daemon started by launchd could not reach your `ssh-agent` to authenticate the fetch. That turned out to be wrong — launchd does hand it `SSH_AUTH_SOCK` — so the rebase now runs in the daemon, which is what makes the structured per-worktree summary and the leave-conflicts-in-place behaviour possible. A practical bonus: the confirmation now lists each branch's **real** behind-count, measured against the freshly fetched rebase target.
  - Consequently this action now needs a **running daemon** (`omni-dev daemon start`) rather than the `omni-dev` CLI on your `PATH`. With no daemon it says so, and points at `omni-dev worktrees rebase <path>`, which still does the whole job locally.
- **Reposition Windows to Match** ([#1407](https://github.com/rust-works/omni-dev/issues/1407)): a new context-menu action in the **Worktrees** view moves and resizes the selected worktrees' open VS Code windows so they sit exactly where the window you invoked it from sits. Select any number of rows, act once, and every one of those windows lands on the same spot at the same size — **without changing which window is in front**: nothing is raised, focused, or activated, so the stacking order you had is the stacking order you keep. The window you act from is the reference and never moves. Worktrees with no open window are skipped, as are windows that are minimized or in fullscreen (where a resize does nothing), and each one is reported with why. There is no confirmation prompt — this changes no files and is a command you repeat — but because the previous layout is otherwise lost, the summary notification offers **Undo**, also available as **omni-dev: Undo Reposition Windows** in the command palette. An extension cannot do any of this itself: VS Code exposes no API for a window's position or size, so the omni-dev daemon does the work and this release requires a daemon built with it. **macOS only**, and it needs a one-time **Accessibility** permission for the omni-dev binary — if it is missing you get an actionable message with a button that opens the right settings pane, and the menu item is hidden entirely on other platforms. Note that granting takes effect only after `omni-dev daemon restart`, and because omni-dev is distributed unsigned the grant has to be re-applied after each upgrade.
- **Claude session cues on worktree rows** ([#1406](https://github.com/rust-works/omni-dev/issues/1406)): every row in the **Worktrees** view now shows what the Claude Code sessions running in that worktree are doing — glyph counts in the row description (`!` waiting on you, `⚙` working, `◦` idle) plus a **colored badge** for the most urgent one: yellow when something is waiting on you, green while work is happening, muted grey when everything is idle. The point is the yellow: a permission prompt in a window you are not looking at is otherwise invisible until you go and check. Sessions are attributed to the **innermost** worktree containing their working directory, so a session in a nested worktree counts there and not against its parent repository. Hovering a row spells the counts out. A row that has both sessions and a pull request shows **both** badges side by side (`⚙1, ✓`), coloured by whichever is more serious — red for failing checks, then yellow for pending checks or a session waiting on you, then green — so a failing build is never hidden behind a busy Claude. Because the two badges necessarily share that one colour, the **pending-checks glyph changes from `●` to `⋯`**, which reads as "in progress" without needing to be yellow (and no longer looks like the idle-session `◦`). A row with no sessions renders exactly as before. Two things to know about accuracy: the state is **exact** for Claude tabs launched after you run `omni-dev sessions install-wrapper` (which puts omni-dev in the Claude process's stream and reads the real state, including permission prompts), and **inferred** for everything else, where a permission prompt is only visible if you have also run `omni-dev sessions install-hooks`. Turn the whole cue off with `omniDevWorktrees.showClaudeSessions`. Polling is skipped entirely while the view is hidden. **Requires** a daemon built with this release.
- **Add to Merge Queue** ([#1401](https://github.com/rust-works/omni-dev/issues/1401)): a new context-menu action on any GitHub-backed worktree row in the **Worktrees** view adds the branch's pull request to the repo's **GitHub merge queue**. It is built for a multi-selection: pick any number of worktrees, act once, and only the ones genuinely ready to merge are queued — the rest are **skipped with a reason** shown up front, never silently included. Ready means: a clean working tree, commits that are all pushed, and an open pull request that is not a draft, has no merge conflicts, and has green checks. The daemon does the checking, so a dirty or unpushed worktree is filtered out without spending any GitHub API budget, and the whole selection resolves in a single API call. A confirmation lists exactly which PRs will be queued and why the others were skipped — enqueuing changes state on GitHub that other people can see, so it always asks, even for one row. The daemon re-checks everything after you confirm, so a worktree that went dirty or was force-pushed while the dialog was open is dropped rather than queued. A PR already in the queue counts as success, and a PR GitHub refuses (merge queue not enabled on the repo, conflicts, insufficient permissions) is reported individually without affecting the rest. **Requires** the merge queue to be enabled on the repository, and a daemon built with this release.

### Changed
- **Claude session cues now arrive by push, not by polling** ([#1414](https://github.com/rust-works/omni-dev/issues/1414)): the session glyphs on worktree rows were the only part of the **Worktrees** view each window fetched on its own timer — everything else already arrived live over the daemon's push stream. Because each window's timer phase is set by whenever that window activated, two windows showing the *same* worktree row could show **different** session cues for up to ten seconds, and which one was out of date was arbitrary: a window opened later, or one whose extension host reloaded, simply stayed behind its neighbours indefinitely. Cues now ride a second push subscription, so every open window flips together. Two related annoyances go with it: a window whose Worktrees view was **hidden** stopped updating entirely and showed whatever it last rendered when you revealed it — it is now already correct on reveal — and each window's ten-second round-trip asking "has anything changed?" is gone. Nothing to configure, and no change to what the cues mean. Against a **daemon too old** to push (they version independently), the extension detects the refusal, logs it once to the **omni-dev** output channel, and falls back to the previous ten-second poll — so an unmatched pair still works exactly as before, and the push resumes on its own the next time the daemon restarts.

## [0.6.0] - 2026-07-22

### Added
- **Per-repository PR polling toggle** ([#1376](https://github.com/rust-works/omni-dev/issues/1376)): a repository node in the **Worktrees** view now has **Enable PR Polling** / **Disable PR Polling** context-menu actions, and its GitHub icon is **green** while the daemon is polling that repo's PR badges and **gray** when it is not. PR polling is now **off by default** and enabled per repo, so with many repos open you can keep live CI badges on the two you are working in and leave the rest un-polled — cutting the daemon's `gh` traffic (and GitHub rate-limit pressure) to just the repos you asked for. **Enabling a repo is a 15-minute lease:** it **auto-disables** after ~15 minutes (the icon greys and badges drop), so an idle repo stops polling even if you forget — re-enable to refresh it, or **Disable** to stop early. The toggle covers **every** worktree/branch of the repo, is shared across all windows, and its remaining lease survives a daemon restart. The existing global `omniDevWorktrees.showPullRequests` setting is a master switch above it: with it off, badges are hidden, repo icons render gray, and the per-repo menu items are hidden. **Note:** because polling now defaults off, PR badges will not appear until you enable a repo. Requires a daemon built with this release.
- **Copy Directory** ([#1369](https://github.com/rust-works/omni-dev/issues/1369)): a context-menu action on **every** row of the **Worktrees** view — repo nodes and worktree nodes alike — copies the item's filesystem directory to the clipboard. With a multi-selection it copies all selected directories **newline-delimited**, deduplicated, in selection order — paste-ready for a shell, `xargs`, or a `while read` loop. A repo node and its main worktree map to the same directory, so selecting both yields one line, not two. Feedback is a transient status-bar message; nothing to confirm, nothing modal.
- **Multi-select on the Worktrees view** ([#1357](https://github.com/rust-works/omni-dev/issues/1357)): ctrl/cmd+click and shift+click now select several rows, and every context-menu action acts on the whole selection. The view lists every window's repos and worktrees, so its natural verbs are plural — "open the PRs for these three branches", "close these five stale worktrees" — each of which used to be N right-clicks, N confirmations, and N notifications.
  - **Open Pull Request…** and **Open Pull Request in Browser…** open every selected row's PR, discovering them in parallel under one notification. A repo node selected alongside one of its own worktrees will not open the same PR twice, and a selection resolving to more than five PRs asks first — a repo node contributes *every* open PR of its repository, which is not a count you picked. Single-row behavior, including the repo-node quick-pick, is unchanged.
  - **Close Worktree** and **Close Window** run as one batch: the safety checks (side-effect-free by design) run in parallel, aggregate into a **single** confirmation listing exactly what will be deleted, and then execute in parallel too, under one progress notification ([#1359](https://github.com/rust-works/omni-dev/issues/1359)). Closing a window is almost entirely a *wait* on that window picking the request up, so closing five takes about as long as closing one (~10s) rather than five times as long. A per-target failure no longer aborts the rest — the failures are reported together at the end. A batch always confirms, even when nothing is at risk: a mis-aimed multi-select is far easier to make than a mis-aimed right-click, and the dialog is the only place you see the full set.
  - A selection containing **this** window's own worktree closes it last, once every other target has finished — closing it shuts down the extension itself, taking any still-running work with it.
  - A main working tree caught up in a **Close Worktree** selection is **skipped and named** in the dialog, never deleted and never quietly downgraded into a window close.
  - **Move Claude Session Here** is hidden while more than one row is selected. Its argument is a single *destination*, not a subject, so "move one session to three worktrees" has no meaning; hiding it beats acting on only the clicked row and silently discarding the rest of the selection.
  - Double-click-to-open is unaffected, and selection gestures (ctrl/shift+click) never trigger it.
- **Open Worktree** ([#1357](https://github.com/rust-works/omni-dev/issues/1357)): a new context-menu action opens — or focuses — a window for every selected worktree. Double-click already did this for one row, but it is inherently single; this is how you restore a whole working set at once.
- **Open Pull Request in Browser…** ([#1354](https://github.com/rust-works/omni-dev/issues/1354)): a second context-menu action on the **Worktrees** view opens a repo's or worktree's pull request(s) on `github.com` in your **default browser**, alongside the existing **Open Pull Request…** ([#1299](https://github.com/rust-works/omni-dev/issues/1299)) that opens them as a tab inside VS Code. The badge on a row already shows there is an open PR; now the row can open it wherever you want to read it.
  - Both actions appear together on any node with a `github.com` origin, in-editor first, and share one discovery flow — the same `gh` lookup, the same friendly "no open pull request" message, and the same multi-select quick-pick when a repo node matches several PRs. Only the open step differs, so the in-editor action's behavior is unchanged.
  - The browser action has **no dependency on the GitHub Pull Requests extension** — it opens the PR's plain `github.com` URL with the OS default browser, so there is no Install/Copy prompt on this path. `gh` is still needed to find the PRs.

### Fixed
- **The degraded PR-badge fallback goes quiet against a daemon that reports "no open PR"** ([#1370](https://github.com/rust-works/omni-dev/issues/1370)): the tree now excludes worktrees carrying the daemon's new explicit `pr_none: true` negative from the per-window `gh pr list` fallback, which previously re-fired every 60s, per repo, per window, forever, for every branch without an open PR — no daemon ever told it there was nothing to learn. Against a current daemon every checked branch carries either a badge or the negative, so the extension runs **no** `gh` for badges at all; against an older daemon the fallback behaves exactly as before (the intended degraded path). A daemon-reported negative is also never overwritten by a fallback badge.

### Changed
- **Pull-request lookups run in the daemon, not per window** ([#1389](https://github.com/rust-works/omni-dev/issues/1389)): "Open Pull Request…" (and the degraded badge fallback) used to shell `gh pr list` **in each window**, so with many windows open the extension — not the daemon — dominated the GitHub GraphQL burn (`gh pr list --json statusCheckRollup` is a GraphQL query), and none of it was counted by the daemon's call counters. Now a branch the daemon already resolved opens **straight from the snapshot badge** (zero `gh`), and a repo-wide lookup goes through the daemon's shared, TTL-cached `open-prs` op, so N windows dedupe to **one** counted `gh pr list` per repo instead of one per window. The extension falls back to its own `gh` only against a daemon too old to serve the op. Separately, the badge fallback now **respects the per-repo polling toggle**: a repo you have not enabled PR polling for (#1376) no longer gets a per-window `gh pr list` — disabling polling now means *zero* `gh` for that repo from the extension too, not merely from the daemon. No visible change to the actions themselves; requires a daemon built with this release for the shared op (older daemons degrade to the previous per-window behavior).
- **Close Window is no longer restricted to a repository's main working tree** ([#1357](https://github.com/rust-works/omni-dev/issues/1357)): it is now offered for **any** worktree that has a window open. Previously a *linked* worktree's window could only be closed by **deleting** the worktree — closing the window and keeping the worktree was unreachable, even though the daemon has always supported it. Window operations and worktree deletion are now cleanly separated: **Open Worktree** and **Close Window** manage windows and delete nothing; **Close Worktree** is the only action that removes anything. Nothing about what gets deleted has changed — a main working tree is still never deleted.
- **Open Claude Code now opens a new session on every click** ([#1347](https://github.com/rust-works/omni-dev/issues/1347)): the editor title-bar button ([#1322](https://github.com/rust-works/omni-dev/issues/1322)) no longer focuses the terminal it already opened — every click launches a **new** Claude Code CLI session as its own editor tab, so starting a second or third concurrent session in one window is one click each. This supersedes the 0.5.0 note that clicking again "focuses" the open terminal; "reuse" only ever meant "the tab is still open" (VS Code's terminal API cannot report whether `claude` is still running), which is not what a click on a launch button asks for.
  - Concurrent terminals are named `Claude Code`, `Claude Code 2`, `Claude Code 3`, … so their editor tabs stay distinguishable, and closing a session frees its number for the next launch instead of letting a counter climb forever.
  - The icon, `editor/title` placement, `cwd` resolution, and the `omniDevWorktrees.claudeCommand` setting are unchanged; the button remains window-level and daemon-independent.

## [0.5.0] - 2026-07-16

### Added
- **Pull request badges on worktree rows** ([#1296](https://github.com/rust-works/omni-dev/issues/1296), [#1324](https://github.com/rust-works/omni-dev/issues/1324), [#1337](https://github.com/rust-works/omni-dev/issues/1337)): each worktree row in the **Worktrees** view now shows its open GitHub pull request — the PR number, a `draft` marker, and a **colored** CI-check badge: green `✓` (passing), red `✗` (failing), or yellow `●` (pending) — so a passing and a failing PR are distinguishable at a glance. A PR line is added to the row's tooltip.
  - The badge is a theme-aware `FileDecoration` (the `charts.{green,red,yellow}` palette) painted from a custom `omnidev-worktree:` `resourceUri` — a custom scheme, so it never collides with git's own folder decorations; the color also tints the row's branch label, matching how git status colors its badges. A row reads `#1319 draft`, with the color badge carrying the check state. A PR is matched to a row by its head branch; a worktree with no PR, and a PR with no checks, show no badge.
  - Check state is resolved **by the omni-dev daemon**, not the extension: the daemon makes a single `gh api graphql` call covering every repo and branch at once and pushes the verdict on the tree snapshot, so CI state stays **live in every window** rather than refreshing only when you expand a repo node. The extension runs no `gh` of its own and reduces no rollup.
  - Gated behind the new `omniDevWorktrees.showPullRequests` setting (default **on**); disable it to hide the badges.
- **Open Claude Code** ([#1322](https://github.com/rust-works/omni-dev/issues/1322)): a **Claude-in-a-box** button in the editor title bar opens the Claude Code CLI in a terminal docked as an **editor tab** (not the bottom panel) and runs the configured command.
  - The working directory is the active window's workspace folder — the focused editor's folder when it sits in one, else the first folder. Clicking again while the terminal is still open **focuses** it instead of spawning a duplicate; after you close it, a fresh click opens a new one.
  - The launch command is the new `omniDevWorktrees.claudeCommand` setting (default `claude`); a shell prefix such as `proxy && claude` is allowed. The button is window-level and daemon-independent, so it works even when the omni-dev daemon is not running.
- **Move Claude Session Here** ([#1295](https://github.com/rust-works/omni-dev/issues/1295)): a context-menu action on a **Worktrees** tree node relocates a Claude Code session's on-disk storage into that worktree's project scope, so the conversation becomes resumable from a VS Code window opened there.
  - It lists **this** window's sessions newest-first with a readable preview label (first user message, or a summary line), then moves both the `<id>.jsonl` transcript and its optional `<id>/` sidecar dir (subagent transcripts, overflow tool-results) into the target worktree's encoded `~/.claude/projects/` folder. **Copy (Fork)** is offered alongside a plain move.
  - A confirmation modal (showing source → destination and the exact artifacts) precedes any change; a session written moments ago is refused as possibly-live ("close its window first"); an id collision in the destination aborts rather than clobbers; and global state (`history.jsonl`, `shell-snapshots/`) is never touched.
  - Entirely a per-user filesystem operation under `~/.claude/projects/` — it needs no daemon and touches no trust boundary.
- **Claude session reporting** ([#1210](https://github.com/rust-works/omni-dev/issues/1210)): the companion now feeds a **second** daemon service — the new Claude Code sessions tracker — by reporting how many Claude editor tabs and integrated terminals each window has, on activate, on the existing ~10s heartbeat, and whenever tabs or terminals change; it unregisters on deactivate.
  - This lets the daemon tag a session's source as VS Code (joining the session's working directory against the window's folders), so `omni-dev sessions list` and the tray's **Claude Sessions** submenu can tell a session running in an editor window from one in a plain terminal, and offer a focus action for it.
  - It reports **counts only — never a tab's session id**, which the Claude extension exposes no API for. This is the extension's first reporting beyond worktrees; it touches no trust boundary and persists nothing.

### Removed
- **The inline "Open in VS Code" action on worktree rows** has been removed, along with its unused `omniDevWorktrees.open` command. Double-clicking a worktree row still opens or focuses its window, which is the affordance the inline button duplicated. (The action was advertised in the 0.2.0 notes; that line no longer applies.)

### Compatibility
- The PR number and `draft` marker work against **any** daemon, but the **colored CI-check badge requires daemon 0.36.0 or later** — an older daemon omits the field, and the extension falls back to a rollup-free `gh pr list` that shows `#65` / `#65 draft` with **no** check badge. This is deliberate: nothing extension-side polls, so a verdict resolved there could never refresh, and a stale tick is worse than none.
- Live `↑ahead ↓behind` refresh after a push or fetch ([#1344](https://github.com/rust-works/omni-dev/issues/1344)) likewise requires daemon 0.36.0 or later; against an older daemon the counts refresh only when a repo node is collapsed and re-expanded.

## [0.4.0] - 2026-07-13

### Added
- **Open Pull Request…** ([#1299](https://github.com/rust-works/omni-dev/issues/1299)): a context-menu action on the **Worktrees** view opens a repo's or worktree's pull request(s) **as a tab inside VS Code**, never a browser.
  - On a **worktree** node it finds the PR(s) whose head branch is that worktree's checked-out branch; on a **repository** node it fans out to all the repo's open PRs. No PR shows a friendly info message, one PR opens directly, and several offer a multi-select quick-pick to open any or all at once.
  - PRs are discovered with the `gh` CLI (reusing its existing auth) and open through the **GitHub Pull Requests** extension's (`GitHub.vscode-pull-request-github`) documented URI handler. When that extension is not installed, a single warning offers **Install** or **Copy PR URL** — it never silently falls back to a browser.
  - Only repos with a `github.com` origin get the action (the daemon reports `owner/name` for those); it requires the `gh` CLI and the GitHub Pull Requests extension. `gh` is resolved from your `PATH`, the usual install locations (Homebrew, `~/.local/bin`, …), or the `OMNI_DEV_GH_BIN` override, so a GUI-launched editor with a minimal `PATH` still finds it.

### Changed
- **Show/hide-closed toggle now syncs across windows** ([#1301](https://github.com/rust-works/omni-dev/issues/1301)): the toggle's state moves from per-window `context.globalState` to the daemon, which carries `show_closed` on every pushed snapshot — so a flip in any window re-renders every other window live, and a freshly-opened window initializes from the daemon's value on its first frame instead of racing a read-once local default. The toggle commands now send a `set-show-closed` op rather than writing `globalState`; the toggle's behaviour and default (all worktrees shown) are otherwise unchanged. Requires daemon 0.35.0 or later.

## [0.3.0] - 2026-07-11

### Added
- **Hide worktrees without a window** ([#1290](https://github.com/rust-works/omni-dev/issues/1290)): a title-bar toggle in the **Worktrees** view collapses the list to just the worktrees a VS Code window currently has open, and back — one button that swaps between an *eye* icon (showing all) and an *eye-closed* icon (hiding).
  - The default is unchanged — **all** worktrees are shown until you toggle.
  - The filter is entirely client-side (the daemon already reports each worktree's open state); its state is persisted in `globalState`, so it reads the same in every window and survives a reload, and a live snapshot keeps it applied.
  - Repos are derived from open windows (each keeps ≥1 open worktree), so hiding only trims closed rows and never empties a repo or the tree.

## [0.2.0] - 2026-07-10

### Added
- **Worktrees tree view** ([#1268](https://github.com/rust-works/omni-dev/issues/1268)): an activity-bar **Worktrees** view lists every repository and git worktree open across all your VS Code windows — the cross-window picture the daemon aggregates and that no single per-window-sandboxed extension can build on its own.
  - Double-click a leaf (or the inline **Open in VS Code** action) to focus an already-open window or open a worktree's folder.
  - Each leaf shows the daemon-computed branch and ahead/behind state (e.g. `main (+2 -1)`), so the extension stays thin and runs no git itself.
  - The view is push-based and self-healing: it re-subscribes after a daemon restart and shows an empty tree — never an error — when the daemon is not running.
- **Close Worktree / Close Window context menus** ([#1277](https://github.com/rust-works/omni-dev/issues/1277)): right-click a leaf to close a worktree's window and, for a **linked** worktree, delete it.
  - A side-effect-free safety check runs first; a modal confirm appears **only** when a removal would lose data (modified or untracked files, an in-progress rebase/merge/cherry-pick, or commits reachable only from a detached HEAD) or would close a multi-root window's other folders. A clean worktree closes with no prompt.
  - Unpushed commits on a named branch never block removal — the branch survives.
  - The main working tree offers **Close Window** only and is never deleted.
- **Marketplace / Open VSX gallery icon** ([#1280](https://github.com/rust-works/omni-dev/issues/1280)): the extension listing now carries a 128×128 gallery icon (`media/icon.png`).

## [0.1.0] - 2026-07-07

### Added
- **Initial companion extension** ([#1111](https://github.com/rust-works/omni-dev/issues/1111)): a thin per-window reporter for the omni-dev daemon's worktrees service, the data producer the service needs to see across the per-window extension-host sandbox.
  - Over the daemon's local `0600` Unix control socket (newline-delimited JSON), it `register`s each window's open folders under a fresh per-activation UUID, `heartbeat`s every ~10s (re-registering when a restarted daemon replies `known: false`), re-registers on workspace-folder changes, and `unregister`s on deactivation.
  - No-ops silently when the daemon is not running — it never surfaces an error or blocks the window.
  - Reports only raw folder paths, leaving branch and ahead/behind enrichment to the daemon; macOS and Linux only.
  - Configurable daemon socket path (`omniDevWorktrees.socketPath`) and heartbeat interval (`omniDevWorktrees.heartbeatSeconds`).
